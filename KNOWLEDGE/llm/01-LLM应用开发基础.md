## 1. 模型如何接收和生成

### 1.1 Prompt 与 System Prompt

**一句话：** Prompt 是提供给模型的输入；System Prompt 是其中用于规定任务、角色和行为边界的高优先级指令。

- 好的任务说明通常写清：**目标、输入、输出格式、约束、例子、如何处理资料不足**。Few-shot 是给少量输入输出示例。
- System Prompt 能提高行为一致性，但**不能保证模型始终遵守**，也不能替代代码校验、权限控制或事实核查。
- 不要把整个应用理解成「一段神奇提示词」：真正可用的系统还需要数据、工具、评测和部署。

**最小例子：** “根据下面的制度原文回答；没有证据就说未找到，并给出引用段落。”这比只说“你是专业助手”更可检验。

### 1.2 Token 与上下文窗口

**一句话：** Token 是分词器将文本编码后的单位；上下文窗口限制一次请求可处理的输入与生成内容总量。

- Token 不固定等于一个汉字或一个英文单词；切分受**模型的 tokenizer、语言、代码和符号**影响。需要预算时用目标模型的 tokenizer 实测。
- 上下文可能包含系统／开发者指令、对话历史、检索片段、工具结果和本次问题。它们会竞争同一个预算。
- 超限时会报错、截断、压缩或摘要，取决于应用实现；**不是所有系统都会机械地把最早消息挤出去**。
- 窗口大不等于所有信息都被同等有效地利用；实践中还要控制检索质量、延迟与成本。

**不要背固定型号的窗口数值。** 型号、配置和价格会变，做项目时再查提供商文档。

### 1.3 幻觉与事实核查

**一句话：** 幻觉是模型输出貌似可信、却无依据或错误的内容。

自回归模型通常逐 token 生成文本；训练目标并不保证每句都与外部事实一致。降低风险的方法：

1. **检索**：给出相关、可信、可引用的材料（RAG）。
2. **工具**：实时事实由可靠 API／数据库查询。
3. **校验**：结构、数值、权限、引用与关键结论由程序或人工核查。
4. **拒答**：证据不足时允许“不知道”。

这些方法只能降低风险，**不能保证零幻觉**。结构化输出只约束格式，不保证字段内容真实。

## 2. 把模型输出接入程序

### 2.1 Structured Output：让结果可解析

**一句话：** 让模型按 JSON 等约定结构返回，使下游程序能处理。

```json
{"category": "合同", "confidence": 0.87, "evidence": "第 2 页第 3 条"}
```

- 只在提示词里写“请输出 JSON”是弱约束；支持时使用 JSON Schema／结构化输出能力。
- 收到输出后仍要检查必填字段、类型、合法值和业务规则。例如 `confidence=3.7` 即使是合法 JSON，也不是合法概率。
- 必须区分**格式有效**与**语义正确**。

### 2.2 Function Calling：模型提出调用，程序执行

**一句话：** 模型在可用工具中选择并提供参数；应用代码或平台执行真实操作，再把结果送回模型。

```text
用户问天气 → 模型产生 get_weather(city="北京") 调用
→ 程序校验参数并调用天气服务 → 返回结果 → 模型组织回答
```

模型**不是因为写出函数名就自动拥有权限**。工具实现、鉴权、超时、重试、审计和危险操作确认由应用控制。工具结果也可能错误或带恶意指令，不能无条件信任。

## 3. RAG：给模型找资料

完整学习与面试版见 [第三章：RAG 检索增强生成](02-RAG检索增强.md)。

### 3.1 它解决什么问题？

**一句话：** RAG 在生成回答前检索外部资料，把相关证据放进模型上下文。

适合：公司知识库、经常更新的制度、可追溯的文档问答。它通常**不修改模型参数**。原始 RAG 思路见 [Lewis 等人的论文](https://arxiv.org/abs/2005.11401)。

### 3.2 完整链路：离线建库与在线回答

```text
离线：文档 → 解析/OCR → 清洗 → 切块 → 加入来源与权限元数据
                 → 建立关键词索引和／或向量索引

在线：问题 → 查询改写（可选）→ 召回 → 权限过滤 → 重排（可选）
          → 选片段与引用 → 模型回答 → 校验与记录
```

| 环节 | 要决定什么 | 常见失败 |
| --- | --- | --- |
| 文档解析 | PDF、表格、图片怎么抽取？标题与页码是否保留？ | OCR 错、表格列错位、页码丢失 |
| 切块 | 按段落、标题或长度切？重叠多少？ | 答案跨块、单块太长、语义断裂 |
| 索引 | 关键词、向量或混合？版本如何更新？ | 新文档未入库、旧版本仍被检索 |
| 查询与召回 | 用户问题如何改写？取前几条？ | 同义词、缩写、数字和专有名词漏召回 |
| 重排与生成 | 哪些证据进上下文？如何引用／拒答？ | 检到了却没用、引用不支持结论 |

**Query** 就是用于检索的查询。它可能直接是用户问题，也可能经过改写、拆分或补全。

### 3.3 Embedding、关键词检索和向量库

- **Embedding**：把文本或图片映射成向量，用相似度寻找语义接近的内容。不同语言和领域能否对齐取决于具体模型，不能保证“意思一样就一定靠近”。
- **关键词检索**：依赖词项匹配，适合精确名称、编号、专有词；不能因有 Embedding 就删掉它。
- **混合检索**：结合关键词与向量，再重排。很多真实知识库比纯向量更稳，需通过评测决定。
- **向量数据库／索引**：负责存储向量并进行近邻搜索；它可以是专用服务，也可以是数据库扩展或本地索引，**不是做 RAG 必须先安装的某一款产品**。[AWS 向量检索文档](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/vector-search.html)可作为实现参照。

### 3.4 RAG 怎么判断做得好？

不能只展示“问一句，答得像样”。至少准备一小批有标准证据的问题，并分开检查：

1. **检索**：正确证据是否进入 Top-k？无答案时是否误召回？
2. **回答**：是否回答对；结论是否得到引用片段支持；该拒答时是否拒答？
3. **工程**：解析失败率、延迟、成本、文档更新速度、权限是否正确。

对于你未来的文档／图像项目，还要单独看扫描质量、表格、图表、OCR 错误等样本。**检索正确不代表生成正确，生成流畅也不代表有证据。**

### 3.5 RAG 与微调怎么选？

| 需求 | 先试什么 |
| --- | --- |
| 获取最新／私有、可引用的事实 | RAG 或数据库／API 查询 |
| 固定输出风格和字段 | 提示词＋结构化输出，必要时再微调 |
| 大量稳定样本表明模型不会某项任务 | 考虑微调并和基线对比 |

两者可以组合。RAG 不是“真相保证器”，微调也不是把文档可靠地“存进模型脑子”的方法。

## 4. 工具、Agent、MCP 与 Skill

### 4.1 Agent：在反馈中决定下一步

**一句话：** Agent 是让模型或控制器根据目标与观察结果，反复选择下一步动作的应用模式。

```text
目标 → 选择动作（检索／工具／回答）→ 执行 → 观察结果
  ↑                                   ↓
  └──────────── 尚未完成则继续 ────────────┘
```

- 固定步骤的流程叫 **workflow**，不一定需要 Agent；可预测任务往往先用固定流程更易测、更稳定。
- Agent 可以规划，但不是每个 Agent 都必须显式写出“思维链”，也不能把“展示推理过程”当作 Agent 定义。
- 实际系统要设最大步骤数、超时、预算、工具权限、失败处理和终止条件。否则可能循环、乱调用或成本失控。
- [ReAct 原论文](https://arxiv.org/abs/2210.03629)是“推理／行动／观察交替”的一个经典实现思路，不是所有 Agent 的唯一结构。

### 4.2 MCP：工具与数据源的标准接口

**一句话：** MCP 标准化 AI 应用与外部系统之间的连接方式，可暴露工具、资源和提示模板。[MCP 官方介绍](https://modelcontextprotocol.io/docs/getting-started/intro)

- 它标准化的是**连接和交互接口**，不是让任意模型自动获得任何工具。
- 仍需要兼容的客户端／服务端、权限配置和实际业务逻辑。
- 小项目直接写函数调用就够；当工具与数据源变多、需要跨客户端复用时，再考虑 MCP。

### 4.3 Skill：可复用的任务说明与工作流程

**一句话：** Skill 通常是把某类任务的指令、步骤、约束与可用资源打包复用的做法。

它不是所有 Agent 平台共有的统一协议，也不等于 MCP。一个 Skill 可以指导 Agent 何时调用哪些工具；一个 MCP 服务可以提供这些工具。实现形式取决于具体平台。

## 5. 微调与模型蒸馏

### 5.1 微调（Fine-tuning）

**一句话：** 用任务数据继续训练已有模型，改变它在目标任务上的参数和行为。

可能用于特定格式、术语、分类／抽取能力或模型适配。要有训练／验证／测试切分、基线和错误分析；只跑通一次训练脚本不代表有效。LoRA 等参数高效方法降低需要训练的参数量，但不免除数据质量和评测要求。

### 5.2 蒸馏（Distillation）

**一句话：** 让学生模型通过老师模型的输出信号学习某项能力，而不是复制老师的参数。[Hinton 等人的知识蒸馏论文](https://arxiv.org/abs/1503.02531)

```text
选定任务与评测集 → 老师给答案／概率分布等训练信号
→ 检查与清洗数据 → 训练较小学生模型 → 比质量、延迟和成本
```

- **硬目标**：只学老师给出的标签／答案；**软目标**：学习类别概率分布等更丰富的信号。大模型场景还常用老师生成的示例数据。
- 蒸馏本身是一种训练策略，常需要对学生模型进行微调；它不等于量化、剪枝，也不能保证学生完全复制老师的能力。
- 做蒸馏必须先明确可用的数据、老师输出的质量、模型服务条款和验证集；不能把老师的错误一起当“真理”学进去。
- 你给的[卡码蒸馏文章](https://notes.kamacoder.com/llm/intro/model_distillation.html)可作入门直觉材料，术语与细节以论文和实际实验为准。

## 6. 部署、缓存与成本

### 6.1 部署不是“代码能跑”

**一句话：** 部署是让模型应用可被调用、可监控、可维护，并在失败时可定位。

最小交付：API／界面、依赖与配置、权限和密钥管理、超时与重试、日志、测试、评测集、延迟与成本记录。对 RAG／Agent 还要记录文档版本、检索证据、工具调用及失败类型。

### 6.2 四种容易混淆的缓存

| 缓存 | 缓存什么 | 主要目的 |
| --- | --- | --- |
| 推理过程中的 KV Cache | 当前生成序列已计算的注意力状态 | 避免生成下一 token 时重算前面内容 |
| 跨请求的 Prompt Cache | 可复用的**相同前缀**计算状态 | 减少重复输入计算与可能的输入费用 |
| 检索缓存 | 某些查询的检索／重排结果 | 减少检索延迟，注意文档更新后失效 |
| 答案缓存 | 同一问题的最终回答 | 省整次生成，注意权限与新鲜度 |

前两者有关联，但**不能写成“KV Cache 一定存磁盘，下次请求一定命中”**。以[官方 OpenAI 文档](https://developers.openai.com/api/docs/guides/prompt-caching)为例，Prompt Cache 复用的是可用且匹配的前缀状态；缓存位置、寿命和计费取决于提供商和模型。缓存命中**不等于**直接复用上次的最终回答。

RAG 场景尤其要注意：系统指令可能不变，但**每次检索出的文档未必相同，顺序也可能不同**。“大部分差不多”不代表前缀逐 token 一致；不能先假设 9000 个 token 全命中。更稳妥的做法是把稳定内容放前面，再观察真实请求里的 `cached_tokens` 或对应指标。

### 6.3 成本怎么算？

一般按不同类别的 token 数乘各自单价：

```text
费用 ≈ 未缓存输入量 × 未缓存输入单价
     + 缓存读取量 × 缓存读取单价
     + 输出量 × 输出单价
     + 其他费用（如缓存写入、检索、工具、存储，视服务而定）
```

**算术练习，不代表任何厂商现价：** 假设每百万 token 的未缓存输入、缓存读取、输出分别为 ¥6、¥1.3、¥24；输入 9200 token、输出 1000 token，且**确实命中** 9000 token：

- 不命中：`9200 / 1e6 × 6 + 1000 / 1e6 × 24 = ¥0.0792`。
- 命中：`9000 / 1e6 × 1.3 + 200 / 1e6 × 6 + 1000 / 1e6 × 24 = ¥0.0369`。
- 此假设下单次省 `¥0.0423`，约 **53%**。若真有每天 10 万次且持续 30 天，差额是 **¥126,900**，不是“几千块”；但实际命中率与费用结构会改变结果。

不要背原文的模型名、上下文窗口和价格表。做项目时记录**具体提供商、型号、计费日期、真实输入／输出／缓存 token、命中率、请求量**，再估成本。

## 7. 一张能力地图与自测

```text
用户问题
  → Prompt／上下文（告诉模型任务与材料）
  → RAG／工具（取得外部证据或执行动作）
  → Agent／Workflow（决定步骤与控制循环）
  → Structured Output／校验（让结果可用且可查）
  → 部署／监控／缓存（让应用可持续运行）

微调／蒸馏：在确有证据表明基础模型能力不足或成本过高时，再改变模型。
```
