贯穿例子：假设我们要做一个**公司报销政策问答系统**。知识库中有一份虚构的《差旅报销规定 V2》：“2026 年 10 月起，高铁二等座可报销；飞机经济舱需要主管提前审批；市内出租车凭票报销。”用户问：“出差坐飞机能报吗？”本章出现的文档、数字和实验结果都是教学例子，不是某家公司的真实政策。

## 1. RAG 解决什么问题

**RAG = Retrieval-Augmented Generation，检索增强生成。** 回答之前先找资料，把相关资料交给语言模型，要求它依据资料组织答案，并把可核查的来源带回去。[原始 RAG 论文](https://arxiv.org/abs/2005.11401)提出将检索到的外部文本用于生成；实际产品中的文档处理、权限、引用和评估还需要另外设计。

不接资料时，模型不知道公司最新政策；直接问“坐飞机能报吗”，它可能按一般经验回答。RAG 的处理是：

~~~text
问题：出差坐飞机能报吗？
→ 找到《差旅报销规定 V2》中的“飞机经济舱需要主管提前审批”
→ 模型回答：可以申请报销经济舱，但须提前获得主管审批。来源：V2 第 3 条。
~~~

RAG 适合**外部知识量大、经常更新、需要引用**的问题：内部手册、产品文档、合同条款、代码仓库问答。创意写作、纯推理或资料很短的问题，未必需要建检索系统。只有一页材料时，可以先把它直接放进提示词。RAG 能提供证据，**不能保证模型绝不出错**：资料可能没检到、已经过期，模型也可能误读或误引。

与微调的区别：RAG 在推理时接入可更新的资料；微调改变模型参数，更常用于输出风格、任务格式或特定能力。二者可结合。不要把“把一批事实训进模型”当作可追溯且随时更新的知识库。

## 2. 完整链路：离线建库与在线问答

“离线”指用户提问前处理资料，“在线”指收到问题后的实时处理。记住每一步的**输入、输出、可能出错点**。

~~~text
离线：原始 PDF/网页/Markdown
   → 解析成文字或结构化内容
   → 清洗、去重、版本与权限处理
   → 切成带来源的 chunk
   → 生成向量并建检索索引

在线：用户问题
   → Query 处理、权限过滤
   → 关键词/向量召回候选
   → 可选：融合、Rerank
   → 选出证据，拼上下文
   → LLM 生成
   → 检查引用、无答案处理、记录日志
~~~

**Chunk** 是一段可单独检索的内容。一个 chunk 除正文外，还需要元数据：

~~~json
{
  "chunk_id": "travel-v2-03",
  "text": "飞机经济舱需要主管提前审批。",
  "source": "差旅报销规定",
  "version": "V2",
  "section": "第3条",
  "effective_date": "2026-10-01",
  "access_group": "all_staff"
}
~~~

若只存正文，回答时就很难给出来源、判断新旧版本或控制谁能看到该文档。数据更新要能定位并删除旧 chunk，再写入新 chunk；不能只不断追加。**权限过滤要在检索和交给模型前落实**，不能等模型看完机密文档才在答案上做遮盖。

同一系统里，离线文档向量和在线问题向量要由**互相兼容的编码器/配置**生成。一般用同一个 embedding 模型；有些检索模型专门提供不同的 query、document 编码方式，这是一对经过训练的兼容方式。换模型或向量维度后，旧索引通常要重新编码。

**小练习：** 如果答案引用了 V1，且 V2 已经入库，你首先会查哪几个地方？提示：索引更新、版本过滤、排序。

## 3. 文档解析、清洗与切片

### 3.1 解析与清洗

PDF 的两栏文字可能被交叉读出；表格可能丢掉行列关系；扫描件需要 OCR；网页常混入导航栏。举例：原表格“飞机经济舱｜需审批”若解析成“飞机经济舱 高铁二等座 需审批 无需审批”，模型不知道哪条规则对应哪种交通工具。应先检查抽样解析结果，再考虑 embedding。

清洗包括去页眉页脚和重复模板、保留标题层级、处理过期版本及空白乱码。表格可转换为“项目—条件—结果”形式；图片或扫描件先识别，再人工抽查关键字段。原文可保留一份，清洗后的文本用于索引，方便追溯。

### 3.2 为什么切片

整篇文档建一个向量，用户只问一句政策时，相关信号被其他主题冲淡；切得太碎，只剩“须提前审批”，又不知道审批什么。目标是让每个 chunk **既容易命中，又能独立说明事实**。

| 方法 | 如何切 | 适用示例 | 主要代价 |
|---|---|---|---|
| 固定长度 | 每若干字符或 token 切开 | 快速基线、无结构文本 | 可能切断句子和条款 |
| 递归切分 | 优先段落，再句子，再字符 | 一般说明文档 | 仍可能跨主题或拆关联 |
| 语义切分 | 在话题变化处切 | 无标题、主题经常变化的文本 | 建库更慢，阈值和大小不稳定 |
| 结构切分 | 沿标题、条款、表格、函数边界切 | 手册、合同、Markdown、代码 | 依赖可靠的结构解析 |

**Overlap（重叠）**指相邻块共享一小段边界文字。例：第一块末尾是“飞机经济舱”，第二块开头是“须提前审批”；重叠可使信息同处一个块。重叠太大会让重复内容占据召回结果。先按有意义的结构切，再按评估结果调块大小和 overlap；不存在对所有文档都最好的 512 token 或 64 token。

**父子块**：用较短的子块找答案，再返回包含它的较长父段落。若子块只有“需审批”，父块包含“飞机经济舱需审批；高铁二等座直接报销”，生成时可看到完整条件。代价是更多上下文 token，父块过大也会引入噪声。

## 4. Embedding、相似度和向量索引

### 4.1 Embedding 是什么

Embedding 模型把文本映射为一串数字。例如为了讲直觉，假设“飞机报销”→ [0.8, 0.6]，“航空出差费用”→ [0.7, 0.7]，“年假余额”→ [-0.7, 0.1]。真实向量通常维度更高，且数值由训练模型决定，不是我们手工定义。相似的表达往往在向量空间中靠近；**靠近不等于能回答问题**。

**余弦相似度**比较方向：cos(q,d) = (q·d) / (||q|| × ||d||)。例如 q=[1,0]，d1=[0.8,0.6] 时相似度 0.8；d2=[0,1] 时为 0。模型和任务不同，欧氏距离、内积或余弦哪种更合适也不同，要按模型说明与验证集选。

**关键词检索**看字面命中，“错误码 E0427”“GPU 型号 RTX 5800”常适合关键词；**向量检索**对“坐飞机能报吗”与“民用航空器差旅费用”这种改写更有帮助。二者都可能漏，后面会组合。

选择 embedding 模型时，先看语言和领域、文档长度、是否需离线部署，再用自己的问答评估集对比召回、延迟和成本。榜单只能帮助挑候选，不能替代业务测试。若使用“查询编码器 + 文档编码器”成对模型，按其文档分别处理，不要把两个任意模型混用。

### 4.2 为什么需要向量索引

假设有 100 万个 chunk，精确搜索要计算问题与每个向量的距离。**ANN（近似最近邻）索引**预先组织向量，查询时少看一部分，以检索速度换取一定召回损失。HNSW 可想成多层导航图；IVF 先把向量分组，再搜索靠近问题的几组。它们的实际速度、内存和召回率都依赖数据分布及参数，不能固定说“总是毫秒级”或“总有 95% 召回”。

| 方案 | 它是什么 | 什么时候考虑 |
|---|---|---|
| FAISS | 向量搜索库，可保存/加载索引；完整元数据和服务逻辑要自己补 | 本地实验、自己控制索引逻辑 |
| Chroma | 易上手的轻量向量存储 | 小型原型 |
| PostgreSQL + pgvector | 在已有关系数据库中加向量与 ANN 索引 | 数据与权限本来就在 PostgreSQL、规模可控 |
| Milvus / Qdrant / Weaviate 等 | 专门的向量检索服务 | 需要更完整的扩展、过滤、运维或规模能力 |

“MySQL/关系数据库绝对做不了向量检索”“pgvector 到百万级必然不行”都过于绝对。应针对数据规模、过滤条件、更新频率、P95 延迟、成本做基准测试。向量数据库负责**快速搜索**，不会自动提高 embedding 的语义质量。

**小练习：** 为什么模型能找到“差旅交通规定”，却不一定能找到精确的“E0427”？解释关键词与向量各自的作用。

## 5. 检索、混合召回、重排与生成

### 5.1 Query 处理与召回

Query 是用户问题。口语化、多轮省略或多条件问题可能需要处理：

- **改写**：把“这个能报吗？”结合对话改成“出差飞机经济舱是否可以报销”；
- **拆分**：把“飞机能报吗、额度多少、谁审批？”拆成三个检索子问题；
- **扩展**：同时查“飞机/航空/机票”，但要防止扩展偏题。

最小系统先用原问题检索；只在评估发现特定问法漏检时加改写。

**Top-K** 是初次返回 K 个候选。K 太小可能漏证据，太大则提高延迟和上下文噪声。具体数字由评估决定。元数据过滤如版本、生效时间和权限，通常应在召回前或召回时生效。

### 5.2 混合检索与 RRF

**混合检索**把向量召回和 BM25 等关键词召回的候选合并。例：用户问“E0427 出差单为什么失败？”向量检索容易找到差旅流程，但精确错误码更可能由 BM25 找到。重复候选先去重，再融合排名。

**RRF（倒数排名融合）**按不同检索器的名次融合，不直接相加不可比的原始分数。简化例：A 在向量结果排第 1、关键词结果排第 3；B 分别排第 5 和第 1。用 1/(c+名次) 的两项和计算，c 是选定常数；A、B 谁排前取决于名次与 c。它不需要把两路分数先校准，但也不是任何数据上都优于调权重。

### 5.3 Rerank 是什么

快速召回先缩小候选池，**Rerank（重排）**再对“问题 + 每个候选块”做更细的相关性判断。常见 Cross-Encoder 会一起读问题和段落；向量双编码器把两者分别编码，适合先索引并快速搜索。例：两段都谈“机票”，只有一段写了“必须主管提前审批”，重排模型可把后者放前。重排**不能找回从未进入候选池的证据**，并会增加推理延迟。

### 5.4 Context、生成、引用与拒答

Context 是送给生成模型的证据。一个清楚的上下文格式：

~~~text
任务：仅依据以下资料回答；若资料不足，说明未找到依据。
[1] 差旅报销规定 V2，第3条，2026-10-01 生效：
飞机经济舱需要主管提前审批。
问题：出差坐飞机能报吗？
~~~

理想回答：“飞机经济舱可以按规定报销，但需主管提前审批。[1]” 只有“[1]”标记还不够；系统应确保引用能指向**实际命中的原文**，并可让用户打开原文核对。不同版本条款冲突时，按生效日期、适用对象和业务规则处理；资料不足时拒答或说明还需确认。降低采样温度、追加“不要编造”提示词都不能替代证据核查。

## 6. 答错时怎样定位问题

拿到错误答案，先保存：用户问题、文档版本、初次候选列表和分数、重排后列表、最终上下文、最终回答。随后沿证据路径查：

~~~text
知识库里真的有答案吗？
├─ 没有 → 拒答、补文档，不应要求模型猜
└─ 有 → 解析后的原文里有吗？
         ├─ 没有 → 查 PDF/OCR/表格解析、清洗、更新
         └─ 有 → 候选 Top-K 里有吗？
                  ├─ 没有 → 查切片、Embedding、查询改写、权限/版本过滤、索引覆盖
                  └─ 有 → 重排后/最终 Context 里有吗？
                           ├─ 没有 → 查融合、Rerank、K、上下文裁剪
                           └─ 有 → 查 Prompt、冲突条款、引用、模型理解与输出校验
~~~

把常见故障进一步记成表：

| 现象 | 可能位置 | 首先检查 |
|---|---|---|
检索到“第 3 页/版权所有” | 文档清洗 | 解析文本和去模板结果 |
找到“须审批”但不知审批什么 | 切片过碎 | 该 chunk 的标题和父段落 |
问法稍变就搜不到 | Embedding/Query | 同义问法的候选列表 |
正确块排第 20，送模型的只有前 5 | 排序/截断 | 候选覆盖与重排前后名次 |
正确证据已送入，却答成“无需审批” | 生成 | 版本冲突、Prompt、引用对齐 |
用户看到了无权限合同 | 权限 | 检索过滤和模型输入日志 |

来源材料把它概括为“检索侧五类、生成侧四类”：检索侧看文档质量、块大小、Embedding、召回覆盖、重排；生成侧看 Prompt 拼装、上下文噪声、引用约束和模型能力。诊断时不用强记“5+4”，按上面的数据流逐步检查即可。

## 7. 怎样逐步优化

先建立简单基线与评估集，再按问题选择改动，每次尽量只变一个因素。常见方向按故障位置排列：

1. **原文不可用**：修 PDF/表格解析、OCR、去重、版本更新。
2. **切片丢条件**：结构切分、加标题、父子块或邻块扩展。
3. **候选没证据**：核对索引覆盖、Embedding 选型、Query 改写、多 Query、关键词 + 向量混合召回、合适的 K。
4. **候选有证据但排序靠后**：RRF 融合、Rerank、针对问答场景训练或选型。
5. **证据进了 Context 仍答错**：删冗余/冲突块、保留生效日期与来源、改 Prompt、按句检查引用与事实。
6. **效果好但太慢/太贵**：缩短上下文、缓存可复用结果、减少多轮检索与重排候选、调整模型和索引。按**真实的重复前缀和缓存命中率**估算收益，检索文档每次不同就不能假设总能命中缓存。

一次实验可以这样记录：基线为“关键词检索 Top-5”；改动为“加向量召回并用 RRF 融合”；在固定 50 道评估题上记录证据命中率、答案正确率、P95 延迟和每题成本；再按错误类型看哪些题变好、哪些题变差。不要直接把文章里的“提升 25%”或任意 Top-K 数字写进自己的简历。

## 8. 长文档、代码与多跳问题

### 8.1 长文档

“员工出差报销有哪些限制？”可能需要同一制度的多条规则。若按固定 500 字切，标题“适用对象”与细则“试用期员工除外”可能分离。改进方法：保留标题树和条款路径；用短块检索、父段落回答；必要时按章节先定位再搜索；把来源页码、版本、生效日期带进答案。

### 8.2 代码检索

用户问“哪个函数处理 token 过期？”代码文件按字符切可能把函数签名和实现拆开。可按语言语法树（AST）或函数/类边界切，同时索引符号名、路径、README、调用说明、仓库/分支/commit。关键词适合精确符号名，向量适合自然语言描述，二者结合更有用。返回代码时附路径和版本，防止引用旧分支。

### 8.3 多跳与全局问题

“张三和李四在哪个项目合作？”也许需要先检索张三参与项目，再查李四是否参与相同项目；单次相似度检索不一定把两份证据都找全。“过去一年所有项目的技术栈趋势？”则需要对许多文档聚合，几个相似块未必代表全局。可以用子问题检索、结构化数据库查询、全库统计或图增强检索，具体取决于数据形态。**先判断问题需要哪些证据，再挑检索方式。**

## 9. 评估：证明系统变好了

### 9.1 建一份小而可信的 Golden Set

从真实问法中整理问题、标准证据 ID、参考答案、适用版本、是否应拒答、问题类型（精确编号/改写/多跳/无答案）。例如：

~~~json
{
  "question": "出差坐飞机能报吗？",
  "gold_evidence": ["travel-v2-03"],
  "reference_answer": "经济舱需主管提前审批后按规定报销。",
  "version": "V2",
  "should_abstain": false,
  "type": "policy_fact"
}
~~~

评估集要有“知识库里没有答案”的问题，也要有旧版与新版冲突的题。训练/调参用一部分，最后留一部分不参与调参，避免只对已见题有效。

### 9.2 检索侧指标

假设一道题相关证据共有 3 个，Top-5 找到 2 个且其中 2 个相关：

- **Recall@5 = 找到的相关证据数 / 全部相关证据数 = 2/3**，看漏了多少。
- **Precision@5 = Top-5 中相关证据数 / 5 = 2/5**，看噪声多少。
- **Hit@5** 看是否至少找到一个相关证据：本题为 1。许多文章把“多少题的 Top-K 至少命中一个”叫召回率；记录指标时要写清分母，别与每题多证据 Recall@K 混淆。
- **MRR** 看第一个相关结果的名次。如果相关证据首次出现在第 4 名，该题倒数名次为 1/4；对所有题取平均。
- **nDCG** 把“高度相关、部分相关、无关”和排名都考虑进去；只有想比较细致排序时再用。

Rerank 在相同候选集合上改变排序，可提高最终小 K 的命中或 MRR，**不会找回初次召回之外的材料**。

### 9.3 生成侧与线上指标

对最终回答逐项看：是否正确回答问题；每个事实是否被所引资料支持（忠实度）；引用是否真指向对应原文；遇到无答案题能否拒答；若有多条约束是否漏答。LLM 可以辅助打分，但要用人工抽样复核，因为裁判模型也会误判。RAGAS 一类框架提供忠实度、答案相关性、上下文相关性/召回等自动评估思路；先定义自己的业务判分标准，再决定是否接工具。

线上再看用户采纳/纠错、人工升级率、P95 延迟、失败率、每题 token 与费用。不要只用“用户点赞”代替事实正确率。优化若提升证据命中率，却使延迟翻倍，应根据业务目标决定是否值得。

**小练习：** 两种方案的 Hit@5 都是 90%，但 A 的 MRR 较低。你认为 A 的结果可能有什么特点？

## 10. Agentic RAG、GraphRAG 与 LightRAG

### Agentic RAG：让检索步骤可动态决定

固定 RAG 通常走预设链路；Agentic RAG 可以判断是否检索、检索哪个源、是否拆问题、证据够不够、是否再查一轮。例如问“去年到今年，差旅审批规则有什么变化”，可分别查 V1 和 V2，再比较。它适合复杂、多步、多源问题，但多轮模型调用增加成本和延迟，也可能循环或错误选源；应设置最大轮数、可访问数据源、停止条件与引用核验。简单单跳问题先用固定链路。

### GraphRAG：从文本块扩展到关系与全局概览

知识图谱把“实体—关系—实体”显式记录。例如“项目 A—负责人—张三”“项目 A—参与者—李四”。微软 GraphRAG 的典型建库过程是：从文档抽实体与关系 → 形成图 → 找到联系紧密的社区 → 为社区写摘要并保留原文来源。查询时，**局部搜索**从具体实体及附近关系找证据；**全局搜索**汇总多个社区摘要，适合“整个项目库的技术趋势是什么”。

这里的“社区”可以想成一个关系密集的主题群。例如项目 A、B、C 都围绕视觉模型，会被组织到相近的群里；预先写好的群摘要有助于从全库层面回答问题。但抽取出的关系可能错，摘要也可能漏细节；建图、实体消歧和更新都有成本。GraphRAG 不是多跳问题的唯一解法，先用多次检索或结构化查询做基线。[微软 GraphRAG 论文](https://arxiv.org/abs/2404.16130)

### LightRAG：另一种图增强实现

LightRAG 使用实体与关系的图结构，提供不同粒度的检索，并关注增量插入。资料中提到 **Naive**（普通向量）、**Local**（具体实体及邻接关系）、**Global**（更宏观的关系信息）、**Hybrid**（合并局部与全局）四种查询模式。对“张三负责什么”与“这几年技术主题怎么变”使用的证据范围不同，因此要按问题类型选择。理解重点是**图结构、查询类型、更新成本**的取舍；具体实现细节应以[LightRAG 论文](https://arxiv.org/abs/2410.05796)及仓库版本为准。不能根据名称断定它在任何数据集上都比 GraphRAG 更快、更便宜或更准。对于当前入门阶段，先把普通 RAG 的解析、召回、评估做明白，再读图增强实现。

| 方案 | 先看什么证据 | 值得试的场景 | 要测的代价 |
|---|---|---|---|
| 普通 RAG | 相似文本块 | 具体事实问答 | 漏检、上下文噪声 |
| Agentic RAG | 动态决定的多轮检索结果 | 多源、需要继续查证 | 调用次数、错误循环、延迟 |
| GraphRAG | 实体关系、社区摘要、原文 | 跨文档关系与全局概览 | 建图、摘要更新、抽取错误 |
| LightRAG | 图中的实体/关系和向量检索结果 | 需要图增强且资料持续变化 | 增量准确性、查询质量、维护成本 |

**自己复述：** “某合同第 3 条写了什么”和“所有合同中的风险主题是什么”，对检索证据的要求有什么不同？

## 11. 面试问法与回答框架

### 11.1 回答一个自己做过的项目

按“**业务目标 → 数据与约束 → 离线/在线链路 → 碰到的具体错误 → 方案与代价 → 指标证据**”讲。没有做过的优化不要说成自己做过；可以明确说“目前做了基线，下一步准备验证”。例：发现相关政策块在初次候选中排第 12，但最终只交给模型前 5 个，因此测 Rerank 后的 Hit@5 和 P95 延迟。这比说“我用了某向量库，效果很好”更有信息。

### 11.2 高频问题速答

| 面试问题 | 回答骨架 |
|---|---|
| 为什么要 RAG？ | 私有/新知识、证据与来源需求；检索后生成；仍需处理漏检和幻觉。 |
| 讲完整链路？ | 离线解析→清洗→切片→元数据→编码建索引；在线过滤→召回→可选融合/重排→上下文→生成→引用/监控。 |
| RAG 和微调如何选？ | 动态可追溯事实偏 RAG；行为/格式/能力问题再评估微调；可组合。 |
| Chunk 多大、overlap 多少？ | 看文档结构、问法粒度；用候选设置在评估集上比较；过小丢条件，过大带噪声。 |
| Embedding 怎么选？ | 看语言/领域/长度/部署成本；业务评估集比较 Recall@K、MRR；更换后重建索引。 |
| 为什么用向量库？ | 快速近邻搜索及元数据管理；产品选择看规模、过滤、更新、P95 和运维。 |
| BM25 和向量为何一起用？ | 专名/编号与语义改写互补；融合后用评估验证收益。 |
| Rerank 解决什么？ | 候选已覆盖证据但名次靠后；它提高排序，增加延迟，救不了漏召回。 |
| Top-K 怎么定？ | 画 K 对证据命中、答案质量、token、延迟的曲线，按目标选择。 |
| 如何减少幻觉？ | 优先保证证据质量；资料不足拒答；逐条核引、检查版本/冲突；Prompt 只是辅助。 |
| 答不准如何排查？ | 沿“原文→候选→最终上下文→回答”四处找证据首次消失或被误用的位置。 |
| 如何评估？ | Golden Set；检索 Hit/Recall/Precision/MRR；生成正确性/忠实度/引用/拒答；线上延迟成本。 |
| 生产落地最难在哪？ | 解析和版本、召回覆盖与排序、生成忠实度会级联；结合具体故障与验证说。 |
| 文档更新怎么办？ | 变更检测、删除/替换旧 chunk、重算受影响向量、索引一致性、版本回溯。 |
| 10 万用户怎么设计？ | 先确认 QPS、文档量、权限、SLO；分离建库与查询；缓存、扩容、监控、权限过滤；压测后选型。 |
| Agentic RAG 什么时候用？ | 多源/多跳/需反复查证时；设预算和停止条件；简单问答保留固定流程。 |
| GraphRAG/LightRAG 何时考虑？ | 先证明确有跨文档关系或全局聚合需求，再比较质量、建索引成本、更新复杂度。 |

### 11.3 五个追问的展开例子

**Q：为什么不能直接把 1000 份文档塞进上下文？** 需估算 token、延迟与费用；还要看模型能否在大量无关材料里稳定找对证据。RAG 先筛候选，但筛错也会漏答。小资料集可直接放上下文，做基线比较。

**Q：召回 Top-20 里已有正确块，为什么答案还是错？** 看正确块重排后是否进入最终上下文；若进了，看是否与旧版本冲突、Prompt 是否丢来源、模型是否误读条件。只换 embedding 不一定触及故障点。

**Q：混合检索权重怎么调？** 先按问题类型区分精确编号与自然语言改写；在验证集比较向量单路、BM25 单路、RRF 和加权融合；同时看 Hit/MRR、延迟。不要直接套“0.7/0.3”。

**Q：HNSW 与 IVF 有什么取舍？** HNSW 用可导航图近邻搜索，IVF 先聚类缩小候选范围；比较内存、建索引耗时、更新方式、召回—延迟曲线。复杂度不能一句“O(log N)”概括全部真实场景。

**Q：GraphRAG 相比普通 RAG 多了什么风险？** 实体/关系抽取错误可能放大；社区摘要可能遗漏或过期；建图及更新花费增加。先用有标注的关系与全局问题测试，再决定是否引入。

## 12. 最小动手任务和复习题

你目前 Python 正在打基础，**这一章先理解系统，不要求今天手搓向量库或写 Agent**。按阶段做：

1. **纸上模拟**：自写 5 条报销政策，每条加标题、版本、权限；设计 6 个问题（同义问法、精确词、无答案各至少 1 个），手工标出应命中的证据。
2. **纯 Python 基线**：把政策存成列表或 JSON，用包含关键词的简单规则返回候选；打印“问题、候选、来源”。先看哪里漏了。
3. **再接真实组件**：替换检索为 embedding，比较相同 6 个问题；需要时试 BM25、Rerank。每次记录变更和结果。
4. **简历项目标准**：有数据来源、基线、Golden Set、错误分析、一次有证据的改进、引用与权限/版本设计、README 和可复现脚本。只有“调通官方 Demo”还不够。

复习时合上笔记，回答：① 离线、在线各有哪些步骤？② 为什么 chunk 不是越小越好？③ BM25、Embedding、Rerank 各做什么？④ 证据在 Top-20 但没进答案，怎么查？⑤ Hit@K 与 Recall@K 的分母区别？⑥ 什么时候需要 Agentic 或图增强？答不出时回对应节，用报销例子重新画一遍。
