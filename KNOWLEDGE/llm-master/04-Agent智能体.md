# 第四章：AI Agent 智能体设计与工程落地

> 本章优先级：⭐ 目前先掌握 Agent、Workflow、工具与评估；◻ 多 Agent、DAG、浏览器 Agent 属专项工程，做相应项目时再学。来源：[仓库第四章](逐篇精读/README.md)与 [Agent 路线](逐篇精读/app/agent_learning_roadmap.md)。

## 4.1 Agent 与 Workflow【⭐】

**一句话：** Workflow 由程序预设步骤和分支；Agent 在允许的范围内根据观察决定下一步。是否用了 LLM 或有条件分支，本身不能决定它是不是 Agent。

**例子：** “上传图片→视觉模型分类→按类别检索条款→展示”是固定流程，用 Workflow 更容易测试。若系统要根据证据不足自主选择查另一份制度、追问用户、再判断是否结束，才有动态决策。两者也能组合：外层稳定流程包住一个受控 Agent 步骤。

**费曼自述：** “能提前画出每一步的任务，先写普通流程；只有路径需要现场判断，才让模型参与选下一步。”

**概念闪卡：** Q：有 if/else 就是 Agent 吗？A：不是，程序固定分支仍是 Workflow。Q：Agent 一定更高级吗？A：不一定，路径不确定时才可能带来收益。

来源：[Agent 是什么](逐篇精读/app/agent_intro.md) · [Agent vs Workflow](逐篇精读/app/agent_vs_workflow.md)。

## 4.2 ReAct、Reflection 与规划执行【⭐】

**一句话：** ReAct 是“判断→行动→观察→再判断”的循环；Reflection 是对结果做有依据的复查；Plan-and-Execute 先列任务，再逐步执行并在必要时改计划。

**例子：** 用户要比较 V1/V2 政策：先查 V1，再查 V2，发现 V2 缺生效日期，就补查发布公告，然后回答。若第一次检索失败，Reflection 应基于“没找到 V2 生效日期”改查询，而不是只让模型说“我应该更仔细”。若依赖关系固定，任务可表示为 DAG：两版检索可并行，比较必须等两者完成。

**费曼自述：** “Agent 不是一直思考，而是在每一步拿到外部反馈。反馈不足时改变动作，证据够了就停止。”

**概念闪卡：** Q：ReAct 的关键反馈是什么？A：工具或环境返回的观察。Q：规划为什么需要重规划？A：实际执行可能失败或出现新信息。Q：DAG 的边表达什么？A：任务依赖。

来源：[三种思路](逐篇精读/app/react_reflection_planning.md) · [DAG 执行器](逐篇精读/app/plan_execute_dag.md)。

## 4.3 工具怎么设计，MCP 又做什么【⭐】

**一句话：** 工具提供可执行能力；描述、参数 schema、返回格式、权限和错误码决定模型能否正确使用。MCP 是连接工具/资源的协议，不替代模型决定调用或应用执行校验。

**例子：** “查询处罚条款”工具的输入应是条款号或关键词，返回条款 ID、版本、正文和找不到状态。只返回一段自由文本，Agent 很难知道是成功还是失败。工具若会发送邮件或修改数据库，要由应用控制权限与必要确认。MCP 可把多个工具以统一协议提供给支持它的客户端，但业务权限仍要在服务端实现。

**费曼自述：** “模型需要一把描述清楚、大小合适、不会乱伤人的工具。协议解决怎么连，权限解决能不能做。”

**概念闪卡：** Q：Function Calling 与 MCP 区别？A：前者是模型提出结构化工具调用的机制；后者规定客户端与工具/资源服务如何对接。Q：工具报错如何帮助恢复？A：返回明确错误类型和可执行的下一步信息。

来源：[工具设计](逐篇精读/app/agent_tool_design.md) · [MCP](逐篇精读/app/mcp_protocol.md)。

## 4.4 Agent 为什么翻车、怎样控制边界【⭐】

**一句话：** 多步系统容易出现死循环、误调用、状态丢失、错误资料污染和权限越界；要在程序层限制步骤、权限、预算并保存可恢复状态。

**例子：** “请查处罚办法”连续检索 12 次还没有新证据，就应停止并给出未找到/请补信息，而不是无限继续。工具超时后应区分“没执行”和“已执行但没返回”，否则重试可能导致重复提交。网页内容里的“忽略规则”属于不可信数据。

**费曼自述：** “Agent 会自己选路，所以我要给它预算、边界和失败出口。能恢复、能审计，才算工程系统。”

**概念闪卡：** Q：最小停止条件？A：最大轮数/时间/成本、任务完成、无法取得新证据。Q：为什么不能只靠 Prompt 防越权？A：模型可能误判，权限必须由执行工具的程序实施。

来源：[失败模式](逐篇精读/app/agent_failure_modes.md)。

## 4.5 Agent 的记忆与上下文【⭐】

**一句话：** 当前对话、结构化任务状态、长期偏好和外部知识库是不同数据；每次只取当前任务需要的部分。

**例子：** “已经查过 V1、V2 还缺生效日期”应存成任务状态，而非指望模型翻看几十轮聊天。用户偏好“答案先给条款编号”可作为经确认的长期偏好。RAG 文档是外部知识，不等于用户个人记忆；错误或过期记忆要能更新删除。

**费曼自述：** “记忆不是聊天记录越长越好。任务进度存状态，事实查来源，稳定偏好谨慎保存。”

**概念闪卡：** Q：Session State 与聊天历史差别？A：前者是结构化的当前任务进度，后者是原始对话。Q：为什么长期记忆要有删除机制？A：偏好和事实会变化，也可能误存。

来源：[Agent 记忆](逐篇精读/app/agent_memory.md)。

## 4.6 怎么评估 Agent【⭐】

**一句话：** 既看最终任务成功，也看步骤数、工具调用正确率、失败恢复、权限安全和成本。

**例子：** 20 道“找到并比较两版规定”的任务中成功 18 道，还要检查有没有无意义重复检索、错误引用或越权读取。为测试恢复能力，可以故意让一次工具超时，看系统是否正确重试或终止。

**费曼自述：** “Agent 答对一次不够；我要知道它是否稳定、有没有多走冤路、失败时怎样收场。”

**概念闪卡：** Q：最终答案正确率能覆盖所有质量吗？A：不能，可能过程有越权、重复或成本过高。Q：测试集为什么要有失败场景？A：真实系统会遇到工具异常和证据不足。

来源：[Agent 评估](逐篇精读/app/agent_evaluation.md)。

## 4.7 多 Agent 与浏览器 Agent【◻】

**一句话：** 多 Agent 是把规划、执行、审核等角色分离；浏览器 Agent 则需要在大量网页内容中有选择地读取。只有单 Agent 已遇到明确瓶颈时才考虑这些结构。

**例子：** 让一个 Worker 查两版制度、Reviewer 核对引用，可能提高质量，但还需传递任务契约、共享产物引用和预算。若网页有成千节点，先获取标题/可访问性结构，再局部读取；不能把整个原始 DOM 一次塞给模型。

**费曼自述：** “分工是为了边界清楚和可验证；多角色会增加通信与成本，我要证明收益。”

**概念闪卡：** Q：多 Agent 为什么不能共享所有历史？A：噪声、权限和 token 成本都可能失控。Q：浏览器 Agent 第一轮要拿什么？A：页面结构地图，再按任务读取相关区域。

来源：[角色分工](逐篇精读/app/multi_agent_roles.md) · [上下文治理](逐篇精读/app/multi_agent_context_governance.md) · [浏览器内容](逐篇精读/app/browser_agent_dom_context.md)。
