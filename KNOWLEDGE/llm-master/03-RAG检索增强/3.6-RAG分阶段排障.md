### 目标与例子

目标：掌握 RAG 线上 Bad Case 的结构化定位方法论，建立“沿因果链向下穿透”的排障漏斗，拒绝“一答错就盲目加模型、改 Prompt”的玩具式调优。
例子：用户提问“三级动火审批需要谁签字？”，系统回答“需要项目总工程师签字”（实际规程规定只需车间安全员签字）。
如果直接归咎于“大模型变笨了”并尝试修改 System Prompt，完全是南辕北辙；经排障漏斗定位发现：原文件其实是扫描版 PDF，在离线解析阶段，审批表格中的“三级动火”与“一级动火”两行发生错位，导致下游检索送入的切片本身就是错误的。这属于典型的上游解析级联故障。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 用户线上失败 Query、用户权限角色、全链路可观测 Trace 日志（包含各环节中间产物及人工/专家核定的金标证据）。 |
| 做什么 | 依照信息流因果依赖，逐级核查：源头是否存在 → 解析是否残缺 → 召回是否命中 → 重排是否截断 → 生成是否忠实。 |
| 输出 | 定位出的首个致错阶段（First Point of Failure）、根因归类标签与针对性工程修复工单。 |
| 哪里出错 | 日志埋点缺失（无法复原各阶段 Snapshot）、以最终现象倒推根因（把检索漏召回误判为模型幻觉）。 |
| 重要参数影响 | 各阶段埋点粒度（决定排障可观测性）、链路超时时间与重试深度。 |

#### RAG 故障级联排查五层漏斗

```text
[第 1 层：源头知识层] 知识库原文中是否存在该问题的有效事实答案？
       │ 否 → 归因：知识库缺漏 / 资料过期。对策：补充知识，触发拒答。
       ↓ 是
[第 2 层：解析切片层] 提取清洗后的切片（Chunks）中，关键事实句是否完整无损？
       │ 否 → 归因：PDF/OCR 解析崩坏、表格错位、跨块硬截断。对策：优化版面解析。
       ↓ 是
[第 3 层：检索召回层] Top-K（如 K=20）初筛候选列表中，是否包含金标 Chunk？
       │ 否 → 归因：稀疏漏专有名词、稠密语义偏移、前置权限元数据误杀。对策：混合检索/改写。
       ↓ 是
[第 4 层：重排上下文层] 最终送入 Prompt 的精选上下文（如 Top-3）中，金标是否保留？
       │ 否 → 归因：Reranker 打分偏训、上下文窗口超限被截断。对策：调优 Rerank/去重。
       ↓ 是
[第 5 层：生成推理层] LLM 输出是否严格依据上下文？声明是否有确凿引用支撑？
       │ 否 → 归因：内在幻觉、多段冲突、推理错误。对策：加强引用约束、调整采样温度。
       ↓ 是
      【系统正常，答案正确】
```

### 面试追问

- 【🔥 必会】用户抱怨 RAG 系统回答有误，你作为应用算法负责人，标准排查 SOP 是什么？
一句话结论：严禁直接调 Prompt，必须导出该请求的 Trace 快照，按“源头→切片→召回→重排→生成”漏斗排查。
展开原理/取舍：首先确认企业原始库是否有正确事实；若有，拿用户 Query 去检索后台拉取召回的 Top-20 原始列表，看金标 Chunk 在不在里面；如果在，看经过重排和 Context 截断后有没有被剔除；如果送进了 Prompt 但模型答错，看是否上下文太长诱发了注意力分散，或者模型存在反向推理缺陷。定位到具体阶段后再做单变量修复。

- 【🔥 必会】为什么说“检索召回环节是整个 RAG 系统的天花板”？下游 Rerank 和大模型能弥补漏召回吗？
一句话结论：下游组件无法“无中生有”，未召回的知识在下游永远丢失。
展开原理/取舍：重排模型（Reranker）的本质是对初筛集合做精细打分排序，如果包含事实的切片根本没有进入 Top-N 候选池，重排器无论多么强大也无能为力；大模型如果面对缺乏关键事实的上下文，要么安全拒答，要么基于参数先验记忆瞎编（触发外在幻觉）。因此初筛召回率（Recall@K）决定了整个系统的理论能力上限。

- 【⭐ 理解】什么是内在幻觉（Intrinsic Hallucination）与外在幻觉（Extrinsic Hallucination）？
一句话结论：内在幻觉是模型篡改了给定上下文的矛盾错误；外在幻觉是模型补充了上下文中没有的事实。
展开原理/取舍：① 内在幻觉：Context 明明写着“违规罚款 500 元”，模型回答“违规罚款 5000 元”，即生成内容与输入证据相悖，多见于数值抽取、因果倒置或否定句误读；② 外在幻觉：Context 仅介绍了高处作业，模型回答时自作主张补充了“依据《特种作业安全法》第七条”，而该法条在上下文中从未出现。外在幻觉必须通过强制引用标记和严密的后置校验进行拦截。

### 故障模式与排障

- 故障模式：多段证据冲突导致模型陷入混乱

- 定位：排查送入 Context 的切片中是否同时包含了 2020 旧版与 2026 新版制度，或者两个不同部门的规章相互抵触，模型无法辨别时效与权威度。

- 修复：在切片元数据中强制注入 version、update_time 与 authority_level；在检索侧加入时效衰减因子或直接进行版本唯一性过滤，确保送入 Context 的证据没有内部冲突。

- 故障模式：Prompt 组装时的“中间遗失（Lost in the middle）”

- 定位：金标 Chunk 成功进入了 Top-5 并被拼入 Context，但放在了第 3 块的位置，LLM 回答时完全对其视而不见。

- 修复：实施重排倒置重组（Re-ordering）：把得分最高的切片分别放置在 Context 序列的最前面与最后面（紧贴用户问题），利用 Transformer 的局部注意力偏置强化对核心证据的感知。

### 工程 trick 与坑

- 全链路 Trace ID 穿透：从前端请求发起、网关鉴权、向量检索、重排服务到 LLM 调用，必须全程透传唯一的 request_id / trace_id，并将每个阶段的 Input/Output 打包落盘到日志中心（如 OpenTelemetry / ES），这是排障诊断的绝对物理前提。

- 排障时的单变量实验原则：发现错误后，严禁同时修改切片长度、更换 Embedding 模型、调整 Prompt 模板。必须固定其他所有环节，仅在失败的一层做 A/B 变量对照验证。

### 循序渐进 Toy Code：Level 6 — 自动化因果链排障诊断器

代码难度定位：Level 6（状态机与工程诊断）。基于真实工业排障漏斗，构建一个根据单次请求的链路快照，自动下钻定位首个致错阶段并输出行动指南的诊断状态机。

```python
"""
3.6 Toy Code: Level 6 - 自动化因果链排障诊断状态机
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
from enum import Enum
from typing import Optional


class RAGFailureStage(str, Enum):
    """RAG 故障发生阶段枚举"""
    SOURCE_DEFICIT = "SOURCE_DEFICIT"                   # 阶段 1：原始文档缺失
    PARSER_LOSS = "PARSER_LOSS"                         # 阶段 2：解析切片丢失
    RETRIEVAL_MISS = "RETRIEVAL_MISS"                   # 阶段 3：初筛召回未命中
    RERANK_DROPPED = "RERANK_DROPPED"                   # 阶段 4：重排或上下文截断丢弃
    CITATION_UNGROUNDED = "CITATION_UNGROUNDED"         # 阶段 5：引用悬空/不存在
    LLM_HALLUCINATION = "LLM_HALLUCINATION"             # 阶段 6：大模型事实幻觉
    HEALTHY = "HEALTHY"                                 # 全链路健康


@dataclass(frozen=True)
class PipelineTraceSnapshot:
    """单次请求的全链路可观测快照"""
    query: str
    gold_evidence_id: str             # 经过专家标注/核实必须命中的切片 ID
    source_contains_answer: bool      # 知识库源文件是否有该事实
    parsed_chunks_have_gold: bool     # 切片产物中是否存在金标切片
    retrieved_candidate_ids: tuple[str, ...] # 检索初筛召回的 Top-K 列表
    final_context_ids: tuple[str, ...]       # 经重排截断后实际塞入 Prompt 的列表
    generated_answer: str             # LLM 最终生成的文本
    cited_ids: tuple[str, ...]        # 从回答中提取出的引用 ID
    is_factually_faithful: bool       # 人工/裁判判定回答是否忠于给定事实


@dataclass(frozen=True)
class DiagnosisReport:
    """自动化诊断报告"""
    stage: RAGFailureStage
    root_cause: str
    actionable_fix: str


def diagnose_rag_pipeline(trace: PipelineTraceSnapshot) -> DiagnosisReport:
    """
    按因果依赖顺序向下穿透，精准锁定第一个破坏链路的故障点
    """
    # 阶段 1：源头检查
    if not trace.source_contains_answer:
        return DiagnosisReport(
            stage=RAGFailureStage.SOURCE_DEFICIT,
            root_cause="知识库源文件中根本没有此问题的正确答案依据。",
            actionable_fix="联系知识运营团队补充录入最新规章，并检查是否应当触发安全拒答。"
        )

    # 阶段 2：解析与切片检查
    if not trace.parsed_chunks_have_gold:
        return DiagnosisReport(
            stage=RAGFailureStage.PARSER_LOSS,
            root_cause="源文件有答案，但解析切片产物中丢失了该事实（表格破损或跨块截断）。",
            actionable_fix="排查 PDF/OCR 解析器，检查分块策略，增加 chunk_overlap 或引入标点吸附。"
        )

    # 阶段 3：初筛检索召回检查
    if trace.gold_evidence_id not in trace.retrieved_candidate_ids:
        return DiagnosisReport(
            stage=RAGFailureStage.RETRIEVAL_MISS,
            root_cause=f"金标切片 {trace.gold_evidence_id} 未进入初筛候选列表。",
            actionable_fix="排查前置权限/时效过滤是否误杀，升级为 BM25 + 向量双路混合检索，或引入 Query 改写。"
        )

    # 阶段 4：重排与 Prompt 截断检查
    if trace.gold_evidence_id not in trace.final_context_ids:
        return DiagnosisReport(
            stage=RAGFailureStage.RERANK_DROPPED,
            root_cause="初筛已成功召回金标，但在重排或上下文配额裁剪时被剔除。",
            actionable_fix="排查 Reranker 打分分布，检查 Prompt 上下文 Token 预算，调整重排截断阈值。"
        )

    # 阶段 5：引用有效性检查
    if trace.gold_evidence_id not in trace.cited_ids:
        return DiagnosisReport(
            stage=RAGFailureStage.CITATION_UNGROUNDED,
            root_cause="模型虽然获得了有效上下文，但在输出中未正确标注该证据来源引用。",
            actionable_fix="强化 System Prompt 中对 [引用: ID] 的少样本格式约束，增加后置引用守卫校验。"
        )

    # 阶段 6：生成忠实度检查
    if not trace.is_factually_faithful:
        return DiagnosisReport(
            stage=RAGFailureStage.LLM_HALLUCINATION,
            root_cause="上下文证据正确且已引用，但模型在组织语言时发生了内在幻觉（数字/逻辑篡改）。",
            actionable_fix="降低模型 Temperature 至 0.0，优化提炼指令，缩减 Context 长度以减少注意力分散。"
        )

    return DiagnosisReport(
        stage=RAGFailureStage.HEALTHY,
        root_cause="全链路证据链流转正常，生成忠实。",
        actionable_fix="无需修复，指标达标。"
    )


def self_test():
    """测试不同故障模式下的精准诊断定位"""
    base_query = "有限空间作业安全标准"
    gold_id = "CHUNK_SAFE_01"

    # 测试用例 1：检索漏召回
    trace_retrieval_miss = PipelineTraceSnapshot(
        query=base_query,
        gold_evidence_id=gold_id,
        source_contains_answer=True,
        parsed_chunks_have_gold=True,
        retrieved_candidate_ids=("CHUNK_OTHER_02", "CHUNK_OTHER_03"),
        final_context_ids=("CHUNK_OTHER_02",),
        generated_answer="依据不足",
        cited_ids=(),
        is_factually_faithful=False
    )
    res1 = diagnose_rag_pipeline(trace_retrieval_miss)
    assert res1.stage == RAGFailureStage.RETRIEVAL_MISS
    assert "初筛候选列表" in res1.root_cause

    # 测试用例 2：重排截断丢弃
    trace_rerank_drop = PipelineTraceSnapshot(
        query=base_query,
        gold_evidence_id=gold_id,
        source_contains_answer=True,
        parsed_chunks_have_gold=True,
        retrieved_candidate_ids=(gold_id, "CHUNK_OTHER_02"),
        final_context_ids=("CHUNK_OTHER_02",), # 金标被剔除
        generated_answer="依据不足",
        cited_ids=(),
        is_factually_faithful=False
    )
    res2 = diagnose_rag_pipeline(trace_rerank_drop)
    assert res2.stage == RAGFailureStage.RERANK_DROPPED

    # 测试用例 3：大模型生成内在幻觉
    trace_hallucination = PipelineTraceSnapshot(
        query=base_query,
        gold_evidence_id=gold_id,
        source_contains_answer=True,
        parsed_chunks_have_gold=True,
        retrieved_candidate_ids=(gold_id,),
        final_context_ids=(gold_id,),
        generated_answer="违规罚款一万元 [引用: CHUNK_SAFE_01]",
        cited_ids=(gold_id,),
        is_factually_faithful=False # 专家判定事实篡改
    )
    res3 = diagnose_rag_pipeline(trace_hallucination)
    assert res3.stage == RAGFailureStage.LLM_HALLUCINATION
    assert "内在幻觉" in res3.root_cause

    print("✅ 3.6 自动化因果链排障诊断状态机自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个遵循因果拓扑排序的诊断状态机 diagnose_rag_pipeline。核心工程不变量是：故障定位具有不可逆的单向穿透性——上游未达标时，绝对不推断下游组件的责任。

- 关键行解析：在第 45-88 行，我将排障逻辑严格划分为源头、切片、初筛、重排、引用与生成 6 个有序检查点。例如在第 57-63 行，只要 gold_id 不在 retrieved_candidate_ids 中，程序立即定性为 RETRIEVAL_MISS，直接阻断后续判定，防止把召回缺陷误判为 Rerank 或 LLM 幻觉。

- 主动说边界与坑：这段诊断代码假定了我们手头拥有单条 Bad Case 的专家金标 gold_evidence_id。在生产规模化治理中，必须主动向面试官展开：我们通常会搭建一套自动化回归流水线，将线上的用户踩坑记录自动聚类转化为评测用例，并使用类似的状态机批量生成全库各模块的“故障占比饼图”，指导下一阶段的研发重心。

### 本节收尾：费曼自述与闪卡

费曼自述：
“查 RAG 答错就像查自来水变浑。你得先去水库看水清不清（源头），再看管道滤网有没有破（解析与切片），再看水流有没有抽上来（召回），再看最后的水龙头有没有过滤（重排与模型）。水库本身就没水，你换再高级的水龙头也没用。”

- Q：为什么排查 RAG 答错时不能第一步就去改 Prompt？
A：因为 80% 以上的线上错误发生在上游的文档解析、切片截断与检索召回环节；上游漏掉证据时，改 Prompt 毫无意义。

- Q：初筛召回（Retrieval）与重排（Rerank）在排障时的分界线是什么？
A：检查金标是否在初筛 Top-20 中。不在则是初筛召回责任；在初筛中但被挤出最终 Top-3 则是重排打分或 Context 截断的责任。

- Q：模型生成发生内在幻觉（篡改上下文）的常用工程降噪手段有哪些？
A：设置 Temperature=0、缩短无关 Context、将关键切片移至末尾紧贴 Question、要求逐句附带 Citation。
