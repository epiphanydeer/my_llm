## 3.8 长文档与代码检索：结构感知、父子块与 AST 解析【🔥 必会】

〔补充自原仓库镜像〕〔本次新补，参考当前面试趋势〕

### 从问题理解这一节

- 长文档按标题、章节、条款建树，代码按类、函数、方法等 AST 节点切分；
- 子块负责检索精度，父块负责给模型补齐上下文，两者用 `parent_id` 关联；
- 代码检索要组合语义检索与关键词检索，符号名、路径和错误码不能只靠向量；
- 每个块都要携带 `repo`、`branch`、`commit`、路径和 ACL 等元数据；
- 在线检索先按身份和目标版本过滤，再召回、Rerank、父级扩展和组装 Context。

一句话：**检索单位不等于返回单位，相关不等于可用，可用还必须满足完整、当前和有权限。**

### 目标与例子

目标：理解长文本的“中间遗失（Lost in the Middle）”与代码的“强语法拓扑依赖”，掌握父子分块（Parent-Child）、层级摘要索引（Hierarchical Indexing）与基于 AST（抽象语法树）的结构化切片工程实现。
例子：

- 长文档场景：一份 120 页的企业《安全生产管理手册》，如果用户询问“动火作业的三级监护人职责”，该职责条款定义在第 8 章第 3 节，但前置必须遵循第 2 章关于“作业人员通用资质”的准入规定。若仅孤立切片，模型拿到了第 8 章的细则却丢掉了第 2 章的前提条件。

- 代码场景：用户提问“AuthManager.verify_token 是如何处理公钥过期的？”，如果用普通纯文本分块，切断了类定义头部与导入语句（import jwt），丢失了类成员变量 self.public_key，模型根本无法理解函数的完整调用上下文。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 长篇 Markdown/PDF 技术文档，或 Python 等编程语言源代码字符串；文件路径、分支版本。 |
| 做什么 | 解析文档骨架（标题树/AST 语法树），保留语义作用域与父子从属关系；按自然语法单元切分并记录精准行号。 |
| 输出 | 携带结构元数据（父类名称、装饰器、起止行号）的代码/文档切片对象。 |
| 哪里出错 | 语法分析崩溃（遇到含语法错误的代码时直接抛出未捕获异常挂掉整个 Ingestion）、符号同名混淆（不同类同名方法互相覆盖）、类成员上下文丢失。 |
| 重要参数影响 | 语法树提取深度（决定切到类级还是函数级）、上下文扩展行数（Context Padding）。 |

#### 为什么 Claude Code 等 AI 编程助手不优先用纯向量 RAG，而用 Grep + AST？

| 维度 | 纯向量 RAG 代码检索 | 语法树（AST）+ 符号（Ctags/LSP）+ Grep |
| --- | --- | --- |
| 精准度 | 容易语义飘移（问 get_user 向量可能召回了 delete_user，因为二者语义接近） | 100% 确定性（精确匹配符号名、声明处与调用链） |
| 时效与索引 | 每次 Git 提交都要重新切片算 Embedding，开销极重且更新延迟大 | 毫秒级直接搜索工作区文本与语法树，零向量化成本 |
| 代码上下文 | 切碎成 300 字符文本块，代码缩进和括号被破坏，极易产生语法幻觉 | 遵循函数与类的语法边界完整抽取，保留作用域完整性 |

### 面试追问

- 【🔥 必会】长文档检索中常说的“父子切片（Parent-Child / Small-to-Big）”到底是怎么落地的？
一句话结论：小块（150字）负责向量检索打分，命中小块后将其所属的完整父块（800字）塞给大模型。
展开原理/取舍：这是解决“检索精度与上下文完整性冲突”的黄金方案。切片越小，向量的语义内聚度越高，匹配度越精准；但小切片注入 Prompt 后信息残缺。因此离线时：切出大父块（包含完整章节），再将父块细切为多个子块，子块向量化存入向量库，元数据记录 parent_id；在线检索时用 Query 与子块向量计算相似度，召回 Top-K 子块后，去重获取其对应的父块完整内容拼入 Prompt。

- 【🔥 必会】代码仓库检索为什么严禁直接用普通的递归字符切分器？
一句话结论：代码不是散文，代码具有强语法闭包性与符号依赖，文本切分会撕裂语法树。
展开原理/取舍：普通文本切分器按字符或换行切断，极易将一个函数的函数签名和函数体切在两个块中，或者把类内的全局配置变量隔离在切片之外；此外，代码极其强调行号（Line Number）的可追溯性以便定位报错堆栈。必须使用语言专用的 AST 解析器，按 FunctionDef 和 ClassDef 节点作为切片原子单元。

- 【⭐ 理解】【排障题】针对代码库建立的 RAG 系统，检索函数名经常返回同名的无用 mock 函数或测试用例，该如何过滤？
一句话结论：在索引元数据中显式提取全限定名（Qualified Name）与文件路径掩码过滤。
展开原理/取舍：在 AST 解析阶段，切片 ID 不能仅用 function_name，必须记录“文件路径 + 类名 + 函数名”（如 src/auth/jwt.py::AuthManager::verify_token）；在线检索时结合路径黑名单过滤机制，默认排除 tests/、test_*.py 与 mock_*.py 目录，或者在 RRF 排序中对主干业务目录下的代码切片赋予更高的优先级权重。

### 故障模式与排障

- 故障模式：源码包含新语法特性导致 AST 解析器崩溃中断建库

- 定位：Python 3.10 解析器去解析使用了 Python 3.12 独有语法（如新类型参数语法 PEP 695）的源文件，直接抛出 SyntaxError 导致批量录入任务中断。

- 修复：构建 AST 解析降级回退机制（Graceful Degradation）：使用 try-except SyntaxError 捕获解析异常，异常时自动降级调用 3.3 节的缩进感知行级滑动窗口切分器，记录告警日志并保证任务不中断。

- 故障模式：长文档上下文拼接引发 LLM“中间遗失（Lost in the middle）”

- 定位：评测集分析显示，当目标证据位于 Prompt 上下文序列的前 10% 或后 10% 时，模型准确率超 90%；而当证据位于中间 50% 区间时，准确率暴跌至 45%。

- 修复：在组装 Context 时，使用双端摆放启发式算法（Edge-placement Heuristic）：将重排得分最高的 Chunk 放在 Context 最前，第二高的放在最后紧贴用户 Question，中等得分的放在中间，最大化激发大模型的边界注意力。

### 工程 trick 与坑

- 装饰器必须与函数主体作为一个整体切片：许多关键逻辑（如 @login_required、@permission_check('admin')）位于函数头部的装饰器中；如果 AST 仅提取 node.lineno，会丢失装饰器，必须向前回溯遍历 node.decorator_list 获取真正的起始物理行号。

- 保留类内上下文元数据：切分单个方法时，务必将该类声明时的 Class Docstring 及构造函数 __init__ 中初始化的成员变量列表作为元数据拼在切片注释中，大幅减少模型对 self.xxx 来源的困惑。

### 循序渐进 Toy Code：Level 8 — 基于 AST 的代码语法结构感知分块器

代码难度定位：Level 8（语法树解析与层级元数据）。利用 Python 标准库 ast，手写一个提取顶层函数、类及其方法、支持装饰器边界捕获、行号精准还原与语法错误优雅降级的工业级切片器。

```python
"""
3.8 Toy Code: Level 8 - 基于 Python AST 的语法结构感知代码切片器
依赖：Python 3.10+ 标准库
"""
import ast
from dataclasses import dataclass
from typing import Optional


@dataclass(frozen=True)
class CodeChunk:
    """结构化代码切片条目"""
    chunk_id: str
    file_path: str
    qualified_name: str         # 全限定名：如 'AuthService.login'
    chunk_type: str             # 'FUNCTION' | 'CLASS_METHOD' | 'CLASS_DECLARATION'
    start_line: int             # 物理起始行号（包含装饰器，从 1 开始计）
    end_line: int               # 物理终止行号
    code_content: str           # 源码文本
    parent_class: Optional[str] = None


class ASTCodeChunker:
    """基于抽象语法树的代码切片提取器"""

    def __init__(self, fallback_line_window: int = 50):
        self.fallback_line_window = fallback_line_window

    def chunk_python_source(self, source_code: str, file_path: str = "main.py") -> list[CodeChunk]:
        """
        解析 Python 源码并切分为函数/类级别的语法块
        
        具备语法错误自愈能力（降级为按行滑动切分）
        """
        if not isinstance(source_code, str):
            raise TypeError("源码必须为字符串")
        if not source_code.strip():
            return []

        lines = source_code.splitlines(keepends=True)
        total_lines = len(lines)

        try:
            tree = ast.parse(source_code, filename=file_path)
        except SyntaxError:
            # 优雅降级：当遇到包含语法错误的破损代码时，回退为按行滑动分块
            return self._fallback_line_chunker(lines, file_path)

        chunks: list[CodeChunk] = []

        def extract_node_bounds(node: ast.AST) -> tuple[int, int]:
            """精准捕获包含装饰器在内的起止行号"""
            start_line = node.lineno
            # 若包含装饰器，起始行向前推移至第一个装饰器所在行
            if hasattr(node, "decorator_list") and node.decorator_list:
                dec_starts = [d.lineno for d in node.decorator_list]
                start_line = min(min(dec_starts), start_line)
            
            end_line = getattr(node, "end_lineno", node.lineno)
            if end_line is None:
                end_line = node.lineno
            return start_line, end_line

        # 遍历顶层节点
        for node in tree.body:
            # 1. 顶层函数
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
                s_line, e_line = extract_node_bounds(node)
                code_text = "".join(lines[s_line - 1 : e_line])
                chunks.append(CodeChunk(
                    chunk_id=f"{file_path}::{node.name}:{s_line}-{e_line}",
                    file_path=file_path,
                    qualified_name=node.name,
                    chunk_type="FUNCTION",
                    start_line=s_line,
                    end_line=e_line,
                    code_content=code_text,
                    parent_class=None
                ))

            # 2. 类及其内部方法
            elif isinstance(node, ast.ClassDef):
                class_s_line, class_e_line = extract_node_bounds(node)
                # 遍历类内部子节点
                for child in node.body:
                    if isinstance(child, (ast.FunctionDef, ast.AsyncFunctionDef)):
                        method_s_line, method_e_line = extract_node_bounds(child)
                        method_text = "".join(lines[method_s_line - 1 : method_e_line])
                        q_name = f"{node.name}.{child.name}"
                        chunks.append(CodeChunk(
                            chunk_id=f"{file_path}::{q_name}:{method_s_line}-{method_e_line}",
                            file_path=file_path,
                            qualified_name=q_name,
                            chunk_type="CLASS_METHOD",
                            start_line=method_s_line,
                            end_line=method_e_line,
                            code_content=method_text,
                            parent_class=node.name
                        ))

        # 后置断言：提取出的代码内容必须与源码按行切片严格恒等
        for c in chunks:
            expected = "".join(lines[c.start_line - 1 : c.end_line])
            assert c.code_content == expected, "AST 切片物理行号重构与源码不匹配"

        return chunks

    def _fallback_line_chunker(self, lines: list[str], file_path: str) -> list[CodeChunk]:
        """降级行切分器实现"""
        chunks = []
        step = max(1, self.fallback_line_window - 10)
        for i in range(0, len(lines), step):
            end_idx = min(i + self.fallback_line_window, len(lines))
            chunk_lines = lines[i:end_idx]
            s_line = i + 1
            e_line = end_idx
            chunks.append(CodeChunk(
                chunk_id=f"{file_path}::raw_fallback:{s_line}-{e_line}",
                file_path=file_path,
                qualified_name="<raw_fallback>",
                chunk_type="FALLBACK_LINE",
                start_line=s_line,
                end_line=e_line,
                code_content="".join(chunk_lines),
                parent_class=None
            ))
            if end_idx >= len(lines):
                break
        return chunks


def self_test():
    """测试 AST 代码切片器的解析完整性、装饰器捕获与容错降级"""
    sample_code = (
        "@audit_log(level='HIGH')\n"
        "def standalone_func():\n"
        "    return 'safe'\n"
        "\n"
        "class SafetySupervisor:\n"
        "    \"\"\"现场安全巡检主管业务类\"\"\"\n"
        "    def __init__(self, site_id: str):\n"
        "        self.site_id = site_id\n"
        "\n"
        "    @require_permission('ADMIN')\n"
        "    async def approve_hot_work(self, permit_id: str) -> bool:\n"
        "        # 审批动火作业\n"
        "        return True\n"
    )

    chunker = ASTCodeChunker()
    chunks = chunker.chunk_python_source(sample_code, file_path="safety/service.py")

    # 1. 验证切片数量：1 个顶层函数 + 2 个类方法 (__init__, approve_hot_work)
    assert len(chunks) == 3

    # 2. 验证独立函数的装饰器捕获与行号
    func_chunk = chunks[0]
    assert func_chunk.qualified_name == "standalone_func"
    assert func_chunk.start_line == 1  # 成功包含 @audit_log 装饰器所在行
    assert func_chunk.end_line == 3
    assert "@audit_log" in func_chunk.code_content

    # 3. 验证类方法的父子级联与全限定名
    method_chunk = chunks[2]
    assert method_chunk.qualified_name == "SafetySupervisor.approve_hot_work"
    assert method_chunk.parent_class == "SafetySupervisor"
    assert method_chunk.chunk_type == "CLASS_METHOD"
    assert "@require_permission" in method_chunk.code_content

    # 4. 验证语法错误降级保护（不中断崩溃）
    broken_code = "def broken_syntax(:\n    pass"
    fallback_chunks = chunker.chunk_python_source(broken_code, file_path="broken.py")
    assert len(fallback_chunks) >= 1
    assert fallback_chunks[0].chunk_type == "FALLBACK_LINE"

    print("✅ 3.8 AST 代码结构感知切片器自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个针对代码特性的 ASTCodeChunker。核心不变量是：每一个切片绑定合法的语法边界，其起止行号严格满足 1 <= start_line <= end_line <= total_lines，且 lines[start_line - 1 : end_line] 必须 100% 字节级还原源码。

- 关键行解析：在第 45-56 行，我编写了 extract_node_bounds 辅助函数，核心处理了 node.decorator_list：由于 Python AST 的 node.lineno 默认只指向 def 那一行，必须倒查装饰器列表取最小值，才能把函数的鉴权注解完整捕获；第 39-44 行加入了针对 SyntaxError 的兜底容错，避免未知坏代码阻塞整个数据入库 Pipeline。

- 主动说边界与坑：这段代码基于 Python 标准库 ast。在跨语言代码库（如兼有 Java、C++、Go）生产环境中，必须主动向面试官展开：我们通常会基于 tree-sitter 统一多语言语法树解析器，提取出同构的 AST 节点；并在向量化之前，通过代码语义增强 Prompt（如拼接全限定名、继承类名与入参出参类型定义），使代码检索在向量空间中具备极高的语义辨识度。

### 本节收尾：费曼自述与闪卡

费曼自述：
“把代码按字数生切，就像把一个钟表按重量切成几块，齿轮和发条全碎了，谁也看不懂是怎么转的。基于语法树分块，就是顺着代码原本的零件结构——把一个函数、一个类完整拆出来当一个零件。不仅带着它的帽子（装饰器），还标清楚它是属于哪台机器的（父类全限定名）。”

- Q：什么是长文档检索中的“父子分块（Parent-Child）”？
A：小切片（Child）只负责计算向量做精准初筛召回，命中小切片后，将其所属的更大、更完整的父级章节（Parent）塞入 Prompt 供模型回答。

- Q：为什么提取 Python 函数切片时必须额外处理 decorator_list？
A：因为 AST 节点的 lineno 默认落在 def 关键字那一行，如果不遍历 decorator_list，权限控制与审计等关键装饰器会被遗漏在上一个切片中。

- Q：在大型代码 RAG 系统中，为什么通常采用“符号索引/正则（Grep）+ AST 结构分块 + 向量语义检索”的三层复合架构？
A：正则/符号用来毫秒级精确定位唯一的变量名与函数名，AST 保证语法完整不截断，向量用来根据模糊自然语言功能描述定位对应实现。
