## 6.4 推理压测：吞吐、P95 与失败率【🔥 必会】

〔融合 GitHub 教程与本地渐进式例子〕

### 一、提出问题：“平均延迟 100ms”，为什么用户依然投诉卡死？

在很多团队做完大模型部署后，经常出现极其尴尬的一幕：
- 算法工程师向领导汇报：“我们接口平均延迟只有 150 毫秒，性能极其强劲！”
- 结果业务一上线，客户疯狂投诉：“你们这个问答助手怎么回事？我经常点开等了 5 秒钟都没反应，页面全卡死！”

**为什么“平均值”成了最大的谎言？**
想象一个高铁班次统计：95 趟高铁准点到达，耗时 0 分钟；但有 5 趟高铁遭遇极端暴风雪，严重晚点了 5 个小时！
如果你算平均值：“平均晚点只有 15 分钟，整体运行平稳！”——你敢坐这趟高铁吗？那 5% 倒霉的乘客在车厢里已经被关了 5 个小时！

在互联网大厂和严肃企业级交付中，**平均延迟毫无参考价值，一切以 SLA 分位数（P95 / P99 尾延迟）说话！**

### 二、心智模型与图解：大模型吐字的两个关键时钟

大模型生成不是一次性吐出整篇文章，而是流式（Streaming）逐字打印的。评测大模型必须正交拆解为**两个关键时钟**：

#### 1. 生活中的“等上菜”比喻
- **首字时间 (TTFT, Time To First Token)**：相当于你去餐馆点完菜，**服务员把第一盘开胃菜端上桌的时间**。如果这盘菜让你等了 10 秒，你就会觉得餐馆奇慢无比想退单；
- **字间时间 (TPOT, Time Per Output Token)**：相当于服务员**上后续每一道菜的节奏间隔**。如果上菜节奏均匀顺畅（比如每秒上两盘），你就会吃得很舒服。

#### 2. 流式推理生命周期分解图

```
用户点击发送
     │
     ▼
[1. 网络排队与排入 Batch 队列]
     │
     ▼
[2. Prefill 阶段：GPU 猛烈计算长 Prompt]
     │
     ▼ ────────────> 第 1 个字打印！【首字时间 TTFT (Time To First Token)】
     │               (反映系统输入吞吐与排队阻塞，要求 P95 < 1.0s)
     ▼
[3. Decode 阶段：逐字自回归吐字]
     │
     ├─> 第 2 个字  ┐
     ├─> 第 3 个字  │ 衡量字间平滑度！【字间时间 TPOT (Time Per Output Token)】
     ├─> 第 4 个字  │ (公式: (总结束时间 - 首字时间) / (总字数 - 1))
     │   ...        │ (反映 GPU 显存带宽吞吐，要求 < 30ms/Token)
     └─> 最终 EOS  ┘
     │
     ▼ ────────────> 【端到端全生命周期耗时 E2E Latency】
```

#### 3. 为什么面试官最爱抓这句错话：“把各阶段 P95 直接相加”？

很多人在答面试题时脱口而出：“端到端 P95 = 排队 P95 + Prefill P95 + Decode P95。”——**面试官当场就会在心里打叉！**

```
【为什么 P95 绝不满足可加性？——“极值独立性”】

请求 A：输入了一篇 1 万字的长论文（Prefill 遭遇极端长尾 P95），但碰巧在深夜无人时发起的（排队时间为 0）；
请求 B：在上午 10 点高峰期排队了 3 秒（排队遭遇极端长尾 P95），但它只问了 3 个字“你好啊”（Prefill 时间极短）。

同一个请求，几乎不可能在【排队、Prefill、Decode】所有阶段同时踩中最极端的 5% 霉运！
如果把三个 P95 直接加在一起，算出来的数字会比真实端到端 P95 虚高 30%~50%！
唯一正确的做法：记录每个完整请求的端到端总时间，在全量样本里统一切分位数！
```

### 核心概念与五要素表

| 五要素 | 并发压测引擎与 TTFT/TPOT/P95 统计套件 (Level 4) |

|---|---|

| **输入 (Input)** | 压测请求批次序列（包含到达时间戳、Prefill 耗时、Decode 步数、每步生成耗时、状态码）、分位数目标（P50, P90, P95, P99）。 |

| **做什么 (Process)** | 模拟并发请求排队与流式响应；逐条解构端到端全生命周期耗时；计算每个请求的 TTFT 与 TPOT；统计全局吞吐量 (Tokens/s)；纯 Python 线性插值计算多阶分位数；比对 SLA 达标门禁。 |

| **输出 (Output)** | 生产级压测报告：包含总并发数、成功率、吞吐量、TTFT 分布、TPOT 分布与 SLA 达标判定。 |

| **哪里出错 (Failure Modes)** | 1. 把各阶段的 P95 简单相加（数学错误！各阶段的 P95 绝不满足可加性）；2. 未剔除预热 (Warmup) 阶段的数据导致初值偏差；3. 并发测试时客户端本身成为瓶颈。 |

| **参数影响 (Parameters)** | 采样频率与测试总样本量：样本量少于 100 时 P99 在统计学上完全失真，建议至少压测 500~1000 条稳定请求。 |

### 面试高频追问

**【🔥 必会】为什么各阶段（如排队、Prefill、Decode）的 P95 耗时不能直接相加作为端到端的 P95 延迟？**  

*结论先行：* 极值发生的独立性原理——同一个请求极少在所有阶段同时遭遇极端长尾。  

*展开解释：* 95 分位数是一个集合统计概念，而非线性算子。遭遇最长排队（P95）的请求，其输入文本可能很短，随后的 Prefill 阶段耗时极低；而遭遇最长 Prefill 的请求可能恰好在空闲时段进入没有发生任何排队。如果将各阶段的 P95 直接相加，算出来的数值会严重脱离现实（通常比真实端到端 P95 虚高 30%~50%），必须统计每个完整请求的端到端耗时序列后再统一切分位数。

**【🔥 必会】如何快速区分线上大模型服务的瓶颈是发生在 Prefill 阶段还是 Decode 阶段？**  

*结论先行：* 观察 TTFT 与 TPOT 的独立变化趋势。  

*展开解释：* 

- 若 **TTFT 暴涨** 而 TPOT 正常：说明瓶颈在输入端。通常是因为并发过大在排队、用户输入了数万字的超长 Prompt、或者 Prefill 阶段算力被吃满；

- 若 **TPOT 暴涨** 而 TTFT 正常：说明瓶颈在输出端。此时输出序列极长，显存带宽被打满，或者 Batch Size 挤压过大导致单步读写 KV Cache 的显存搬运严重阻塞。

**【⭐ 理解】当压测报告显示并发达到 32 时 P95 延迟断崖式恶化，作为算法工程师应从哪些维度优化？**  

*结论先行：* 从“连续批处理优化”、“KV Cache 显存瘦身”与“动态请求调度”三向协同突破。  

*展开解释：* 

1. 开启 **Continuous Batching (迭代级调度)**：彻底废弃静态 Padding 等待，某个序列生成完 EOS 立即剔除，空出的槽位动态插入新请求；

2. 开启 **Chunked Prefill**：将大请求的超长输入切块，避免一次性卡死计算核心达数秒；

3. 压缩 **KV Cache 精度至 FP8**：显存带宽占用直接减少 50%，在同等显存带宽下可承载的并发吞吐直接翻倍。

### 生产级代码实现：生产级并发压测引擎与 TTFT/TPOT/P95 统计套件 (Level 4)

```python

"""6.4 生产级并发压测引擎与 TTFT/TPOT/P95 统计套件 (Level 4 进阶实战)

业务场景：

在外企大模型服务投产前，执行标准化高并发模拟与 SLA 合规性审计：

1. 模拟流式生成生命周期（请求到达、首字产出、逐字生成、连接关闭）；

2. 正交分离首字时间 (TTFT) 与字间时间 (TPOT)；

3. 纯 Python 严格计算分位数分布 (P50, P90, P95, P99)，无外部库依赖；

4. 自动化输出吞吐 (Tokens/s) 与工业级 SLA 达标判断。

"""

from __future__ import annotations

import math

from dataclasses import dataclass

from typing import Any, Dict, List, Optional, Tuple

@dataclass(frozen=True)

class StreamInferenceTrace:

    """单次流式推理真实观测追踪"""

    request_id: str

    arrival_time_ms: float

    first_token_time_ms: float

    finish_time_ms: float

    generated_tokens_count: int

    http_status_code: int = 200

    @property

    def ttft_ms(self) -> float:

        """首字延迟: 发起到第一个 Token 打印的时间"""

        return self.first_token_time_ms - self.arrival_time_ms

    @property

    def total_e2e_ms(self) -> float:

        """端到端全生命周期耗时"""

        return self.finish_time_ms - self.arrival_time_ms

    @property

    def tpot_ms(self) -> float:

        """字间延迟: 篇间每个 Token 的平均生成时间"""

        decode_duration = self.finish_time_ms - self.first_token_time_ms

        tokens_in_decode = self.generated_tokens_count - 1

        if tokens_in_decode <= 0:

            return 0.0

        return decode_duration / tokens_in_decode

@dataclass

class SLAPerformanceBenchmarkReport:

    """SLA 性能测试审计报告"""

    total_requests: int

    success_rate: float

    tokens_per_second_throughput: float

    # TTFT 首字分位数

    ttft_p50_ms: float

    ttft_p95_ms: float

    ttft_p99_ms: float

    # TPOT 字间分位数

    tpot_p50_ms: float

    tpot_p95_ms: float

    # 端到端延迟分位数

    e2e_p50_ms: float

    e2e_p95_ms: float

    sla_compliance: bool

    diagnosis_message: str

def compute_percentile(values: List[float], p: float) -> float:

    """纯 Python 线性插值计算精确分位数"""

    if not values:

        return 0.0

    sorted_v = sorted(values)

    n = len(sorted_v)

    if n == 1:

        return sorted_v[0]

    idx = (n - 1) * p

    f = math.floor(idx)

    c = math.ceil(idx)

    if f == c:

        return sorted_v[int(idx)]

    d0 = sorted_v[int(f)] * (c - idx)

    d1 = sorted_v[int(c)] * (idx - f)

    return d0 + d1

class InferenceBenchmarkAnalyzer:

    """工业级大模型推理性能基准分析套件"""

    @classmethod

    def evaluate_benchmark(

        cls,

        traces: List[StreamInferenceTrace],

        max_ttft_p95_sla_ms: float = 1000.0,

        max_failure_rate_sla: float = 0.01

    ) -> SLAPerformanceBenchmarkReport:

        """分析流式压测追踪记录，生成 SLA 评估大表"""

        if not traces:

            raise ValueError("压测追踪记录列表不能为空")

        total = len(traces)

        successful_traces = [t for t in traces if t.http_status_code == 200]

        success_rate = len(successful_traces) / total

        if not successful_traces:

            raise RuntimeError("全部压测请求均失败，无法计算性能分位数")

        # 校验时序递增约束

        for t in successful_traces:

            if not (t.arrival_time_ms <= t.first_token_time_ms <= t.finish_time_ms):

                raise ValueError(f"Trace {t.request_id} 时序矛盾：到达 <= 首字 <= 结束 断言失败！")

        ttft_list = [t.ttft_ms for t in successful_traces]

        tpot_list = [t.tpot_ms for t in successful_traces]

        e2e_list = [t.total_e2e_ms for t in successful_traces]

        # 统计吞吐量: 总生成 Token / 压测时间窗口 (秒)

        earliest_start = min(t.arrival_time_ms for t in successful_traces)

        latest_finish = max(t.finish_time_ms for t in successful_traces)

        wall_clock_sec = (latest_finish - earliest_start) / 1000.0

        total_tokens = sum(t.generated_tokens_count for t in successful_traces)

        throughput = total_tokens / wall_clock_sec if wall_clock_sec > 0 else 0.0

        # 计算多阶分位数

        ttft_p50 = compute_percentile(ttft_list, 0.50)

        ttft_p95 = compute_percentile(ttft_list, 0.95)

        ttft_p99 = compute_percentile(ttft_list, 0.99)

        tpot_p50 = compute_percentile(tpot_list, 0.50)

        tpot_p95 = compute_percentile(tpot_list, 0.95)

        e2e_p50 = compute_percentile(e2e_list, 0.50)

        e2e_p95 = compute_percentile(e2e_list, 0.95)

        failure_rate = 1.0 - success_rate

        sla_pass = (ttft_p95 <= max_ttft_p95_sla_ms) and (failure_rate <= max_failure_rate_sla)

        if sla_pass:

            msg = f"SLA 审计通过！P95 首字延迟 ({ttft_p95:.1f}ms) 达标，失败率 ({failure_rate*100:.2f}%) 满足生产准入要求。"

        else:

            reasons = []

            if ttft_p95 > max_ttft_p95_sla_ms:

                reasons.append(f"P95 首字延迟超标 ({ttft_p95:.1f}ms > {max_ttft_p95_sla_ms:.1f}ms)")

            if failure_rate > max_failure_rate_sla:

                reasons.append(f"请求失败率超标 ({failure_rate*100:.2f}% > {max_failure_rate_sla*100:.2f}%)")

            msg = f"SLA 审计阻断！原因: {'; '.join(reasons)}"

        return SLAPerformanceBenchmarkReport(

            total_requests=total,

            success_rate=round(success_rate, 4),

            tokens_per_second_throughput=round(throughput, 1),

            ttft_p50_ms=round(ttft_p50, 1),

            ttft_p95_ms=round(ttft_p95, 1),

            ttft_p99_ms=round(ttft_p99, 1),

            tpot_p50_ms=round(tpot_p50, 1),

            tpot_p95_ms=round(tpot_p95, 1),

            e2e_p50_ms=round(e2e_p50, 1),

            e2e_p95_ms=round(e2e_p95, 1),

            sla_compliance=sla_pass,

            diagnosis_message=msg

        )

def self_test():

    """验证并发时延正交解构、分位数计算、吞吐统计与 SLA 门禁断言"""

    # 模拟 20 个流式推理 Trace

    traces = []

    # 构造 19 个正常快速样本

    for i in range(18):

        traces.append(

            StreamInferenceTrace(

                request_id=f"req_{i:02d}",

                arrival_time_ms=100.0 * i,

                first_token_time_ms=100.0 * i + 150.0,  # TTFT = 150ms

                finish_time_ms=100.0 * i + 150.0 + 400.0, # 总耗时 = 550ms

                generated_tokens_count=21,              # 20 个 decode token -> TPOT = 20ms

                http_status_code=200

            )

        )

    # 构造 2 个发生严重排队的极端长尾慢请求 (P95 压力样本)

    traces.append(

        StreamInferenceTrace(

            request_id="req_tail_slow_1",

            arrival_time_ms=1900.0,

            first_token_time_ms=1900.0 + 1100.0,

            finish_time_ms=1900.0 + 1100.0 + 800.0,

            generated_tokens_count=21,

            http_status_code=200

        )

    )

    traces.append(

        StreamInferenceTrace(

            request_id="req_tail_slow",

            arrival_time_ms=2000.0,

            first_token_time_ms=2000.0 + 1200.0,       # TTFT 达到 1200ms 超标！

            finish_time_ms=2000.0 + 1200.0 + 800.0,

            generated_tokens_count=21,

            http_status_code=200

        )

    )

    # 1. 验证 P95 超标阻断 (SLA = 1000ms)

    report = InferenceBenchmarkAnalyzer.evaluate_benchmark(traces, max_ttft_p95_sla_ms=1000.0)

    assert report.total_requests == 20

    assert report.success_rate == 1.0

    # TTFT P50 应该是 150ms

    assert report.ttft_p50_ms == 150.0

    # TTFT P95 必然受到 1200ms 长尾拉升超过 1000ms！

    assert report.ttft_p95_ms > 1000.0

    assert report.sla_compliance is False

    assert "P95 首字延迟超标" in report.diagnosis_message

    print(f"✅ 长尾尾延迟精准捕捉通过！P50 TTFT: {report.ttft_p50_ms}ms, P95 TTFT: {report.ttft_p95_ms}ms (SLA 成功拦截)")

    # 2. 放宽 SLA 阈值到 1500ms 验证达标通过

    relaxed_report = InferenceBenchmarkAnalyzer.evaluate_benchmark(traces, max_ttft_p95_sla_ms=1500.0)

    assert relaxed_report.sla_compliance is True

    assert "SLA 审计通过" in relaxed_report.diagnosis_message

    print("✅ 放宽 SLA 阈值自检通过！")

    # 3. 边界测试：时序倒挂拦截 (首字时间早于发起时间)

    bad_trace = [

        StreamInferenceTrace("bad_t", 500.0, 400.0, 600.0, 10, 200) # 400 < 500 倒挂！

    ]

    try:

        InferenceBenchmarkAnalyzer.evaluate_benchmark(bad_trace)

        raise AssertionError("未拦截时序倒挂异常")

    except ValueError as e:

        assert "时序矛盾" in str(e)

    print("✅ 倒挂时序异常防御测试通过！")

    print("✅ 6.4 生产级并发压测引擎与 TTFT/TPOT/P95 统计套件自检全部通过！")

if __name__ == "__main__":

    self_test()

```

### 排障指南（常见故障、定位方法、修复策略）

| 常见故障 (Failure) | 定位方法 (Diagnosis) | 修复策略 (Mitigation) |

|---|---|---|

| **并发达到 100 时全量超时** | 监控看到连接数暴增，大量请求由于排队过长达到网关 30 秒超时直接断开。 | 在反向代理层（如 Nginx/Envoy）开启基于令牌桶的限流排队与优雅排队等待页，设置最大排队深度，超量立即熔断快速失败。 |

| **P99 出现离群的“卡顿”尖刺** | 观察 TTFT 曲线，每隔约 2 分钟就会出现一个长达 5 秒的异常尖刺。 | 排查后台垃圾回收机制。通常是 Python 全局 GC 或未开启显存池导致的重度碎片内存整理；在启动参数中开启预分配显存池。 |

| **字间时间 (TPOT) 随并发剧烈恶化** | 单个请求时 TPOT 只有 15ms，并发到 16 时 TPOT 暴增到 120ms。 | 显存带宽饱和（Memory Bandwidth Saturation）。将模型权重加载到更高带宽的 GPU，或开启 Tensor Parallelism (TP) 跨多卡拆分权重，倍增聚合显存带宽。 |

### 工程 trick 与坑

1. **绝对剔除压测预热阶段 (Warmup)**：大模型刚启动的前 10~20 个请求在做 CUDA Kernel 编译与显存初次分配，耗时可能比平稳期慢 10 倍。正式统计分位数前，必须先打 50 个预热请求并显式剔除。

2. **区分物理并发与逻辑并发**：压测脚本里的 `concurrency=32` 指的是同时发起 32 个连接，但服务端底层实际在并发跑的可能是动态批处理队列（Continuous Batching）。必须同时记录服务端的真实活跃 Batch Size。

3. **测试数据长度必须对齐生产分布**：严禁拿固定的“10个字提问，10个字回答”做压测！必须按照线上真实日志的 Token 长度分布（如均值 1500 输入，300 输出的对数正态分布）进行仿真加压。

### 面试怎么讲（三段式：项目背景与选型理由、架构设计与核心机制、踩坑排障与量化收益）

**使用约定：**下面的项目情境和数字仅为虚构示例，不能直接当作本人经历或结果；只使用自己实际参与且有证据的内容。

> **面试官提问**：“你在项目中是如何做大模型推理性能压测的？如何衡量和保障线上高并发下的服务质量？”

> 

> **回答范式**：

> 1. **背景与选型**：“在工业安检问答与报告生成系统上线前，为了向企业客户承诺严格的 SLA（首字响应 < 1.0 秒，失败率 < 0.1%），我们必须进行严谨的生产级全链路并发压测。我们坚决摒弃了只看平均延迟的粗糙做法，建立了覆盖全生命周期指标的压测规范。”

> 2. **架构与机制**：“我们搭建了一套分布式的流式压测采集与分析套件。在时延维度，将每个请求的时间戳物理拆解为：负责反映排队与 Prefill 算力速度的首字延迟 (TTFT)，以及反映 Decode 显存带宽平滑度的字间延迟 (TPOT)；在统计维度，纯自研了线性插值的分位数统计器，严格输出 P50/P90/P95/P99 梯队指标，并实时监控吞吐量 (Tokens/s) 随并发压力的拐点走势。”

> 3. **踩坑与收益**：“在首轮压测中我们发现：当并发突破 16 时，TTFT 的 P95 发生了从 320ms 飙升至 2.4s 的断崖式恶化。通过将指标正交拆解，定位出是长文本 Prefill 阻塞了计算核心。我们据此在 vLLM 调度层开启了 Chunked Prefill 与 FP8 缓存量化，最终在并发翻倍至 32 时，P95 首字延迟依然稳健压在 680ms 以内，单卡吞吐量拉升了 2.4 倍，圆满通过了客户苛刻的验收压测。”

### 费曼自述与闪卡

**费曼自述（3 分钟白板口述框架）**：  

“去外企面试聊性能，只要你张嘴说‘我的模型平均只要 100 毫秒’，面试官心里就已经给你打不及格了。因为现实生活中从来没有‘平均’这回事！这就好比你坐高铁，平均晚点 1 分钟，但有 5% 的班次晚点了 3 个小时，这高铁你还敢坐吗？所以大厂只看 P95 和 P99。把 100 个请求从快到慢排队，看第 95 个人到底等了多久！另外，大模型吐字有两个关键时间：第一个叫‘首字时间’（TTFT），就是等服务员把第一盘菜端上来的时间；第二个叫‘字间时间’（TPOT），就是服务员给你上后续菜的节奏。前一个慢，是厨房在备料（算力算不过来）；后一个慢，是传菜员腿脚慢（显存带宽读不过来）。分清楚这两个，优化才能一针见血！”

**备考闪卡 Q&A**：  

- **Q：什么是 TTFT（Time To First Token）与 TPOT（Time Per Output Token）？**  

  *A：* TTFT 是从发起请求到接收首个 Token 的时间（反映排队与预填充耗时）；TPOT 是后续生成每个 Token 的平均耗时（反映解码平滑度）。

- **Q：为什么评估系统可用性必须看 P95/P99 尾延迟？**  

  *A：* 平均值会被大量简单的极短请求拉低，严重掩盖长文本或高并发排队造成的长尾超时；P95 才能真实反映绝大多数用户的最坏容忍边界。
