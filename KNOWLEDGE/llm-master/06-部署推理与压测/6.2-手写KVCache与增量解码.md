## 6.2 KV Cache：prefill、decode 与分页【🔥 必会】

### 一、提出问题：大模型逐字生成，为什么会发生“灾难级重算”？

想象你在写一部悬疑连载小说：
- 写**第 1 章**时，你脑子里只有主角张三，下笔如飞；
- 写**第 10 章**时，前面出场了 10 个人物，你得花时间把前 9 章翻一遍，确保设定不冲突；
- 写到**第 100 章**时，前面有 100 个人物、无数条伏笔。**如果你每次写下一个字之前，都必须把前 99 章从头到尾一字不差地重新读一遍**，你会怎么样？——你会当场累瘫，越写越慢，慢到最后根本写不动！

**大语言模型的自回归生成，本质上就是在干这件蠢事！**

```
【没有 KV Cache 时的自回归生成（灾难级愚蠢重算）】：

第 1 步：输入 ["今天", "天气"]       -> 模型计算 2 个词 -> 生成 "真"
第 2 步：输入 ["今天", "天气", "真"]  -> 模型重新计算 3 个词（前两个完全重算！） -> 生成 "好"
第 3 步：输入 ["今天", "天气", "真", "好"] -> 模型重新计算 4 个词（前三个完全重算！） -> 生成 "啊"
...
第 1000 步：为了生成第 1000 个词，前 999 个词的 Q、K、V 被整整从头算了 1000 遍！
计算复杂度直接飙到了恐怖的 O(N^3)！
```

**痛点总结**：自注意力机制中，由于因果掩码（Causal Mask）的存在，前面的词根本看不到后面的词，所以**过去所有词算出来的 Key 向量和 Value 向量，在后面永远不会改变，是绝对的历史常量！** 每次重新计算它们，完全是白白浪费 GPU 算力。

---

### 概念：为什么需要这一环

**一句话：** 自回归生成时，缓存已处理 token 的 Key/Value，避免每次生成新 token 都把前文完整重算；缓存需要显存。PagedAttention 等方法改善缓存内存管理，Prefix Cache 在可复用前缀上减少重复计算。

### 二、心智模型与图解：给大模型装一个“角色卡片盒”

既然前文的 Key 和 Value 永远不变，那我们能不能找个抽屉把它们存起来？
这就是 **KV Cache（键值缓存）**。

#### 1. 生活中的大白话类比
- **Query（查询向量）**：相当于你现在手里**最新写出的那一个字**，他在大喊：“全场注意，我是第 100 号词，我要找跟我有关系的人！”
- **Key（特征键）**：相当于过去出场过的每一个词挂在胸前的**名牌**（“我是时间”、“我是天气”、“我是标点”）；
- **Value（内容值）**：相当于每个词背包里装的**具体信息**。

有了缓存盒之后，你每写出一个新字：
1. **只为这一个新字计算一次 Q、K、V**；
2. 把他的 $K$ 和 $V$ 卡片插进抽屉里（留给未来用）；
3. 拿他这一个 $Q$，跟抽屉里所有现成的 $K$ 名牌挨个碰一下（点积算关联度）；
4. 按照碰出来的分数，把抽屉里所有的 $V$ 礼物加权打包，得到当前字的输出！

#### 2. 直观数据流走向图（一张图看懂 Prefill 与 Decode）

```
阶段一：Prefill（预填充阶段，首字响应 TTFT）
------------------------------------------------------------
用户输入: ["今天", "天气", "真好"] (一次性全量并行输入)
           ↓       ↓       ↓
        [ViT/LLM 并行计算所有位置的 Q, K, V]
           ↓       ↓       ↓
      ┌─────────────────────────┐
      │  生成初始 KV Cache 缓存盒  │ -> [K_今天, K_天气, K_真好]
      │  (驻留在 GPU 高速显存中)  │ -> [V_今天, V_天气, V_真好]
      └─────────────────────────┘
           ↓
      输出第 1 个字: "，" (首字出炉，Prefill 结束！)


阶段二：Decode（自回归逐字解码阶段，平滑度 TPOT）
------------------------------------------------------------
当前只输入最新生成的单字: "，" (长度只有 1！)
           ↓
   [只为这 1 个字计算 q_新, k_新, v_新] (计算量极小！)
           ↓
   ┌──────────────────────────────────────────┐
   │ 1. 把 k_新, v_新 追加进缓存盒           │ -> 抽屉变成 4 张卡片
   │ 2. 拿单根 q_新 与抽屉里所有 [K] 碰分数   │ -> 1 维向量乘矩阵
   │ 3. 拿分数加权抽屉里所有 [V] 内容        │
   └──────────────────────────────────────────┘
           ↓
      输出第 2 个字: "出" (速度极快，单步耗时从 O(N^2) 降为 O(N)！)
```

#### 3. 为什么面试官总问“算力受限”与“显存带宽受限”？
看懂上面的图，你就能秒懂大厂面试经典考题：
- **Prefill 阶段（首字）**：大矩阵乘大矩阵，Tensor Core 疯狂计算，此时 GPU 像一个开足马力的发动机，瓶颈是 **GPU 算力上限（Compute-bound）**；
- **Decode 阶段（后续吐字）**：每次只计算一个词，算力根本消耗不完。但是！为了算这一个词，GPU 必须在几十毫秒内，把显存抽屉里几千张庞大的 $K$ 和 $V$ 完整搬进计算核心。此时计算单元大部分时间在“傻傻等待数据搬运”，瓶颈是 **显存带宽（Memory-bandwidth-bound）**！

---

### 核心概念与五要素表

| 五要素 | 增量 KV Cache 自注意力与状态机内核 (Level 2) |

|---|---|

| **输入 (Input)** | 当前步输入 Token 嵌入向量、历史 KV 缓存张量池（含已缓存长度 `cached_len`）、投影权重。 |

| **做什么 (Process)** | 区分 Prefill 与 Decode 状态；Prefill 阶段全量并行前向并初始化缓存；Decode 阶段仅增量计算单步 QKV，将当前 KV 追加进缓存池；单 Query 跨全量缓存注意力加权；验证增量解码结果与无缓存全量前向严格数值等价。 |

| **输出 (Output)** | 当前步生成的单 Token 隐藏态向量，以及更新后的缓存状态对象。 |

| **哪里出错 (Failure Modes)** | 1. 缓存长度越界超出最大显存容量池；2. 增量更新时 Key/Value 时间轴拼接错位；3. 没有将多轮对话的历史缓存正确复用。 |

| **参数影响 (Parameters)** | 缓存数据类型（FP16/FP8/INT8）：采用 FP8 缓存可直接节省 50% 的 KV 显存占用，并提升访存带宽吞吐。 |

---

### 面试高频追问

**【🔥 必会】请在白板上详细画出带 KV Cache 的 Decoder 自回归单步生成数据流。**  

*结论先行：* 每次只输入新生成的单个 Token，仅产生长度为 1 的 Query，与缓存的全部历史 Keys 做点积。  

*展开解释：* 

1. 输入：新 Token 向量 $x_t \in \mathbb{R}^{1 	imes C}$；

2. 投影：仅对该 Token 投影计算 $Q_t = x_t W_q, K_t = x_t W_k, V_t = x_t W_v$（全部为 $1 	imes C$）；

3. 缓存更新：将 $K_t, V_t$ 追加拼接到全局缓存张量 $K_{cache} \in \mathbb{R}^{t 	imes C}, V_{cache} \in \mathbb{R}^{t 	imes C}$；

4. 注意力计算：$Scores =  rac{Q_t \cdot K_{cache}^T}{\sqrt{d}}$（形状为 $1 	imes t$），经过 Softmax 后与 $V_{cache}$ 相乘输出 $1 	imes C$ 向量。计算量与历史长度 $t$ 成线性比例。

**【🔥 必会】大模型推理的 Prefill 阶段和 Decode 阶段，在系统性能瓶颈上有什么本质区别？**  

*结论先行：* Prefill 是算力受限（Compute-bound），Decode 是显存带宽受限（Memory-bound）。  

*展开解释：* 

- Prefill 处理长文本 Prompt 时，是高维矩阵乘大矩阵（GEMM），GPU 的 Tensor Core 全负荷运转，主要看算力 TFLOPS；

- Decode 每步只有一个词，是用一根小向量去乘庞大的历史 KV 矩阵（GEMV）。算力只消耗一点点，但 GPU 的显存控制器必须把整个巨幅 KV Cache 从显存颗粒读入芯片缓存中。计算速度远快于数据搬运速度，导致计算单元大量空转等待显存读取。提高 Decode 吞吐的核心是增加批次 (Batch Size) 或压缩 KV Cache 精度以提高显存带宽利用率。

**【⭐ 理解】vLLM 的 PagedAttention 是如何解决显存碎片问题的？**  

*结论先行：* 借鉴操作系统虚拟内存分页，将物理显存切为离散 Block 动态按需分配。  

*展开解释：* 传统系统为了应对不可预期的输出长度，必须为每个请求预分配连续的显存空间（如提前划拨最大 2048 长度），造成严重的“未用预留浪费”以及不同请求生命周期结束造成的“外部碎片”。PagedAttention 将显存切分成固定大小（如每个 Block 存 16 个 Token 的 KV），物理上不需要连续，通过逻辑块表动态寻址；需要新空间时才分配一个新页，支持不同序列间共享 Prompt 前缀缓存（Copy-on-Write），极大释放了并发承载力。

### 生产级代码实现：纯手撕 KV Cache 增量自注意力与状态机 (Level 2)

```python

"""6.2 纯手撕 KV Cache 增量自注意力与状态机 (Level 2 顶峰实战)

业务场景：

彻底吃透大模型自回归推理底层运转与加速基石。

实现纯 Python / NumPy 零外部黑盒依赖的 IncrementalKVCacheAttention：

1. 区分 Prefill 预填充阶段与 Decode 逐步解码阶段；

2. 增量状态更新：每次只为单个新 Token 计算 QKV，追加写入 KV 缓存池；

3. 核心数学等价断言：严格证明带 KV Cache 的单步增量输出与全量前向计算结果绝对数值吻合 (误差 < 1e-9)；

4. 模拟 PagedAttention 块表 (Block Table) 映射与显存计数。

"""

from __future__ import annotations

import math

from dataclasses import dataclass, field

from typing import Dict, List, Optional, Tuple

@dataclass

class PagedKVCache:

    """轻量模拟分页 KV 缓存池与块表管理器"""

    block_size: int = 4              # 每个物理块容纳的 Token 数量

    max_blocks: int = 16             # 最大物理块容量

    # 模拟物理显存块: block_id -> (K_chunk, V_chunk)

    physical_blocks_k: Dict[int, List[List[float]]] = field(default_factory=dict)

    physical_blocks_v: Dict[int, List[List[float]]] = field(default_factory=dict)

    # 请求的逻辑块表映射: request_id -> List[block_id]

    block_tables: Dict[str, List[int]] = field(default_factory=dict)

    current_free_block_id: int = 0

    def allocate_or_append(

        self,

        request_id: str,

        k_token: List[float],

        v_token: List[float]

    ) -> None:

        """将单步新 Token 的 KV 动态写入分页块表中"""

        if request_id not in self.block_tables:

            self.block_tables[request_id] = []

        table = self.block_tables[request_id]

        # 检查是否需要分配新的物理 Block

        if not table or len(self.physical_blocks_k[table[-1]]) >= self.block_size:

            if self.current_free_block_id >= self.max_blocks:

                raise MemoryError("PagedAttention 显存物理块池耗尽，触发 OOM 保护！")

            new_block_id = self.current_free_block_id

            self.current_free_block_id += 1

            table.append(new_block_id)

            self.physical_blocks_k[new_block_id] = []

            self.physical_blocks_v[new_block_id] = []

        # 写入当前最新的物理块中

        latest_block_id = table[-1]

        self.physical_blocks_k[latest_block_id].append(k_token)

        self.physical_blocks_v[latest_block_id].append(v_token)

    def fetch_all_kv(self, request_id: str) -> Tuple[List[List[float]], List[List[float]]]:

        """通过块表映射，从离散物理块中顺序读取完整历史 KV 矩阵"""

        table = self.block_tables.get(request_id, [])

        all_k: List[List[float]] = []

        all_v: List[List[float]] = []

        for blk_id in table:

            all_k.extend(self.physical_blocks_k[blk_id])

            all_v.extend(self.physical_blocks_v[blk_id])

        return all_k, all_v

class IncrementalKVCacheAttention:

    """纯手写带 KV Cache 的因果自注意力算子"""

    def __init__(self, dim: int = 4) -> None:

        self.dim = dim

        self.scale = 1.0 / math.sqrt(dim)

        # 模拟可训练的 Q, K, V 投影权重矩阵: (dim, dim)

        self.w_q = [[(0.1 * (i * 2 + j)) for j in range(dim)] for i in range(dim)]

        self.w_k = [[(0.08 * (i + j * 3)) for j in range(dim)] for i in range(dim)]

        self.w_v = [[(0.12 * (i * 3 + j)) for j in range(dim)] for i in range(dim)]

    def _linear(self, vec: List[float], weight: List[List[float]]) -> List[float]:

        """矩阵向量乘法: vec (1, D) @ weight (D, D)"""

        out = [0.0] * self.dim

        for j in range(self.dim):

            out[j] = sum(vec[i] * weight[i][j] for i in range(self.dim))

        return out

    def prefill_phase(

        self,

        request_id: str,

        prompt_tokens: List[List[float]],

        cache_manager: PagedKVCache

    ) -> List[List[float]]:

        """Prefill 阶段：一次性处理输入 Prompt 并构建初始 KV 缓存"""

        seq_len = len(prompt_tokens)

        all_q, all_k, all_v = [], [], []

        for token in prompt_tokens:

            q = self._linear(token, self.w_q)

            k = self._linear(token, self.w_k)

            v = self._linear(token, self.w_v)

            all_q.append(q)

            all_k.append(k)

            all_v.append(v)

            # 写入分页缓存池

            cache_manager.allocate_or_append(request_id, k, v)

        # 计算标准因果注意力输出 (对 Prompt 内部全量计算)

        outputs: List[List[float]] = []

        for i in range(seq_len):

            scores = []

            for j in range(i + 1):  # 因果掩码：只能看过去和当前

                dot = sum(all_q[i][d] * all_k[j][d] for d in range(self.dim)) * self.scale

                scores.append(dot)

            # Softmax

            max_s = max(scores)

            exp_s = [math.exp(s - max_s) for s in scores]

            sum_exp = sum(exp_s)

            probs = [e / sum_exp for e in exp_s]

            # 加权 V

            attn_vec = [0.0] * self.dim

            for j in range(i + 1):

                for d in range(self.dim):

                    attn_vec[d] += probs[j] * all_v[j][d]

            outputs.append(attn_vec)

        return outputs

    def decode_step_with_cache(

        self,

        request_id: str,

        new_token: List[float],

        cache_manager: PagedKVCache

    ) -> List[float]:

        """Decode 阶段：仅计算单步 QKV，读取历史 KV Cache 进行高效增量解码！

        复杂度：从无缓存的 O(N^2) 骤降为仅与当前 Token 相关的 O(N)！

        """

        # 1. 核心加速点：仅对最新单个 Token 计算 Q, K, V！

        q_curr = self._linear(new_token, self.w_q)

        k_curr = self._linear(new_token, self.w_k)

        v_curr = self._linear(new_token, self.w_v)

        # 2. 追加新 KV 到分页缓存池

        cache_manager.allocate_or_append(request_id, k_curr, v_curr)

        # 3. 从块表中获取包含当前步在内的全部历史 Keys 和 Values

        history_k, history_v = cache_manager.fetch_all_kv(request_id)

        total_len = len(history_k)

        # 4. 单 Query 跨历史 KV 计算点积注意力

        scores = []

        for j in range(total_len):

            dot = sum(q_curr[d] * history_k[j][d] for d in range(self.dim)) * self.scale

            scores.append(dot)

        # Softmax

        max_s = max(scores)

        exp_s = [math.exp(s - max_s) for s in scores]

        sum_exp = sum(exp_s)

        probs = [e / sum_exp for e in exp_s]

        # 加权求和

        out_token = [0.0] * self.dim

        for j in range(total_len):

            for d in range(self.dim):

                out_token[d] += probs[j] * history_v[j][d]

        return out_token

    def full_recomputation_without_cache(

        self,

        full_tokens: List[List[float]]

    ) -> List[float]:

        """低效基准：无缓存的全量重新计算（作为正确性对照真值）"""

        total_len = len(full_tokens)

        all_k = [self._linear(t, self.w_k) for t in full_tokens]

        all_v = [self._linear(t, self.w_v) for t in full_tokens]

        # 只取最后一个位置的 Query

        q_last = self._linear(full_tokens[-1], self.w_q)

        scores = [

            sum(q_last[d] * all_k[j][d] for d in range(self.dim)) * self.scale

            for j in range(total_len)

        ]

        max_s = max(scores)

        exp_s = [math.exp(s - max_s) for s in scores]

        sum_exp = sum(exp_s)

        probs = [e / sum_exp for e in exp_s]

        out_token = [0.0] * self.dim

        for j in range(total_len):

            for d in range(self.dim):

                out_token[d] += probs[j] * all_v[j][d]

        return out_token

def self_test():

    """验证 KV Cache 增量输出与全量计算无差异断言、分页块表动态分配与加速验证"""

    dim = 4

    attn = IncrementalKVCacheAttention(dim=dim)

    # block_size=2，测试离散分页

    cache_mgr = PagedKVCache(block_size=2, max_blocks=10)

    req_id = "req_audit_001"

    # 1. 模拟 Prompt 输入（3 个 Token）

    prompt = [

        [0.5, 0.2, -0.1, 0.4],

        [0.1, 0.8, 0.3, -0.2],

        [-0.3, 0.4, 0.9, 0.1],

    ]

    # 执行 Prefill 预填充

    prefill_outs = attn.prefill_phase(req_id, prompt, cache_mgr)

    assert len(prefill_outs) == 3

    # 3 个 Token 跨越了 2 个物理块 (Block 0 存 2 个，Block 1 存 1 个)

    assert len(cache_mgr.block_tables[req_id]) == 2

    print(f"✅ Prefill 阶段完成：初始化 3 个 Token，动态挂载 {len(cache_mgr.block_tables[req_id])} 个物理块")

    # 2. 模拟 Decode 阶段：生成第 4 个 Token（单字步进）

    token_4 = [0.25, -0.5, 0.15, 0.8]

    cached_decode_out_4 = attn.decode_step_with_cache(req_id, token_4, cache_mgr)

    # 3. 核心数学等价断言：对比无缓存全量重新计算的结果，两者必须绝对数值相等！

    full_sequence_4 = prompt + [token_4]

    ground_truth_out_4 = attn.full_recomputation_without_cache(full_sequence_4)

    for d in range(dim):

        diff = abs(cached_decode_out_4[d] - ground_truth_out_4[d])

        assert diff < 1e-9, f"KV Cache 数学等价性校验失败：维度 {d} 差异 {diff} > 1e-9"

    print("✅ 核心数学定理断言通过：增量 KV Cache 解码与全量重算绝对数值等价！")

    # 4. 继续生成第 5 个 Token，触发第 3 个物理块的分配

    token_5 = [-0.1, 0.3, -0.4, 0.6]

    cached_decode_out_5 = attn.decode_step_with_cache(req_id, token_5, cache_mgr)

    full_sequence_5 = full_sequence_4 + [token_5]

    ground_truth_out_5 = attn.full_recomputation_without_cache(full_sequence_5)

    for d in range(dim):

        assert abs(cached_decode_out_5[d] - ground_truth_out_5[d]) < 1e-9

    # 第 5 个 Token 进入，当前总长 5，块大小 2 -> 必须分配了 3 个块！

    assert len(cache_mgr.block_tables[req_id]) == 3

    print(f"✅ PagedAttention 动态分块扩容测试通过：当前序列长度 5，块表占用 {len(cache_mgr.block_tables[req_id])} 块")

    print("✅ 6.2 纯手撕 KV Cache 增量自注意力与状态机自检全部通过！")

if __name__ == "__main__":

    self_test()
```

### 排障指南（常见故障、定位方法、修复策略）

| 常见故障 (Failure) | 定位方法 (Diagnosis) | 修复策略 (Mitigation) |

|---|---|---|

| **长文本下自回归生成质量崩塌** | 序列生成超过 2048 词后，模型开始重复胡言乱语。 | 检查位置编码是否与 KV Cache 对齐。在 RoPE 中，必须为增量单 Token 传递当前的绝对位置索引 `position_ids=[cached_len]`，严禁每步都传 `position_ids=[0]`。 |

| **高并发下发生显存段错误崩溃** | 没有内存分页管理，多个长短不一的请求同时生成导致物理显存碎片化耗尽。 | 接入 PagedAttention（如 vLLM）。淘汰早期 HuggingFace 原生拼接的连续内存张量方案，使用离线块表进行显存分页统一纳管。 |

| **Decode 吐字卡顿，GPU 利用率极低** | 监控显示 GPU 显存占满，但 GPU 计算核心利用率 (SM Util) 只有 15%。 | 典型的显存带宽瓶颈（Memory-bound）。调大连续批处理（Continuous Batching）并发数，或开启 FP8 KV Cache 将单次访存字节数砍半。 |

### 工程 trick 与坑

1. **Chunked Prefill 算力访存混排**：在真实生产引擎中，Prefill（算力吃满）和 Decode（访存吃满）如果分开排队会导致严重的互相阻塞。近代成熟方案（如 vLLM 的 Chunked Prefill / FlashInfer）将长输入的 Prefill 切块，与当前批次的 Decode 放在同一个 CUDA Kernel 中混跑，同时填饱算力核心与显存带宽。

2. **多轮对话 Prefix Caching（前缀缓存）**：在客服和 Agent 场景中，所有用户共享相同的长系统提示词。利用 PagedAttention 的不可变特性，将 System Prompt 所在的 Block 设为只读共享块（Reference Count > 1），新会话秒级复用已计算好的 KV，使首字时间 (TTFT) 从数秒骤降至几十毫秒！

3. **KV Cache 量化注意精度损失**：如果将 KV Cache 直接暴力压缩为 INT4，长文本注意力的 Softmax 分布会发生锐化漂移导致回答错乱；建议优先采用 FP8 (E4M3 / E5M2) 或使用带通道缩放 (K-Scale / V-Scale) 的方案。

### 面试怎么讲（三段式：项目背景与选型理由、架构设计与核心机制、踩坑排障与量化收益）

**使用约定：**下面的项目情境和数字仅为虚构示例，不能直接当作本人经历或结果；只使用自己实际参与且有证据的内容。

> **面试官提问**：“请详细讲讲大模型推理中 KV Cache 的原理，它为什么能加速？如果没有 PagedAttention 会遇到什么问题？”

> 

> **回答范式**：

> 1. **背景与选型**：“在大模型落地初期，我们直接使用 HuggingFace 原生 `generate()` 部署在线问答接口。在并发达到 10 以上时，服务器频繁发生 CUDA OOM，且长文本下每个字的生成延迟越来越慢。经过底层 profiling 分析，我们明确了推理架构必须全面升级为基于 KV Cache 与 PagedAttention 的高性能部署方案。”

> 2. **架构与机制**：“KV Cache 的本质是‘空间换时间’。在自回归生成中，由于因果注意力掩码的存在，过去所有 Token 的 Key 和 Value 是永不改变的历史常量。通过在 Prefill 阶段构建初始 KV 缓存池，在随后的 Decode 阶段，单步只需对新生成的一个 Token 计算投影，直接追加到缓存中，与历史全量 Keys/Values 进行增量注意力计算，使单步复杂度从原本反复全量计算的 $O(N^2)$ 降低到 $O(N)$。同时，我们通过类似操作系统的分页块表管理物理显存，将预分配浪费降到最低。”

> 3. **踩坑与收益**：“在自研服务调优中，我们曾遇到多轮会话重复计算 System Prompt 导致的 Prefill 延迟瓶颈。通过在 PagedAttention 之上落地前缀缓存共享机制，将相同安全规程 Prompt 的 KV Block 在多租户间只读复用，最终使首字延迟 (TTFT) 平均降低了 72%，并发吞吐提升了 3.8 倍，显存碎片浪费彻底控制在 4% 以内。”

### 费曼自述与闪卡

**费曼自述（3 分钟白板口述框架）**：  

“要想给面试官讲透 KV Cache，你就拿‘写连载小说’打比方。如果没有 KV Cache，作者写第 100 章时，为了不写错前面的设定，必须把前 99 章从头到尾一字不差地重新读一遍（全量重算），越往后写越慢，慢到最后作者自己先累垮了；而有了 KV Cache，作者找了个秘书（缓存池），在写完前 99 章时把每个人物叫什么、什么特征全写在卡片上。写第 100 章时，作者只需要把第 100 章的新角色卡片插进盒子里，然后抬头看一眼整盒卡片就能下笔，速度永远像写第一章一样飞快！至于 PagedAttention，就是给这套卡片装了一个活页夹（分页机制），哪一页写满了就动态夹进去一张新纸，再也不用提前买一个 500 页的巨大笨重笔记本放在桌上占地方了。”

**备考闪卡 Q&A**：  

- **Q：为什么有了 KV Cache，自回归生成的单步计算复杂度能从 $O(N^2)$ 降为 $O(N)$？**  

  *A：* 历史 Tokens 的 Key 和 Value 已经缓存，单步只需对当前单个 Token 计算一次 QKV 投影，并与缓存的历史 $N$ 个 Keys 做单向量点积，无需重新对前文做两两全量注意力计算。

- **Q：Decode 阶段属于 Compute-bound 还是 Memory-bound？为什么？**  

  *A：* 属于 Memory-bandwidth-bound（显存带宽受限）。单步计算量只有单个向量点积，但必须完整从显存颗粒搬运全量历史 KV 矩阵，计算单元耗费大量时间等待数据从显存搬入。
