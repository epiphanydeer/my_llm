## 5.1 RAG 与 SFT：从需求和基线选方案【🔥 必会】

**个人经历口径：**文中的项目话术与数字是示例，不能当作本人经历或成绩；只使用自己参与且有证据的事实。

〔补充自原仓库镜像〕〔本次新补，参考中国境内外企应用岗面试高频考点〕

目标 + 例子。 彻底根除“遇到任务不假思索直接上微调”的低级工程错误。在真实企业级落地中，微调 (SFT) 与检索增强生成 (RAG) 不是互斥的对立关系，而是解决不同维度问题的两种武器：

- RAG 的核心定位：解决知识的时效性、外部私有知识库挂载、事实精准溯源与权限隔离。当法规制度每周更新、知识库有数万页文档、或者需要精准引用“某制度第3章第2条”时，必须首选 RAG；

- SFT 的核心定位：解决输出格式规范性（如严格遵循特定复杂 JSON Schema）、专业领域表达口吻与风格对齐、多步复杂推理习惯固化。当 Prompt 提示词无论怎么强调，模型依然偶发输出 Markdown 标记破坏下游 API 解析时，SFT 才是对症下药的解法；

- 架构演进原则：“Prompt 优先 → RAG 跟进 → SFT 兜底格式 → 组合拳 (RAG+SFT)”。在未穷尽少样本提示 (Few-shot) 和检索优化前，切忌盲目启动微调。

### 一、先破一个最常见的误解：微调 ≠ 给模型加知识

绝大多数人第一次纠结"微调还是 RAG"，都是从一个错误前提出发的：

“模型不知道我们公司的业务，那我微调一下，让它把这些知识记住，不就行了？”

**这个理解是错的，而且错得很彻底。**

微调改的从来不是"模型知道什么"，而是"模型怎么做"。

我们之前在 [SFT 那一篇](../原仓库Markdown/docs/llm/app/finetuning_sft_rlhf_dpo.md) 反复强调过一句话：**微调更常见的价值不是补知识，而是控行为。**

你想让模型输出固定的 JSON 格式、想让它用客服那种语气说话、想让它在医疗/法律场景里有更专业的判断风格——这些是"行为"，微调能搞定。

但你想让它知道"公司这周刚改的退款政策"、"这个客户签了哪几条合同"——这些是"知识"，而且是**会变的、私有的、要追溯来源的**知识。

这种东西硬塞进参数里，是灾难：

- **知识一变就得重训**，政策周一改了，你周二就得重新训一遍模型？
- **答错了无法追溯**，模型张口就来，你不知道它依据的是哪份文档
- **还容易引发灾难性遗忘**，为了记住新知识，反而把原来会的搞忘了

补这种知识，是 RAG 的活儿。我们在 [为什么有了大模型还需要 RAG](../原仓库Markdown/docs/llm/app/why_rag.md) 里讲过它解决的正是这四个问题：幻觉、私有知识、时效性、可追溯。

所以微调和 RAG 的本质区别，一张图就能说清：

这张图回答的是：微调和 RAG 到底动了模型的什么。

看那一格格的方块，它代表模型的参数（权重）。

左边 RAG，**那些格子从头到尾全是灰的、一格没变**——模型参数全程冻结。它只是在运行时去知识库里检索，把查到的内容喂进输入，知识根本不进权重。所以知识改了，改文档就行，模型不用重训。

右边微调，**格子有几个变成了蓝色**——参数被实打实地改写了，行为焊进了权重。好处是稳定、不占上下文；代价是知识一变就得重训。

记住这条主线，下面所有判断都从它推出来：

**缺知识，找 RAG；缺行为，才考虑微调。**

### 面试高频追问

【🔥 必会】大模型在专业领域问答经常胡说八道，究竟应该选 RAG 还是微调 (SFT)？
结论先行： 解决事实知识盲区优先选 RAG；解决格式与推理习惯选 SFT。
展开解释： 知识的本质是动态的。微调是将信息隐式编码进千亿权重矩阵中，更新成本极高且无法避免参数幻觉，更无法给出法律级可溯源的文档切片；RAG 将外部知识显式注入上下文，保证随时更新且有据可查。只有当专业领域有极度固定的特定输出语法或风格时，才在 RAG 基础上结合 SFT。

【🔥 必会】既然 RAG 这么灵活，什么场景下微调是不可替代的？
结论先行： 复杂严格格式输出、领域特定语言风格、以及长指令遵循能力。
展开解释： 1. 复杂格式要求（如要求输出特定 AST 抽象语法树或嵌套 JSON），Prompt 容易偶发格式崩塌，微调能将输出语法概率固化；2. 节省延迟与成本，如果每次调用都要在 Prompt 里塞入 3000 Token 的 Few-shot 样例，不如通过微调将范例内化进模型，使输入上下文减少 80%。

【⭐ 理解】什么是 RAG + SFT 组合拳架构？你们项目中是如何落地的？
结论先行： 用 SFT 定制模型的思考方式与格式，用 RAG 供给外部最新证据。
展开解释： 在安全隐患问答项目中，我们先对开源模型进行轻量 LoRA 微调，专门教会它理解“请根据依据给出【违规点、法规依据、整改建议】三段式结构”；而在实际运行中，外部条款由 RAG 动态检索召回填入上下文。微调负责结构，RAG 负责事实，实现端到端工业级闭环。

### 生产级代码实现：业务边界与选型决策树路由模型 (Level 1)

```python
"""5.1 RAG vs SFT 业务边界与选型决策路由模型 (Level 1 基础实战)

业务场景：
在外企应用架构评审中，针对不同业务场景进行技术路线选型，
避免“为了技术而技术”，用量化评估替代主观拍脑袋。

本模块实现纯 Python 规则决策引擎：
1. 需求维度强类型规范（时效性、格式严苛度、溯源要求、标注量）；
2. 自动化评分与边界冲突检测；
3. 输出可解释的选型推荐与工程取舍清单。
"""

from __future__ import annotations
from dataclasses import dataclass
from enum import Enum
from typing import Any, Dict, List, Optional


class KnowledgeUpdateFrequency(Enum):
    STATIC = "static"          # 知识几年不变（如高中物理定律）
    PERIODIC = "periodic"      # 知识定期更新（如月度/季度安全管理规章）
    REALTIME = "realtime"      # 知识实时变动（如工单状态、当天排班）


class FormatRigidity(Enum):
    LOOSE_TEXT = "loose_text"  # 自由文本，容忍灵活表述
    STRUCTURED = "structured"  # 结构化文本（如固定三段式）
    STRICT_JSON = "strict_json"# 严格机器可读格式，下游直接反序列化，错一个标点即崩溃


class TraceabilityRequirement(Enum):
    NONE = "none"              # 无需溯源
    DESIRABLE = "desirable"    # 最好有引用
    MANDATORY = "mandatory"    # 法律/合规级强溯源，必须给出具体页码与原文切片


class SolutionType(Enum):
    PROMPT_ONLY = "prompt_only"            # 仅靠 Prompt / Few-shot 即可解决
    RAG_ONLY = "rag_only"                  # 纯 RAG 检索增强
    SFT_ONLY = "sft_only"                  # 纯 SFT 监督微调
    HYBRID_RAG_SFT = "hybrid_rag_sft"      # RAG 检索 + SFT 格式/领域适配组合拳


@dataclass(frozen=True)
class ProjectRequirement:
    """项目需求特征向量"""
    knowledge_frequency: KnowledgeUpdateFrequency
    format_rigidity: FormatRigidity
    traceability: TraceabilityRequirement
    labeled_samples_count: int  # 可用的高质量标注数据对数
    latency_budget_ms: float    # 端到端延迟预算上限


@dataclass
class ArchitectureDecision:
    """架构选型裁决报告"""
    recommended_solution: SolutionType
    confidence_score: float
    pros: List[str]
    cons: List[str]
    rationale: str


class SolutionDecisionEngine:
    """工业级大模型方案选型决策引擎"""

    @staticmethod
    def evaluate(req: ProjectRequirement) -> ArchitectureDecision:
        if req.labeled_samples_count < 0:
            raise ValueError("标注样本数不能为负数")
        if req.latency_budget_ms <= 0:
            raise ValueError("延迟预算必须为正数")

        # 规则 1：强溯源要求或知识高频更新 -> 必须强制依赖 RAG
        needs_rag = (
            req.knowledge_frequency in {KnowledgeUpdateFrequency.PERIODIC, KnowledgeUpdateFrequency.REALTIME}
            or req.traceability == TraceabilityRequirement.MANDATORY
        )

        # 规则 2：格式极度严苛且具备一定标注数据，或者极度严苛的延迟限制 -> 强烈倾向 SFT
        needs_sft = (
            req.format_rigidity == FormatRigidity.STRICT_JSON
            and req.labeled_samples_count >= 100
        )

        # 决策逻辑
        if needs_rag and needs_sft:
            return ArchitectureDecision(
                recommended_solution=SolutionType.HYBRID_RAG_SFT,
                confidence_score=0.95,
                pros=["兼具外部知识精准检索与严格机器可读格式输出", "事实可溯源且下游系统解析零报错"],
                cons=["系统架构复杂度高", "需维护检索索引与轻量微调权重两套生命周期"],
                rationale="知识更新频繁且需要法律级溯源，同时下游依赖严格 JSON 解析，组合拳方案是最优解。"
            )

        if needs_rag:
            return ArchitectureDecision(
                recommended_solution=SolutionType.RAG_ONLY,
                confidence_score=0.90,
                pros=["无需训练模型，知识更新秒级入库", "天然支持出处溯源与权限过滤"],
                cons=["受限于检索召回精度", "长上下文导致推理首字延迟较高"],
                rationale="核心痛点是动态知识与可溯源性，微调无法解决时效性问题，首选 RAG。"
            )

        if needs_sft:
            return ArchitectureDecision(
                recommended_solution=SolutionType.SFT_ONLY,
                confidence_score=0.88,
                pros=["模型行为高度稳定，输出格式 100% 固化", "减少输入 Prompt 长度，降低推理成本与延迟"],
                cons=["缺乏外部知识更新机制", "需要准备标注数据与训练算力"],
                rationale="知识相对静态，核心痛点是下游 API 对格式的严苛要求，通过微调固化格式性价比最高。"
            )

        # 默认基础场景
        return ArchitectureDecision(
            recommended_solution=SolutionType.PROMPT_ONLY,
            confidence_score=0.85,
            pros=["零研发门槛，极快原型验证", "无需微调算力，无需向量数据库基础设施"],
            cons=["依赖基座模型通用能力", "无法处理海量私域长知识库"],
            rationale="知识静态、格式容忍度高、无需严格溯源，依靠高质量 Prompt 工程即可满足需求。"
        )


def self_test():
    """验证不同业务场景下的架构路由裁决准确性与边界测试"""
    engine = SolutionDecisionEngine()

    # 1. 测试安全法规审查场景（法规定期更新 + 强溯源 + 严格三段式输出 + 300条标注）
    # 期望：组合拳 HYBRID_RAG_SFT
    safety_req = ProjectRequirement(
        knowledge_frequency=KnowledgeUpdateFrequency.PERIODIC,
        format_rigidity=FormatRigidity.STRICT_JSON,
        traceability=TraceabilityRequirement.MANDATORY,
        labeled_samples_count=300,
        latency_budget_ms=1000.0
    )
    d1 = engine.evaluate(safety_req)
    assert d1.recommended_solution == SolutionType.HYBRID_RAG_SFT
    assert "组合拳方案是最优解" in d1.rationale
    print("✅ 工业合规场景：RAG+SFT 组合拳路由测试通过！")

    # 2. 测试纯文档问答场景（知识频繁变动 + 文本回答即可）
    # 期望：RAG_ONLY
    doc_qa_req = ProjectRequirement(
        knowledge_frequency=KnowledgeUpdateFrequency.PERIODIC,
        format_rigidity=FormatRigidity.LOOSE_TEXT,
        traceability=TraceabilityRequirement.MANDATORY,
        labeled_samples_count=0,
        latency_budget_ms=1500.0
    )
    d2 = engine.evaluate(doc_qa_req)
    assert d2.recommended_solution == SolutionType.RAG_ONLY
    print("✅ 动态文档场景：纯 RAG 路由测试通过！")

    # 3. 测试特定工具调用分类器场景（知识固定 + 格式严格 JSON + 500条标注）
    # 期望：SFT_ONLY
    classifier_req = ProjectRequirement(
        knowledge_frequency=KnowledgeUpdateFrequency.STATIC,
        format_rigidity=FormatRigidity.STRICT_JSON,
        traceability=TraceabilityRequirement.NONE,
        labeled_samples_count=500,
        latency_budget_ms=300.0
    )
    d3 = engine.evaluate(classifier_req)
    assert d3.recommended_solution == SolutionType.SFT_ONLY
    print("✅ 静态格式场景：纯 SFT 路由测试通过！")

    # 4. 边界校验：非法参数拦截
    try:
        invalid_req = ProjectRequirement(
            knowledge_frequency=KnowledgeUpdateFrequency.STATIC,
            format_rigidity=FormatRigidity.LOOSE_TEXT,
            traceability=TraceabilityRequirement.NONE,
            labeled_samples_count=-5,
            latency_budget_ms=500.0
        )
        engine.evaluate(invalid_req)
        raise AssertionError("未拦截负数样本量异常")
    except ValueError as e:
        assert "标注样本数不能为负数" in str(e)
    print("✅ 非法输入边界防御测试通过！")

    print("✅ 5.1 RAG 与 SFT 业务边界选型决策路由自检全部通过！")


if __name__ == "__main__":
    self_test()
```

### 排障指南（常见故障、定位方法、修复策略）

| 常见故障 (Failure) | 定位方法 (Diagnosis) | 修复策略 (Mitigation) |
| --- | --- | --- |
| 试图用微调解决知识时效 | 客户抱怨上周新颁布的安全条例，微调后的模型根本不知道，或者编造条文。 | 立即纠偏架构路线：将知识库剥离微调范围，接入基于向量检索与 BM25 混合的 RAG 系统，通过索引更新解决时效。 |
| 试图用 Prompt 解决超复杂格式 | 复杂的 5 层嵌套 JSON 输出，Prompt 里写满了约束，但高并发下依然有 3% 的请求漏掉闭合括号。 | 收集 200~300 条真实高难格式样本进行轻量 LoRA 微调；或引入结构化输出库（如 Guidance / Outlines）在解码阶段用 Logit Processor 强制语法约束。 |
| 过度设计（Over-engineering） | 简单的事实查阅任务硬上了全套复杂微调，上线耗时 3 个月，模型一升级全部需要重训。 | 遵循奥卡姆剃刀原则：从 Prompt 优化出发，只有遇到明确无法逾越的性能/延迟/格式天花板时才引入微调。 |

### 工程 trick 与坑

- 先算算力账与数据账：SFT 的隐性成本极高，不仅在于几张 GPU 的租金，更在于持续维护清洗数百条高质量标注数据的工程人力。如果 RAG 加两句 Prompt 能做到 85 分，永远不要为了 88 分仓促上 SFT。

- 长尾格式微调的收益递减：如果基座模型本身遵循能力很强（如 Qwen2.5-7B/14B），通过两遍 Few-shot 往往就能解决格式问题；微调应专注于深度的领域习惯固化。

- 区分参数知识与非参数知识：参数知识是模型的逻辑推理框架，非参数知识是具体的制度数字与规程条目。前者用 SFT 锻造，后者交给 RAG 注入。

### 面试怎么讲（三段式：项目背景与选型理由、架构设计与核心机制、踩坑排障与量化收益）

**使用约定：**下面的项目情境和数字仅为虚构示例，不能直接当作本人经历或结果；只使用自己实际参与且有证据的内容。

面试官提问：“在你们的业务中，面对专业知识问答和特定格式需求，你是如何做 RAG 与微调（SFT）的权衡和技术选型的？”

回答范式：

- 背景与选型：“在工业特种作业合规审查项目中，团队最初对于‘是直接在千万级安全文献上微调一个大模型，还是搭一个 RAG 系统’存在很大分歧。我主导进行了技术边界分析：国家安全规范和企业内部施工规章平均每季度更新一次，且安监执法必须要求答复能够精确溯源到‘具体哪一部文件的哪一条款’。因此我坚定否决了纯微调方案，确立了以 RAG 为核心的知识挂载骨干。”

- 架构与机制：“同时，考虑到下游工单派发系统依赖严格的 JSON 数据结构，而原生基座模型在长上下文下直接输出自由文本容易产生解析错误，我们最终采纳了‘RAG 检索证据 + LoRA 轻量微调固化输出格式’的组合拳架构：用 RAG 提供最新条文与法律切片，用 300 条领域格式微调让模型稳定输出结构化三段式报告。”

- 踩坑与收益：“这套选型决策避免了盲目投入数十万算力微调参数知识的巨大沉没成本。系统上线后，规程更新从以往的‘重新微调耗时 3 天’缩减为‘重新向量化入库仅需 5 分钟’，同时下游结构化数据解析成功率从 82.4% 跃升至 99.8%，成为部门评选的优秀工程实践标杆。”

### 费曼自述与闪卡

费曼自述（3 分钟白板口述框架）：
“做大模型落地，最忌讳拿着锤子找钉子。很多人一听到‘垂直领域大模型’，就以为一定要去微调模型。其实大模型就像一个‘超级大学生’，RAG 相当于给他发一本最新的《专业参考书》，他一边查书一边考试（开卷考试），错不了而且随时能翻最新版；而微调（SFT）相当于天天让他抄写特定的卷子格式，让他闭着眼睛都能写出标准公文格式。知识常变、要查出处的，坚决用 RAG；格式复杂、要改变说话习惯的，才考虑 SFT。两者结合，才是工业落地的杀手锏。”

备考闪卡 Q&A：

- Q：什么是知识的时效性，为什么 SFT 无法解决时效性？
A： 现实业务数据持续变化。SFT 将知识固化进静态模型参数，更新需重新收集数据与训练，滞后且易产生虚构幻觉。

- Q：RAG+SFT 组合拳架构中两者的具体分工是什么？
A： RAG 负责供给动态、权威、可溯源的外部上下文证据；SFT 负责固化领域推理模式与高严苛度输出格式。
