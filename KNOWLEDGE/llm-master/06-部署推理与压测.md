# 第六章：部署、推理与压测工程化

> 本章优先级：🔥 部署选型、延迟与压测；⭐ KV Cache、量化的原理和取舍。来源：[仓库第六章](逐篇精读/README.md)。

## 6.1 云 API、托管推理、自部署【🔥】

**一句话：** 按数据权限、成本、延迟、并发、运维能力和模型可控性选部署方式，没有通用最优解。

**例子：** 公开演示项目可先接云 API，快速验证业务；公司图片若不能上传外部服务，需要内网或合规托管方案。自己有 GPU 不代表自部署一定更便宜，还要算显存、闲置率、维护和失败恢复。

**费曼自述：** “先列业务约束，再选模型在哪里跑。部署方式是为了满足约束，不是为了炫技术栈。”

**概念闪卡：** Q：选云 API 最先核对什么？A：数据可否外传、价格/配额、延迟和能力。Q：自部署额外要负责什么？A：容量、模型加载、监控、升级、故障处理和安全。

来源：[部署方式](逐篇精读/app/deployment_options.md)。

## 6.2 KV Cache、PagedAttention 与 Prefix Cache【⭐】

**一句话：** 自回归生成时，缓存已处理 token 的 Key/Value，避免每次生成新 token 都把前文完整重算；缓存需要显存。PagedAttention 等方法改善缓存内存管理，Prefix Cache 在可复用前缀上减少重复计算。

**例子：** 100 个并发用户，每人都有长历史和检索资料。即使模型权重已装入 GPU，100 份会话的 KV Cache 仍会占显存；上下文越长、并发越多，压力越大。把所有 RAG 文档都假定可缓存是不对的，因为不同用户检索到的段落可能不一样。

**费曼自述：** “模型生成时要记住前面 token 算过的注意力信息。为了省重复计算，会用显存存它；并发和长上下文让这笔显存账变大。”

**概念闪卡：** Q：KV Cache 是训练参数吗？A：不是，是推理期间随请求产生的中间状态。Q：Prefix Cache 什么时候有效？A：多请求共享符合实现规则的相同前缀时。

来源：[KV Cache 与 PagedAttention](逐篇精读/app/kv_cache_paged_attention.md)。

## 6.3 量化的对象与代价【⭐】

**一句话：** 量化用较低精度表示权重、激活或 KV Cache，以减少存储/带宽占用；速度和精度变化依硬件、实现及任务而异。

**例子：** 4-bit 权重量化可能让模型能装进一张 GPU，但图像细节任务的回答质量是否受损要在自己测试集上测。权重变小，也不代表 KV Cache、视觉 token 和中间激活都同步变小。

**费曼自述：** “量化是在数值表示上省资源；要分别看压了哪里、系统能不能真正跑快、任务质量有没有损失。”

**概念闪卡：** Q：权重 4-bit 就等于整个推理只用 4-bit 吗？A：不是，激活/KV/计算可能另用精度。Q：选择量化版本至少测什么？A：任务质量、显存、吞吐、延迟。

来源：[量化](逐篇精读/app/model_quantization.md)。

## 6.4 服务压测与 Goodput【🔥】

**一句话：** 压测要在真实输入长度、输出长度与并发分布下看用户体验和稳定性，不能只报“每秒 token 最多”。

| 指标 | 想回答的问题 |
|---|---|
TTFT | 用户多久看到第一个输出 token？ |
TPOT / 输出速率 | 后续 token 出得多快？ |
P95/P99 延迟 | 慢的请求有多慢？ |
吞吐 | 单位时间处理多少请求或 token？ |
Goodput | 满足业务延迟目标的有效请求有多少？ |
错误率 | 超时、OOM、无效结果多不多？ |

**例子：** 平均 2 秒、P95 15 秒的问答服务，用户仍可能频繁抱怨慢。提升并发也许提高总吞吐，但让 TTFT 变差；要按目标 SLO 选负载点。含图片的 VLM 输入还要测不同分辨率、图片数量和生成长度。

**费曼自述：** “压测不是把 GPU 跑满，而是找出业务能接受的并发、延迟和失败率。”

**概念闪卡：** Q：为什么平均延迟不足以判断体验？A：长尾慢请求会被平均值掩盖。Q：Goodput 比峰值吞吐多了什么约束？A：请求必须在服务目标内成功完成。

来源：[压测](逐篇精读/app/stress_testing.md)。
