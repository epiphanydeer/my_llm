# 第三章：RAG 检索增强——从原理到优化

本章整体：🔥 必会。已有完整的 [RAG 深入笔记](03-RAG检索增强/README.md)，覆盖仓库 [RAG 专题](https://github.com/youngyangyang04/llm-master/blob/main/docs/topics/rag.md) 的 10 篇主干和 4 篇面试深化。本页按原专栏的学习顺序提供快速复习、例子与闪卡；难点看深入版。你的工业安全图片＋处罚条款项目会直接用到这些能力。

贯穿例子：知识库包含《差旅规定 V2》“飞机经济舱须提前审批”。用户问：“出差坐飞机能报吗？”我们要给出正确结论和可打开的条款来源。

## 3.1 为什么有大模型还需要 RAG【🔥】

一句话： 模型未必知道私有或新近修订的事实；RAG 在回答前检索外部证据，支持更新和引用，但不保证零幻觉。

例子： V1 规定“飞机不可报”，V2 改为“经济舱审批后可报”。直接问模型可能引用旧经验；RAG 必须找到 V2，并判断生效日期。若索引仍保留旧版而没有版本过滤，RAG 也会答错。

费曼自述： “RAG 像先查手册再回答。它把资料交给模型，但查错页或读错条款仍会出错。”

概念闪卡： Q：RAG 主要弥补什么？A：外部、私有和更新频繁的知识，以及来源追溯。Q：它能消除幻觉吗？A：不能，只能通过正确证据与核验降低错误。

来源：[为什么需要 RAG](原仓库Markdown/docs/llm/app/why_rag.md)。

## 3.2 离线建库与在线问答【🔥】

一句话： 离线把文档处理成带来源、版本和权限的可检索块；在线把问题变成检索请求，选证据，再生成带引用的答案。

```text
离线：文档 → 解析清洗 → 切片 → 元数据 → Embedding/索引
在线：问题 → 过滤与召回 → 可选重排 → 证据上下文 → 生成与引用检查
```

例子： “飞机经济舱须审批”这个块需要同时保存政策名、V2、生效时间、第 3 条与访问权限。用户提问时先确保他有权限，再检索、回答。

费曼自述： “一边负责把知识准备好，另一边负责在提问时找对并用对。来源和版本贯穿两边。”

概念闪卡： Q：元数据有什么用？A：版本/日期/权限过滤与引用。Q：只向量化整篇 PDF 可行吗？A：可做基线，但定位具体条款通常粒度太粗。

来源：[完整链路](原仓库Markdown/docs/llm/app/chain_of_rag.md)。

## 3.3 切片、Embedding、向量索引【🔥】

一句话： 切片决定检索单位；Embedding 把文本编码成向量；索引让大量向量可快速搜索。三者解决不同问题。

例子： 切片只剩“需审批”会丢掉“飞机经济舱”条件；切整个制度又有太多噪声。结构切分可保留完整条款。向量检索能把“坐飞机能报吗”与“航空差旅报销”联系起来，关键词检索则更适合精确条款号。换 Embedding 模型时要核对向量空间兼容性，通常重建文档索引。向量库选型看规模、过滤、更新和延迟，不按名称定优劣。

费曼自述： “先决定一个知识块应该包含什么，再把它变成可比较的数字，最后用索引快速找相近内容。搜得快不代表搜得对。”

概念闪卡： Q：Chunk 太小会怎样？A：语义不完整。Q：ANN 是什么？A：近似最近邻索引，用一定的召回代价换检索效率。Q：向量库会修复差的 Embedding 吗？A：不会。

来源：[切片](原仓库Markdown/docs/llm/app/how_to_chunking.md) · [Embedding](原仓库Markdown/docs/llm/app/embedding.md) · [向量数据库](原仓库Markdown/docs/llm/app/vector_database.md)。

## 3.4 混合检索、Rerank 与 Context【🔥】

一句话： 向量与关键词检索互补；Rerank 给已召回的候选重新排序；Context 是最后交给生成模型的证据。

例子： 问“处罚办法第 17 条怎么规定”，BM25 易命中“第 17 条”；问“没戴安全帽会怎样”，向量检索有助于找到“未按规定佩戴头部防护用品”。两路合并后，重排把最能回答问题的条款放前面。若第 17 条根本没入候选，重排无法补救。

费曼自述： “混合检索先尽量找到，重排再把真正有用的放前；最后只把少量高质量证据交给模型。”

概念闪卡： Q：BM25 擅长什么？A：精确词和编号。Q：Rerank 救不了哪类错误？A：候选池里根本没有正确证据。Q：Top-K 越大越好？A：不是，还会带来噪声、token 与延迟。

来源：[优化策略](原仓库Markdown/docs/llm/app/rag_optimization.md)。

## 3.5 答不准时怎么排障【🔥】

一句话： 找到正确证据第一次“消失或被误用”的环节，再改那个环节。

```text
原文里有吗？
→ 解析文本里有吗？
→ 检索候选里有吗？
→ 最终 Context 里有吗？
→ 回答是否正确引用了它？
```

例子： 正确处罚条款已在 Top-20，却被截断在最终 Top-5 之外，应查融合和排序；正确条款已进 Context，回答却引用旧版，应查版本、冲突和生成约束。

费曼自述： “先查证据走到哪一步，不是一错就换大模型。”

概念闪卡： Q：检索不到时先看什么？A：原文解析、索引覆盖、切片、查询与过滤。Q：检索到却答错看什么？A：最终上下文、版本冲突、Prompt、引用和模型理解。

来源：[常见问题排查](原仓库Markdown/docs/llm/app/rag_problems.md)。

## 3.6 长文档、代码与多跳问题【⭐】

一句话： 长文档要保留标题和父子关系；代码要保留函数、路径和版本；跨文档问题需要多份证据而不只是相似度最高的一段。

例子： 问“哪个函数检查 token 过期？”可按函数边界索引并保存路径/commit；问“制度 V1 到 V2 审批流程变了什么？”要先找两个版本，再对比，而不是只拿最新一块。

费曼自述： “资料有结构，就要让检索保留结构；问题要比较多份资料，就要把证据集合找齐。”

概念闪卡： Q：父子块是什么？A：短块用于匹配，返回较完整的父段落供回答。Q：代码为什么不宜只按固定字数切？A：可能把函数签名、实现和注释分开。

来源：[长文档与代码检索](原仓库Markdown/docs/llm/app/long_document_code_retrieval.md)。

## 3.7 RAG 评估【🔥】

一句话： 用固定的题目和标注证据分别评测检索、生成、引用、拒答，再看延迟与成本。

例子： 一道题有 3 个相关条款，Top-5 找到 2 个，则 Recall@5 = 2/3；若至少找到了一个，Hit@5 = 1。回答引用了错误条款，即使语言流畅也不合格。评估题要含同义问法、精确编号、无答案及新旧版冲突。

费曼自述： “系统最终答对要建立在证据找对和证据用对之上。我用固定测试集把这两部分分别测量。”

概念闪卡： Q：Recall@K 与 Hit@K 区别？A：前者看相关证据找回多少，后者看至少命中一条的题占比。Q：RAGAS 或 LLM 裁判能代替人工吗？A：不能完全代替，关键样本仍需核验。

来源：[评估](原仓库Markdown/docs/llm/app/rag_evaluation.md)。

## 3.8 Agentic RAG 与面试回答【⭐】

一句话： 复杂问题可让系统动态决定查哪个源、是否再查一轮；面试要讲项目中的决策和指标，不能只念名词。

例子： 问“去年和今年的处罚标准差异”，Agentic RAG 可先分别找两版，再判断证据够不够。若只是“第 17 条是什么”，固定检索更简单。面试可按“业务问题 → 基线 → 错误 → 改动 → 评估 → 代价”回答。

费曼自述： “我先让简单链路可靠工作；只有固定检索解决不了的多步问题，才增加动态检索。”

概念闪卡： Q：Agentic RAG 的代价？A：多次模型/检索调用、更多延迟与不稳定路径。Q：项目面试为什么必须报基线？A：没有基线无法证明改动有效。

来源：[Agentic RAG](原仓库Markdown/docs/llm/intro/agentic_rag.md) · [面试框架](原仓库Markdown/docs/llm/app/rag_interview_framework.md)。更多面试问答见[深入版第 11 节](03-RAG检索增强/3.11-RAG项目面试.md)。
