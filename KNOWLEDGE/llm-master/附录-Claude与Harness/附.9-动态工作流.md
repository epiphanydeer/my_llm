## 附.9 动态工作流：依赖、并行与结果汇总【◻ 按需】

〔补充自原仓库镜像〕〔本次新补，参考当前面试趋势〕

目标 + 例子。 复杂任务可拆成阅读、测试、文档与汇总；先明确依赖，再判断哪些任务具备并行条件，不能只看任务名称不同就同时修改共享文件。

### 先搞清楚：默认那套 harness，是为「写代码」定制的

harness 是什么？就是控制 Claude **读什么、什么时候动手、产出怎么验证**的那层编排。Claude Code 自带的 harness 打磨得很好，但有个前提——它是冲着**写代码**这件事调出来的。

可你实际让 Claude Code 干的活，远不止写代码：深度调研、安全审计、给一队 Agent 分工、代码评审……这些任务的「最佳跑法」和写代码不一样。过去要把它们做到极致，你得**自己在 Claude Code 之上手搓一套 harness**。

动态工作流的意思就一句话：**这套针对任务的 harness，不用你手搓了，Claude 自己现场写。**

### 概念与数据流

| 五要素 | 任务依赖分阶段 |
| --- | --- |
| 输入 | 任务与前置任务的有向依赖关系。 |
| 做什么 | 检查缺失与环，按拓扑依赖计算每一轮可开始的任务。 |
| 输出 | 分阶段任务集合；本例不真正执行任务。 |
| 哪里出错 | 循环依赖、漏掉共享资源冲突、错误把失败任务标为完成。 |
| 参数影响 | 粒度、依赖和共享资源决定潜在并行度及协调开销。 |

依赖满足只是并行的必要条件之一，不保证文件写入、外部资源或权限互不冲突。真实调度还需要任务状态、失败处理、超时和结果核验；Agent 工具循环与 DAG 失败传播分别见第 4.4 和 4.9 节。

### 面试追问

【⭐ 理解】什么时候适合拆成并行任务？ 结论：任务相互独立且交付物可验证时。还要检查共享文件、资源和依赖，再权衡沟通与合并成本。

【🔥 必会】并行任务结果冲突怎么排查？ 结论：先检查共享状态与任务边界。核对每项修改和依赖，必要时改为顺序执行并重新验证。

【◻ 按需】图无环就一定能安全并行吗？ 结论：不能。无环只说明依赖关系可排序，不覆盖资源冲突和权限。

### 故障模式与排障

- 计划无法推进：检查缺失节点和循环依赖；修正依赖后重新排序。

- 并行修改互相覆盖：检查共享文件和操作顺序；隔离修改或改为顺序执行。

- 失败任务被视为完成：真实执行器需记录实际状态，失败时阻止依赖任务并保留原因。

### 工程 trick 与坑

- 本例只计算阶段，调用 done 是算法演示，不代表任务真实执行成功。

- 程序不启动子代理，也不判断权限、共享资源或结果质量。

- 完整任务执行和失败传播示例见第 4.9 节。

### Toy code：依赖分阶段

运行前提：Python 3.10+，标准库；虚构任务不执行任何操作。

```python
"""验证虚构任务依赖并计算可并行阶段；不启动子代理。"""
from graphlib import CycleError, TopologicalSorter


def stages(graph: dict[str, tuple[str, ...]]) -> tuple[tuple[str, ...], ...]:
    """输入节点到前置节点的映射，返回每轮可执行节点。"""
    if not graph:
        raise ValueError('任务图不能为空')
    for node, dependencies in graph.items():
        if not isinstance(node, str) or not node.strip():
            raise ValueError('任务名必须非空')
        if any(not isinstance(dep, str) or not dep.strip() for dep in dependencies):
            raise ValueError('依赖名必须非空')
        if len(set(dependencies)) != len(dependencies) or any(dep not in graph for dep in dependencies):
            raise ValueError('依赖不能重复或引用不存在的任务')
    sorter = TopologicalSorter(graph)
    try:
        sorter.prepare()
    except CycleError as exc:
        raise ValueError('任务依赖存在环') from exc
    result: list[tuple[str, ...]] = []
    while sorter.is_active():
        ready = tuple(sorted(sorter.get_ready()))
        if not ready:
            raise RuntimeError('存在无法继续的任务')
        result.append(ready)
        sorter.done(*ready)
    assert sum(map(len, result)) == len(graph)
    return tuple(result)


def main() -> None:
    """验证依赖层次、独立任务、缺失节点和循环。"""
    graph = {'阅读': (), '测试': ('阅读',), '文档': ('阅读',), '汇总': ('测试', '文档')}
    result = stages(graph)
    assert result == (('阅读',), ('文档', '测试'), ('汇总',))
    invalid = ({}, {'a': ('missing',)}, {'a': ('b',), 'b': ('a',)})
    for item in invalid:
        try:
            stages(item)
        except ValueError:
            pass
        else:
            raise AssertionError('空图、缺失依赖或循环必须拒绝')
    print('虚构依赖图分阶段自检通过:', result)
    print('本程序不执行任务、不创建子代理，也不判断并行是否安全。')


if __name__ == '__main__':
    main()

```

逐段理解。 stages 检查依赖存在与无环，再使用 TopologicalSorter 获取每轮 ready 任务；自检覆盖缺失和循环。

### 这段代码怎么在面试里讲

- 不变量：所有依赖节点存在且无环，每个任务恰出现一次。

- 关键过程：逐轮取当前无未完成前置依赖的任务，构造阶段列表。

- 边界与坑：这是静态规划，不启动任务或处理实际失败；无环不保证共享资源操作安全。

### 本节收尾：费曼自述与闪卡

费曼自述： 任务依赖可以用 DAG 表示，拓扑排序找出可开始的任务；真实并行还要考虑资源、权限和失败。

- 问：无环就能安全并行吗？答：不能，还要检查共享资源和副作用。

- 问：本例是否启动了子代理？答：没有，只计算虚构阶段。

- 问：依赖有环怎么办？答：拒绝计划并修正依赖。

- 问：真实上游失败后下游应怎样？答：按策略阻止或处理，不能假装成功。
