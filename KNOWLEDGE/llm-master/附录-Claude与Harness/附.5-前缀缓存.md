## 附.5 Prompt Cache：前缀、命中与版本边界【◻ 按需】

〔补充自原仓库镜像〕〔本次新补，参考当前面试趋势〕

目标 + 例子。 重复请求可能共享稳定前缀；比较消息变更位置可以帮助定位缓存命中变化，但实际命中由供应商的缓存规则、token 和有效期决定。

### 一、先搞清楚：Prompt Cache 缓存的不是答案

很多录友一听缓存，第一反应是：

是不是用户问过的问题，下次直接把答案拿出来？

不是。

Prompt Cache 缓存的不是模型回答。

它缓存的是模型处理输入上下文时的中间计算。

你可以这么理解。

Claude Code 每一轮跟模型交互，并不是只把你刚输入的那句话发过去。

它要把一整套东西重新发给模型：

- 系统提示词
- 工具定义
- CLAUDE.md 里的项目规则
- 当前项目上下文
- 前面所有对话消息
- 工具调用结果
- 你这一轮的新输入

模型本身并不会在两次 API 请求之间“记住”上一次聊到哪了。

所以每一轮请求都要带上完整上下文。

如果没有缓存，那长会话越聊越贵，越聊越慢。

这也是为什么很多 Agent demo 一开始看起来很丝滑，但跑一会儿就开始变慢。

它不是突然变笨了。

是上下文越来越长，每次都在重算。

Prompt Cache 解决的就是这个问题：

**前面已经算过、下一轮又完全一样的部分，就不要再算一遍。**

但这里有一个关键限制。

它靠的是前缀匹配。

不是“这段内容大概一样”。

也不是“这个文件之前读过”。

而是从请求开头开始，连续一段内容必须一致，才能命中缓存。

![Prompt Cache 命中依赖请求前缀连续一致](https://file1.kamacoder.com/i/web/20260601095801_claude_prompt_cache_01_prefix_layers_compressed.png?v=20261005)

所以 Claude Code 的请求组织方式很讲究：

第一层，静态系统提示词和工具定义。

这部分最好全局稳定，不同项目都能复用。

第二层，CLAUDE.md 和项目上下文。

这部分在同一个项目里稳定。

第三层，会话上下文。

这部分在同一个会话里稳定。

第四层，对话消息和工具结果。

这部分会随着聊天增长。

第五层，本轮新增输入。

每一轮只让最后一点点内容变化。

这样前面大部分内容都能命中缓存。

**静态内容放前面，动态内容放后面。**

这是做 Agent 产品时最朴素、也最容易被忽略的缓存原则。

### 概念与数据流

| 五要素 | 消息前缀比较 |
| --- | --- |
| 输入 | 两组有序消息，每条包含角色与文本。 |
| 做什么 | 从头逐条比较完整消息，定位首个不同项。 |
| 输出 | 相同完整消息数和差异类型。 |
| 哪里出错 | 前缀包含动态字段、模型或模板变化、误把消息数当缓存 token。 |
| 参数影响 | 提示内容顺序、模型版本、缓存规则与有效期可能影响真实命中。 |

Prompt cache 通常用于复用符合服务规则的输入计算，不等于缓存最终回答。不同服务的缓存单位、有效期、写入与计费规则不同；应查目标版本文档并查看实际 usage。本例只比较完整消息，不实现 token 化或真实缓存。

### 面试追问

【⭐ 理解】Prompt cache 和答案缓存有什么不同？ 结论：前者通常复用输入处理，后者复用结果。具体机制由服务实现；不能因为命中输入缓存就认为输出必然相同。

【🔥 必会】缓存命中下降怎么定位？ 结论：核对实际请求前缀和服务规则。检查模型、模板、动态字段、工具定义、有效期与 usage，再对照供应商文档。

【◻ 按需】两次消息完全相同是否保证命中？ 结论：不保证。缓存有效期、服务配置和其他条件也会影响结果。

### 故障模式与排障

- 共同前缀被动态信息打断：比较实际序列化请求，确认变动位置；在不改变任务语义前提下组织稳定前缀。

- 估算节省与账单不符：核对实际缓存读写字段、计价规则和请求次数，不用字符或消息数量代替 usage。

- 缓存结果与预期不一致：核对模型、版本、有效期和服务状态；必要时做可控对照实验。

### 工程 trick 与坑

- 本例只比较完整消息，不处理消息内部部分前缀、token、工具 schema 或实际缓存键。

- 前缀一致不保证服务端命中；不同产品的缓存规则和价格可能变化。

- 消息可能含敏感数据，实际排障应按业务限制日志内容和访问范围。

### Toy code：比较完整消息前缀

运行前提：Python 3.10+，标准库；不调用模型或缓存服务。

```python
"""比较两组虚构消息的共同前缀；不模拟服务商缓存命中。"""
from dataclasses import dataclass


@dataclass(frozen=True)
class Message:
    """消息角色与文本内容。"""
    role: str
    content: str


def common_prefix(left: list[Message], right: list[Message]) -> tuple[int, str]:
    """返回相同完整消息数量与首个差异类型。"""
    if not left or not right:
        raise ValueError('两组消息均不能为空')
    allowed = {'system', 'user', 'assistant', 'tool'}
    for msg in left + right:
        if msg.role not in allowed or not isinstance(msg.content, str) or not msg.content.strip():
            raise ValueError('消息角色或内容非法')
    count = 0
    for a, b in zip(left, right):
        if a != b:
            reason = 'role' if a.role != b.role else 'content'
            return count, reason
        count += 1
    reason = 'length' if len(left) != len(right) else 'same'
    assert count <= min(len(left), len(right))
    return count, reason


def main() -> None:
    """检查内容差异、角色差异、长度差异和空消息。"""
    original = [Message('system', '固定规则'), Message('user', '问题一')]
    changed = [Message('system', '固定规则'), Message('user', '问题二')]
    assert common_prefix(original, changed) == (1, 'content')
    assert common_prefix(original, original[:1]) == (1, 'length')
    assert common_prefix(original, original) == (2, 'same')
    assert common_prefix(original, [Message('user', '固定规则')]) == (0, 'role')
    for invalid in ([], [Message('unknown', 'x')], [Message('user', '')]):
        try:
            common_prefix(original, invalid)
        except ValueError:
            pass
        else:
            raise AssertionError('空消息或非法角色必须拒绝')
    print('虚构消息前缀对比自检通过。')
    print('共同消息数量不等于任何供应商的实际缓存命中 token。')


if __name__ == '__main__':
    main()

```

逐段理解。 Message 表示角色与内容；common_prefix 逐条比较并指出首个差异类别；自检覆盖内容、角色、长度和非法输入。

### 这段代码怎么在面试里讲

- 不变量：两组消息非空，角色和内容有效，前缀长度不超过较短列表。

- 关键过程：从头比较完整消息，遇到第一处差异即停止。

- 边界与坑：相同消息数不是实际缓存 token，程序不检查服务端条件或消息内部分前缀。

### 本节收尾：费曼自述与闪卡

费曼自述： 输入前缀变化可能影响缓存复用，但真实命中和计费由服务规则决定；消息对比只能辅助排障。

- 问：Prompt cache 等于答案缓存吗？答：不是，通常复用的是输入处理。

- 问：消息完全相同一定命中吗？答：不一定，还需满足服务规则和有效期。

- 问：本例计算了真实缓存 token 吗？答：没有，只比较完整消息。

- 问：如何核对真实节省？答：查看目标服务 usage、价格和账单。
