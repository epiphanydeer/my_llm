## 11.1 新模型发布：从宣称到任务验证【◻ 按需】

### 为什么要关注这个问题

**一句话：** 对新模型只问与你任务相关的四件事：输入输出能力、独立评测、运行约束、可复现程度。

〔本次新补，参考当前面试趋势〕

目标 + 例子。 看到 VLM 发布新闻后，先核对具体版本和官方资料，再用自己的小目标、遮挡等样本评测；单张成功截图不能证明业务效果。

### 概念与数据流

| 五要素 | 新模型记录 |
| --- | --- |
| 输入 | 版本、发布时间、来源引用和目标任务测试记录。 |
| 做什么 | 检查字段和时间是否自洽，区分待测试与已有测试。 |
| 输出 | 下一步应准备测试还是分析已有测试的提示。 |
| 哪里出错 | 引用过期、版本混淆、仅凭厂商案例判断、样本量不足。 |
| 参数影响 | 测试集分布、评测标准和样本量决定结论范围。 |

官方发布说明是能力和接口的起点，不等于独立业务验证；同条件选型与分桶评测参见第 10.7 节。新闻标题和日期仅作线索，不应当作当前模型或价格事实。

### 面试追问

【⭐ 理解】怎样判断新模型值不值得试？ 结论：先匹配任务和硬约束。核对官方版本、输入输出及部署，再用目标测试集比较质量、延迟和成本。

【⭐ 理解】官方案例好但实际效果差怎么查？ 结论：比较数据和评测条件。检查图片类型、预处理、样本难度和成功标准，再分析失败切片。

【◻ 按需】一条测试记录能证明模型可靠？ 结论：不能。要检查样本量、覆盖、标注和不确定性。

### 故障模式与排障

- 型号和接口对不上：核对版本标识与官方文档；重新测试目标部署配置。

- 案例无法复现：检查输入、提示、模型和运行时间；保存允许公开的实验记录。

- 数据过少得出过强结论：报告样本量和失败样例，补充独立任务集。

### 工程 trick 与坑

- 本例不会联网或核验所谓官方来源是否真实；所有记录均为虚构。

- “已有测试”只表示记录中样本数大于零，不代表测试质量合格。

- 模型发布、价格和可用性可能变化，应按实际使用时间查官方资料。

### Toy code：模型动态记录检查

运行前提：Python 3.10+，标准库；无网络或真实模型。

```python
"""检查虚构新模型记录的资料与目标任务测试状态。"""
from dataclasses import dataclass
from datetime import date


@dataclass(frozen=True)
class ModelRecord:
    """模型版本、发布时间、官方资料和目标数据测试状态。"""
    version: str
    released: date
    official_source: str
    target_tested: bool
    test_count: int


def assess(record: ModelRecord, as_of: date) -> dict[str, object]:
    """校验记录，区分已有目标测试与仍需测试。"""
    if not record.version.strip() or not record.official_source.strip():
        raise ValueError('版本和官方资料引用不能为空')
    if type(record.released) is not date or type(as_of) is not date or record.released > as_of:
        raise ValueError('发布日期或检查日期非法')
    if not isinstance(record.target_tested, bool) or isinstance(record.test_count, bool) or not isinstance(record.test_count, int) or record.test_count < 0:
        raise ValueError('测试状态或样本数非法')
    if record.target_tested != (record.test_count > 0):
        raise ValueError('测试状态与样本数不一致')
    result: dict[str, object] = {'version': record.version, 'as_of': as_of.isoformat(),
                                 'next_step': '分析测试质量' if record.target_tested else '准备目标数据评测',
                                 'test_count': record.test_count}
    assert result['test_count'] == record.test_count
    return result


def main() -> None:
    """验证未知测试、已有测试、未来日期和矛盾字段。"""
    today = date(2026, 6, 1)
    record = ModelRecord('mock-v1', date(2026, 5, 1), '虚构官方来源', False, 0)
    assert assess(record, today)['next_step'] == '准备目标数据评测'
    tested = ModelRecord('mock-v2', date(2026, 5, 1), '虚构官方来源', True, 2)
    assert assess(tested, today)['test_count'] == 2
    for bad in (ModelRecord('x', date(2027, 1, 1), 'source', False, 0),
                ModelRecord('x', date(2026, 1, 1), 'source', True, 0)):
        try:
            assess(bad, today)
        except ValueError:
            pass
        else:
            raise AssertionError('未来发布日期或矛盾记录必须拒绝')
    print('虚构模型动态记录自检通过:', assess(record, today))
    print('此程序不核实来源真实性或模型效果。')


if __name__ == '__main__':
    main()

```

逐段理解。 ModelRecord 保存版本和测试状态；assess 检查日期与状态是否一致；自检覆盖未来日期、未测试和矛盾记录。

### 这段代码怎么在面试里讲

- 不变量：版本和来源引用非空，发布日期不晚于检查日，测试状态与样本数一致。

- 关键过程：先检查记录自洽，再给出准备测试或分析测试的下一步。

- 边界与坑：程序不核验来源、样本质量或模型效果；已有少量测试不能证明可靠。

### 本节收尾：费曼自述与闪卡

费曼自述： 发布新闻提供候选线索；真实选择要核对版本和官方资料，再在目标数据上评测并分析失败。

- 问：一张成功截图能证明整体效果吗？答：不能，需要代表性测试集。

- 问：代码会验证来源真实性吗？答：不会，只检查记录是否自洽。

- 问：测试过两条样本就足够吗？答：不能据此证明稳定效果。

- 问：模型版本变化后应做什么？答：核对接口和配置，并重新回归。

## 11.2 价格与缓存新闻：核对时间和计量口径【◻ 按需】

### 为什么要关注这个问题

**一句话：** 记住 token 与请求成本的算法，不背某天的单价。核对官方当前定价、缓存规则、长上下文档位及配额。

〔本次新补，参考当前面试趋势〕

目标 + 例子。 新闻称模型降价时，不背旧数字；核对目标服务当前官方价格、币种、输入/输出/缓存项目和适用条件，再按实际流量估算。

### 概念与数据流

| 五要素 | 价格快照检查 |
| --- | --- |
| 输入 | 模型、计价类别、币种、单价、核对日期及允许的快照年龄。 |
| 做什么 | 检查单位、类别和日期是否可比；过期快照标记需重新核对。 |
| 输出 | 可比或待核对状态，以及同类别同币种的单价差。 |
| 哪里出错 | 价格过期、输入输出混比、币种不同、遗漏缓存写入或额外费用。 |
| 参数影响 | 快照有效期、价格档位、币种和请求分布影响估算。 |

价格随服务和时间变化；本例的最大快照年龄只是人为检查规则，不代表价格在期限内必然未变。系统总成本还涉及重试、检索、图像、固定资源和运维，计算示例见 1.7 和 6.1。

### 面试追问

【⭐ 理解】新闻说降价，是否意味着系统成本一定下降？ 结论：不一定。要按实际输入、输出、缓存和其他服务用量重新计算，并考虑运行配置变化。

【⭐ 理解】成本表与账单不一致怎么查？ 结论：核对日期、单位与所有计费项。检查币种、缓存、重试和附加费用，再按账单逐项对照。

【◻ 按需】快照在设定天数内就一定有效吗？ 结论：不保证。它只提示是否需要重新检查，实际变更以官方信息为准。

### 故障模式与排障

- 把输入和输出价格混比：记录计价类别与单位，只在同口径下比较。

- 使用过期价格：保存核对日期并回查官方价格，更新成本模型。

- 单价下降但总成本上升：检查请求量、输出长度、重试和其他组件费用。

### 工程 trick 与坑

- 所有单价和日期为虚构；程序不联网，不能验证实际报价。

- 同币种同类别不代表服务完全可比，还需核对档位、缓存规则及税费。

- 价格差不是总成本差，真实成本按完整流量和合同计算。

### Toy code：虚构价格快照校验

运行前提：Python 3.10+，标准库，无真实账单。

```python
"""验证虚构价格快照的日期与计量单位；不查询实际报价。"""
from dataclasses import dataclass
from datetime import date
from decimal import Decimal


@dataclass(frozen=True)
class Quote:
    """模型、计价类别、币种、每百万 token 单价和核对日期。"""
    model: str
    category: str
    currency: str
    rate: Decimal
    checked_on: date


def compare(a: Quote, b: Quote, as_of: date, max_age_days: int) -> dict[str, object]:
    """仅在币种和计价类别相同时对比；过期快照标记待核对。"""
    if type(as_of) is not date or isinstance(max_age_days, bool) or not isinstance(max_age_days, int) or max_age_days < 0:
        raise ValueError('检查日期或最大间隔非法')
    for quote in (a, b):
        if not quote.model.strip() or quote.category not in {'input', 'output', 'cached_input'}:
            raise ValueError('模型或计价类别非法')
        if quote.currency not in {'CNY', 'USD'} or not isinstance(quote.rate, Decimal) or not quote.rate.is_finite() or quote.rate < 0:
            raise ValueError('币种或单价非法')
        if type(quote.checked_on) is not date or quote.checked_on > as_of:
            raise ValueError('核对日期不能晚于比较日')
    if a.category != b.category or a.currency != b.currency:
        raise ValueError('币种和计价类别必须一致')
    stale = any((as_of - q.checked_on).days > max_age_days for q in (a, b))
    return {'status': 'recheck' if stale else 'comparable',
            'rate_difference': None if stale else b.rate - a.rate}


def main() -> None:
    """检查可比、过期、币种不符与未来日期。"""
    today = date(2026, 6, 1)
    a = Quote('A', 'input', 'USD', Decimal('1'), date(2026, 5, 31))
    b = Quote('B', 'input', 'USD', Decimal('1.5'), date(2026, 5, 30))
    assert compare(a, b, today, 3)['rate_difference'] == Decimal('0.5')
    assert compare(a, b, today, 0)['status'] == 'recheck'
    invalid = [Quote('B', 'input', 'CNY', Decimal('1'), today),
               Quote('B', 'input', 'USD', Decimal('1'), date(2026, 6, 2))]
    for item in invalid:
        try:
            compare(a, item, today, 3)
        except ValueError:
            pass
        else:
            raise AssertionError('币种不符或未来快照必须拒绝')
    print('虚构价格快照比较自检通过；没有查询真实报价。')


if __name__ == '__main__':
    main()

```

逐段理解。 Quote 保存价格口径与日期；compare 校验可比性并标记过期；自检覆盖价格差、币种不符和未来日期。

### 这段代码怎么在面试里讲

- 不变量：单价为非负有限 Decimal，比较的类别和币种一致，核对日期不晚于比较日。

- 关键过程：检查快照年龄，过期时要求复核，否则计算同口径单价差。

- 边界与坑：日期阈值不保证报价未变；程序未检查实际条款和完整系统成本。

### 本节收尾：费曼自述与闪卡

费曼自述： 价格要带时间、单位和计费类别；新闻数字只提供线索，实际成本要按当前规则与用量核算。

- 问：示例价格是真实报价吗？答：不是，全部虚构。

- 问：输入和输出单价能直接对比吗？答：不能，需要相同计价类别。

- 问：快照没过期就一定准确吗？答：不能保证，仍需核对官方资料。

- 问：模型单价降低是否必然降低总成本？答：不一定，还要看完整用量和其他费用。

## 11.3 Agent 与工具新闻：区分宣称和验证【◻ 按需】

### 为什么要关注这个问题

**一句话：** 关注“一个任务怎样被规划、执行、测试和恢复”，但不要把某产品的使用教程直接当成通用工程原理。

〔本次新补，参考当前面试趋势〕

目标 + 例子。 看到某工具宣称支持自动执行和验证时，记录版本、来源和自己是否测试；再把通用的工具权限、状态、停止和回归问题映射到实际项目。

### 概念与数据流

| 五要素 | 工具功能记录 |
| --- | --- |
| 输入 | 产品与版本、功能描述、来源地址和本地测试状态。 |
| 做什么 | 检查记录结构，区分已验证、失败和未测试。 |
| 输出 | 各状态数量及后续待验证项。 |
| 哪里出错 | 版本不匹配、把宣传当实测、来源失效或把单次成功当稳定性。 |
| 参数影响 | 产品版本、测试场景、工具权限和运行环境影响结果。 |

Harness 可理解为围绕模型组织工具、状态、约束和反馈的运行机制；不同产品实现不同。阅读新闻时区分“官方宣称”“自己的验证”和“适用于目标项目的工程原则”，具体工具循环见第 4 章。

### 面试追问

【⭐ 理解】如何判断新工具功能是否适合项目？ 结论：先核对版本和实际任务。查看官方文档，再在可控环境测试功能、权限、失败恢复与成本。

【⭐ 理解】产品宣传与实际行为不一致怎么查？ 结论：固定版本和复现步骤。核对配置、权限和日志，保存失败样本；不能只依据宣传判断。

【◻ 按需】一次成功说明系统可靠么？ 结论：不说明。需要覆盖不同任务、失败与恢复，并持续回归。

### 故障模式与排障

- 文档和工具版本不一致：记录实际版本，查对应文档并重测。

- 功能标为通过却没有证据：补充可复现的测试记录，未知保持未测试。

- 工具调用失败被忽略：检查调用轨迹与退出状态；明确失败、重试或人工处理。

### 工程 trick 与坑

- 示例仅校验 URL 格式，不访问网页，也不确认其是否为官方来源。

- 验证结果依赖人工提供的证据文本；程序无法确认测试是否真实或充分。

- 不把某条招聘或产品新闻视为所有岗位的通用要求。

### Toy code：功能宣称与验证状态

运行前提：Python 3.10+，标准库；数据和地址均为虚构，不联网。

```python
"""整理虚构工具功能宣称及本地验证状态；不访问网页。"""
from dataclasses import dataclass
from urllib.parse import urlparse


@dataclass(frozen=True)
class FeatureRecord:
    """功能、产品版本、来源地址及本地验证结果。"""
    product: str
    version: str
    feature: str
    source_url: str
    result: str
    evidence: str


def review(records: list[FeatureRecord]) -> dict[str, int]:
    """检查唯一功能记录，并统计已验证、失败和未测试。"""
    if not records:
        raise ValueError('记录不能为空')
    seen: set[tuple[str, str, str]] = set()
    counts = {'verified': 0, 'failed': 0, 'not_tested': 0}
    for record in records:
        if any(not isinstance(v, str) or not v.strip() for v in (record.product, record.version, record.feature)):
            raise ValueError('产品、版本和功能不能为空')
        key = (record.product, record.version, record.feature)
        if key in seen:
            raise ValueError('功能记录重复')
        seen.add(key)
        parsed = urlparse(record.source_url)
        if parsed.scheme not in {'http', 'https'} or not parsed.hostname:
            raise ValueError('来源地址格式非法')
        if record.result not in counts:
            raise ValueError('验证状态非法')
        if record.result != 'not_tested' and not record.evidence.strip():
            raise ValueError('已测试记录需要证据描述')
        counts[record.result] += 1
    assert sum(counts.values()) == len(records)
    return counts


def main() -> None:
    """覆盖未测试、已验证、缺证据和重复记录。"""
    a = FeatureRecord('mock', 'v1', '工具调用', 'https://example.org/docs', 'not_tested', '')
    b = FeatureRecord('mock', 'v1', '事件流', 'https://example.org/docs', 'verified', '本地测试记录')
    assert review([a, b]) == {'verified': 1, 'failed': 0, 'not_tested': 1}
    for invalid in ([], [a, a], [FeatureRecord('m', 'v', 'f', 'https://example.org', 'verified', '')]):
        try:
            review(invalid)
        except ValueError:
            pass
        else:
            raise AssertionError('重复或缺证据必须拒绝')
    print('虚构功能记录自检通过；未核验网页或真实产品。')


if __name__ == '__main__':
    main()

```

逐段理解。 FeatureRecord 保存产品版本、功能与状态；review 检查来源格式、唯一性和测试证据；自检覆盖未测、重复及缺证据。

## 11.4 故障与安全事件：事实、时间和根因【◻ 按需】

### 为什么要关注这个问题

**一句话：** 事件类文章可以启发风险清单，但事实与原因要回到官方公告和可验证材料；不需要背事件日期或传闻。

目标 + 例子。 从服务故障新闻中提炼超时、恢复与监控等工程问题，但先区分事件发生、公告发布时间和核对时间；未经证实的原因保持未知。

### 概念与数据流

| 五要素 | 事件记录核对 |

### 面试追问

【⭐ 理解】故障新闻如何转化成工程学习？ 结论：先核实事实，再提炼可验证的改进。结合自身系统检查超时、回退、监控和恢复，不把别人的推测直接套用。

【⭐ 理解】报道时间就是故障发生时间吗？ 结论：不一定。需要区分发生、发现、发布和更新，并确认时区。

【◻ 按需】官方还没确认根因怎么办？ 结论：保留未知。持续关注后续公告，不编造解释。

### 故障模式与排障

- 时间线冲突：检查事件发生、发布日期和时区；回查原始公告并记录未知项。

- 推测被写成确定根因：区分来源声明与自己的假设；未确认时标记未知。

- 把单次事故当成普遍结论：结合自身流量和依赖做故障演练，验证改进是否有效。

### 工程 trick 与坑

- 示例只检查给定时间顺序，不能验证事件、来源或根因真实性。

- 真实事件的起止时间可能未知，也可能有多次公告；本例数据结构为简化练习。

- 面试讲事故应区分亲历、公开资料和推测，不夸大个人经历。

### Toy code：虚构事件时间线

运行前提：Python 3.10+，标准库；数据和来源均为虚构。

```python
"""整理虚构故障事件的发生、发布和核对时间，不判断真实原因。"""
from dataclasses import dataclass
from datetime import datetime, timezone


@dataclass(frozen=True)
class Incident:
    """事件时间、报告时间、核对时间及已确认或未知的原因。"""
    name: str
    happened_at: datetime
    reported_at: datetime
    checked_at: datetime
    source: str
    confirmed_cause: str | None


def inspect(record: Incident) -> dict[str, str]:
    """检查带时区时间和顺序；未确认原因保持未知。"""
    if not record.name.strip() or not record.source.strip():
        raise ValueError('事件名称和来源不能为空')
    times = (record.happened_at, record.reported_at, record.checked_at)
    if any(not isinstance(t, datetime) or t.tzinfo is None or t.utcoffset() is None for t in times):
        raise ValueError('所有时间必须包含时区')
    if not record.happened_at <= record.reported_at <= record.checked_at:
        raise ValueError('示例要求发生、发布、核对时间依次递增')
    if record.confirmed_cause is not None and not record.confirmed_cause.strip():
        raise ValueError('已确认原因不能是空白')
    return {'name': record.name, 'cause': record.confirmed_cause or '未知，待核实',
            'checked_at_utc': record.checked_at.astimezone(timezone.utc).isoformat()}


def main() -> None:
    """验证未知原因、时间顺序、时区和缺失来源。"""
    t1 = datetime(2026, 6, 1, 1, tzinfo=timezone.utc)
    t2 = datetime(2026, 6, 1, 2, tzinfo=timezone.utc)
    t3 = datetime(2026, 6, 1, 3, tzinfo=timezone.utc)
    good = Incident('虚构故障', t1, t2, t3, '虚构公告', None)
    assert inspect(good)['cause'] == '未知，待核实'
    invalid = [Incident('x', t2, t1, t3, 'source', None),
               Incident('x', datetime(2026, 6, 1), t2, t3, 'source', None),
               Incident('x', t1, t2, t3, '', None)]
    for record in invalid:
        try:
            inspect(record)
        except ValueError:
            pass
        else:
            raise AssertionError('错误时间或缺来源必须拒绝')
    print('虚构事件时间与未知原因自检通过:', inspect(good))
    print('程序不核验事件、来源或根因。')


if __name__ == '__main__':
    main()

```

逐段理解。 Incident 保存三个带时区的时间；inspect 检查示例顺序并保留未知原因；自检覆盖无时区、错误顺序和缺来源。

### 这段代码怎么在面试里讲

- 不变量：时间带时区，示例中发生不晚于发布、发布不晚于核对。

- 关键过程：校验事件记录，将核对时间转为 UTC；未确认原因显示未知。

- 边界与坑：此顺序是简化假设，程序不验证公告或根因；真实事件可能有未知时间和多次更新。

### 本节收尾：费曼自述与闪卡

费曼自述： 事故学习先核对来源与时间线，未知原因保持未知，再把事实转化为自己系统可验证的改进。
