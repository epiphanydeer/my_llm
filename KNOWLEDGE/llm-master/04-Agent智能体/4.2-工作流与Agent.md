### 一、先说结论：流程能写死，就优先 Workflow

很多人一听 Workflow，就觉得它不如 Agent 高级。

这个理解是错的。

Workflow 不是低级方案。

在很多生产系统里，Workflow 才是更靠谱的方案。

什么是 Workflow？

简单说，就是**步骤固定、规则明确、输入输出稳定的流程编排。**

比如发票审核：

1. OCR 识别发票图片。
2. 提取金额、税号、日期。
3. 校验字段是否合法。
4. 调用财务系统入账。
5. 返回审核结果。

这个流程很清楚。

先做什么，后做什么，异常怎么处理，都能提前写出来。

这种场景，你根本不需要让模型每次自由发挥：

“我思考一下，接下来要不要入账。”

这就很危险。

因为财务流程最需要的不是“灵活”，而是**稳定、可审计、可回放、可控制。**

所以第一条原则很简单：

**如果流程能稳定写死，就优先用 Workflow，不要硬上 Agent。**

### 目标与例子

目标：掌握在复杂业务场景下区分并选择固定工作流（Deterministic Workflow）与自主智能体（Autonomous Agent）的工程决策框架，破除“言必称 Agent、把简单流程复杂化”的盲目跟风，建立高确定性、低成本与快速迭代的产品架构观。
例子：企业要求实现“员工报销单据智能审核与入账系统”：

- 错误选型（盲目上全自主 Agent）：让大模型自主决定去调哪个内部 API、自己查政策、自己算金额并自己决定打款。由于大模型存在概率采样与幻觉，可能某一次自作聪明跳过了财务主管审核直接放款，或者在死循环里反复查询相同单据，引发重大财务事故；

- 正确选型（确定性工作流 + LLM 局部赋能）：主干全链路采用严格的确定性工作流（Workflow）：OCR识别发票 -> 代码规则校验金额与税号 -> 若超额自动路由至人工审批流 -> 财务系统入账。仅在“发票模糊手写体解读”或“报销理由合规性初审”这两个离散节点上调用大模型。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 业务需求规格、输入不确定性程度、错误容忍度（Blast Radius）、端到端 P95 延迟与 Token 成本预算。 |
| 做什么 | 依照四维决策漏斗评估：能用传统代码/规则穷举的坚决用 Workflow，仅在路径高度发散、未知未知项多时引入 Agent。 |
| 输出 | 架构选型结论（Workflow vs Router RAG vs ReAct Agent vs Multi-Agent）及状态机蓝图。 |
| 哪里出错 | 把简单流水线包装成 Agent 导致稳定性暴跌、忽略状态机边界导致流程失控。 |
| 重要参数影响 | 任务分支分支数、业务容错率、单次调用成本上限。 |

#### Workflow vs Agent 终极选型四维矩阵

| 评估维度 | 固定工作流 (Deterministic Workflow) | 自主智能体 (Autonomous Agent) |
| --- | --- | --- |
| 控制流主导权 | 硬编码代码/DAG 主导（If-Else 由工程师预定义） | 大模型主导（LLM 在运行时自主决定下一步） |
| 执行路径 | 确定、线性或可穷举的条件跳转，结果 100% 可复现 | 动态、自适应多步探索，不同运行可能走出不同路径 |
| 单次执行成本 | 固定、可预测（调用次数恒定） | 浮动、不可预测（受迭代步数影响，可能波动 1x~5x） |
| 适合业务场景 | 严肃企业核心业务：报销审核、客户工单流转、安全合规检查 | 开放探索型业务：代码跨仓库重构、竞品开放情报调研、深度研究 |

### 面试追问

- 【🔥 必会】外企/大厂面试高频题：“你们项目中什么时候选 Workflow，什么时候选 Agent？如何说服业务方不盲目上 Agent？”
一句话结论：按“容错代价”与“路径可穷举性”决定：能穷举的、高容错代价的坚决用 Workflow。
展开原理/取舍：回答决策框架：“我们遵循三个核心准则：① 业务容错代价（Risk of Failure）：涉及资金结算、权限审批、生产环境修改等零容忍业务，主干必须由代码级 Workflow 强力把关；② 分支可穷举性：如果业务逻辑在 PRD 中能画出清晰的状态流转图，坚决用确定性代码编写；③ 收益与成本比：Agent 存在 1.5~3 倍的额外延迟与多轮 Token 账单。我们只在‘输入高度未知、探索路径无法预先写死、且允许失败重试’的场景（如辅助开发者做代码 Bug 定位探索）才引入 Agent。”

- 【🔥 必会】【排障题】一个原本表现稳定的工作流，引入了所谓的 Agent 规划节点后经常出现业务逻辑偶发短路或超时，怎么定位？
一句话结论：排查模型的非确定性输出漂移，将开放式自然语言决策收敛为严格有限枚举状态。
展开原理/取舍：LLM 本质是概率分布，当温度或上游输入微调时，开放式 Prompt 会导致模型在某些 Corner Case 下产生未定义的决策意图。治理方法：对规划节点施加 JSON Schema 严格受限枚举（Restricted Enum），把模型的输出强行限制为预定义的 ["APPROVE", "REJECT", "ESCALATE_HUMAN"] 三个字符串之一；若吐出未定义字段，系统直接走降级回退通道，严禁让模型自由发挥写代码逻辑。

- 【⭐ 理解】为什么在现代 AI 应用开发中，“Router + Workflow”通常是比纯 Agent 更有性价比的生产实践？
一句话结论：用大模型做单次意图路由（Router），后续执行全部交还给稳健代码（Workflow），兼顾智能与高稳定。
展开原理/取舍：这种架构又称“受限自治”。例如在客服场景，大模型仅负责理解用户一句口语化的问题到底是想“查物流”、“退货”还是“投诉”（单次分类路由）；一旦意图识别完成，立刻交由早已成熟稳定的传统微服务工作流去查数据库和改状态，不需要 Agent 拿着一堆工具在运行时反复尝试，在极短延迟（<300ms）内实现极高可靠性。

### 故障模式与排障

- 故障模式：过度复杂化导致系统“脆弱性（Fragility）”倍增

- 定位：明明是一个两步查询，却设计了 3 个 Agent（Planner / Worker / Critic）来回开会讨论，单次问答耗时超 15 秒且经常因网络抖动超时。

- 修复：奥卡姆剃刀重构：大刀阔斧干掉多余的 Agent 角色，将其平铺为一个简单的 Python 顺序函数调用，仅保留核心必要的大模型调用。

- 故障模式：工作流中未捕获模型抛出的非结构化异常

- 定位：工作流中的某个 LLM 节点偶尔因安全风控（Content Filter）返回了拒答文本，下游节点假设其为 JSON 直接 json.loads 导致整个微服务线程崩溃。

- 修复：在工作流中每一个接入 LLM 的边界处包裹防护代理（Safe Guard Wrapper），强制执行空值校验、Schema 校验与异常回退。

### 工程 trick 与坑

- 80/20 混合架构原则：生产级 AI 系统的标准骨架往往是 80% 确定性代码 + 20% 局部模型注入。让大模型做它最擅长的自然语言理解和信息归纳，让代码做它最擅长的逻辑判断、循环计数与事务提交。

- 状态流转白名单断言：在工作流的关键节点之间插入状态断言（State Transition Assertions），例如状态绝对不允许直接从 DRAFT 跳到 PAID，防止模型注入引发的越权跳步。

### 循序渐进 Toy Code：Level 2 — 确定性安全审批与路由工作流引擎

代码难度定位：Level 2（确定性分支与门控）。手写一个结构极为严密的工业合规审批工作流引擎，展示确定性规则路由、受控模型分类节点与状态跃迁断言。

```python
"""
4.2 Toy Code: Level 2 - 确定性安全审批与路由工作流引擎
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
from enum import Enum
from typing import Optional


class WorkPermitType(str, Enum):
    """作业类型枚举"""
    HOT_WORK = "HOT_WORK"           # 动火作业
    HEIGHT_WORK = "HEIGHT_WORK"     # 高处作业
    GENERAL = "GENERAL"             # 一般作业


class ApprovalStatus(str, Enum):
    """审批流转状态"""
    AUTO_APPROVED = "AUTO_APPROVED"         # 自动审批通过
    REQUIRE_CHIEF_ENGINEER = "CHIEF_ESCALATE" # 需总工特批
    REQUIRE_SAFETY_OFFICER = "OFFICER_REVIEW" # 需现场安全员核验
    REJECTED = "REJECTED"                   # 自动驳回


@dataclass(frozen=True)
class PermitRequest:
    """提交的作业审批单据"""
    permit_id: str
    permit_type: WorkPermitType
    risk_level: int                # 风险等级 (1: 低风险, 2: 中风险, 3: 高风险/重大风险)
    has_qualified_license: bool    # 是否具备有效特种作业执业证书
    is_wind_speed_safe: bool       # 现场风速检测是否达标


@dataclass(frozen=True)
class WorkflowExecutionResult:
    """工作流执行审计结果"""
    permit_id: str
    final_status: ApprovalStatus
    audit_trail: tuple[str, ...]
    is_safe: bool


def deterministic_safety_workflow(request: PermitRequest) -> WorkflowExecutionResult:
    """
    确定性业务安全审批工作流
    
    工程特性：
    1. 零随机性，100% 规则驱动与因果可重放
    2. 严格的单向状态转移与门限拦截
    """
    if not request.permit_id.strip():
        raise ValueError("单据 ID 不能为空")
    if not (1 <= request.risk_level <= 3):
        raise ValueError("风险等级必须在 1 到 3 之间")

    logs: list[str] = [f"启动作业单 [{request.permit_id}] 审核流"]

    # 门控检查 1：资质硬性准入（Hard Pre-condition）
    if not request.has_qualified_license:
        logs.append("门控拦截：作业人员未持有有效特种作业执照，直接驳回。")
        return WorkflowExecutionResult(
            permit_id=request.permit_id,
            final_status=ApprovalStatus.REJECTED,
            audit_trail=tuple(logs),
            is_safe=False
        )

    # 门控检查 2：环境安全硬性约束（如高处作业现场环境）
    if request.permit_type == WorkPermitType.HEIGHT_WORK and not request.is_wind_speed_safe:
        logs.append("门控拦截：高处作业现场风速超标（>=5级大风），直接驳回。")
        return WorkflowExecutionResult(
            permit_id=request.permit_id,
            final_status=ApprovalStatus.REJECTED,
            audit_trail=tuple(logs),
            is_safe=False
        )

    # 门控检查 3：基于确定性业务逻辑做角色审批路由分发
    if request.risk_level == 3 or request.permit_type == WorkPermitType.HOT_WORK:
        logs.append("分级路由：重大风险或动火作业，升级呈批至项目总工程师（Chief Engineer）。")
        final_status = ApprovalStatus.REQUIRE_CHIEF_ENGINEER
    elif request.risk_level == 2:
        logs.append("分级路由：中度风险作业，路由派单至现场专职安全员现场复核。")
        final_status = ApprovalStatus.REQUIRE_SAFETY_OFFICER
    else:
        logs.append("快速通道：低风险一般作业且前置资质齐全，系统自动盖章通过。")
        final_status = ApprovalStatus.AUTO_APPROVED

    return WorkflowExecutionResult(
        permit_id=request.permit_id,
        final_status=final_status,
        audit_trail=tuple(logs),
        is_safe=True
    )


def self_test():
    """测试工作流在不同场景下的确定性路由与拦截"""
    # 场景 1：无证施工 -> 硬性驳回
    req_no_license = PermitRequest(
        permit_id="P-001",
        permit_type=WorkPermitType.HEIGHT_WORK,
        risk_level=1,
        has_qualified_license=False, # 无证
        is_wind_speed_safe=True
    )
    res1 = deterministic_safety_workflow(req_no_license)
    assert res1.final_status == ApprovalStatus.REJECTED
    assert res1.is_safe is False
    assert "特种作业执照" in res1.audit_trail[-1]

    # 场景 2：动火作业中风险 -> 自动路由至总工审批
    req_hot_work = PermitRequest(
        permit_id="P-002",
        permit_type=WorkPermitType.HOT_WORK,
        risk_level=2,
        has_qualified_license=True,
        is_wind_speed_safe=True
    )
    res2 = deterministic_safety_workflow(req_hot_work)
    assert res2.final_status == ApprovalStatus.REQUIRE_CHIEF_ENGINEER
    assert res2.is_safe is True

    # 场景 3：低风险一般作业 -> 秒级自动通过
    req_general = PermitRequest(
        permit_id="P-003",
        permit_type=WorkPermitType.GENERAL,
        risk_level=1,
        has_qualified_license=True,
        is_wind_speed_safe=True
    )
    res3 = deterministic_safety_workflow(req_general)
    assert res3.final_status == ApprovalStatus.AUTO_APPROVED

    print("✅ 4.2 确定性安全审批与路由工作流自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个具备严格因果断言的企业级安全工作流 deterministic_safety_workflow。核心不变量是：凡进入审批流的申请，若前置环境或执照不达标，状态严格锁定为 REJECTED；任何可能引发重大事故的高危操作，绝对禁止直接进入 AUTO_APPROVED 状态。

- 关键行解析：在第 52-72 行，我用纯粹的代码逻辑锁死了核心门禁，不需要耗费任何模型 Token，毫秒级实现 100% 确定的安全阻断；第 75-84 行展示了清晰的业务分级路由策略，为不同风险等级的单据绑定确切的审批责任人。

- 主动说边界与坑：这段代码诠释了 Workflow 的核心价值。在面向外企面试官时，要主动进行技术思辨：许多初级开发者盲目把这种流程做成 Multi-Agent，不仅引入模型幻觉风险，还徒增几秒的延迟与调用失败率；而将主干做成确定性 Workflow、仅在“附件合同语义合规审查”等非结构化环节局部调用大模型，才是工业界最稳健的架构。

### 本节收尾：费曼自述与闪卡

费曼自述：
“工作流就像修了一条带红绿灯的封闭高速公路：每一辆车（单据）到路口该左拐还是右拐，路牌写得清清楚楚，绝对不会开到沟里去；而 Agent 就像把车钥匙交给一个新手司机在野地里自由驾驶。对于严肃的保命业务，你必须老老实实修高速路（工作流）；只有在野外探险、没路可走的时候，才把钥匙交给司机让他自己探路（Agent）。”

- Q：如何用一句话区分 Workflow 与 Agent 的本质？
A：Workflow 是工程师用代码预定义好的确定性执行网络；Agent 是由大模型在运行时根据反馈自主决定执行步骤的自适应控制流。

- Q：为什么在金融支付和安全生产等领域，坚决禁止让 Agent 自主完成资金打款或设备操作？
A：因为大模型自回归生成存在固有概率幻觉与易受提示注入攻击的弱点；涉及高危与资金动作必须通过代码强约束的工作流与人工最终授权。

- Q：什么是“受控自治（Restricted Autonomy）”架构？
A：外层主干由确定性工作流把控边界与审计，内层仅在需要自然语言理解、摘要或多维意图分类的特定节点调用模型，实现稳定性与智能度的平衡。
