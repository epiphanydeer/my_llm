### 一、为什么会有 MCP

先别急着背架构。

我们先看没有 MCP 的世界是什么样。

假设你要做一个代码助手，让它能完成这些事：

- 读本地文件
- 搜 GitHub Issue
- 查数据库
- 看 Sentry 报错
- 发 Slack 消息
- 读公司知识库

如果没有统一协议，每接一个系统，都要自己定义一套工具格式：

- 工具怎么发现？
- 参数 Schema 怎么描述？
- 工具怎么调用？
- 工具结果怎么返回？
- 工具权限怎么控制？
- 本地工具和远程工具怎么通信？
- 工具变了，客户端怎么知道？

这些问题如果每个产品都自己解决，就会非常乱。

对工具提供方也很痛苦。

比如你做了一个数据库查询工具。

你想让 Claude Desktop 能用。

想让 Cursor 能用。

想让 VS Code 里的 AI 插件能用。

想让公司内部 Agent 也能用。

难道每个宿主都写一套插件？

这就太浪费了。

MCP 的思路是：

**工具提供方按 MCP 标准暴露能力，AI 应用按 MCP 标准连接这些能力。**

这样工具和 AI 应用之间就有了一层统一协议。

就像前后端之间用 HTTP API 通信。

就像数据库客户端通过统一协议连接数据库。

MCP 解决的不是“模型怎么推理”。

它解决的是：**AI 应用怎么标准化地拿到上下文、调用工具、使用提示模板。**

### 目标与例子

目标：掌握由 Anthropic 发起、现已成为跨平台开源事实标准的 Model Context Protocol (MCP，模型上下文协议) 的系统分层架构，理解其解决传统“工具碎片化开发”的物理机制，理清 MCP 与 Function Calling 的技术分界线，能手撕基于标准 JSON-RPC 2.0 规范的工具发现（tools/list）与安全调用（tools/call）通信分发器。
例子：

- 传统碎片化模式（$N \times M$ 灾难）：企业有 5 个不同的数据源（飞书文档、Postgres 数据库、GitLab、Jira、现场监控），若为 OpenAI 写一套插件、为 Claude 写一套工具、为本地开源模型又写一套，需要维护 $5 \times 3 = 15$ 套适配代码，任何一个接口变更全线崩溃；

- MCP 标准化模式（$N + M$ 解耦）：每一个数据源只需开发一个轻量级的 MCP Server（遵守标准协议暴露 Tools 和 Resources）；无论前端宿主（Host）是 Claude Code、Cursor、还是自研的 Python Agent，通过统一的 JSON-RPC 协议即插即用、秒级挂载。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 标准 JSON-RPC 2.0 请求数据包（jsonrpc: "2.0", 唯一递增 id, method, params）。 |
| 做什么 | 规范化处理三大能力原语：Tools（模型可调用的动作）、Resources（只读文件/数据流）、Prompts（预设交互模板）。 |
| 输出 | 携带对应请求 id 的标准 JSON-RPC 响应体（result 或标准错误 error）。 |
| 哪里出错 | JSON-RPC 版本号未显式声明 "2.0"、Stdio 通道被普通 print 日志污染导致解析崩溃、跨版本协议握手不兼容。 |
| 重要参数影响 | 传输通道类型（Transport）：本地进程 stdio（零网络开销、极高安全性）vs 远程服务 Streamable HTTP / SSE。 |

#### MCP 三层系统架构全景

```text
┌────────────────────────────────────────────────────────┐
│   宿主应用环境 (Host Application)                       │
│   (如: Claude Code, Cursor, 自研企业 Agent Runtime)     │
│                                                        │
│   ┌────────────────────────────────────────────────┐   │
│   │  MCP 客户端 (MCP Client)                       │   │
│   │  负责生命周期管理、协议序列化与安全权限审批       │   │
│   └───────────────────────▲────────────────────────┘   │
└───────────────────────────┼────────────────────────────┘
                            │ 标准 JSON-RPC 2.0 协议通道
                            │ (Local Stdio 或 Remote SSE/HTTP)
┌───────────────────────────▼────────────────────────────┐
│   MCP 服务端 (MCP Server)                              │
│   (独立无状态或轻量服务进程，由各数据源提供方维护)      │
│                                                        │
│   ├── Tools API       ──► 动态工具发现与动作执行       │
│   ├── Resources API   ──► 静态/流式数据资产安全读取    │
│   └── Prompts API     ──► 标准提示词模板注入           │
└────────────────────────────────────────────────────────┘
```

### 面试追问

- 【🔥 必会】外企/大厂面试常问：MCP 协议和传统的 Function Calling 到底有什么区别和联系？
一句话结论：Function Calling 是模型与应用间的“语义输出格式”；MCP 是应用与外部世界间的“连接总线标准”。
展开原理/取舍：① Function Calling：定义的是“大模型如何在自回归生成中吐出结构化 JSON 实参”的语法规则，它发生在 LLM 与 Host 程序之间；② MCP：定义的是“Host 程序如何去发现外部有哪些工具可用、如何通过进程间通信（IPC）或网络触发该工具并拿回结构化数据”的传输层总线协议，它发生在 Host 与外部服务之间。二者完美协同：Host 通过 MCP 发现工具并转成 JSON Schema 喂给大模型；大模型通过 Function Calling 发起调用；Host 再通过 MCP 将调用分发给目标 Server。

- 【🔥 必会】在开发本地 stdio 传输模式的 MCP Server 时，Python 代码中有一个极其致命的调试大忌是什么？
一句话结论：绝对禁止使用 print() 打印普通调试日志！必须全部改用 sys.stderr.write() 或专用 Logger。
展开原理/取舍：在 stdio 模式下，MCP 客户端与服务端是通过标准输入（Stdin）和标准输出（Stdout）按行收发严格的 JSON 字符串进行通信的。如果在服务端代码中随手写了一句 print("DEBUG: 正在处理数据")，这串非 JSON 格式的字符串会直接被混入 Stdout 数据流中，导致客户端的 JSON 解析器抛出致命的 JSONDecodeError，直接引发整个 MCP 会话崩溃断连。所有调试信息必须重定向至标准错误流（Stderr）。

- 【⭐ 理解】MCP 协议是否自带了“用户鉴权与安全防护”？如果恶意 MCP Server 植入了危险命令怎么办？
一句话结论：MCP 是协议规范，不自动阻断危险；安全边界必须由 MCP Host（宿主应用）实施“用户知情与审批确认机制”。
展开原理/取舍：MCP Server 是第三方编写的外部进程。在成熟的 MCP Host（如 Claude Code）设计中，每一个由 MCP 暴露出来的工具，首次被模型调用前都会在终端弹窗或停顿，显式展示将要执行的完整参数并请求人类授权（Human Approval）；同时对本地 Server 实施沙箱容器化隔离，严格限制文件系统读写范围，防止恶意工具执行提权攻击。

### 故障模式与排障

- 故障模式：Client 报错 Method not found (code: -32601)

- 定位：排查请求中的 method 拼写是否未按 MCP 规范。例如把标准的 tools/list 错写为了 list_tools，或把 tools/call 写成了 call_tool。

- 修复：严格遵循 JSON-RPC 2.0 规范，将路由方法名严格标准化为 tools/list、tools/call、resources/read 等带斜杠的命名空间格式。

- 故障模式：长耗时工具导致 MCP 客户端触发连接超时断开

- 定位：某个本地查询工具执行耗时超过了 Client 默认的 10 秒超时设置。

- 修复：在 Client 侧按工具性质动态配置 timeout；对于极慢任务，在 MCP Server 端实现进度通知（Progress Notifications）机制，定期向通道回传心跳。

### 工程 trick 与坑

- 标准错误码规范：完全对齐 JSON-RPC 2.0 标准规范：-32700（解析错误）、-32600（无效请求）、-32601（方法不存在）、-32602（无效参数）；业务自定义错误码必须落在 -32000 到 -32099 之间。

- 协议握手版本自适应：在实际编写 MCP Client 时，应当在启动建立连接时先向 Server 发起握手探测（Handshake），获取 Server 支持的能力集（Capabilities），自适应开启流式或动态重连。

### 循序渐进 Toy Code：Level 8 — 纯标准库手撕 JSON-RPC 2.0 MCP 协议分发器

代码难度定位：Level 8（网络协议与通信规范）。零第三方库依赖，纯 Python 手写一个严格遵循 JSON-RPC 2.0 规范、支持 tools/list 动态发现与 tools/call 参数校验调用的微型 MCP 服务分发器。

```python
"""
4.8 Toy Code: Level 8 - 纯标准库手撕 JSON-RPC 2.0 MCP 协议分发器
依赖：Python 3.10+ 标准库 (无需第三方框架)
"""
from dataclasses import dataclass
import json
from typing import Any, Callable, Optional


# JSON-RPC 2.0 标准保留错误码常量定义
RPC_PARSE_ERROR = -32700
RPC_INVALID_REQUEST = -32600
RPC_METHOD_NOT_FOUND = -32601
RPC_INVALID_PARAMS = -32602
RPC_INTERNAL_ERROR = -32603


@dataclass(frozen=True)
class MCPToolDefinition:
    """MCP 工具能力元数据定义"""
    name: str
    description: str
    input_schema: dict[str, Any]
    handler_func: Callable[[dict[str, Any]], Any]


class MiniMCPServerDispatcher:
    """遵循 MCP 核心规范的 JSON-RPC 2.0 协议分发处理器"""

    def __init__(self, server_name: str = "safety-mcp-server", version: str = "1.0.0"):
        self.server_name = server_name
        self.version = version
        self.registered_tools: dict[str, MCPToolDefinition] = {}

    def register_tool(
        self,
        name: str,
        description: str,
        input_schema: dict[str, Any],
        handler: Callable[[dict[str, Any]], Any]
    ) -> None:
        """向服务端注册工具能力"""
        if not name.strip() or not description.strip():
            raise ValueError("工具名称与描述必须为非空文本")
        self.registered_tools[name] = MCPToolDefinition(
            name=name,
            description=description,
            input_schema=input_schema,
            handler_func=handler
        )

    def handle_raw_json_rpc_message(self, raw_message_str: str) -> str:
        """
        处理单条原始 JSON-RPC 报文并返回响应报文字符串
        
        执行流：
        1. JSON 反序列化验证
        2. 协议头合规性校验 (jsonrpc: "2.0")
        3. 路由分发: 'tools/list' 与 'tools/call'
        4. 标准错误包装
        """
        # 1. 解析原始 JSON
        try:
            req = json.loads(raw_message_str)
        except json.JSONDecodeError as exc:
            return self._build_error_response(req_id=None, code=RPC_PARSE_ERROR, msg="JSON 解析错误")

        # 2. 校验 JSON-RPC 2.0 基础结构
        if not isinstance(req, dict) or req.get("jsonrpc") != "2.0" or "method" not in req:
            return self._build_error_response(
                req_id=req.get("id") if isinstance(req, dict) else None,
                code=RPC_INVALID_REQUEST,
                msg="无效请求：必须包含严格的 jsonrpc='2.0' 和 method 字段"
            )

        req_id = req.get("id")
        method = req["method"]
        params = req.get("params", {})

        # 3. 路由分发处理
        # 路由 A：工具发现协议 (tools/list)
        if method == "tools/list":
            tools_list_payload = [
                {
                    "name": t.name,
                    "description": t.description,
                    "inputSchema": t.input_schema
                }
                for t in self.registered_tools.values()
            ]
            return self._build_success_response(req_id, {"tools": tools_list_payload})

        # 路由 B：工具调用协议 (tools/call)
        elif method == "tools/call":
            if not isinstance(params, dict) or "name" not in params:
                return self._build_error_response(req_id, RPC_INVALID_PARAMS, "缺少必填参数 'name'")
            
            tool_name = params["name"]
            tool_args = params.get("arguments", {})

            if tool_name not in self.registered_tools:
                return self._build_error_response(
                    req_id, RPC_METHOD_NOT_FOUND, f"未知的工具名称: '{tool_name}'"
                )

            tool_def = self.registered_tools[tool_name]
            
            # 基础类型参数校验
            if not isinstance(tool_args, dict):
                return self._build_error_response(req_id, RPC_INVALID_PARAMS, "arguments 必须为字典对象")

            try:
                # 执行具体业务 Handler
                exec_result = tool_def.handler_func(tool_args)
                # MCP 规范要求：工具执行结果包装在 content 数组中
                mcp_content_payload = {
                    "content": [
                        {"type": "text", "text": str(exec_result)}
                    ],
                    "isError": False
                }
                return self._build_success_response(req_id, mcp_content_payload)
            except Exception as e:
                # 捕获工具内部业务异常，以 isError=True 返回而非打崩通道
                mcp_error_payload = {
                    "content": [
                        {"type": "text", "text": f"工具执行异常: {str(e)}"}
                    ],
                    "isError": True
                }
                return self._build_success_response(req_id, mcp_error_payload)

        else:
            return self._build_error_response(
                req_id, RPC_METHOD_NOT_FOUND, f"不支持的 MCP 协议方法: '{method}'"
            )

    def _build_success_response(self, req_id: Any, result: Any) -> str:
        """组装标准 JSON-RPC 成功响应体"""
        return json.dumps({
            "jsonrpc": "2.0",
            "id": req_id,
            "result": result
        }, ensure_ascii=False)

    def _build_error_response(self, req_id: Any, code: int, msg: str) -> str:
        """组装标准 JSON-RPC 错误响应体"""
        return json.dumps({
            "jsonrpc": "2.0",
            "id": req_id,
            "error": {
                "code": code,
                "message": msg
            }
        }, ensure_ascii=False)


def self_test():
    """测试 MCP 分发器的工具发现、合规调用与标准错误码拦截"""
    server = MiniMCPServerDispatcher()

    # 注册一个安全规范查询工具
    def query_safety_rule_handler(args: dict[str, Any]) -> str:
        zone = args.get("zone")
        if zone == "高空":
            return "强制要求：作业高度超2米必须系挂五点式安全带。"
        elif zone == "危险":
            raise RuntimeError("检测到未隔离高压电，拒绝调阅")
        return "常规安全要求正常"

    server.register_tool(
        name="get_safety_rules",
        description="按区域查询安全防范强制规范",
        input_schema={"type": "object", "properties": {"zone": {"type": "string"}}},
        handler=query_safety_rule_handler
    )

    # 1. 测试工具发现协议 (tools/list)
    discover_req = json.dumps({
        "jsonrpc": "2.0",
        "id": 1,
        "method": "tools/list"
    })
    raw_resp1 = server.handle_raw_json_rpc_message(discover_req)
    resp1 = json.loads(raw_resp1)
    
    assert resp1["jsonrpc"] == "2.0"
    assert resp1["id"] == 1
    assert len(resp1["result"]["tools"]) == 1
    assert resp1["result"]["tools"][0]["name"] == "get_safety_rules"

    # 2. 测试合法工具调用协议 (tools/call)
    call_req = json.dumps({
        "jsonrpc": "2.0",
        "id": 2,
        "method": "tools/call",
        "params": {
            "name": "get_safety_rules",
            "arguments": {"zone": "高空"}
        }
    })
    raw_resp2 = server.handle_raw_json_rpc_message(call_req)
    resp2 = json.loads(raw_resp2)
    assert resp2["result"]["isError"] is False
    assert "五点式安全带" in resp2["result"]["content"][0]["text"]

    # 3. 测试工具内部抛出异常时的优雅捕获 (isError=True)
    call_err_req = json.dumps({
        "jsonrpc": "2.0",
        "id": 3,
        "method": "tools/call",
        "params": {"name": "get_safety_rules", "arguments": {"zone": "危险"}}
    })
    resp3 = json.loads(server.handle_raw_json_rpc_message(call_err_req))
    assert resp3["result"]["isError"] is True
    assert "未隔离高压电" in resp3["result"]["content"][0]["text"]

    # 4. 测试未知协议方法拦截 (-32601)
    unknown_req = json.dumps({"jsonrpc": "2.0", "id": 4, "method": "unsupported/method"})
    resp4 = json.loads(server.handle_raw_json_rpc_message(unknown_req))
    assert resp4["error"]["code"] == RPC_METHOD_NOT_FOUND

    # 5. 测试语法损坏报文拦截 (-32700)
    resp5 = json.loads(server.handle_raw_json_rpc_message("{bad_json"))
    assert resp5["error"]["code"] == RPC_PARSE_ERROR

    print("✅ 4.8 JSON-RPC 2.0 MCP 协议分发器自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个遵循标准 JSON-RPC 2.0 规范的 MCP 协议分发器 MiniMCPServerDispatcher。核心不变量是：所有进出报文严格遵循 jsonrpc="2.0" 标准头，响应中的 id 必须与请求保持数值完全一致；任何异常必须映射为标准保留错误码（如 -32601 Method not found），通道永不崩溃。

- 关键行解析：在第 77-90 行与第 92-138 行，我完整实现了 MCP 规范的两个支柱方法：tools/list（向 Host 宣告支持的工具与参数架构）以及 tools/call（执行具体操作并按规范封装为 {"content": [...], "isError": bool} 结果包）；在第 128-137 行，即使业务 Handler 抛出意外异常，也以 isError=True 捕获回传，防止未处理异常打断底层长连接。

- 主动说边界与坑：这段代码手撕了 MCP 协议的报文处理核心。在面向生产落地时，必须向面试官展开：在真实客户端接入（如将数据库工具挂载到 Claude Code）时，通常基于 FastMCP 或官方 TypeScript SDK 运行在本地子进程中；面试时要强调“调试时绝不在 Stdout 乱打 print 日志”，展现深刻的一线排障踩坑经验。

### 本节收尾：费曼自述与闪卡

费曼自述：
“以前给大模型装工具，就像不同品牌的手机各自用各自奇形怪状的充电线（接口碎片化）；而 MCP 协议就像统一下发了 Type-C 接口标准。不管你是哪家公司做的数据源（Server），只要焊上 Type-C 协议头，插上任何一个支持 Type-C 的 AI 软件（Host）就能马上通电用起来。”

- Q：MCP 协议相较于传统插件系统（Plugins）的最革命性进步是什么？
A：将生态架构从“$N \times M$ 的网状耦合适配”进化为“以 JSON-RPC 为总线的 $N + M$ 模块化解耦”，工具开发者无需为每个新 LLM 框架重复编写封装代码。

- Q：在 MCP 协议中，tools/list 和 tools/call 分别负责什么任务？
A：tools/list 是动态发现握手，返回当前 Server 支持的所有工具名和 InputSchema；tools/call 是动作执行，传递具体参数并回传执行状态与内容。

- Q：本地 Stdio 传输模式下的 MCP Server 为什么严禁使用 print？
A：因为 Stdio 依赖标准输出流传输合法的 JSON-RPC 报文；普通打印会污染通道引发反序列化解析崩溃，日志必须输出至 Stderr。
