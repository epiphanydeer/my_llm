## 4.9 Plan-and-Execute：有向无环图（DAG）调度与失败级联【◻ 按需】

〔补充自原仓库镜像〕〔本次新补，参考当前面试趋势〕

### 面试官会怎么问

"你们的Plan-and-Execute是怎么实现的？"

很多录友的回答是：

"模型输出了一个步骤列表，我们用for循环依次执行，每步调一个工具，执行完返回结果。"

这个回答有三个问题：

**第一，它默认了所有步骤都必须串行。** 实际上很多步骤互相不依赖，完全可以并行，for循环把能30秒跑完的任务拉成2分钟。

**第二，它没说失败怎么办。** 第3步挂了，前两步的结果丢不丢？整个任务重来还是跳过继续？

**第三，它没考虑计划本身可能有问题。** 执行到一半发现某步的结果证明后续步骤没意义了，只能整个推翻重来，还是能局部调整？

面试官真正想听的是：**你们怎么把文本计划变成可调度的DAG，怎么处理并行、失败、恢复和重规划。**

### 目标与例子

目标：掌握复杂多步长任务的“先规划、后执行（Plan-and-Solve）”架构模式，理解将任务序列形式化为有向无环图（DAG，Directed Acyclic Graph）的工程优势，能从零手撕基于拓扑排序（Topological Sort）与入度算法（Kahn's Algorithm）的轻量级 DAG 任务调度引擎，实现失败下游级联跳过（Cascade Skip）与独立分支隔离执行。
例子：复杂现场巡检任务分解为 4 个子任务：

- 节点 1：detect_hazards（视觉识别隐患图片）

- 节点 2：query_regulations（依据隐患查合规制度，强依赖节点 1）

- 节点 3：generate_rectification（生成整改通知书，强依赖节点 2）

- 节点 4：audit_inspector_id（核实巡检员资质，与上述链路完全独立，仅依赖用户初始输入）
如果节点 1 因图片损坏解析失败，DAG 调度器能精准判定：节点 2、节点 3 自动标记为 SKIPPED（因为上游前驱未就绪）；但完全独立的节点 4 依然能成功执行并落盘，避免单点局部故障引发全盘瘫痪。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 规划器生成的任务节点集合（Nodes）、节点间因果有向边依赖集（Edges: $u \to v$ 表示 $u$ 先于 $v$ 完成）、各节点绑定的执行函数。 |
| 做什么 | 执行静态有环检测（Cycle Detection）→ 计算入度构建拓扑执行队列 → 逐节点状态推进与前驱状态校验 → 失败级联标记。 |
| 输出 | 全图所有节点的终态字典（SUCCESS / FAILED / SKIPPED），以及全链路输出数据包。 |
| 哪里出错 | 大模型生成的图存在死循环环路（$A \to B \to A$ 导致无法执行）、上游失败后下游强行执行引发空指针崩溃。 |
| 重要参数影响 | 最大任务节点数、最大并发执行线程数、超时配额。 |

#### Plan-and-Execute DAG 调度架构

```text
       ┌─────────── 用户复合复杂任务 ───────────┐
       │                                     │
       ▼                                     │
┌──────────────┐                             │
│ 规划器 (LLM) │ ──► 生成有向依赖关系         │
└──────┬───────┘                             │
       │                                     │
       ▼                                     │
┌──────────────┐ (静态有向无环检测: Cycle Detection)
│ DAG 调度器   │
└──────┬───────┘
       │ 拓扑排序调度: 优先执行入度为 0 的节点
       │
       ├─────────────────────────────────┐
       ▼                                 ▼
┌──────────────┐                  ┌──────────────┐
│  任务 1 (成功)│                  │  任务 4 (独立)│ (并行/独立执行)
└──────┬───────┘                  └──────┬───────┘
       │                                 │
       ▼                                 ▼
┌──────────────┐                  【任务 4 成功落盘】
│  任务 2 (失败)│ (如: 数据源超时)
└──────┬───────┘
       │ 触发失败级联传播 (Cascade Skip)
       ▼
┌──────────────┐
│  任务 3 (跳过)│ (标记 SKIPPED, 不盲目调用)
└──────────────┘
```

### 面试追问

- 【🔥 必会】外企高频设计题：“ReAct 循环与 Plan-and-Execute（先规划再执行）架构的核心区别是什么？各自适合什么场景？”
一句话结论：ReAct 走一步看一步（贪心决策）；Plan-and-Execute 先宏观画蓝图再有序执行，适合宏观多步骤。
展开原理/取舍：① ReAct（单步自适应）：模型每走一步都要重新思考下一动向，动态应变力极强，但容易在 5 步以上的长链条任务中“迷失宏观总目标”或在局部打转；② Plan-and-Execute（全局有向无环图）：模型在最开始基于全局视野生成清晰的步骤蓝图（DAG），随后调度器以高吞吐快速推进各个子任务，大大减少了每一步都要调用 LLM 重新思考的延迟与 Token 账单；缺点是如果执行到中途发现蓝图设计错误，需要触发**局部重规划（Re-planning）**更新未执行的子图。

- 【🔥 必会】在执行大模型生成的 DAG 之前，为什么必须首先进行“有环检测（Cycle Detection）”？
一句话结论：大模型生成的结构可能存在因果逻辑闭环，有环会导致拓扑排序死锁，任务永远无法启动。
展开原理/取舍：例如模型在规划重构时输出了：任务 A 依赖任务 B、任务 B 又反向依赖任务 A。在拓扑排序算法中，两个节点的入度永远大于 0，调度引擎将陷入死锁等待。工程硬门禁：在解析完模型生成的 DAG 后，必须先用深度优先遍历（DFS 着色法）或入度统计算法验证图的无环性（Acyclic Property）；一旦检测到有环，直接打回让模型修正或报警阻断。

- 【⭐ 理解】【排障题】DAG 中途某个节点失败了，必须把整个流程全盘推倒重来吗？
一句话结论：不需要！实行“前驱缓存 + 局部重规划（Partial Re-planning）”。
展开原理/取舍：在成熟的 DAG 调度引擎（如 LangGraph / Airflow）中，每个节点输出的数据都会被固化在执行快照（Checkpoint）中。当节点 2 失败时，节点 1 已经计算完成的有效数据完全保留；调度引擎只需将“当前失败节点、未执行的下游子图以及节点 1 的产物”打包成提示词，仅要求大模型对剩余未完成的局部子路径重新规划（Re-plan），极大节约了算力与已完成前驱的等待时间。

### 故障模式与排障

- 故障模式：节点间数据传递契约破损（Contract Drift）

- 定位：节点 1 输出的数据键为 {"image_tags": [...]}，而由模型编写的节点 2 却假设输入键为 {"tags": [...]}，导致取值为 None 抛出空指针异常。

- 修复：在 DAG 的节点流转之间定义显式的数据包总线（State Channel / Typed Data Bus），强类型校验输入出参映射。

- 故障模式：独立分支的并发读写数据踩踏（Race Condition）

- 定位：两个并行的独立分支任务同时向共享全局状态的同一个数组执行写操作，导致乱序与脏写覆盖。

- 修复：采用不可变状态快照（Immutable State Snapshots）并在合并节点执行原子汇总（Reducer / State Merge）。

### 工程 trick 与坑

- 动态并发控制（Concurrency Throttle）：DAG 中所有入度为 0 的节点理论上可以并行执行；但切忌启动无限线程并发，必须限制 max_workers = 4，防止瞬时并发击垮下游依赖的第三方微服务。

- 纯 Python 标准库实现优于外部大库：在单机轻量级场景下，不必为了跑一个 5 节点的图就引入笨重的 networkx 或配置一套分布式 Airflow；几十行纯 Python 拓扑排序代码完全能提供极致的性能与确定性。

### 循序渐进 Toy Code：Level 9 — 纯 Python 零依赖轻量 DAG 任务调度引擎

代码难度定位：Level 9（拓扑调度与级联容错）。零外部依赖纯 Python 手撕一个支持静态环路死锁检测、Kahn 入度拓扑排序与上游失败下游级联跳过（Cascade Skip）的 DAG 调度引擎。

```python
"""
4.9 Toy Code: Level 9 - 纯 Python 零依赖轻量 DAG 任务调度引擎
依赖：Python 3.10+ 标准库 (无需第三方图库)
"""
from dataclasses import dataclass
from enum import Enum
from typing import Any, Callable, Optional


class TaskNodeStatus(str, Enum):
    """节点终态枚举"""
    PENDING = "PENDING"
    SUCCESS = "SUCCESS"
    FAILED = "FAILED"
    SKIPPED = "SKIPPED" # 前驱未成功，主动级联跳过


@dataclass(frozen=True)
class NodeExecutionResult:
    """单个节点的执行产出报告"""
    node_id: str
    status: TaskNodeStatus
    output_data: Optional[Any]
    error_message: Optional[str]


class MinimalDAGScheduler:
    """具备拓扑排序与失败级联控制的轻量 DAG 引擎"""

    def __init__(self):
        self.nodes: set[str] = set()
        self.node_handlers: dict[str, Callable[[dict[str, Any]], Any]] = {}
        # 依赖有向边: parent -> children (parent 必须先于 children 执行)
        self.adjacency_list: dict[str, set[str]] = {}
        # 反向依赖: child -> parents (child 依赖哪些 parents)
        self.in_dependencies: dict[str, set[str]] = {}

    def add_node(self, node_id: str, handler: Callable[[dict[str, Any]], Any]) -> None:
        """向图注册执行节点"""
        if not node_id.strip():
            raise ValueError("节点 ID 不能为空")
        if node_id in self.nodes:
            raise ValueError(f"重复注册节点: '{node_id}'")
            
        self.nodes.add(node_id)
        self.node_handlers[node_id] = handler
        self.adjacency_list.setdefault(node_id, set())
        self.in_dependencies.setdefault(node_id, set())

    def add_dependency(self, parent_id: str, child_id: str) -> None:
        """定义执行先后约束: parent 必须先于 child 执行 (parent -> child)"""
        if parent_id not in self.nodes or child_id not in self.nodes:
            raise ValueError(f"依赖节点未注册: {parent_id} -> {child_id}")
        if parent_id == child_id:
            raise ValueError(f"禁止自我循环依赖: {parent_id}")
            
        self.adjacency_list[parent_id].add(child_id)
        self.in_dependencies[child_id].add(parent_id)

    def topological_sort(self) -> list[str]:
        """
        基于 Kahn 算法计算拓扑排序，并实施静态死锁环路检测 (Cycle Detection)
        """
        # 计算每个节点的入度 (即前驱依赖数)
        in_degree = {n: len(self.in_dependencies[n]) for n in self.nodes}
        # 入度为 0 的节点作为执行起点
        queue = [n for n, deg in in_degree.items() if deg == 0]
        sorted_order: list[str] = []

        while queue:
            # 保证确定性：同级节点按 ID 字母序排序
            queue.sort()
            curr = queue.pop(0)
            sorted_order.append(curr)

            # 遍历下游子节点，减少其入度
            for child in self.adjacency_list.get(curr, set()):
                in_degree[child] -= 1
                if in_degree[child] == 0:
                    queue.append(child)

        # 核心环路断言：若排出来的节点数少于总节点数，证明图中必存在死锁环路！
        if len(sorted_order) != len(self.nodes):
            raise ValueError("严重逻辑错误：检测到 DAG 中存在死循环环路依赖 (Cycle Detected)，无法执行！")

        return sorted_order

    def execute_dag(self, initial_input_data: Optional[dict[str, Any]] = None) -> dict[str, NodeExecutionResult]:
        """
        按拓扑顺序调度执行图任务
        
        不变量保证：
        1. 仅当某个节点的所有直接前驱均处于 SUCCESS 时，该节点才允许被执行
        2. 只要有任意一个前驱处于 FAILED 或 SKIPPED，该节点直接标记为 SKIPPED
        3. 独立并行的旁路分支绝不受影响
        """
        exec_order = self.topological_sort()
        results: dict[str, NodeExecutionResult] = {}
        node_outputs: dict[str, Any] = {"_initial": initial_input_data or {}}

        for node_id in exec_order:
            parents = self.in_dependencies[node_id]

            # 检查所有前驱依赖的状态
            is_blocked = False
            for p in parents:
                parent_status = results[p].status
                if parent_status != TaskNodeStatus.SUCCESS:
                    is_blocked = True
                    break

            if is_blocked:
                # 触发失败级联传播，安全跳过
                results[node_id] = NodeExecutionResult(
                    node_id=node_id,
                    status=TaskNodeStatus.SKIPPED,
                    output_data=None,
                    error_message="前驱节点未全部成功，级联跳过执行"
                )
                continue

            # 前驱齐全，执行具体业务逻辑
            handler = self.node_handlers[node_id]
            try:
                out = handler(node_outputs)
                results[node_id] = NodeExecutionResult(
                    node_id=node_id,
                    status=TaskNodeStatus.SUCCESS,
                    output_data=out,
                    error_message=None
                )
                node_outputs[node_id] = out
            except Exception as e:
                results[node_id] = NodeExecutionResult(
                    node_id=node_id,
                    status=TaskNodeStatus.FAILED,
                    output_data=None,
                    error_message=str(e)
                )

        assert len(results) == len(self.nodes)
        return results


def self_test():
    """测试 DAG 引擎的拓扑排序、环检测与失败级联跳过"""
    dag = MinimalDAGScheduler()

    # 注册 4 个业务节点
    # 链路 1: detect_hazards -> query_rules -> generate_report
    # 链路 2: audit_inspector (独立无依赖)
    dag.add_node("detect_hazards", lambda ctx: "发现隐患: 未戴安全带")
    dag.add_node("query_rules", lambda ctx: f"匹配规程[针对:{ctx['detect_hazards']}]")
    dag.add_node("generate_report", lambda ctx: f"生成整改报告[依据:{ctx['query_rules']}]")
    dag.add_node("audit_inspector", lambda ctx: "资质核验: 巡检员具备高级资质")

    dag.add_dependency("detect_hazards", "query_rules")
    dag.add_dependency("query_rules", "generate_report")

    # 1. 测试正常拓扑全链路执行
    report1 = dag.execute_dag()
    assert report1["detect_hazards"].status == TaskNodeStatus.SUCCESS
    assert report1["query_rules"].status == TaskNodeStatus.SUCCESS
    assert report1["generate_report"].status == TaskNodeStatus.SUCCESS
    assert report1["audit_inspector"].status == TaskNodeStatus.SUCCESS
    assert "生成整改报告" in report1["generate_report"].output_data

    # 2. 测试中途故障级联跳过测试 (上游失败，下游跳过，独立分支照常成功)
    failing_dag = MinimalDAGScheduler()
    def broken_detector(ctx):
        raise RuntimeError("视觉识别网络超时崩溃")

    failing_dag.add_node("detect_hazards", broken_detector)
    failing_dag.add_node("query_rules", lambda ctx: "规程")
    failing_dag.add_node("generate_report", lambda ctx: "报告")
    failing_dag.add_node("audit_inspector", lambda ctx: "资质正常")

    failing_dag.add_dependency("detect_hazards", "query_rules")
    failing_dag.add_dependency("query_rules", "generate_report")

    report2 = failing_dag.execute_dag()
    # 核心级联断言：
    assert report2["detect_hazards"].status == TaskNodeStatus.FAILED
    assert report2["query_rules"].status == TaskNodeStatus.SKIPPED      # 级联跳过！
    assert report2["generate_report"].status == TaskNodeStatus.SKIPPED  # 级联跳过！
    assert report2["audit_inspector"].status == TaskNodeStatus.SUCCESS  # 独立分支不受任何影响！

    # 3. 测试死锁环路检测拦截 (A -> B -> A)
    cyclic_dag = MinimalDAGScheduler()
    cyclic_dag.add_node("A", lambda ctx: 1)
    cyclic_dag.add_node("B", lambda ctx: 2)
    cyclic_dag.add_dependency("A", "B")
    cyclic_dag.add_dependency("B", "A") # 构成环
    try:
        cyclic_dag.execute_dag()
        raise AssertionError("存在环路的图应当抛出 ValueError")
    except ValueError as e:
        assert "死循环环路依赖" in str(e)

    print("✅ 4.9 纯 Python 零依赖轻量 DAG 任务调度引擎自检全部通过！")


if __name__ == "__main__":
    self_test()
```

- 主动说边界与坑：这段代码手撕了 DAG 的单机调度核心。在面对大型复杂工业流水线（如需要持久化恢复）时，必须向面试官展开：每个节点产生的数据应当写入支持版本快照的状态库中；当发生异常时，通过对比哪些节点处于 FAILED，可以仅针对该子图发起轻量级局部重规划（Re-plan），杜绝全盘重跑带来的高昂成本。

### 本节收尾：费曼自述与闪卡

费曼自述：
“DAG 就像工地的施工计划表：必须先打地基（节点1），才能砌墙（节点2），最后才能封顶（节点3）；但工地的电工拉电线（节点4）跟砌墙没关系。如果今天打地基挖出水管漏水停工了（节点1失败），调度员马上通知砌砖队今天别来（下游跳过），但电工照样干自己的活（独立分支不受影响）。最关键的是，排计划表时绝不能出现‘砌墙要等封顶、封顶又要等砌墙’这种画圈圈的脑残计划（环路检测）！”

- Q：什么是拓扑排序（Topological Sort）？它在 Agent 任务编排中解决什么问题？
A：将有向无环图的所有节点排成一个满足因果先后顺序的线性序列，确保每一个任务在被执行时，其所有前置依赖项已经完全执行完毕。

- Q：在任务图执行中，为什么“失败级联跳过（Cascade Skip）”能大幅保护系统稳定性？
A：当上游数据源故障时，下游强行执行必然因缺少入参而抛出空指针或幻觉；级联跳过能立即止损，同时让其他独立的正常分支继续交付价值。

- Q：什么是有向图的 Kahn 算法？它是如何检测出环路死锁的？
A：不断将入度为 0 的节点移入队列并消除其出边；若最终排出的节点数少于图的总节点数，证明剩余节点之间存在相互等待的死循环闭环。
