## 4.10 Planner、Worker、Reviewer：多角色分工、交接契约与返工熔断【◻ 按需】

〔补充自原仓库镜像〕〔本次新补，参考当前面试趋势〕

### 面试官会怎么问

“你们的Multi-Agent为什么要分Planner、Worker、Reviewer？三个角色怎么传递任务，怎么防止Worker越权，Reviewer发现问题后又怎么退回？”

很多录友会回答：

“Planner负责规划，Worker负责执行，Reviewer负责检查。”

这句话方向没错，但还停在角色名字上。

**第一，没有定义交接物。** Planner说“调研一下故障”，Worker不知道查多深、交什么、什么算完成，只能继续猜。

**第二，没有拆开权限。** 三个角色如果共享全部工具，Worker仍然可以改计划，Reviewer也可能一边修改产物、一边给自己判通过。

**第三，没有失败退回路径。** Reviewer只说“不够好”，却不指出哪条验收标准没过，任务就会在多个Agent之间反复踢皮球。

面试官真正想听的是：**每个角色拥有什么决策权，交接的数据结构是什么，谁能调用哪些工具，以及不通过时退回给谁。**

### 目标与例子

目标：掌握多智能体协同（Multi-Agent Collaboration）的经典架构范式（规划-执行-评审），理解多角色分工的工程收益与隐性代价，能手撕具备结构化交接任务包（Task Package）、上下文作用域隔离与最大返工轮次（Max Revision Loops）熔断保护的多角色协作状态机。
例子：针对“编制一份危化品泄漏应急处置预案”的复杂多角色流转：

- Planner（规划者）：拆解出阶段任务包：步骤 1 查泄漏源隔离规范，步骤 2 查防毒护具标准，步骤 3 查疏散警戒半径；

- Worker（执行者）：针对步骤 1 调取规章生成预案初稿；

- Reviewer（审查者）：对照企业国家强制标准进行合规性审计，发现初稿漏掉了“风向标测定要求”，判定审查不通过，给出具体改进意见（Feedback）；

- 返工循环（Revision Loop）：Worker 携带审查者的具体反馈执行二次修订；如果连续返工 2 次依然无法通过，状态机触发硬熔断，安全将任务升级呈报给人类安全总监，坚决不让两个模型在后台互相争论不休。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 用户全局复合目标、各角色的专用 Prompt 与受限工具集、全局最大返工次数上限（如 2 次）。 |
| 做什么 | 规划者制定结构化蓝图 → 执行者专项深耕产出草案 → 审查者基于客观规则验收 → 不合格携带定向反馈回退返工。 |
| 输出 | 最终经严格验收的合规交付物、各角色评审审计流水，或超限移交人工报告。 |
| 哪里出错 | 角色互相推诿争论死循环、上下文全量广播导致严重信息污染与 Token 爆炸、审查者流于形式变成夸夸群。 |
| 重要参数影响 | 最大返工修改次数 max_revisions（生产绝对硬顶，通常设为 1~2 次）、审查通过阈值。 |

#### Multi-Agent 结构化交接流水线

```text
       ┌────────── 用户全局目标 ──────────┐
       │                                │
       ▼                                │
┌──────────────┐                        │
│   Planner    │ ──► 输出结构化任务包     │
│   (规划者)    │     (Task Package)     │
└──────┬───────┘                        │
       │                                │
       ▼                                │
┌──────────────┐                        │
│    Worker    │◄─────────────────┐      │
│   (执行者)    │                  │      │
└──────┬───────┘                  │ 审查未通过，携带具体意见
       │ 提交草案 (Draft)          │ 触发返工 (受 Max Revisions 约束)
       ▼                          │
┌──────────────┐                  │      │
│   Reviewer   │──────────────────┘      │
│   (审查者)    │                        │
└──────┬───────┘                        │
       │                                │
       ├─ 审查通过 ──────────────────────┼──► 【合格交付用户】
       │                                │
       └─ 返工耗尽仍未通过 ───────────────┴──► 【安全移交人工 (Handoff)】
```

### 面试追问

- 【🔥 必会】外企高频架构题：“Multi-Agent（多智能体）架构看起来很美好，但在真实生产落地时最大的‘隐形杀手’是什么？如何治理？”
一句话结论：最大杀手是“角色互相死循环争论”与“上下文爆炸”；必须建立结构化任务包、上下文隔离与返工熔断。
展开原理/取舍：① 无限争论死循环（Infinite Debate Loop）：如果没有设置硬退出条件，Reviewer 指责 Worker 不严谨，Worker 反驳或修改后引入新瑕疵，两个模型能在后台对喷几十轮，烧掉上百美元 Token；② 上下文灾难（Context Blast）：许多框架（如 AutoGen 早期模式）把所有 Agent 发言直接全量广播到一个大聊天室里，导致每个 Agent 的输入上下文呈平方级膨胀，无关信息极度稀释注意力；③ 工程解法：建立结构化任务包（Task Package），角色之间只传递必要的输入出参，严禁共享全量原始对话；设置 max_revisions <= 2，返工超额直接挂起移交人工。

- 【🔥 必会】Reviewer（审查者）角色在设计时，如何防止它退化为“无论执行者写什么都无脑说通过的夸夸群”？
一句话结论：审查者必须与执行者 Prompt 隔离，且必须强制要求其先输出“找茬扣分清单”。
展开原理/取舍：大模型天生具有“顺从性（Sycophancy）偏见”，如果 Prompt 只笼统地写“请审核以下内容”，模型倾向于打出极高分；工业级设计模式：① 批判者人格 Prompt（Adversarial Prompting）：明确赋予其“严格质检员”角色，指令开头强制要求“你的职责是尽全力挑出草案中的至少 1 个事实漏洞与不合规项；只有当你确实找不出任何漏洞时才允许打通过”；② 结构化打分卡（Rubric Scorecard）：提供类似“是否有条款编号、是否有明确责任人、数值是否有单位”等 5 项打勾清单，必须全部勾选才放行。

- 【⭐ 理解】为什么不同 Agent 角色应该分配“最小化受限工具集（Principle of Least Privilege）”？
一句话结论：隔离动作爆炸半径，防止规划者或审查者越权触发底层写操作。
展开原理/取舍：Planner 的职责是宏观思考，它只需要只读的目录概览工具，绝不能给它写数据库的权限；Reviewer 的职责是合规核验，它只需要查看原文规程的只读权限，绝不能给它发送邮件或删除数据的权限；只有具体的某个专项 Worker，才被按需赋予特定的单一写权限。将工具集与角色强绑定，即便某个角色遭受了提示注入，其破坏力也被死死锁在局部沙箱内。

### 故障模式与排障

- 故障模式：执行者与审查者陷入“各说各话”的理解分歧

- 定位：Reviewer 返回的拒批理由是一段含糊的自然语言：“写得不够详细”，Worker 不知道该改哪里，修改后依然被驳回。

- 修复：结构化反馈协议（Structured Feedback Schema）：Reviewer 的输出必须为 JSON：{"approved": false, "missing_elements": ["风向标要求"], "actionable_instructions": "请补充第3章第2条规程"}，确保 Worker 获得极其精准的修正靶向。

- 故障模式：多角色并行执行产生孤儿状态

- 定位：由于网络抖动，某个子 Worker 崩溃退出，主线程陷入无休止等待。

- 修复：在协作总线上配置角色心跳与超时挂起（Per-role Timeout），子角色超过 10 秒无响应立即标记该节点失败，通知 Planner 重构计划。

### 工程 trick 与坑

- 单向信息隐藏（Information Hiding）：Worker 只需要看到当前分配给它的这 1 个小任务包，不需要知道公司全局战略；Reviewer 只需要看到最终草案和标准规程，不需要看到 Worker 中间复杂的工具试错草稿纸，将上下文 Token 消耗降至最低。

- 不同角色选择不同规格的模型：Planner 与 Reviewer 需要极强的逻辑严谨度与长远推演能力，应选用最顶级大模型（如 Claude 3.5 Sonnet / GPT-4o）；而承担繁重重复信息提取的 Worker，可以大量使用低成本的开源小模型（如 Qwen2.5-7B），实现性能与成本的最佳平衡。

### 循序渐进 Toy Code：Level 10 — 多角色协作（规划-执行-审查）与返工熔断状态机

代码难度定位：Level 10（多角色协作与控制流闭环）。纯标准库手写一个具备结构化任务包交接、精准反馈指导、审查门禁与最大返工次数硬熔断的多智能体协同中心。

```python
"""
4.10 Toy Code: Level 10 - 多角色协作 (规划-执行-审查) 与返工熔断状态机
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
from enum import Enum
from typing import Optional


class CollaborationStatus(str, Enum):
    """协作终态枚举"""
    APPROVED_AND_DELIVERED = "DELIVERED"         # 审查合格，正式交付
    ESCALATED_MAX_REVISIONS = "ESCALATED_HUMAN" # 返工次数耗尽，移交人工处理
    PLANNING_FAILED = "PLANNING_FAILED"         # 规划阶段校验不通过


@dataclass(frozen=True)
class TaskPackage:
    """Planner 输出给 Worker 的结构化任务包"""
    task_id: str
    target_goal: str
    mandatory_clauses_needed: tuple[str, ...] # 必须包含的合规采分点


@dataclass(frozen=True)
class WorkDraft:
    """Worker 提交给 Reviewer 的初稿或修改稿"""
    draft_id: str
    content_text: str
    revision_count: int                       # 当前是第几次修改版本


@dataclass(frozen=True)
class ReviewVerdict:
    """Reviewer 输出的结构化审查判决书"""
    is_approved: bool
    missing_points: tuple[str, ...]           # 找出的未达标缺陷清单
    feedback_guidance: Optional[str]          # 具体精准修改指导意见


@dataclass(frozen=True)
class MultiAgentCollaborationReport:
    """多角色协作最终全链路审计报告"""
    final_status: CollaborationStatus
    delivered_content: Optional[str]
    total_revisions_used: int
    full_audit_log: tuple[str, ...]


# 模拟三个专业角色的确定性行为
class MockPlannerAgent:
    """模拟规划者：制定不可篡改的合格验收标准"""
    def plan_task(self, user_goal: str) -> TaskPackage:
        return TaskPackage(
            task_id="TASK_COMPLIANCE_01",
            target_goal=user_goal,
            mandatory_clauses_needed=("佩戴五点式安全带", "挂点双钩互锁", "现场设置警示牌")
        )


class MockWorkerAgent:
    """模拟执行者：根据任务包或审查意见撰写草案"""
    def draft_proposal(self, pkg: TaskPackage, feedback: Optional[str], rev_idx: int) -> WorkDraft:
        if rev_idx == 0:
            # 首次草稿：故意漏掉一项以测试审查者与返工逻辑
            text = "高处作业规程：现场施工人员必须佩戴五点式安全带，且挂点双钩互锁。"
        else:
            # 携带审查意见进行返工修改
            text = "高处作业规程：现场施工人员必须佩戴五点式安全带，挂点双钩互锁，且必须在现场设置警示牌。"
            
        return WorkDraft(
            draft_id=f"DRAFT_REV_{rev_idx}",
            content_text=text,
            revision_count=rev_idx
        )


class MockReviewerAgent:
    """模拟审查者：严格基于采分点进行质检"""
    def review_draft(self, draft: WorkDraft, pkg: TaskPackage) -> ReviewVerdict:
        missing = []
        for point in pkg.mandatory_clauses_needed:
            if point not in draft.content_text:
                missing.append(point)

        if not missing:
            return ReviewVerdict(is_approved=True, missing_points=(), feedback_guidance=None)
        
        guidance = f"驳回修改：当前草案遗漏关键强制项：{missing}，请依据规范立即补齐。"
        return ReviewVerdict(is_approved=False, missing_points=tuple(missing), feedback_guidance=guidance)


class MultiAgentCollaborationHub:
    """多智能体协作中枢：把控角色时序与返工配额"""

    def __init__(self, max_revisions: int = 2):
        if max_revisions < 0:
            raise ValueError("最大返工次数不能为负数")
        self.max_revisions = max_revisions
        self.planner = MockPlannerAgent()
        self.worker = MockWorkerAgent()
        self.reviewer = MockReviewerAgent()

    def run_collaboration(self, user_request: str) -> MultiAgentCollaborationReport:
        """
        驱动 Planner -> Worker -> Reviewer 状态流转
        
        核心不变量保证：
        1. 返工次数严格受限于 max_revisions，绝不发生无限死循环争论
        2. 仅当 Reviewer 给出 is_approved=True 时才允许进入 DELIVERED
        3. 耗尽配额时强制转移至 ESCALATED_HUMAN
        """
        audit_logs: list[str] = [f"收到任务需求: '{user_request}'"]

        # 1. 规划阶段 (Planner)
        task_package = self.planner.plan_task(user_request)
        audit_logs.append(f"Planner 拆解出任务包 [{task_package.task_id}]，采分点={task_package.mandatory_clauses_needed}")

        current_feedback: Optional[str] = None
        current_revision = 0
        final_approved_draft: Optional[WorkDraft] = None

        # 2. 执行与评审循环 (Worker <-> Reviewer)
        while current_revision <= self.max_revisions:
            # 执行者撰写/修订草案
            draft = self.worker.draft_proposal(task_package, current_feedback, current_revision)
            audit_logs.append(f"Worker 提交草案版本 [{draft.draft_id}]")

            # 审查者把关
            verdict = self.reviewer.review_draft(draft, task_package)
            
            if verdict.is_approved:
                audit_logs.append("Reviewer 审查通过：所有强制采分点均已达标，准予正式交付！")
                final_approved_draft = draft
                break
            else:
                audit_logs.append(f"Reviewer 审查未通过：{verdict.feedback_guidance}")
                current_feedback = verdict.feedback_guidance
                current_revision += 1

        # 3. 终态分流处理
        if final_approved_draft is not None:
            return MultiAgentCollaborationReport(
                final_status=CollaborationStatus.APPROVED_AND_DELIVERED,
                delivered_content=final_approved_draft.content_text,
                total_revisions_used=current_revision,
                full_audit_log=tuple(audit_logs)
            )
        else:
            audit_logs.append(f"硬熔断触发：已达到最大返工上限 ({self.max_revisions})，停止自动修改，安全移交人工安全主管。")
            return MultiAgentCollaborationReport(
                final_status=CollaborationStatus.ESCALATED_MAX_REVISIONS,
                delivered_content=None,
                total_revisions_used=current_revision,
                full_audit_log=tuple(audit_logs)
            )


def self_test():
    """测试多角色协作的返工自愈与超额熔断"""
    hub = MultiAgentCollaborationHub(max_revisions=2)

    # 场景 1：经历 1 次返工后成功自愈交付
    report1 = hub.run_collaboration("编制高处作业特种安全防范方案")
    assert report1.final_status == CollaborationStatus.APPROVED_AND_DELIVERED
    assert report1.total_revisions_used == 1 # 第 0 次初稿被拒，第 1 次修改后通过
    assert "警示牌" in report1.delivered_content
    assert any("准予正式交付" in log for log in report1.full_audit_log)

    # 场景 2：设定最大返工次数为 0（严苛模式：初稿不合格直接移交人工）
    strict_hub = MultiAgentCollaborationHub(max_revisions=0)
    report2 = strict_hub.run_collaboration("编制高处作业特种安全防范方案")
    assert report2.final_status == CollaborationStatus.ESCALATED_MAX_REVISIONS
    assert report2.delivered_content is None
    assert any("移交人工安全主管" in log for log in report2.full_audit_log)

    print("✅ 4.10 多角色协作 (规划-执行-审查) 与返工熔断状态机自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个针对多角色编排的协作中枢 MultiAgentCollaborationHub。核心不变量是：角色间采用结构化实体解耦通信，返工尝试次数严格受限于 $0 \le \text{revisions} \le \text{max_revisions}$；未通过审查的产物绝对禁止进入交付态，达到上限必须原子性转移至移交人工状态。

- 关键行解析：在第 93-125 行，我实现了标准的“规划 → 执行 → 质检审查 → 返工自愈”状态转移循环；在第 113-124 行，通过精准的 verdict.feedback_guidance 靶向回传，彻底杜绝了角色漫无目的的自由胡说，在 self_test 中证明了系统在 1 轮内精准自愈，并在超额时秒级触发风控熔断。

- 主动说边界与坑：这段代码诠释了 Multi-Agent 的生产级骨架。在面向外企与大厂高难度架构面试时，必须向面试官展开：在真实落地中，切忌让多个 Agent 在一个共享 Context 里自由开会；生产模式必须践行**“结构化任务包（Task Contract）+ 作用域单向隔离 + 返工硬上限”**，用极小的 Token 代价收获极致的确定性交付质量。

### 本节收尾：费曼自述与闪卡

费曼自述：
“多 Agent 协作就像办报纸：主编（Planner）负责排版选题，记者（Worker）负责去前线采访写稿，校对（Reviewer）拿着放大镜查错别字。校对发现错别字，必须拿红笔圈出来清清楚楚告诉记者怎么改（结构化反馈）。但主编必须定规矩：最多只准改两遍，第三遍还写不好，直接撤稿找老师傅重写（移交人工），绝不准两个人在办公室一直吵到天黑（防止死循环）！”

- Q：为什么在 Multi-Agent 架构中必须对各个角色的输入上下文实施“信息隐藏与隔离”？
A：如果所有角色共享大聊天室，上下文会呈平方级爆炸消耗海量 Token；单向仅传递结构化任务包，既省成本，又能防止无关历史稀释各角色的专业注意力。

- Q：什么是多角色协作中的“返工熔断机制（Max Revision Guard）”？它防止了什么故障？
A：限制执行者与审查者之间的修改循环次数（如最多 2 次）；防止因审查意见分歧导致两个模型在后台无限争论对喷，打崩系统延迟与费用。

- Q：在实际生产中，如何为多角色分配不同能力层级的模型以优化 ROI？
A：由需要高深规划与严密审判的 Planner 和 Reviewer 选用顶尖大模型（如 Claude 3.5 Sonnet / GPT-4o），执行具体重复动作的 Worker 选用低成本的小模型（如 Qwen2.5-7B）。
