## 4.4 ReAct 与工具循环：调用、观察与停止【🔥 必会】

### 一、先别背名词，Agent 本质是一个循环

很多人一上来就背：

“ReAct = Reasoning + Acting。”

这句话没错，但太浅了。

面试官真正想听的不是英文展开，而是你有没有理解 Agent 的运行方式。

一个 Agent 最基本的循环是：

**看到目标 -> 想下一步 -> 调工具 -> 看结果 -> 再想下一步。**

比如用户说：

“帮我查一下最近 7 天订单失败率升高的原因。”

Agent 不能直接瞎猜。

它应该先想：

“我要先看失败率趋势。”

然后调用数据工具。

拿到结果后发现失败率是从周三开始涨的。

它再想：

“那我要查周三有没有发布、支付接口有没有异常、库存服务有没有超时。”

然后继续调用工具。

这就是 Agent 的味道。

不是一次性给答案，而是**每一步都根据上一步结果继续判断。**

所以 ReAct、Reflection、规划执行，本质上都是在回答同一个问题：

**Agent 到底应该怎么推进任务？**

只是推进方式不同。

### 目标与例子

目标：掌握大模型应用工程的核心链路——从零手写 ReAct（Reasoning + Acting）工具调用循环，闭卷讲透 Prompt 装配、工具 Schema 下发、tool_calls 结构化请求解析、参数校验、执行分发、tool_call_id 结果严格配对以及多重防死循环熔断机制。
例子：用户提问“排查 1 号行车起重机的巡检状态，若异常给出处理依据”：

- 第 1 轮：模型发起思考，输出 tool_calls: [{id: "call_01", name: "query_device", args: {"id": 101}}]；

- 环境反馈：宿主程序拦截并执行只读查询，追加工具消息 role: "tool", tool_call_id: "call_01", content: "{status: '超期未检'}"；

- 第 2 轮：模型基于新线索再次思考，发起第二跳调用 tool_calls: [{id: "call_02", name: "get_policy", args: {"topic": "超期未检"}}}]；

- 环境反馈：回传对应法条“超期设备必须立即停止作业并贴封条”；

- 第 3 轮：模型判定证据充足，输出最终自然语言答复并终止循环。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 用户目标 Query、系统 Prompt 规则、已注册的工具 Schema 列表、不可变历史对话上下文。 |
| 做什么 | 构建调用协议 → 触发 LLM 推理 → 拦截并解析工具调用 → 执行工具逻辑 → 依据调用 ID 组装 Observation → 循环更新上下文直至终结。 |
| 输出 | 最终业务答复文本、完整的结构化动作与观察轨迹（Trace），或明确的超限熔断原因。 |
| 哪里出错 | 参数 JSON 损坏或格式错误、tool_call_id 配对错位、相同动作无限震荡死循环、模型输出截断导致状态撕裂。 |
| 重要参数影响 | max_steps 最大步数（通常硬限 3~5 步）、parallel_tool_calls 开关、temperature=0.0（工具调用必须极度稳定）。 |

### 面试追问

- 【🔥 必会】外企/大厂手撕高频题：“请从零手写一个最小的 ReAct 循环，不能依赖 LangChain 等第三方框架，重点讲清消息如何流转。”
一句话结论：维护一个消息列表，把 LLM 吐出的 tool_calls 与工具执行生成的 role='tool' 按 ID 结对追加，循环直到模型输出普通文本。
展开原理/取舍：核心流程分四步：① 构造初始消息数组 [System, User]；② 调模型获取响应，判断 finish_reason：若是 stop 且 content 非空，说明思考结束，跳出循环；③ 若是 tool_calls，先将模型的助手消息原样追加进列表，遍历所有工具调用，在宿主程序执行后生成 {"role": "tool", "tool_call_id": call.id, "content": ...} 追加回列表；④ 带着膨胀后的消息历史重新请求模型。必须手写最大步数熔断器，防止模型进入无限自问自答。

- 【🔥 必会】为什么在现代 OpenAI 兼容接口规范中，工具结果消息必须显式携带 tool_call_id？
一句话结论：为了支持多工具并行调用（Parallel Tool Calls）时的高并发无序异步对齐。
展开原理/取舍：在单步操作中，大模型可能在同一个思考周期内同时发起 3 个独立的工具调用（如同时查天气、查股票、查新闻），产生 3 个带有不同 ID 的 tool_call。在异步网络环境中，这 3 个任务在后台由线程池并发执行，返回的先后顺序是随机的；通过在结果中回传 tool_call_id，模型底层注意力机制能精确将每一个结果与发起时的具体实参进行点对点绑定，避免时序倒挂引发的因果混乱。

- 【⭐ 理解】【排障题】线上 Agent 出现“工具反复调用相同参数陷入死循环”，有哪三道工程防线？
一句话结论：硬步数熔断、连续动作签名哈希去重、空进展主动退出。
展开原理/取舍：① 第一道防线（硬步数截断）：设置 step_count >= max_steps，强行跳出；② 第二道防线（连续动作签名检测）：将每轮调用的 (tool_name, arguments_hash) 维护在一个滑动窗口中，一旦检测到连续两次执行了完全相同名称且完全相同参数的调用（说明上一轮的环境反馈并未帮助模型产生新认知），立即阻断并标记 CYCLE_DETECTED；③ 第三道防线（错误纠偏注入）：在检测到重复时，不立刻中断，而是向模型注入一条系统警告：“你刚才已使用该参数查询过且未取得进展，严禁重复调用，请换用其他工具或直接向用户说明依据不足”。

### 故障模式与排障

- 故障模式：模型返回截断 JSON 导致 json.loads 报错崩溃

- 定位：排查模型的 finish_reason 是否为 "length"。如果是 "length"，说明模型的输出达到了 max_tokens 上限，生成在参数写到一半时被物理腰斩。

- 修复：在解析 arguments 之前先检查 finish_reason；若为 "length"，直接判定为 TRUNCATED_RESPONSE 异常，跳过解析并提示模型重新精炼输出，或适当上调 max_tokens 配额。

- 故障模式：消息历史中存在“孤儿 Tool 消息（Orphan Tool Result）”导致接口报错 400

- 定位：上一轮对话由于超时或网络断开，只把 role='tool' 的结果消息写入了持久化数据库，而发起该调用的 role='assistant' 工具调用消息丢失了。

- 修复：严格实行原子批处理追加（Atomic Append）：必须将 Assistant 消息与它所触发的全部 Tool 结果作为一组事务（Transaction）原子写入历史，任何一个失败整组回滚。

### 工程 trick 与坑

- parallel_tool_calls 的谨慎开启：如果业务工具具有前后因果依赖（例如必须先创建订单拿订单号，再调支付接口），在请求模型时必须显式设置 parallel_tool_calls=False，强制模型一步一步串行思考，杜绝并发调用产生的依赖空指针异常。

- 工具结果大小安全截断：工具返回的文本必须经过 content[:max_tool_chars] 强截断防护（如限制在 2000 字符以内），严禁将万字原始日志未经摘要直接抛进消息历史中。

### 循序渐进 Toy Code：Level 4 — 纯 Python 手撕可终止的 ReAct 循环内核

代码难度定位：Level 4（核心链路必手撕点）。不使用 LangChain 等外部重型框架，纯 Python 从零手撕一个带参数安全反序列化、调用 ID 配对、连续动作哈希防震荡与最大轮次熔断的 ReAct 工具循环引擎。

```python
"""
4.4 Toy Code: Level 4 - 纯 Python 手撕可终止的 ReAct 循环引擎
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
import hashlib
import json
from typing import Any, Protocol


# 1. 规范化数据结构定义 (遵循标准 Chat Completions 协议)
@dataclass(frozen=True)
class ToolCallObject:
    """模型输出的单条工具调用对象"""
    call_id: str
    function_name: str
    arguments_json_str: str


@dataclass(frozen=True)
class ModelCompletionChoice:
    """模拟大模型单次前向输出的 Choice 结构"""
    finish_reason: str              # 'stop' | 'tool_calls' | 'length'
    content: str | None             # 普通自然语言输出
    tool_calls: list[ToolCallObject] | None # 工具调用列表


@dataclass(frozen=True)
class ReActExecutionReport:
    """循环执行终态报告"""
    status: str                     # 'FINISHED' | 'MAX_STEPS_REACHED' | 'CYCLE_DETECTED' | 'TRUNCATED'
    final_answer: str
    total_iterations: int
    full_message_history: list[dict[str, Any]]


# 2. 模拟外部受控工具实现
def execute_mock_tool(name: str, arguments: dict[str, Any]) -> str:
    """实际执行工具逻辑，返回字符串形式的 Observation"""
    if name == "query_safety_standard":
        topic = arguments.get("topic", "")
        if "高处" in topic:
            return json.dumps({"found": True, "clause": "高处作业人员必须佩戴全身式五点安全带，挂点需高于作业面。"})
        return json.dumps({"found": False, "clause": None})
    return json.dumps({"error": f"未知工具: {name}"})


class FakeLLMClient:
    """可配置的确定性模拟大模型（用于无网离线闭环自检）"""
    def __init__(self, scripted_responses: list[ModelCompletionChoice]):
        self._responses = list(scripted_responses)

    def generate_chat_completion(self, messages: list[dict[str, Any]]) -> ModelCompletionChoice:
        if not self._responses:
            raise RuntimeError("模拟大模型响应队列已耗尽")
        return self._responses.pop(0)


# 3. 核心手撕：ReAct 循环调度引擎
def run_minimal_react_loop(
    llm_client: FakeLLMClient,
    user_query: str,
    max_iterations: int = 3
) -> ReActExecutionReport:
    """
    从零手撕 ReAct 循环内核
    
    不变量保证：
    1. 历史消息列表保持严格的时序交替 (User -> Assistant[tool_calls] -> Tool[id] -> Assistant)
    2. 循环迭代次数严格满足 1 <= iterations <= max_iterations
    3. 严密拦截连续相同动作的死循环震荡
    """
    if not user_query.strip():
        raise ValueError("用户提问不能为空")
    if max_iterations <= 0:
        raise ValueError("max_iterations 必须为正整数")

    # 初始化上下文
    messages: list[dict[str, Any]] = [
        {"role": "system", "content": "你是一个安全合规专家。回答问题前必须通过工具核查规程。"},
        {"role": "user", "content": user_query.strip()}
    ]

    action_signatures_history: list[str] = []

    for iteration in range(1, max_iterations + 1):
        # 步骤 1：触发大模型单步推理
        response_choice = llm_client.generate_chat_completion(messages)

        # 异常截断防御
        if response_choice.finish_reason == "length":
            return ReActExecutionReport(
                status="TRUNCATED",
                final_answer="生成被物理截断，超出模型最大输出长度限制。",
                total_iterations=iteration,
                full_message_history=messages
            )

        # 步骤 2：判断是否已经推导出最终自然语言答案 (完成态)
        if response_choice.finish_reason == "stop" or not response_choice.tool_calls:
            final_text = response_choice.content or ""
            # 将最终答案存入历史
            messages.append({"role": "assistant", "content": final_text})
            return ReActExecutionReport(
                status="FINISHED",
                final_answer=final_text,
                total_iterations=iteration,
                full_message_history=messages
            )

        # 步骤 3：处理工具调用请求 (tool_calls 分支)
        assert response_choice.finish_reason == "tool_calls"
        assert response_choice.tool_calls is not None

        # 将 Assistant 的工具发起意图先记入上下文（必须按标准格式包含 tool_calls）
        assistant_msg_repr: dict[str, Any] = {
            "role": "assistant",
            "content": response_choice.content,
            "tool_calls": [
                {
                    "id": tc.call_id,
                    "type": "function",
                    "function": {"name": tc.function_name, "arguments": tc.arguments_json_str}
                }
                for tc in response_choice.tool_calls
            ]
        }
        messages.append(assistant_msg_repr)

        # 步骤 4：依次执行每一个工具并严格绑定 tool_call_id
        for tc in response_choice.tool_calls:
            # 死循环震荡检测：计算 (tool_name, arguments) 规范化哈希
            sig = f"{tc.function_name}::{tc.arguments_json_str.strip()}"
            sig_hash = hashlib.md5(sig.encode("utf-8")).hexdigest()
            
            # 若连续两次动作完全相同，立即熔断
            if len(action_signatures_history) >= 1 and action_signatures_history[-1] == sig_hash:
                return ReActExecutionReport(
                    status="CYCLE_DETECTED",
                    final_answer="检测到模型陷入相同工具参数的死循环震荡，安全熔断中断。",
                    total_iterations=iteration,
                    full_message_history=messages
                )
            action_signatures_history.append(sig_hash)

            # 解析参数
            try:
                parsed_args = json.loads(tc.arguments_json_str)
            except json.JSONDecodeError:
                observation_str = json.dumps({"error": "参数 JSON 反序列化失败"})
            else:
                observation_str = execute_mock_tool(tc.function_name, parsed_args)

            # 核心不变量：将环境反馈以 role='tool' 且附带对应 tool_call_id 注入历史
            messages.append({
                "role": "tool",
                "tool_call_id": tc.call_id,
                "content": observation_str
            })

    # 步数上限硬熔断
    return ReActExecutionReport(
        status="MAX_STEPS_REACHED",
        final_answer="达到最大迭代轮次，任务未能在限额内完成。",
        total_iterations=max_iterations,
        full_message_history=messages
    )


def self_test():
    """测试 ReAct 循环内核在正常收敛、死循环与异常截断场景下的行为"""
    # 场景 1：两轮顺利收敛 (Query -> ToolCall -> ToolResult -> FinalAnswer)
    normal_responses = [
        # 第 1 步：模型发起查询
        ModelCompletionChoice(
            finish_reason="tool_calls",
            content=None,
            tool_calls=[ToolCallObject("call_001", "query_safety_standard", '{"topic": "高处作业"}')]
        ),
        # 第 2 步：拿到证据后，模型直接给出最终答案并 stop
        ModelCompletionChoice(
            finish_reason="stop",
            content="经查，高处作业人员必须佩戴全身式五点安全带，挂点需高于作业面。",
            tool_calls=None
        )
    ]
    client1 = FakeLLMClient(normal_responses)
    report1 = run_minimal_react_loop(client1, "高处作业有什么要求？", max_iterations=3)
    
    assert report1.status == "FINISHED"
    assert report1.total_iterations == 2
    assert "全身式五点安全带" in report1.final_answer
    # 验证上下文时序：System, User, Assistant(tool_calls), Tool(obs), Assistant(final)
    assert len(report1.full_message_history) == 5
    assert report1.full_message_history[3]["role"] == "tool"
    assert report1.full_message_history[3]["tool_call_id"] == "call_001"

    # 场景 2：死循环震荡拦截（连续两次发起一模一样的调用）
    looping_responses = [
        ModelCompletionChoice(
            finish_reason="tool_calls",
            content=None,
            tool_calls=[ToolCallObject("c1", "query_safety_standard", '{"topic": "高处"}')]
        ),
        ModelCompletionChoice(
            finish_reason="tool_calls",
            content=None,
            tool_calls=[ToolCallObject("c2", "query_safety_standard", '{"topic": "高处"}')] # 完全相同的调用！
        )
    ]
    client2 = FakeLLMClient(looping_responses)
    report2 = run_minimal_react_loop(client2, "高处作业要求", max_iterations=3)
    assert report2.status == "CYCLE_DETECTED"
    assert "死循环震荡" in report2.final_answer

    # 场景 3：物理长度超限截断
    truncated_response = [
        ModelCompletionChoice(finish_reason="length", content=None, tool_calls=None)
    ]
    client3 = FakeLLMClient(truncated_response)
    report3 = run_minimal_react_loop(client3, "长文本提问", max_iterations=3)
    assert report3.status == "TRUNCATED"

    print("✅ 4.4 纯 Python 手撕可终止 ReAct 循环内核自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我从零手撕了一个遵循 Chat Completions 协议的 run_minimal_react_loop 内核。核心不变量是：上下文消息历史严格满足 [System, User, (Assistant_ToolCalls, Tool_Result)*, Assistant_Final] 的交替因果拓扑；每一个工具结果必须与上游发起的 call_id 严格同构；循环必然且仅能在 4 种确定性终态中跳出。

- 关键行解析：在第 85-103 行，我优先判断模型的 finish_reason == 'stop'，一旦模型得出结论立即释放并退出；在第 110-145 行，实现了针对 tool_calls 的安全反序列化与调用分发，并在第 130-136 行设计了动作签名哈希对比，在两次执行同一调用时就地熔断，彻底阻断了模型震荡死循环。

- 主动说边界与坑：这段代码手撕了核心调度逻辑。在工业界对接 OpenAI、Claude 或 DeepSeek 生产 API 时，必须主动向面试官展开两点工程细节：① 必须将 temperature 设为 0，防止工具参数采样漂移；② 实际服务中需要对并发多工具（Parallel Tool Calls）进行并行协程加速（如 asyncio.gather），在返回时保持 tool_call_id 的精准配对。

### 调库选型：手写循环 vs 调高层库（LangChain AgentExecutor）

- 为什么外企和大厂应用岗倾向于手写循环而非调库？
LangChain 的 AgentExecutor 或 LlamaIndex 的 Agent Runner 内部封装了多层复杂的抽象链条，导致在发生超时、模型吐出畸形 JSON、需要精细化重试或做 Token 级截断时，开发者根本无法打断点精细介入；手写上述百行循环内核，不仅零额外依赖、轻量可控，而且能随时在每一步插入内部系统的审计 Trace、超时拦截与状态快照（Checkpoint）。

### 本节收尾：费曼自述与闪卡

费曼自述：
“ReAct 循环就像侦探查案：先在心里盘算‘我得去查一下档案’（思考），然后给助手下指令‘把 1 号档案拿给我’（动作）；助手把档案递过来（观察），侦探看完档案再琢磨下一步该去哪里。如果连续两次拿同一份档案看（死循环），助手必须马上拍醒他；如果翻了三遍卷宗还没头绪（达到最大步数），就必须停下来向法官报告查不出来，绝对不能闭着眼睛瞎编凶手！”

- Q：ReAct 范式中的“思考（Reasoning）”与“动作（Acting）”是如何交替进行的？
A：模型首先在内部自回归生成中推演出下一步动作（Thought + ToolCall），环境执行后将真实世界反馈作为输入喂回给模型，模型结合新输入进入下一轮思考，形成闭环。

- Q：为什么在工具调用循环中，必须把模型的 Assistant 消息先存入上下文，才能追加 Tool 消息？
A：因为接口规范要求因果严谨：必须先有“模型发出了带有 call_id 的调用请求”，后面才能合法跟随“带有相同 call_id 的执行结果”，否则服务端校验将直接判定为孤儿结果报错 400。

- Q：在手写 ReAct 循环时，如何从底层防止模型因为找不到答案而一直调用工具？
A：设置硬步数上限（Max Iterations）、维护动作签名哈希列表（拦截连续相同动作）、在 Prompt 中明确规定“找不到证据时必须回答依据不足”。
