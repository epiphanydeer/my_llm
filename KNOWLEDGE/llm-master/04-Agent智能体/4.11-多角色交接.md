## 4.11 多角色交接：最小信息契约、字段投影与上下文隔离【◻ 按需】

〔补充自原仓库镜像〕〔本次新补，参考当前面试趋势〕

### 面试官会怎么问

“你们多个Agent之间怎么传上下文？并行消息怎么保证不乱序？子Agent还能创建子Agent时，怎么防止Token爆掉？”

很多录友会回答：

“主Agent把历史发给子Agent，子Agent完成后把结果传回来；上下文太长就做摘要，Token超了就停止。”

这个回答的问题很具体。

**第一，完整复制历史会把角色污染掉。** Worker会看到与当前任务无关的讨论、其他Worker的猜测和过期工具结果，不仅浪费Token，还可能把未经验证的内容当成事实。

**第二，按返回时间拼消息会破坏因果。** 并行任务谁先完成只代表谁更快，不代表它应该先被消费。重试还可能把同一结果送两遍。

**第三，超限后才停止已经太晚。** 多个子Agent并发执行时，如果没有预留和原子扣减，每个Agent都以为预算还有剩余，总消耗很容易一起穿透上限。

面试官真正想听的是：**上下文怎样隔离和按需组装，事件怎样标识因果与幂等，预算怎样分配、回收、降级和熔断。**

### 目标与例子

目标：掌握在复杂多智能体协同（Multi-Agent System）中实施“数据最小化（Data Minimization）”与“上下文作用域隔离（Context Scoping）”的工程治理规范，能手撕基于结构化字段白名单投影（Field Projection）、敏感元数据物理剥离与严格预算配额的跨角色交接路由代理。
例子：在“车间特种设备违规隐患排查”任务中，主任务记录包含了：① 用户提问；② 现场证据切片；③ 执行者撰写的整改报告草案；④ 企业内部对该巡检员的绩效负面考核备注（机密敏感信息）。

- 错误的广播交接（全量 Context 广播）：将这 4 项内容打包成一个大字典，直接广播给所有的 Worker 和 Reviewer。不仅 Reviewer 的输入上下文暴增消耗数倍 Token，更严重的是模型的注意力被内部考核备注所吸引，在生成的审查意见中甚至不慎泄露了内部敏感隐私，造成重大数据安全违规；

- 工业级最小信息交接：通过字段投影路由器进行精准白名单剪裁：发给 Planner 的仅有 (task_id, question)；发给 Worker 的仅有 (task_id, question, evidence)；发给 Reviewer 的仅有 (task_id, question, evidence, draft)；内部敏感备注从内存结构层面被物理剥离，既保护数据隐私，又让每个角色保持极致的注意力聚焦。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 包含全量上下文的主任务记录对象、目标接收角色标识（Recipient Role）、单次交接的字符/Token 预算上限。 |
| 做什么 | 基于预定义的接收角色权限白名单实施字段投影映射，剔除私有与敏感字段；核算交付物尺寸，超限时触发阻断。 |
| 输出 | 裁剪后专供目标角色消费的受控任务数据包（Scoped Task Payload），以及交接审计日志。 |
| 哪里出错 | 白名单缺失导致敏感数据向第三方模型泄露、剪裁过狠丢掉关键约束导致审查误判、超限后静默截断造成数据断头。 |
| 重要参数影响 | 字段白名单字典 ALLOWED_PROJECTIONS、最大交接字符/Token 预算 max_payload_chars。 |

#### 多角色信息隔离与投影流转矩阵

```text
               ┌────────────────────────────────────────────────────────┐
               │        全量主任务数据总线 (Master Task Record)          │
               │  [task_id, question, evidence, draft, internal_notes]  │
               └───────────────────────────┬────────────────────────────┘
                                           │
                         ┌─────────────────┴─────────────────┐
                         ▼                                   ▼
          【字段投影：Planner 白名单】          【字段投影：Worker 白名单】
          - task_id                           - task_id
          - question                          - question
          (去除所有具体证据与敏感备注)           - evidence

                         │                                   │
                         ▼                                   ▼
                  ┌──────────────┐                    ┌──────────────┐
                  │ Planner 节点 │                    │  Worker 节点 │
                  └──────────────┘                    └──────────────┘
```

### 面试追问

- 【🔥 必会】外企/大厂面试常问：在构建多 Agent 系统时，为什么坚决反对把全局对话历史广播给所有 Agent？
一句话结论：全局广播会导致上下文复杂度呈 $O(N^2)$ 指数级膨胀，稀释模型注意力并引入严重的数据泄漏风险。
展开原理/取舍：如果系统有 4 个 Agent，每个 Agent 产生 1000 Token 的思考草稿；若全量广播，每个 Agent 在第 4 轮时都要吃下其他所有人前面的所有废话，单次会话将消耗数万 Token，端到端延迟直接被拉长到数秒；更严重的是，Agent-A 的某句错误的假设推论会被 Agent-B 误当作客观事实继续推演，形成“多 Agent 幻觉共振”。正确的工程范式是“单向依赖、按需投影、信息隐藏”。

- 【🔥 必会】如果交接的数据包超出了目标 Agent 的接收预算上限，应该直接截断末尾还是报错阻断？
一句话结论：必须直接报错阻断或触发结构化摘要，严禁盲目静默截断末尾。
展开原理/取舍：静默截断是生产系统中最隐蔽的 Bug 源头之一。若直接对文本切片截断，往往把最重要的结论句、免责声明或代码后半段的括号直接切掉；目标 Agent 收到残缺数据后，无法感知自己拿到的是残卷，仍然会自信地推导，导致灾难性幻觉。正确做法是 Fail-fast 报错中断，倒逼上游进行结构化蒸馏或分批次交接。

- 【⭐ 理解】【排障题】Reviewer 经常把 Worker 的正确方案误判为违规，排查发现是交接裁剪导致的，怎么治理？
一句话结论：确立“审核所需最小充要条件清单（Sufficient Checklist）”，建立交接数据完整性契约。
展开原理/取舍：数据最小化不能走向另一个极端——过度剪裁。Reviewer 进行合规判断时，不仅需要看草案本身，还必须看到草案所依据的原始条文与特殊工况参数；如果投影白名单只给了 (question, draft) 而漏掉了 evidence_text，审查者因为缺乏事实对照依据，必然发生大量误判。必须通过编写单元测试，对每个角色的输入契约定义前置断言。

### 故障模式与排障

- 故障模式：内部机密或个人隐私（PII）泄露到第三方模型服务商

- 定位：未做显式字段白名单投影，直接使用了 dataclasses.asdict() 将整个 Python 内存对象直接 dump 成 JSON 发给了云端 API。

- 修复：采用显式白名单投影（Explicit Whitelist Projection）：严禁使用黑名单过滤，每一项允许透传的字段必须在字典中逐个枚举，未在白名单中的字段一律物理丢弃。

- 故障模式：多角色交接中出现“字段名称漂移（Field Renaming Drift）”

- 定位：Worker 吐出的字段叫 rectification_plan，而 Reviewer 的输入 Schema 期待的字段叫 draft_plan，导致审查者认为草稿为空。

- 修复：使用统一的强类型 Data Class 作为跨角色数据交换总线（Data Bus），跨角色传递时禁止随意重命名字段。

### 工程 trick 与坑

- 深度不可变拷贝（Deep Immutability）：在将主任务记录投影给下游 Agent 时，必须确保返回的是不可变的深拷贝或不可变结构（tuple / MappingProxyType），防止下游某个 Agent 恶意修改字典中的全局变量，污染上游的主数据总线。

- 动态预算分配：根据目标任务难度动态调整交接预算。若任务涉及复杂的法律合同比对，向 Reviewer 倾斜 70% 的 Token 配额；若仅为简单意图路由，压缩至 500 字符以内。

### 循序渐进 Toy Code：Level 11 — 跨角色受控字段投影与最小信息交接路由代理

代码难度定位：Level 11（上下文治理与数据安全）。纯标准库手写一个带角色白名单严格投影、敏感内部私有字段物理剥离、交接预算超限拦截与强类型数据契约的交接中枢。

```python
"""
4.11 Toy Code: Level 11 - 跨角色受控字段投影与最小信息交接路由代理
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
from typing import Any, Optional


@dataclass(frozen=True)
class MasterSafetyTaskRecord:
    """企业工单全量主数据总线（包含公共业务字段与内部机密元数据）"""
    task_id: str
    user_question: str
    target_equipment_id: int
    retrieved_safety_clause: str
    worker_generated_draft: str
    internal_safety_inspector_memo: str # 内部员工敏感备忘录（绝对严禁外泄！）


# 严格的角色投影字段白名单（严禁任何黑名单机制）
ROLE_FIELD_PROJECTION_WHITELIST: dict[str, tuple[str, ...]] = {
    # 规划者仅需要宏观意图与设备编号
    "planner": ("task_id", "user_question", "target_equipment_id"),
    # 执行者需要具体规程以撰写报告，无需敏感内部备忘录
    "worker": ("task_id", "user_question", "target_equipment_id", "retrieved_safety_clause"),
    # 审查者需要对照规程核查草案，无需敏感内部备忘录
    "reviewer": ("task_id", "user_question", "retrieved_safety_clause", "worker_generated_draft"),
}


@dataclass(frozen=True)
class ScopedHandoffPayload:
    """完成投影后的受控交付物包"""
    recipient_role: str
    projected_data: dict[str, Any]
    total_payload_chars: int


class MultiAgentHandoffRouter:
    """多角色最小信息交接路由代理"""

    def __init__(self, max_payload_chars: int = 500):
        if max_payload_chars <= 0:
            raise ValueError("交接配额 max_payload_chars 必须为正整数")
        self.max_payload_chars = max_payload_chars

    def route_to_role(
        self,
        record: MasterSafetyTaskRecord,
        recipient_role: str
    ) -> ScopedHandoffPayload:
        """
        根据接收角色身份，执行不可逆的字段白名单安全投影
        
        核心不变量保证：
        1. 仅允许白名单显式注册的字段流向目标角色
        2. 内部机密字段 'internal_safety_inspector_memo' 在任何角色下必须被 100% 物理剥离
        3. 投影后的数据包尺寸绝不超出 max_payload_chars
        """
        role_key = recipient_role.strip().lower()
        if role_key not in ROLE_FIELD_PROJECTION_WHITELIST:
            raise ValueError(f"未登记的未知接收角色: '{recipient_role}'")

        allowed_fields = ROLE_FIELD_PROJECTION_WHITELIST[role_key]
        projected: dict[str, Any] = {}
        total_chars = 0

        for field_name in allowed_fields:
            if not hasattr(record, field_name):
                raise ValueError(f"主数据总线中缺失预期字段: '{field_name}'")
            
            field_val = getattr(record, field_name)
            # 基础非空校验
            if isinstance(field_val, str) and not field_val.strip():
                raise ValueError(f"交接字段 '{field_name}' 内容为空，阻断不完整交接")

            projected[field_name] = field_val
            total_chars += len(str(field_val))

        # 核心安全断言：机密字段必须彻底消失
        assert "internal_safety_inspector_memo" not in projected, "严重数据泄露漏洞：机密备忘录被泄露至交接包！"
        assert set(projected.keys()) == set(allowed_fields)

        # 预算硬门禁检查
        if total_chars > self.max_payload_chars:
            raise ValueError(
                f"交接阻断：向角色 [{recipient_role}] 发送的数据总尺寸 ({total_chars} 字符) "
                f"超出了安全配额 ({self.max_payload_chars} 字符)，拒绝静默截断！"
            )

        return ScopedHandoffPayload(
            recipient_role=role_key,
            projected_data=projected,
            total_payload_chars=total_chars
        )


def self_test():
    """测试多角色最小信息投影的隔离有效性与超限保护"""
    master_record = MasterSafetyTaskRecord(
        task_id="TASK_2026_099",
        user_question="2号配电箱复查要求",
        target_equipment_id=102,
        retrieved_safety_clause="必须由双人操作，一人监护一人作业，穿戴绝缘鞋。",
        worker_generated_draft="整改措施：指派张三单人完成合闸测试。", # 明显不合规草案
        internal_safety_inspector_memo="【机密】该工段近期发生过触电险情，责任人已被行政记过。"
    )

    router = MultiAgentHandoffRouter(max_payload_chars=300)

    # 1. 验证 Planner 视角：仅拿到任务和设备 ID
    planner_pkg = router.route_to_role(master_record, "planner")
    assert planner_pkg.recipient_role == "planner"
    assert set(planner_pkg.projected_data.keys()) == {"task_id", "user_question", "target_equipment_id"}
    assert "retrieved_safety_clause" not in planner_pkg.projected_data

    # 2. 验证 Reviewer 视角：拿到了规程和草案，但绝拿不到内部记过备忘录！
    reviewer_pkg = router.route_to_role(master_record, "reviewer")
    assert reviewer_pkg.recipient_role == "reviewer"
    assert "retrieved_safety_clause" in reviewer_pkg.projected_data
    assert "worker_generated_draft" in reviewer_pkg.projected_data
    # 核心安全断言：机密字段物理隔离
    assert "internal_safety_inspector_memo" not in reviewer_pkg.projected_data
    assert "行政记过" not in str(reviewer_pkg.projected_data)

    # 3. 验证超限预算拦截（拒绝静默截断）
    tiny_router = MultiAgentHandoffRouter(max_payload_chars=30)
    try:
        tiny_router.route_to_role(master_record, "reviewer")
        raise AssertionError("超限数据包必须抛出 ValueError 阻断")
    except ValueError as e:
        assert "超出了安全配额" in str(e)

    # 4. 验证非法未定义角色拦截
    try:
        router.route_to_role(master_record, "hacker_spy_role")
        raise AssertionError("未知角色应被拦截")
    except ValueError as e:
        assert "未登记的未知接收角色" in str(e)

    print("✅ 4.11 跨角色受控字段投影与最小信息交接路由代理自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个遵循数据最小化原则的交接代理 MultiAgentHandoffRouter。核心不变量是：每一个目标接收角色仅能且必须仅能获得 ROLE_FIELD_PROJECTION_WHITELIST 中注册的同构属性集合；私有敏感情报（如内部考评记录）在物理内存层面保证绝不出圈；交接总尺寸严格受限于 max_payload_chars。

- 关键行解析：在第 65-85 行，我实现了基于属性反射的白名单投影机制，并在第 88 行设置了硬安全断言 assert 'internal_safety_inspector_memo' not in projected；在第 92-97 行，当数据包超出预算时坚决执行 Fail-fast 阻断并告警，彻底根除了由于盲目截断导致下游 Reviewer 误判的重大缺陷。

- 主动说边界与坑：这段代码演示的是进程内的上下文作用域隔离。在企业多微服务 Agent 编排（如通过 gRPC / REST 通信）时，必须向面试官展开：在传输层还需对输出的 JSON 进行 PII 脱敏过滤（如自动掩码身份证、手机号），并配合 OpenTelemetry 记录跨角色数据流转的 SHA-256 审计指纹，满足金融与工业级数据合规（GDPR/等保三级）要求。

### 本节收尾：费曼自述与闪卡

费曼自述：
“多 Agent 协作就像不同部门交接公文包：给前线施工队（Worker）看的文件，只要把图纸和标准装进去就行，千万别把公司领导对工长的内部背调私信（机密备忘录）也一股脑塞进去。发公文包必须严格按工种列清单（字段白名单），多装一张纸都算泄密；公文包装太满拉不上拉链（超出预算），必须停下来重新精简，绝对不能把文件生生剪成两半硬塞过去！”

- Q：为什么在多 Agent 系统中，字段白名单投影（Whitelist）显著优于黑名单过滤（Blacklist）？
A：黑名单机制容易因业务新加了私有字段而发生遗漏；显式白名单遵循“零信任默认拒绝”原则，只有经过明确安全审计的字段才被允许流向下游角色。

- Q：当交接数据超出预算时，为什么“拒绝静默截断”是至关重要的工程防线？
A：静默截断会破坏文本与代码的语义闭包，导致接收方 Agent 在不知情的情况下依据残缺上下文做出严重错误的推断；报错阻断能倒逼系统执行安全的语义摘要。

- Q：实施上下文隔离（Context Scoping）对大模型注意力聚焦有什么显著收益？
A：剥离与当前任务无关的宏观背景或中间草稿，能极大提升注意力信噪比，避免模型受远端不相关 Token 误导产生幻觉，同时将单次推理 Token 账单减少 40%~70%。
