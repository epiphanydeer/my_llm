### 一、为什么 Agent 评估比普通问答难

普通大模型问答的评估，通常是这样：

用户问一个问题。

模型给一个答案。

然后看答案是否正确、是否完整、是否符合格式。

但 Agent 多了很多中间环节。

比如用户说：

“帮我分析这个仓库为什么启动慢，并给优化建议。”

Agent 可能要：

1. 读取项目目录。
2. 找启动入口。
3. 查看配置文件。
4. 搜索初始化逻辑。
5. 查慢日志。
6. 总结可能原因。
7. 给出优化优先级。

这里面每一步都可能出问题。

它可能目录读错。

它可能搜错关键词。

它可能把测试配置当成生产配置。

它可能工具失败后继续硬编。

它可能只看了一个模块，就开始总结全局问题。

所以 Agent 评估至少要回答四个问题：

**第一，最终任务完成了吗？**

也就是用户目标有没有达成。

**第二，中间过程靠谱吗？**

有没有乱调用工具、重复调用、越权调用、忽略失败。

**第三，成本和效率怎么样？**

同样的任务，是 5 步完成，还是绕了 30 步。

**第四，失败时能不能收住？**

缺参数、工具超时、权限不足时，是追问和停止，还是继续瞎猜。

这就是为什么 Agent 评估不能只看“答案像不像”。

**要看结果，也要看轨迹。**

### 目标与例子

目标：掌握自主智能体（Agent）的离线轨迹回放（Trajectory Replay）与量化评测体系，建立“任务终态结果指标”与“执行过程效率指标”双轮度量模型，能手撕计算任务完成率（Success Rate / Pass@1）、步骤效率（Step Efficiency）、无效工具调用率（Invalid Tool Ratio）以及失败根因归类直方图。
例子：评估 50 条“特种设备安全合规审查”自动化任务：

- 低水平评估：“我们调了大模型当裁判，模型说 90% 的回答语言通顺、格式很专业。”（只看表面文本流畅度，无法反映工具调用是否冗余、数据库是否真正落盘）；

- 工业级全生命周期评测：
① 终态结果：任务完成率 = 76%（38/50 条任务真正完成了符合预期的状态更新）；
② 步骤效率：成功任务的平均调用步数 = 2.4 步（衡量规划效率，剔除绕弯路）；
③ 工具调用质量：无效工具调用率 = 6.5%（参数反序列化失败或调用未知工具的占比）；
④ 失败归因：在 12 条失败用例中，4 条源于步数超限熔断（死循环）、5 条源于权限不足拦截、3 条源于下游系统超时。

#### Agent 核心评测指标公式全景

| 指标维度 | 考察核心 | 数学定义 | 生产参考达标线 |
| --- | --- | --- | --- |
| 任务完成率 (Task Success Rate) | 目标最终是否真正达成（客观断言） | $\frac{\text{成功完成任务数}}{\text{总评测任务数}}$ | 垂直生产任务通常要求 $\ge 85%$ |
| 步骤效率 (Step Efficiency) | 解决问题是否简洁高效、有无绕圈子 | $\frac{\text{成功任务消耗的总工具步数}}{\text{成功任务总数}}$ | 简单任务 $\le 2.0$，复杂任务 $\le 4.0$ |
| 无效工具调用率 (Tool Error Rate) | 模型理解和使用工具的能力 | $\frac{\text{抛出 Schema 或未登录错误的调用数}}{\text{全量工具调用总数}}$ | 严控在 $\le 5%$ 以下 |
| 单任务平均成本 (Cost per Task) | 商业落地经济性 | $\frac{\text{所有尝试消耗的总 Token 费用}}{\text{总评测任务数}}$ | 需建立严格版本预算基线 |

### 面试追问

- 【🔥 必会】外企高频系统题：“如何客观评测一个工具型 Agent 的真实能力？为什么不能直接套用聊天机器人的 BLEU 或 ROUGE 评测？”
一句话结论：Agent 的本质是产生外部世界的状态变化，评测必须看环境最终状态断言，而非字面相似度。
展开原理/取舍：传统文本评测（如 BLEU/ROUGE）只比对自然语言文本重合度，但 Agent 的核心使命是“完成操作”（如发邮件、查单据、改状态）。评测 Agent 必须引入基于测试环境沙箱的环境终态比对（Environment State Assertion）：检查数据库里的记录是否真正被插入、邮件是否真实发出、入参是否准确；过程层面还要审计 Trace 轨迹中是否存在多余的试错调用，只有“状态达标 + 路径合理”才算真正成功。

- 【🔥 必会】为什么在计算“无效工具调用率（Invalid Tool Rate）”时，分母必须是“工具调用总数”而不是“任务总数”？
一句话结论：分母必须对应具体度量事件的物理发生载体，否则指标失去数学意义。
展开原理/取舍：一个复杂的排查任务可能触发了 10 次工具调用，其中有 1 次参数拼写错误触发重试，随后自愈成功；如果分母除以任务总数（1），会得出“100% 任务发生错误”的误导性结论，掩盖了该任务 90% 调用完全健康的真实情况；将分母严格锚定为调用事件总数（$\sum \text{Calls}$），才能精确衡量模型在微观原子动作层面的 Schema 遵循准确度。

- 【⭐ 理解】【排障题】新模型升级后，Agent 任务成功率提升了 10%，但单月 Token 账单暴涨了 3 倍，该怎么定位？
一句话结论：排查模型是否通过“冗余暴力试错”刷高了完成率，监控步骤效率（Step Efficiency）指标。
展开原理/取舍：有些大模型由于推理策略更保守，在找不到答案时会疯狂调用 5~6 个无关工具四处探索，最终碰巧在第 7 步撞上正确答案；虽然任务完成率看似上升了，但单任务的平均步数从 2.0 飙升到了 6.5，且伴随大量冗长的上下文膨胀导致 Token 费用失控。治理方案：在评测中引入惩罚性步数预算（Step Penalty）：只将步数小于等于上限（如 3 步以内）的成功算入“高质量完成率（Efficient Success Rate）”。

### 故障模式与排障

- 故障模式：评测集出现“测试泄漏（Data Contamination）”导致指标虚高

- 定位：评测集里的任务 Query 和标准答案被不慎混入了少量 Few-shot 示例或 Prompt 模板中。

- 修复：建立评测集版本哈希管控，评测用例的构造必须采用动态环境插桩（如每次测试使用动态生成的随机工单号和临时数据库），杜绝静态固定 ID 泄漏。

- 故障模式：LLM 裁判打分结果每次运行不一致（Variance Instability）

- 定位：用大模型给回答的合规性打分时，采样温度设为了 0.7 导致打分存在随机浮动。

- 修复：裁判模型温度强制设为 0.0；核心指标优先使用代码规则和数据库断言，非结构化部分采用双向置换一致性校验。

### 工程 trick 与坑

- 零工具调用的除零防御：某些任务模型直接给出回答没有调用任何工具，此时全库的工具调用总数在某些切片下可能为 0。计算 invalid_call_rate 时必须做除零保护返回 None 或 0.0，严禁抛出 ZeroDivisionError 中断批处理评测。

- 失败归因的标准化分类字典：团队必须沉淀统一的枚举标签（如 TIMEOUT, AUTH_DENIED, CYCLE_LOOP, SCHEMA_CORRUPT, UNKNOWN），严禁使用自由自然语言记录失败原因，否则无法自动生成报表饼图。

### 循序渐进 Toy Code：Level 7 — 纯 Python 手撕 Agent 离线轨迹评测套件

代码难度定位：Level 7（评测体系实现）。纯 Python 从零手写一个支持多任务轨迹输入、精确多维度分母对齐、步骤效率统计与失败原因分布聚类的离线评测套件。

```python
"""
4.7 Toy Code: Level 7 - 纯 Python 手撕 Agent 离线轨迹评测套件
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
from enum import Enum
import math
from statistics import mean
from typing import Optional


class TaskFailureReason(str, Enum):
    """标准化的任务失败根因分类"""
    SCHEMA_ERROR = "SCHEMA_ERROR"           # 参数格式校验失败
    MAX_STEPS_EXCEEDED = "MAX_STEPS_EXCEEDED" # 死循环或超长未收敛
    AUTH_FORBIDDEN = "AUTH_FORBIDDEN"       # 权限越界拦截
    DOWNSTREAM_TIMEOUT = "DOWNSTREAM_TIMEOUT" # 下游网络/服务超时
    INSUFFICIENT_EVIDENCE = "INSUFFICIENT"   # 证据不足主动拒答


@dataclass(frozen=True)
class TaskTrajectoryLog:
    """单个测试任务的全量执行审计轨迹"""
    task_id: str
    is_success: bool                       # 是否真正达成业务目标（客观断言）
    total_tool_calls: int                  # 发生的工具调用总次数
    invalid_tool_calls: int                # 其中调用失败（报错/参数错）的次数
    duration_seconds: float                # 任务总耗时
    token_cost_usd: float                  # 本次任务总 Token 费用
    failure_reason: Optional[TaskFailureReason] = None


@dataclass(frozen=True)
class AgentBenchmarkReport:
    """Agent 全量基准评测报告"""
    total_tasks: int
    success_rate: float                    # 任务完成率 (0.0 ~ 1.0)
    avg_steps_successful_tasks: float      # 仅统计成功任务的平均步骤效率
    overall_invalid_call_rate: Optional[float] # 无效工具调用率 (以总调用数为分母)
    mean_duration_s: float
    total_cost_usd: float
    failure_distribution: dict[str, int]   # 失败归因直方图分布统计


def evaluate_agent_benchmark(
    trajectories: list[TaskTrajectoryLog]
) -> AgentBenchmarkReport:
    """
    聚合多任务执行轨迹，生成工业级评测报表
    
    不变量保证：
    1. 成功任务的 failure_reason 必须为 None；失败任务必须有确切归因
    2. invalid_tool_calls <= total_tool_calls
    3. 指标分母严格区分任务总数与工具调用总数
    """
    if not trajectories:
        raise ValueError("评测轨迹列表不能为空")
    if len({t.task_id for t in trajectories}) != len(trajectories):
        raise ValueError("存在重复的 task_id，数据存在脏记录")

    success_count = 0
    successful_steps_list: list[int] = []
    
    total_calls_all_tasks = 0
    total_invalid_calls_all_tasks = 0
    durations: list[float] = []
    total_cost = 0.0

    failure_histogram: dict[str, int] = {}

    for t in trajectories:
        if not t.task_id.strip():
            raise ValueError("task_id 不能为空")
        if t.total_tool_calls < 0 or t.invalid_tool_calls < 0:
            raise ValueError("调用计数必须为非负整数")
        if t.invalid_tool_calls > t.total_tool_calls:
            raise ValueError(f"任务 [{t.task_id}] 的无效调用数超过了总调用数")
        if not math.isfinite(t.duration_seconds) or t.duration_seconds < 0:
            raise ValueError("耗时数值非法")

        # 归因合法性校验
        if t.is_success:
            if t.failure_reason is not None:
                raise ValueError(f"逻辑错误：成功任务 [{t.task_id}] 不应带有失败归因！")
            success_count += 1
            successful_steps_list.append(t.total_tool_calls)
        else:
            if t.failure_reason is None:
                raise ValueError(f"数据缺失：失败任务 [{t.task_id}] 必须指定明确的失败归因枚举！")
            reason_key = t.failure_reason.value
            failure_histogram[reason_key] = failure_histogram.get(reason_key, 0) + 1

        total_calls_all_tasks += t.total_tool_calls
        total_invalid_calls_all_tasks += t.invalid_tool_calls
        durations.append(t.duration_seconds)
        total_cost += t.token_cost_usd

    # 1. 成功任务平均步数（步骤效率）
    avg_steps = mean(successful_steps_list) if successful_steps_list else 0.0

    # 2. 无效调用比例（除零保护：全库未发生任何工具调用时设为 None）
    invalid_rate = (
        total_invalid_calls_all_tasks / total_calls_all_tasks
        if total_calls_all_tasks > 0 else None
    )

    return AgentBenchmarkReport(
        total_tasks=len(trajectories),
        success_rate=success_count / len(trajectories),
        avg_steps_successful_tasks=avg_steps,
        overall_invalid_call_rate=invalid_rate,
        mean_duration_s=mean(durations),
        total_cost_usd=total_cost,
        failure_distribution=failure_histogram
    )


def self_test():
    """测试评测套件在各种任务指标分布下的聚合准确性"""
    # 模拟一份包含成功、自愈与失败的真实评测集跑分日志
    test_runs = [
        # 任务 1：顺利完成，用时 2 步，无错
        TaskTrajectoryLog(
            task_id="TASK_01",
            is_success=True,
            total_tool_calls=2,
            invalid_tool_calls=0,
            duration_seconds=1.2,
            token_cost_usd=0.005,
            failure_reason=None
        ),
        # 任务 2：成功自愈，经历了 1 次参数错重试，共 3 步最终达成
        TaskTrajectoryLog(
            task_id="TASK_02",
            is_success=True,
            total_tool_calls=3,
            invalid_tool_calls=1, # 包含 1 次无效尝试
            duration_seconds=2.1,
            token_cost_usd=0.008,
            failure_reason=None
        ),
        # 任务 3：死循环步数耗尽失败，共 5 步
        TaskTrajectoryLog(
            task_id="TASK_03",
            is_success=False,
            total_tool_calls=5,
            invalid_tool_calls=2,
            duration_seconds=4.5,
            token_cost_usd=0.015,
            failure_reason=TaskFailureReason.MAX_STEPS_EXCEEDED
        ),
        # 任务 4：权限越权被秒级阻断，共 1 步
        TaskTrajectoryLog(
            task_id="TASK_04",
            is_success=False,
            total_tool_calls=1,
            invalid_tool_calls=1,
            duration_seconds=0.3,
            token_cost_usd=0.002,
            failure_reason=TaskFailureReason.AUTH_FORBIDDEN
        )
    ]

    report = evaluate_agent_benchmark(test_runs)

    # 理论值手算断言验证：
    # 1. 任务完成率 = 2 成功 / 4 总数 = 50.0%
    assert math.isclose(report.success_rate, 0.50)

    # 2. 步骤效率 (仅统计 Task 1 与 Task 2): (2 + 3) / 2 = 2.5 步
    assert math.isclose(report.avg_steps_successful_tasks, 2.5)

    # 3. 无效调用比例:
    # 全量工具调用数 = 2 + 3 + 5 + 1 = 11 次
    # 无效调用数 = 0 + 1 + 2 + 1 = 4 次
    # 比例 = 4 / 11 ≈ 0.3636
    assert math.isclose(report.overall_invalid_call_rate, 4 / 11, abs_tol=1e-4)

    # 4. 失败归因直方图完整性校验
    assert report.failure_distribution["MAX_STEPS_EXCEEDED"] == 1
    assert report.failure_distribution["AUTH_FORBIDDEN"] == 1
    assert sum(report.failure_distribution.values()) == 2 # 失败任务总数

    print(f"✅ 4.7 Agent 离线轨迹评测套件自检全部通过！"
          f"[成功率={report.success_rate * 100:.1f}%, 成功平均步数={report.avg_steps_successful_tasks:.1f}步, "
          f"无效调用率={report.overall_invalid_call_rate * 100:.1f}%, 总费用=${report.total_cost_usd:.4f}]")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个针对 Agent 复杂交互的离线评测套件 evaluate_agent_benchmark。核心不变量是：每一个成功任务必须严格满足环境断言且 failure_reason is None，每一个失败任务必须强制绑定预定义的标准化分类枚举；步骤效率仅计算成功样本的平均步长，杜绝失败的长尾死循环对效率基准造成虚假拉高。

- 关键行解析：在第 96-107 行，我对每一条 Trace 执行严谨的归因校验；在第 112-120 行，我将“任务分母（4）”与“工具调用总数分母（11）”进行了严格解耦，计算出真实的无效调用率（4/11=36.4%），为模型微调或 Prompt 改版提供了精准的微观归因支撑。

- 主动说边界与坑：这段代码演示的是离线评测引擎。在工业界持续集成（CI/CD）流水线中，必须主动向面试官展开：我们通常会搭建一套“自动化发布门禁（Release Gate）”——每次模型版本迭代或 Prompt 修改提交 PR 时，后台自动触发 100 条代表性真实用例回归，只有当“完成率不跌、平均步骤效率不增、无效调用率小于 5%”时，才允许灰度上线，彻底消除人工靠感觉瞎猜的黑盒风险。

- Q：为什么在评测 Agent 步骤效率时，通常只统计“成功任务”的平均步数？
A：因为失败任务（如死循环直到超限截断）往往跑满了全部步数（如 5 步或 10 步）；如果混入统计，会掩盖模型在正常执行时的真实规划智商。

- Q：在实际生产中，如何获取客观准确的“任务成功（is_success）”标签？
A：通过测试环境插桩（Mock Environment）做数据库终态比对、API 状态反查或执行后置业务断言，严禁完全听信大模型自己的“自问自答完成声明”。

- Q：什么是 Agent 回放评测中的“失败归因直方图”？它有什么实际研发价值？
A：将所有失败用例归并到标准化枚举（如超时、越权、参数错误、死循环），直接生成归因饼图，精准指引团队下一阶段是该优化 Schema 描述、该加大超时配额，还是该强化死循环拦截。
