# 03 进程调度算法你了解多少？

## 1. 🎯 一句话听懂 + 生活大白话例子

- **一句话听懂**：电脑里同时开着几十个程序，但 CPU 核心只有几个，**进程调度算法**就是决定“下一个该轮到哪个进程上 CPU 干活、干多久”的排队规则。
- **生活大白话例子**：把 CPU 想象成银行里唯一的**业务办理窗口**，就绪队列里的进程就是排队的**顾客**。银行经理可以用不同的叫号策略：
    - **先来先服务（FCFS）**：老老实实按取号顺序排队，哪怕前面那位大爷要办 2 小时的复杂公证，后面只想存 100 块钱的年轻人也得干等。
    - **短进程优先（SPF/SRT）**：谁办业务最快（比如只要 1 分钟）谁先上，平均等待时间最短，但要办 2 小时的大爷可能会一直被插队“饿死”。
    - **时间片轮转（RR）**：每人最多坐柜台办 5 分钟，到点没办完就回队尾重新排队，人人都有机会，适合大家都要即时响应的场景。
    - **多级反馈队列（MLFQ）**：设好几个 VIP 和普通窗口——新来的先去快速窗口试 5 分钟，5 分钟没办完说明是个“大活”，就降级去下一个 15 分钟的普通窗口，既照顾了快任务，又不让大任务饿死。

## 2. 🧠 底层机制与核心对比

### 七大经典调度算法（大白话拆解）

1. **先来先服务（FCFS）**：谁先到就绪队列就先服务谁，**非抢占式**。逻辑最简单，但长任务会堵死后面的短任务（护航效应）。
2. **短进程优先（SPF）与最短剩余时间优先（SRT）**：
    - **SPF（非抢占）**：挑预计运行时间最短的先跑；如果所有任务几乎同时到达，它的平均等待时间理论最优。
    - **SRT（抢占式）**：半路杀出个更短的新任务，立刻把当前任务踢回就绪队列，让更短的先跑。缺点是需要提前预估运行时间，且长任务容易“饥饿”。
3. **优先级调度（PSA）**：给每个进程贴个重要度标签（静态固定或动态调整），分抢占和非抢占。适合实时系统，但低优先级任务可能被饿死。
4. **高响应比优先（HRRN）**：专门治“饥饿”的改良版！每次挑 **响应比 = (等待时间 + 预计运行时间) / 预计运行时间** 最高的执行。短任务分母小占优势，而长任务等久了分子变大，优先级也会自然涨上去。
5. **时间片轮转（RR）**：把 CPU 时间切成固定小块（如 10ms），靠时钟中断按顺序轮流发牌。**分时/交互式系统**的核心，公平且响应快；但时间片太大退化成 FCFS，太小则切换开销爆炸。
6. **多级队列调度**：把任务按类型（比如前台交互 vs 后台批处理）分进不同队列，各队列内部用自己的算法（如前台用 RR，后台用 FCFS），队列之间再定优先级。
7. **多级反馈队列（MLFQ）**：现代通用操作系统的经典基石！设置多个优先级递减的队列，时间片逐级变大：新进程先进最高优先级队列，用完时间片还没结束就降级到下一层；低层任务等太久还可以“老化”升回去，兼顾短任务响应和长任务吞吐。

### 进程调度算法核心对比表

| **算法名称** | **是否抢占** | **核心规则** | **优点** | **缺点 / 风险** | **适用场景** |
| --- | --- | --- | --- | --- | --- |
| **FCFS（先来先服务）** | 非抢占 | 按到达顺序排队 | 实现简单、绝对公平 | 平均等待时间长，长作业阻塞短作业 | 批处理系统 |
| **SPF / SRT（短进程优先）** | SPF非抢占 / SRT抢占 | 运行时间/剩余时间最短优先 | 平均等待和周转时间最优 | 需要预估时间，长进程可能“饥饿” | 短作业较多的批处理 |
| **PSA（优先级调度）** | 可选 | 优先级高者先得 | 灵活，能保证关键任务及时执行 | 低优先级进程可能“饥饿” | 实时系统、内核关键任务 |
| **HRRN（高响应比优先）** | 非抢占 | 响应比=(等待+运行)/运行 | 兼顾公平与效率，不会饿死长作业 | 每次调度都要计算响应比，有开销 | 作业长短差异大的批处理 |
| **RR（时间片轮转）** | 抢占 | 每人固定时间片，轮流上台 | 响应快、公平，无饥饿 | 频繁上下文切换有开销；不区分紧急度 | 交互式、分时系统 |
| **多级队列** | 可选 | 按任务类型分队列，各管各的 | 可针对不同业务定制策略 | 低优先级队列可能饿死 | 混合型负载系统 |
| **多级反馈队列（MLFQ）** | 抢占 | 新进高优短片，超时降级加片 | 自适应！短任务快、长任务不饿死 | 实现复杂，参数调优难度大 | 通用操作系统（Windows/早期Unix） |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面对“了解哪些进程调度算法”，千万别报菜名一样乱背，按**“演进痛点线”**串起来，面试官会觉得你理解极深：

1. **起点（简单但低效）**：最基础的是 **FCFS**，按先来后到，但遇到长任务会堵死短任务；为了缩短平均等待时间，演化出 **SPF/SRT**（短任务优先），但这又会导致长任务“饥饿”。
2. **折中与公平**：为了防止长任务饿死，批处理场景有 **HRRN（高响应比优先）**，等得越久权重越高；而交互式桌面系统更看重响应速度，于是有了 **时间片轮转（RR）**，大家轮流用 CPU。
3. **集大成者（现代系统）**：真实系统既有前台交互又有后台计算，于是把“优先级 + 时间片轮转”结合成 **多级反馈队列（MLFQ）**，新任务先给高优先级小时间片（保证交互快），跑不完再降级给大时间片（减少切换开销）。（顺带一提 Linux 现今用基于红黑树的 **CFS 完全公平调度**）。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：时间片轮转（RR）里，时间片设多大比较合适？**
    - **参考答法**：需要做权衡。如果时间片**太大**，所有任务都在一个时间片内跑完了，RR 就退化成了先来先服务（FCFS），交互响应变慢；如果时间片**太小**，CPU 大量时间都浪费在保存和恢复上下文的“切换开销”上，真正干活的时间变少。通常操作系统会设在 **10ms ~ 100ms** 之间，让上下文切换开销控制在 1% 以内。
- **追问 2：什么是“饥饿”现象？哪些调度算法容易出现饥饿？**
    - **参考答法**：饥饿是指一个进程明明准备好了，但因为调度策略偏心，长期甚至永远得不到 CPU 资源。比如 **SPF/SRT** 遇到源源不断的短任务时，长任务会饥饿；**静态优先级调度**中，低优先级任务会饥饿。解决方法是引入**老化（Aging）机制**——等得越久，优先级自动涨得越高（比如 HRRN）。

## 5. 🤖 和大模型/AI 开发有什么关系

- **大模型推理调度（Continuous Batching）**：当你用 vLLM 部署大模型 API 时，有的用户只问“你好”（生成 5 个 token 的短任务），有的用户让写一篇万字长文（长任务）。如果推理引擎用死板的 FCFS，写长文的请求就会把问“你好”的用户卡死！现代推理引擎借鉴了操作系统调度思想，采用**按 Token 步进的抢占/连续批处理**，甚至类似 MLFQ 的**分级队列调度**，保证短请求毫秒级响应、长请求不饿死。
