# 01 TCP三次握手的详细流程及核心目的

## 1. 🎯 一句话听懂 + 生活大白话例子

- **一句话听懂**：TCP 三次握手就是在正式发数据前，客户端和服务器互相确认**“我能发、你能收、你也能发、我也能收”**，顺便把双方的起始编号（序列号）对齐。
- **生活大白话例子**：
    - 就像两个人在信号不太好的地方用对讲机通话：
        1. **第一次握手（你问）**：“喂，老王，我是小张，我从第 100 句开始说，能听见吗？”（客户端发 `SYN=1, seq=x`）。
        2. **第二次握手（他答+他问）**：“小张你好，我听见了！你的第 100 句收到，准备听你的第 101 句。另外我从第 500 句开始说，你能听见我吗？”（服务器发 `SYN=1, ACK=1, seq=y, ack=x+1`）。
        3. **第三次握手（你答）**：“妥了老王，我也听见你了，准备听你的第 501 句！那咱开始聊正事吧。”（客户端发 `ACK=1, seq=x+1, ack=y+1`）。

## 2. 🧠 底层机制与核心对比

### 核心子概念（大白话版）

- **SYN（同步信号）**：相当于“请求建立连接 + 告诉你我的起始编号”。每次发 `SYN` 都会占掉 1 个序列号。
- **ACK（确认信号）**：相当于“收到！我接下来期待你发下一号”。不带数据的纯 `ACK` 报文不消耗序列号。
- **ISN（初始序列号）**：双方各自随机挑一个起始数字（`x` 和 `y`），防止旧连接残留的数据包或者黑客猜中序号来捣乱。
- **LISTEN / SYN-SENT / SYN-RCVD / ESTABLISHED 状态**：分别代表服务器的“开门等客”、客户端的“拨号等待”、服务器的“接到电话等对方最后确认”、以及双方的“正式接通”。
- **保活计时器（Keepalive Timer）**：接通后如果客户端突然拔网线失联了，服务器会等一段时间后每隔 75 秒发一次探测包，连发 10 次都没回音就主动挂断，防止白占资源。

### 三次握手状态与报文变化表

| **握手阶段** | **发送方向** | **核心标志位与序号** | **发送方状态变化** | **核心目的（大白话）** |
| --- | --- | --- | --- | --- |
| **准备阶段** | 服务器 | 无 | `CLOSED` → `LISTEN` | 服务器开机开门，等待连接 |
| **第一次握手** | 客户端 → 服务器 | `SYN=1, seq=x` | `CLOSED` → `SYN-SENT` | 证明客户端“能发”，同步客户端起始号 `x` |
| **第二次握手** | 服务器 → 客户端 | `SYN=1, ACK=1, seq=y, ack=x+1` | `LISTEN` → `SYN-RCVD` | 证明服务器“能收也能发”，同步服务器起始号 `y` |
| **第三次握手** | 客户端 → 服务器 | `ACK=1, seq=x+1, ack=y+1`（可带数据） | 客户端、服务器先后进入 `ESTABLISHED` | 证明客户端“能收”，防止旧的延迟请求误建连接 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试时按 **“状态前置 -> 三步报文与状态流转 -> 两大核心目的”** 回答，一气呵成：

“TCP 三次握手是建立全双工可靠连接的过程，首先服务端处于 `LISTEN` 状态：

- **第一次**：客户端发 `SYN=1, seq=x`，进入 `SYN-SENT`；
- **第二次**：服务端收到后回复 `SYN=1, ACK=1, seq=y, ack=x+1`，进入 `SYN-RCVD`；
- **第三次**：客户端回复 `ACK=1, seq=x+1, ack=y+1`，双方先后进入 `ESTABLISHED`，连接建立（这次可以顺带携带应用层数据）。 它的核心目的有两个：第一是**验证双方的收发能力都正常**并同步各自的初始序列号（ISN）；第二是**防止历史失效的延迟** `SYN` **报文突然到达服务端**，导致服务端白白开启无效的‘半开连接’浪费资源。”

## 4. ❓ 高频面试追问与参考答法

- **Q1：为什么第三次握手可以携带数据，前两次不行？**
    - **参考答法**：第一次握手如果允许带数据，黑客只要疯狂伪造 `SYN` 包带上几 KB 垃圾数据，服务器还没确认对方身份就得分配内存去收，极易被内存打满（放大 SYN Flood 攻击风险）；而到了第三次握手时，客户端已经收到了服务器的确认，连接在客户端侧已算建立完成，所以可以顺便把第一份 HTTP 请求数据捎过去，省掉一次往返时间。
- **Q2：什么是 SYN 洪水攻击（SYN Flood）？服务器怎么防？**
    - **参考答法**：黑客用假 IP 疯狂发“第一次握手（SYN）”，服务器回完“第二次握手（SYN-ACK）”后进入 `SYN-RCVD` 并把连接放进**半连接队列**傻等第三次握手，结果永远等不到，把半连接队列塞满导致正常用户连不上。防御手段主要有：开启 **SYN Cookie**（收到 SYN 先不占队列内存，把信息算成一个加密数字放序号里发回去，等第三次握手带回来再真正建连）以及调大队列和减少重试次数。

## 5. 🤖 和大模型/AI 开发有什么关系

- **为什么大模型首字延迟（TTFT）包含网络握手开销？**：当你在网页或 App 里给大模型发消息时，如果还没建立连接，就得先花 1 个往返（RTT）做 TCP 三次握手，再花 1~2 个 RTT 做 TLS 加密握手，然后才能发出 Prompt。这几十到几百毫秒都会直接算进用户的“首字等待时间（TTFT）”里。
- **AI 网关与推理服务的连接复用**：为了省掉每次调大模型都重新三次握手的开销，AI SDK（如 OpenAI Python SDK 的 `httpx` 连接池）和 API 网关都会复用底层已经完成三次握手的 TCP 长连接。
- **高并发 Agent 并发调用时的端口/队列瓶颈**：如果 Agent 一次性并发几十个工具调用或批量跑评测，瞬间发出大量新连接，可能会把本地或网关的半连接/全连接队列打满导致超时，这时就需要合理配置连接池大小。
