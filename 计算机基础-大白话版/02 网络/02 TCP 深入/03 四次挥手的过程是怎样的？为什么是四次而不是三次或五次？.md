# 03 四次挥手的过程是怎样的？为什么是四次而不是三次或五次？

## 1. 🎯 一句话听懂 + 生活大白话例子

- **一句话听懂**：TCP 是双向车道（全双工），关连接必须双方各自说一声“我发完了”并得到对方回一声“收到”，一共两来两回，所以要四次挥手。
- **生活大白话例子**：
    - 就像两个人在电话里结束通话：
        1. **第一次挥手（你提出挂断）**：“我这边要说的都说完了，准备挂了啊。”（客户端发 `FIN`）。
        2. **第二次挥手（对方先确认）**：“好，我知道你说完了，但你等下，我这儿还有两句补充没说完。”（服务端回 `ACK`，此时你不能再说，但还能听）。
        3. **第三次挥手（对方也说完了）**：“行了，我这边也全部说完了，我也准备挂了。”（服务端发 `FIN+ACK`）。
        4. **第四次挥手（你最后确认）**：“收到，拜拜！”（客户端回 `ACK` 后，等一会儿确认对方没再追问才彻底放听筒）。

## 2. 🧠 底层机制与核心对比

### 核心子概念（大白话版）

- **半关闭状态（Half-Close）**：第二次挥手完成后，客户端到服务器的发送通道关了，但服务器到客户端的通道还开着，服务器可以把剩下的尾货数据继续发完。
- **CLOSE-WAIT 与 LAST-ACK**：服务器收到 `FIN` 回 `ACK` 后进入 `CLOSE-WAIT`（“等我自己业务数据发完”）；发完后发出自己的 `FIN`，进入 `LAST-ACK`（“等对方最后一句拜拜”）。
- **TIME-WAIT（2MSL 等待）**：主动关闭方发完第四次挥手的 `ACK` 后，不能立刻撤退，必须原地多等 **2 倍报文最大生存时间（2MSL）**，万一最后那句“拜拜”丢了，好能听到对方重喊并再回一次“拜拜”。
- **第三次挥手的** `ACK=1` **特殊性**：第三次挥手同时带着 `FIN=1` 和 `ACK=1`，既宣布“我也要关了”，又顺带确认之前的通信，是服务端整个生命周期里最后一次发数据的机会。

### 四次挥手流程与状态对比表

| **挥手阶段** | **发送方向** | **核心标志位** | **发起方状态** | **接收方状态** | **大白话含义** |
| --- | --- | --- | --- | --- | --- |
| **第一次挥手** | 客户端 → 服务器 | `FIN=1, seq=u` | `FIN-WAIT-1` | `CLOSE-WAIT` | “我说完了，我要关我这边的通道” |
| **第二次挥手** | 服务器 → 客户端 | `ACK=1, ack=u+1` | `FIN-WAIT-2` | `CLOSE-WAIT` | “知道你说完了，等我把手里剩的发完” |
| **第三次挥手** | 服务器 → 客户端 | `FIN=1, ACK=1, seq=w, ack=u+1` | `FIN-WAIT-2` | `LAST-ACK` | “我也发完了，现在关我这边的通道” |
| **第四次挥手** | 客户端 → 服务器 | `ACK=1, seq=u+1, ack=w+1` | `TIME-WAIT`（等 2MSL 后 `CLOSED`） | `CLOSED` | “收到，拜拜！”（服务端收到即关，客户端多等一会儿） |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问这题时，按 **“四步状态流转 -> 为什么是 4 次（不是 3 次或 5 次）”** 回答：

“TCP 四次挥手是全双工连接双向优雅关闭的过程（假设客户端主动关闭）：

1. 客户端发 `FIN` 进入 `FIN-WAIT-1`；
2. 服务端回 `ACK` 进入 `CLOSE-WAIT`，客户端收到后进入 `FIN-WAIT-2`，此时客户端不再发数据但还能收；
3. 服务端把剩余数据发完后，发 `FIN+ACK` 进入 `LAST-ACK`；
4. 客户端回最后一个 `ACK` 进入 `TIME-WAIT` 等待 2MSL 后彻底关闭，服务端收到后直接进入 `CLOSED`。 之所以**是四次而不是三次**，是因为 TCP 是全双工的，服务端收到 `FIN` 时通常还有数据没发完，不能立刻把 `ACK` 和 `FIN` 合并发送；之所以**不是五次**，是因为一发一收两对确认已经足够完整关闭两个方向的数据流，再多一步纯属冗余。”

## 4. ❓ 高频面试追问与参考答法

- **Q1：什么时候四次挥手真的可以变成“三次挥手”？**
    - **参考答法**：当被动关闭方（服务端）收到 `FIN` 的那一刻，**刚好没有剩余数据要发**，并且开启了**延迟确认（Delayed ACK）**机制时，服务端可以把第二次挥手的 `ACK` 和第三次挥手的 `FIN` 合并成一个 `FIN+ACK` 包发回去，四次挥手在抓包里就会变成三次。
- **Q2：如果服务器上突然出现大量** `CLOSE-WAIT` **状态，说明什么问题？**
    - **参考答法**：说明**服务端代码写出了 Bug（资源泄露）**！`CLOSE-WAIT` 是服务端收到对方 `FIN` 并回了 `ACK` 之后，等待自己应用程序调用 `close()` 发第三次挥手的状态。如果卡在 `CLOSE-WAIT` 一直不走，通常是因为后端代码忘了关闭 Socket 连接、连接池没归还，或者线程卡死，导致迟迟发不出第三次挥手。

## 5. 🤖 和大模型/AI 开发有什么关系

- **流式推理中断时的优雅关闭**：用户在网页上点击“停止生成（Stop Generating）”时，前端主动中断 SSE/HTTP 请求，底层就会触发客户端向大模型网关发起 `FIN`（第一次挥手）。如果后端推理服务没有正确监听连接断开事件并释放资源，不仅会浪费宝贵的 GPU 算力继续生成无用 Token，还可能堆积大量 `CLOSE-WAIT` 连接。
- **高并发压测/Agent 频繁短连接**：如果 AI 微服务之间（比如 Agent 调检索服务、重排服务）用短连接频繁断开，主动关闭方就会堆积大量 `TIME-WAIT` 连接，甚至耗尽端口导致报错。
