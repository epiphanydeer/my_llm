# 01 HTTP/1.0和HTTP/1.1的区别？

## 1. 🎯 一句话听懂 + 生活大白话例子

- **一句话听懂**：HTTP/1.0 像“一问一挂的公用电话”，每要一张图片就重新拨一次号；HTTP/1.1 升级成了“默认不断线的长电话”，还加上了分机号（Host）、分批发货（分块传输）、断点续传和更聪明的本地缓存。
- **生活大白话例子**：
    - **HTTP/1.0 买菜**：你跑去菜市场买 10 样菜，买完一颗白菜就回家锁门，然后再跑一趟买一根萝卜……光路上跑腿（TCP 三次握手/四次挥手）就把人累死了。
    - **HTTP/1.1 买菜**：你打通电话后先不挂（**默认长连接**），一连串点完白菜、萝卜、西红柿；还能精确报出要找市场里哪家摊位（**Host 头**）；如果老板正在现切肉不知道多重，可以切一块发一块（**分块传输**）；看视频拉进度条时，还能只让老板发“第 50 分钟到第 55 分钟”那一段（**范围请求 / 断点续传**）。

## 2. 🧠 底层机制与核心对比

### 核心子概念（大白话版）

- **默认长连接（Keep-Alive）**：HTTP/1.0 默认每次请求完就关 TCP 连接；HTTP/1.1 默认保持连接不断开，后续请求直接复用，省去大量重复握手开销。
- **Host 头字段**：HTTP/1.0 没这个字段，一个 IP 只能挂一个网站；HTTP/1.1 必带 `Host`，从此一台云服务器上可以同时托管成百上千个不同域名的网站（虚拟主机）。
- **分块传输编码（Chunked）**：HTTP/1.0 必须提前算好总字节数写进 `Content-Length`；HTTP/1.1 允许一边生成动态内容一边切成小块往外发，特别适合实时流式输出。
- **缓存机制升级**：HTTP/1.0 只有按绝对时间过期的 `Expires` 和按修改时间对比的 `Last-Modified`；HTTP/1.1 新增了相对时间 `Cache-Control`（不怕客户端电脑时间调错）和基于文件内容哈希的 `ETag`（更精准）。
- **范围请求（Range）**：HTTP/1.1 允许只请求文件的某一段字节（返回 `206 Partial Content`），支撑了大文件断点续传和视频拖动进度条。
- **队头阻塞（HOL Blocking）**：HTTP/1.1 虽然允许同一条长连接连续发请求，但服务器必须**按顺序依次回复**——只要排在最前面的那个请求卡慢了，后面的响应就算做好了也得干等。

### HTTP/1.0 与 HTTP/1.1 核心对比表

| **对比维度** | **HTTP/1.0** | **HTTP/1.1** |
| --- | --- | --- |
| **默认连接方式** | 短连接（每次请求后关掉，需手动加头才长连） | **默认长连接**（标准化复用 TCP 连接） |
| **Host 头（虚拟主机）** | 不支持（单 IP 只能绑单域名） | **强制支持**（单 IP 可托管多域名） |
| **分块传输编码** | 不支持（必须提前知道 `Content-Length`） | **支持**（`Transfer-Encoding: chunked` 流式发送） |
| **缓存控制** | 仅 `Expires` / `Last-Modified` | 新增 `Cache-Control` 与 `ETag / If-None-Match` |
| **断点续传（范围请求）** | 不支持（只能整文件重下） | **支持**（`Range` 头 + `206` 状态码） |
| **队头阻塞** | 无（因为每次都是独立短连接） | **存在**（单连接内响应必须严格按请求顺序返回） |
| **状态码** | 仅基础状态码 | 新增 `100`、`409`、`410` 等，扩展至 40+ |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试时按 **“连接复用 -> 虚拟主机与动态传输 -> 缓存与断点续传 -> 遗留痛点”** 四条线来答，非常干脆：

“HTTP/1.1 相比 HTTP/1.0 的核心升级，本质上是**从‘一次性小作坊’升级到了‘高并发现代 Web 架构’**，主要体现在五个方面：

1. **连接管理**：从默认短连接升级为**默认长连接（Keep-Alive）**，复用 TCP 连接大幅减少握手延迟。
2. **支持虚拟主机**：新增必传的 `Host` **请求头**，让单台服务器同一个 IP 可以托管多个域名网站。
3. **流式与断点传输**：新增 `Transfer-Encoding: chunked` **分块传输**，支持服务端边生成边发送动态内容；新增 `Range` **范围请求**（206 状态码），实现大文件断点续传。
4. **缓存更精准**：新增 `Cache-Control`（相对时间，避免客户端时钟不准）和 `ETag`（文件内容指纹，比秒级时间戳更精准）。
5. **遗留局限**：HTTP/1.1 虽然支持长连接和管道化，但同一条连接内响应必须严格按序返回，依然存在**应用层队头阻塞问题**，这也直接催生了后来的 HTTP/2 多路复用。”

## 4. ❓ 高频面试追问与参考答法

- **Q1：为什么 HTTP/1.1 的“管道化（Pipelining）”号称可以连续发请求，实际浏览器却默认禁用它？**
    - **参考答法**：因为管道化只解决了“客户端不用等就能连发”，却没解决“服务端必须按请求顺序排队返回”的死规定。一旦第 1 个请求是个慢查询，后面第 2、3、4 个早就算好的请求也全被堵在后面（**服务端队头阻塞**），甚至还容易被老旧代理服务器搞乱顺序，所以现代浏览器干脆禁用管道化，直接用多条连接或升级 HTTP/2。
- **Q2：HTTP 和 TCP 到底是什么关系？HTTP/3 为什么又抛弃了 TCP？**
    - **参考答法**：TCP 是传输层“修路的”，负责把字节流可靠送到；HTTP 是应用层“定规矩的”，规定信件怎么写格式。HTTP/1.1 和 HTTP/2 都跑在 TCP 上，但 TCP 内核一旦丢一个包就会卡住整条连接；所以 HTTP/3 直接改用基于 UDP 的 **QUIC 协议**，在应用层自己实现不互相阻塞的多路复用和 0-RTT 快速握手。

## 5. 🤖 和大模型/AI 开发有什么关系

- **大模型流式输出全靠 HTTP/1.1 的分块传输**：当你看到 ChatGPT 像打字机一样一个词一个词往外蹦时，正是利用了 HTTP/1.1 引入的 `Transfer-Encoding: chunked`（配合 SSE `text/event-stream`）——模型每推理出一个 Token 就立刻切成一个小块发给前端，不用等几千字全生成完才返回。
- **百 GB 模型权重断点续传**：用 `huggingface-cli` 或 `aria2` 下载几十 GB 的大模型权重时，如果半路网断了重新接着下，靠的就是 HTTP/1.1 的 `Range: bytes=...` 请求头和 `206 Partial Content`。
