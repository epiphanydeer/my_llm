# 02 HTTP请求方式有哪些？

## 1. 🎯 一句话听懂 + 生活大白话例子

- **一句话听懂**：HTTP 请求方式就是客户端给服务器发消息时，贴在信封上的“动作标签”，告诉服务器你这次来是想“查东西、交表单、改资料”还是“删数据”。
- **生活大白话例子**：
    - 想象你去图书馆办事：**GET** 是只借书看，不涂不画（只读）；**POST** 是交一张新办卡申请表（新增）；**PUT** 是把旧档案抽出来整本换掉（全量替换）；**PATCH** 是只改档案上的手机号那一栏（局部修改）；**DELETE** 是注销档案（删除）；**HEAD** 是只问管理员“这本书还在不在、几几年出版的”，不用搬书出来；**OPTIONS** 是先问窗口“你们这儿支持办哪些业务”。

## 2. 🧠 底层机制与核心对比

### 核心子概念（大白话版）

- **HTTP/1.1 原生 8 种方法**：早期 HTTP/1.1 规范（RFC 2616）定下了 8 个标准动作：`GET`、`POST`、`PUT`、`DELETE`、`HEAD`、`OPTIONS`、`TRACE`、`CONNECT`。
- **扩展方法 PATCH**：后来（RFC 5789）专门补了一个“打补丁”动作，解决每次只改一个字段却要传整份大数据的浪费。
- **安全性（Safe）**：这里的“安全”不是指防黑客加密，而是指**“只看不改”**——不会改变服务器上的数据状态（比如 GET、HEAD）。
- **幂等性（Idempotent）**：点 1 次和不小心手抖连点 10 次，服务器最终的结果一模一样，不会多出 10 条重复记录（比如查询、删除同一条记录、覆盖式更新）。

### 核心对比表

| **请求方法** | **一句话大白话解释** | **是否安全（只读不改）** | **是否幂等（连点结果一样）** | **典型使用场景** |
| --- | --- | --- | --- | --- |
| **GET** | “把某样东西拿给我看看” | 是 | 是 | 打开网页、搜索商品、查列表 |
| **POST** | “我提交一份新数据，你帮我处理/新建” | 否 | 否 | 注册账号、提交订单、发评论 |
| **PUT** | “用我这份完整新数据，把原来的整份替换掉” | 否 | 是 | 提交完整的个人资料覆盖保存 |
| **PATCH** | “只改其中的一两个字段，别的不动” | 否 | 通常否 | 只修改用户昵称或头像 |
| **DELETE** | “把指定的那条数据删掉” | 否 | 是 | 删除文章、移除购物车商品 |
| **HEAD** | “只给我看响应头信息，正文别传了” | 是 | 是 | 检查大文件存不存在、看缓存过期没 |
| **OPTIONS** | “先探探路，问服务器支持哪些动作/权限” | 是 | 是 | 浏览器跨域请求前的“预检” |
| **TRACE** | “把我发的话原样回显，用来排查链路” | 是 | 是 | 调试排错（因安全风险生产环境通常禁用） |
| **CONNECT** | “帮我挖一条穿过代理的加密隧道” | 否 | 否 | 通过 HTTP 代理访问 HTTPS 网站 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

回答这个问题时，按 **“8 种原生 + 1 种扩展 -> 常用 4 个 CRUD -> 3 个特殊辅助 -> 安全与幂等概念”** 来答，条理会非常清晰：

“HTTP/1.1 规范最初定义了 **8 种核心请求方法**，后来又通过扩展规范补充了 **PATCH**，一共 9 种常见方法。 日常业务开发最常用的是对应增删改查的 5 个：**GET** 用来查询（安全且幂等），**POST** 用来新增或触发业务（不安全也不幂等），**PUT** 用来全量替换（幂等），**PATCH** 用来局部更新，**DELETE** 用来删除（幂等）。 另外还有 4 个偏底层和辅助的方法：**HEAD** 只拿响应头不拿正文，常用于探测文件大小或缓存状态；**OPTIONS** 用来查询服务器支持的方法，最常见于浏览器的跨域预检请求；**CONNECT** 用于代理服务器建立 HTTPS 隧道；**TRACE** 用于回显调试，因为有跨站追踪安全风险线上一般禁用。”

## 4. ❓ 高频面试追问与参考答法

- **Q1：PUT 和 PATCH 都是修改，到底有什么区别？**
    - **参考答法**：**PUT 是“整本换新”，PATCH 是“涂改液改一行”**。用 PUT 更新用户信息时，哪怕你只想改个昵称，也得把姓名、年龄、邮箱全量传过去，不传的字段可能会被置空；而 PATCH 只需要把“昵称”这一个变动字段传过去就行，省流量也更灵活。
- **Q2：什么是“安全”和“幂等”？为什么 POST 不幂等而 DELETE 幂等？**
    - **参考答法**：“安全”指的是请求**不会修改服务器上的资源状态**（比如 GET）；“幂等”指的是**执行 1 次和执行 N 次，服务器上资源的最终状态是一样的**。POST 连发两次可能会创建两个一模一样的订单，所以不幂等；而 DELETE 删除同一个订单，第一次删掉了，第二次虽然可能返回“资源已不存在”，但服务器上这条数据没了的最终状态是一样的，所以是幂等的。
- **Q3：为什么 Java 的** `HttpServlet` **源码里只定义了 7 种方法？**
    - **参考答法**：因为 `CONNECT` 是代理/服务器底层自己处理的隧道动作，业务代码不需要也不应该管它，所以业务框架通常只暴露其余 7 个（甚至生产环境还会关掉 `TRACE`）。

## 5. 🤖 和大模型/AI 开发有什么关系

- **大模型 API 为什么几乎全用 POST？**：不管是调 ChatGPT、Claude 还是本地部署的 vLLM 接口，对话接口（如 `/v1/chat/completions`）都是 **POST**。因为 prompt 上下文、历史消息、温度参数往往很长（URL 放不下），且每次调用模型生成的内容都不同、还可能扣减 token 额度，属于典型的“提交复杂数据 + 触发非幂等计算”。
- **Agent 工具调用（Function Calling / MCP）与 RESTful 接口**：当我们让 AI Agent 去操作外部系统（查天气、建日程、删邮件）时，本质上就是让模型根据语义选择对应的 HTTP 方法——查知识库用 `GET`，创建工单用 `POST`，修改状态用 `PATCH`，取消任务用 `DELETE`。如果接口没有遵守幂等性规范，Agent 重试一次就可能给用户下两单！
- **模型权重下载与断点续传**：从 Hugging Face 下载几十 GB 的模型文件前，下载器常先发一个 `HEAD` 请求探明文件总大小（`Content-Length`）和是否支持断点续传，确认无误后再拉取正文。
