# 缓存雪崩、穿透、击穿

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：这三个词形容的是保护数据库的“Redis 防弹衣”失效的三种事故——**穿透**是有人专挑“根本不存在的东西”问，子弹直接穿过防弹衣打穿数据库；**击穿**是防弹衣上**某一个热点孔洞**刚好到期破了，无数子弹全从这一个洞灌进去；**雪崩**是防弹衣**整片失效或彻底烂了**，所有请求像雪崩一样直接把数据库压垮。

**生活大白话例子**：把数据库想象成后厨大厨，Redis 是前台展柜：

- **缓存穿透（来找茬的，店里根本没这道菜）**：有人故意点一道“红烧恐龙肉”，展柜里没有，服务员只好跑去问大厨，大厨说没有；结果这人每秒点 1 万次“红烧恐龙肉”，每次都把大厨烦死（既没缓存、库里也没数据）。
- **缓存击穿（爆款招牌菜刚好卖完撤牌，门口排着 1 万人）**：双十一“1 元秒杀 iPhone”这个爆款商品缓存刚好过期的一瞬间，10 万个买家同时点进来，展柜一空，10 万人同时冲进后厨问大厨要货，瞬间踩踏。
- **缓存雪崩（停电了，或者所有菜牌同一秒全过期）**：中午 12 点整，所有 1 万道菜的缓存牌同时到期失效（或者前台展柜直接塌了/Redis 宕机），所有点菜请求瞬间全部砸向后厨大厨，后厨直接瘫痪。

## 2. 🧠 底层机制与核心对比

### 三大缓存事故的精准拆解与解法

- **缓存穿透（查不存在的数据）**：
    - **怎么防**：① **入口参数校验**（把 `id <= 0` 或格式非法的请求直接挡在门外）；② **缓存空值**（库里查不到也往 Redis 存一个短 TTL 的空值，下次直接挡住）；③ **布隆过滤器（Bloom Filter）**（用极小内存预先登记所有合法 ID，不存在的一律秒拦）。
- **缓存击穿（单个极热点 key 突然过期）**：
    - **怎么防**：① **互斥锁 / 分布式锁**（缓存失效时只放 1 个线程去查库并重建缓存，其他人等一会再读缓存，强保护数据库）；② **逻辑过期 + 异步重建**（不设物理 TTL，把过期时间写在 value 里，发现过期先返回旧数据同时后台异步更新，保高可用）；③ **热点预热**（大促前提前把热点加载好）。
- **缓存雪崩（大量 key 同时过期 / Redis 整体挂掉）**：
    - **怎么防**：① **TTL 加随机值**（比如基础 30 分钟 + 随机 1~10 分钟，把集中过期时间打散）；② **Redis 高可用**（主从 + 哨兵 / 集群，防止单点宕机）；③ **多级缓存**（本地内存缓存 + Redis，Redis 挂了还有本地缓存顶一层）；④ **限流、降级、熔断**（实在扛不住时主动丢弃部分非核心请求，死保数据库不崩）。

### 缓存三大问题全景对比表

| **问题名称** | **核心特征** | **典型诱因** | **核心解决思路（大白话）** | **常用技术手段** |
| --- | --- | --- | --- | --- |
| **缓存穿透** | 查的数据**Redis 和库里都没有** | 恶意攻击、爬虫、非法参数 | **门外拦住不存在的请求** | 参数校验、缓存空值、布隆过滤器 |
| **缓存击穿** | **单个热点 key** 过期瞬间并发回源 | 爆款商品、秒杀活动到期 | **单点限流或先给旧值再异步刷** | 互斥锁（双检锁）、逻辑过期、热点预热 |
| **缓存雪崩** | **大批 key 同时过期**或 Redis 挂了 | 批量导数据设相同 TTL、节点宕机 | **打散过期时间 + 系统级兜底** | 随机 TTL、高可用集群、多级缓存、限流熔断 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问这三兄弟，最喜欢看你**“精准区分定义 + 各自对症下药”**，千万别把解法张冠李戴：

1. **先用一句话把三者边界划清**：
    - **穿透**：压根不存在的数据（点打穿）；
    - **击穿**：单个热点 key 过期（点打穿）；
    - **雪崩**：大量 key 同时过期或 Redis 宕机（面压垮）。
2. **再按“防线思维”分别给方案**：
    - 防穿透：**入口校验 + 缓存空值 + 布隆过滤器**；
    - 防击穿：**互斥锁回源（保一致）或 逻辑过期异步刷新（保可用）+ 提前预热**；
    - 防雪崩：**随机打散 TTL + Redis 集群高可用 + 本地多级缓存 + 限流熔断**。
3. **补一句工程权衡**：说明在击穿场景下，互斥锁虽然保护了数据库但会让其他请求等待；对一致性要求没那么死板的展示类热点，用“逻辑过期 + 异步重建”用户响应更快。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：“缓存空值”和“布隆过滤器”都能防缓存穿透，实际怎么选？**
    - **参考答法**：如果业务数据规模不大、攻击模式固定，**缓存空值**实现最简单（查不到就存个 `""` 设 2 分钟过期），缺点是如果黑客用几百万个随机假 ID 攻击，会把 Redis 内存撑满；而**布隆过滤器**用极小内存就能存下上亿个合法 ID，特别适合防海量随机假 ID 的恶意穿透（缺点是有极小误判率且不支持直接删除）。实际高并发系统常把两者**串联使用**。
- **追问 2：用互斥锁解决缓存击穿时，为什么拿到锁之后还要再查一次缓存（Double Check）？**
    - **参考答法**：假设 1000 个线程同时发现缓存失效去抢锁，线程 A 抢到了，查库并把新数据写回缓存然后释放锁；这时一直在门口等着的线程 B 紧接着抢到了锁——如果线程 B 不再查一次缓存，它就会傻傻地再去查一遍数据库！所以拿到锁后必须先 Double Check 一次缓存，发现已经有值就直接返回。
- **追问 3：给 TTL 加随机值只能防“批量过期引起的雪崩”，如果是 Redis 整个宕机引起的雪崩怎么破？**
    - **参考答法**：这就需要系统级高可用兜底：事前靠 **Redis 哨兵/集群**自动故障切换，外加**本地缓存（如 Caffeine）做二级兜底；事中靠网关和微服务层的限流、降级、熔断**（比如直接返回兜底页或报错提示），防止数据库被瞬间打死。

## 5. 🤖 和大模型/AI 开发有什么关系

- **AI 网关语义缓存的抗压设计**：在热门 AI 产品或大促客服场景下，成千上万用户同时问同一个热点问题（如“双十一满减规则是什么”），如果这条语义缓存刚好过期，就会触发典型的**缓存击穿**——几千个请求同时涌向昂贵的大模型推理集群（GPU 直接 OOM 或 Token 账单暴涨）！用**逻辑过期 + 后台异步重新调 LLM 生成**，能完美避免并发击穿大模型。
- **防止恶意用户刷空知识库检索（穿透）**：如果外部脚本不断发乱码或不存在的文档 ID 请求 RAG 系统，先在入口做好参数校验 + 布隆过滤器拦截，能省下大量无谓的 Embedding 计算和向量检索算力。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. “缓存击穿”和“缓存雪崩”都是缓存过期导致的，它们最明显的区别是什么？
2. 为什么说解决缓存穿透时，“缓存空值”最简单，但遇到海量随机假 ID 攻击时还得靠“布隆过滤器”？
3. 解决缓存击穿的两种常见手段（互斥锁 vs 逻辑过期），在“数据库压力”和“用户体验（延迟/旧数据）”上各有什么取舍？

**自检参考要点**：1）击穿是**单个**热点 key 过期导致并发回源；雪崩是**大批** key 同时失效或 Redis 整体不可用；2）海量随机假 ID 每次都不重样，缓存空值会占满 Redis 内存；布隆过滤器占内存极小且能提前全部拦住；3）互斥锁保证数据最新但其他请求要排队等待；逻辑过期不阻塞用户（先返回旧值再后台异步刷），可用性极高但允许短时间看到旧数据。
