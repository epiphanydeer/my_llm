# Redis 分布式锁

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：当你的程序部署在好几台服务器上时，单机锁管不住别的机器；Redis 分布式锁就是大家公认的“公共抢麦器”，谁先在 Redis 里成功写下“我占着这把锁 + 30 秒自动过期”，谁就能执行关键操作，干完活后再凭自己的专属暗号把锁安全摘掉。

**生活大白话例子**：想象一个跨国公司只有一间 VIP 会议室（共享资源），不同分公司的员工（多台服务器）都要去用：

- **加锁原子性（SET key 暗号 NX PX 30000）**：你冲进会议室必须在门口挂牌“张三占用，30 分钟后自动作废”——这一挂牌和设倒计时必须**一口气做完**，万一你刚挂上牌还没来得及设倒计时就突然晕倒（服务器宕机），这间会议室就永远被锁死成死锁了！
- **防误删（专属暗号 + 原子比对删除）**：你写了一张“我是张三（唯一 `requestId`）”的暗号纸条压在锁下。万一你开会太久超过 30 分钟牌子自动失效了，李四进去开会了；你开完会出来准备摘牌时，必须**先看一眼纸条是不是写的“张三”**，不是就不许摘，免得把李四的锁给误删了！
- **自动续期（看门狗 Watchdog）**：如果怕会开不完，就雇个秘书在门口盯着（后台定时线程）：只要张三还在里面好好开会，每隔 10 秒就帮他把牌子有效期再续回 30 秒。

## 2. 🧠 底层机制与核心对比

### 分布式锁的四大核心要素（大白话拆解）

- **加锁原子性（**`NX + PX/EX`**）**：`NX` 保证“没人占的时候我才能占”，`PX` 保证“万一我挂了锁也能自动到期释放”。两条指令必须合成一条原子命令执行，不能拆成两步。
- **防误删（唯一** `requestId` **+ 原子比对释放）**：每次加锁生成一个全局唯一 ID（如 UUID + 线程号）当 value；释放锁时必须把“查 value 是不是我的 + 删除 key”打包成不可分割的原子操作（如通过 Lua 脚本执行），防止校验完刚要删的那一毫秒锁刚好过期被别人抢走。
- **业务超时续期（Watchdog 看门狗）**：如果业务执行时间不可控（可能比锁 TTL 长），像 Redisson 这样的成熟框架会启动后台看门狗线程，只要持锁线程还活着，就定期把锁的 TTL 续满。
- **常见踩坑警示**：① `SETNX` 和 `EXPIRE` 分两步写（中间宕机就死锁）；② 直接 `DEL` 释放锁不校验归属（误删别人锁）；③ 抢锁失败后死循环疯狂重试（把 Redis 打满，应配合退避休眠或快速失败）。

### 分布式锁关键环节对比表

| **关键环节** | **错误/简陋做法** | **正确工程做法** | **解决的核心风险** |
| --- | --- | --- | --- |
| **加锁** | 先 `SETNX`，再单独 `EXPIRE` | 单条原子命令 `SET key id NX PX ttl` | 防止加完锁还没设过期时间就宕机导致死锁 |
| **锁标识** | value 随便写个 `"1"` 或固定值 | 写入全局唯一 `requestId`（UUID+线程ID） | 区分锁是谁加的，避免张冠李戴 |
| **释放锁** | 直接执行 `DEL key` | 原子比对 `GET == requestId` 后再 `DEL` | 防止自己业务超时后误删别人新加的锁 |
| **超时续期** | 拍脑袋设一个死 TTL | 引入 **Watchdog 看门狗**自动续期 | 防止业务还没跑完锁先过期，导致并发踩踏 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问“Redis 分布式锁怎么实现”，最看重你能不能把**“四个核心问题（原子加锁、自动过期、防误删、超时续期）+ 主从极端缺陷”**一次性讲透：

1. **先讲为什么需要**：单机锁（如 `synchronized`）跨不了进程/机器，多实例部署下需要 Redis 做全局协调。
2. **拆解标准实现四步**：
    - **加锁**：用 `SET lockKey requestId NX PX 30000`，一条命令保证互斥和自动过期；
    - **归属防误删**：value 存唯一 `requestId`；
    - **安全解锁**：释放时先比对 value 再删除，且必须保证原子性（避免误删其他线程的锁）；
    - **续期机制**：业务耗时不固定时，借助 Redisson 的 **Watchdog（看门狗）** 自动续期。
3. **主动点出边界与局限**：诚实说明 Redis 分布式锁在主从异步复制下不是 100% 强一致（主节点刚加锁还没同步给从节点就宕机，从节点上位后可能导致两个客户端同时拿到锁），对资金强一致要求极高的场景需结合数据库唯一约束/乐观锁兜底。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：为什么不能先** `SETNX`**，成功后再紧接着执行** `EXPIRE`**？**
    - **参考答法**：因为这是两条独立命令，**不具备原子性**。如果在执行完 `SETNX` 之后、执行 `EXPIRE` 之前，客户端进程突然崩溃或机器断电了，这个锁就没有过期时间，永远不会自动释放，整个业务就会彻底死锁。
- **追问 2：释放锁的时候，我先** `GET` **一下看看是不是自己的，如果是再** `DEL`**，行不行？**
    - **参考答法**：不行！`GET` 和 `DEL` 之间也有时间差。假设你 `GET` 完确认是自己的（此时锁还剩 1 毫秒过期），刚准备发 `DEL` 命令时发生了一次网络卡顿或 GC 停顿，锁在这期间过期了，线程 B 抢到了新锁——你的 `DEL` 随后到达，照样把线程 B 的锁给误删了。所以校验和删除必须合并成一个原子操作。
- **追问 3：主从切换时 Redis 分布式锁为什么会失效？怎么解决？**
    - **参考答法**：因为 Redis 主从同步默认是**异步**的。客户端 A 在主节点加锁成功，主节点还没来得及把这把锁同步给从节点就挂了；哨兵把从节点升为新主节点后，新主里根本没有这把锁，客户端 B 就能再次加锁成功。解法有：1）业务层做好幂等和数据库乐观锁兜底（最实用）；2）使用 **Redlock**（向半数以上独立主节点同时加锁，但争议大、运维重）；3）对一致性要求极其严苛的场景改用 ZooKeeper / etcd 等强一致（CP）组件。

## 5. 🤖 和大模型/AI 开发有什么关系

- **防止 Agent 重复触发外部副作用操作**：在多副本部署的 AI Agent 后端里，如果用户连续手抖点了两次“提交报销/发送邮件”，或者定时任务集群同时扫到同一条待处理任务，必须用 **Redis 分布式锁**（按 `task_id` 加锁）确保同一时刻只有一个容器实例去调用大模型或外部支付/发信 API，防止重复扣费和重复发信。
- **知识库文档解析任务抢占**：多台 Worker 节点同时监听文档上传事件做切分和向量化（Embedding）时，用分布式锁锁住 `doc_id`，能避免两台机器同时烧算力重复解析同一份大 PDF。

尝试不看笔记，用大白话回答下面 3 个问题：

1. Redis 分布式锁中 `NX` 和 `PX` 两个参数各自起什么作用？
2. 为什么释放锁时，一定要校验 value 等于自己加锁时生成的 `requestId`？
3. Redisson 的“看门狗（Watchdog）”机制解决的是什么痛点？

**自检参考要点**：1）`NX` 保证只有 key 不存在时才能加锁成功（互斥），`PX` 设置毫秒级过期时间防止死锁；2）防止自己业务超时导致锁自动过期后，误删了其他客户端新拿到的锁；3）解决“业务执行时间不确定，锁可能提前过期”的问题，只要持锁线程还活着就自动延长 TTL。
