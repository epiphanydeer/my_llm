# Redis 缓存淘汰策略

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：当 Redis 设定的内存上限（`maxmemory`）装满了，但新数据还在往里塞时，Redis 就得按预先定好的规矩“腾地方”——要么拒绝新数据直接报错（`noeviction`），要么按“最近谁没被翻牌（LRU）”或“平时谁最冷门（LFU）”把旧数据踢出去。

**生活大白话例子**：把 Redis 想象成一个只有 100 个格子的热门超市寄存柜（`maxmemory`）：

- `noeviction`**（死守不踢）**：柜子满了就挂出“已满暂停寄存”牌子，谁再来存新包直接拒绝报错。
- `allkeys-lru`**（踢掉最久没来取的）**：不管什么柜子，看看谁放进去后**最久没人碰过**，就把那个包清走腾地方。
- `allkeys-lfu`**（踢掉平时访问次数最少的）**：就算某个包 5 分钟前刚被人摸过一次，但一整天总共就摸了 1 次；另一个包昨天摸了 1000 次。LFU 会果断踢掉那个“总共只摸 1 次”的冷门包，保住真正的热门货。
- `volatile-*`**（只踢贴了“临时条”的）**：只允许在贴了过期时间（TTL）的柜子里挑人踢，没贴过期条的“长期VIP柜”坚决不动。

## 2. 🧠 底层机制与核心对比

### 核心触发条件与策略分类（大白话拆解）

- **何时触发**：只有配置了 `maxmemory` 且当前使用内存达到上限，**再执行需要申请内存的写命令**时才会触发（普通读命令不受影响）。
- **三大阵营（共 8 种策略）**：
    1. **不淘汰（**`noeviction`**）**：默认兜底策略，内存满后写请求直接报错（OOM），适合不允许丢数据的场景。
    2. **仅在带过期时间的 key 中淘汰（**`volatile-*`**）**：包括 `volatile-lru`（最久未用）、`volatile-lfu`（最不常用）、`volatile-random`（随机）、`volatile-ttl`（谁快过期先踢谁）。**注意前提**：必须有足够多设置了过期时间的 key，否则依然会报 OOM！
    3. **在所有 key 中淘汰（**`allkeys-*`**）**：包括 `allkeys-lru`、`allkeys-lfu`、`allkeys-random`。纯缓存场景最省心、最常用。
- **LRU vs LFU 的核心差异**：**LRU** 看“最后一次访问离现在有多远”，**LFU** 看“一段时间内访问频率高不高”。此外，Redis 为了不拖慢主线程，用的是**随机抽样近似 LRU/LFU**，而不是全量排序。

### Redis 8 大淘汰策略对比表

| **策略名称** | **挑选范围** | **淘汰依据（大白话）** | **适用场景** |
| --- | --- | --- | --- |
| `noeviction` | 不淘汰 | 满了我就不收新写入，直接报错 | Redis 当数据库用、绝对不能自动丢数据 |
| `allkeys-lru` | **所有 key** | **谁最久没被访问就踢谁** | **纯缓存场景最经典默认选择** |
| `allkeys-lfu` | **所有 key** | **谁访问频率最低就踢谁** | **热点分布稳定、要死保高频数据的缓存** |
| `allkeys-random` | 所有 key | 闭眼随机踢一个 | 访问毫无规律、大家热度差不多 |
| `volatile-lru` | 仅设了 TTL 的 key | 带过期时间的里面，谁最久没用踢谁 | 缓存与持久配置混用，只准踢临时缓存 |
| `volatile-lfu` | 仅设了 TTL 的 key | 带过期时间的里面，谁频率最低踢谁 | 同上，且更看重保留长期高频热点 |
| `volatile-ttl` | 仅设了 TTL 的 key | 谁剩下的寿命最短（最快到期）踢谁 | 希望优先清理快过期的临时数据 |
| `volatile-random` | 仅设了 TTL 的 key | 带过期时间的里面随机踢 | 对临时缓存无所谓淘汰顺序 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问“Redis 内存满了怎么淘汰”，按**“触发条件 -> 三大分类 -> 生产选型建议”**三步答就非常稳：

1. **先说触发前提**：配置了 `maxmemory` 且达到上限后，再来写入命令就会触发淘汰策略。
2. **再按三大阵营梳理**：不淘汰（`noeviction`）、只从带过期时间的 key 里挑（`volatile-lru/lfu/ttl/random`）、从所有 key 里挑（`allkeys-lru/lfu/random`）。
3. **给出实战选型结论**：如果 Redis 纯粹当缓存用，首选 `allkeys-lru`（热点变化快）或 `allkeys-lfu`（热点长期稳定）；如果实例里混存了永久有效的业务数据，选 `volatile-*` 保护永久 key，但要警惕“带 TTL 的 key 不够多导致依然 OOM”的坑。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：为什么有时候明明配了** `volatile-lru`**，Redis 还是报内存溢出（OOM）错误？**
    - **参考答法**：因为 `volatile-lru` **只能从设置了过期时间（TTL）的 key 里挑人淘汰**。如果业务写入了大量**没设过期时间**的永久 key 把内存吃满了，Redis 找不到足够多带 TTL 的候选 key 来踢，最后照样只能返回 OOM 错误。
- **追问 2：**`LRU` **和** `LFU` **到底怎么选？LRU 有什么经典缺陷？**
    - **参考答法**：LRU 的经典缺陷是**容易被“突发批量扫描”污染**——比如半夜跑了个脚本把 10 万条冷门历史数据全扫了一遍，这些冷数据瞬间全变成“刚刚访问过”，反而把真正高频的热点数据给挤出去了。而 **LFU** 记录了访问频率，偶尔被扫一次的冷数据频率很低，很快会被踢掉，保住了真正的长期热点；如果业务热点切换很快，则用 LRU 更直观。
- **追问 3：**`noeviction` **模式下，内存满了之后连读请求也会报错吗？**
    - **参考答法**：不会。`noeviction` 拒绝的是**需要申请更多内存的写命令**（如 `SET`、`LPUSH` 等），普通的 `GET` 读请求和 `DEL` 删除请求依然可以正常执行。

## 5. 🤖 和大模型/AI 开发有什么关系

- **语义缓存（Semantic Cache / Prompt Cache）的容量管理**：为了省大模型 API 费用和降低延迟，很多 AI 网关会用 Redis 缓存“高频提问 -> 大模型回答”。这类缓存本质上具有极强的幂律分布（少数常见问题被问成千上万次），采用 `allkeys-lfu` 策略能牢牢保住高频问答缓存不被偶尔出现的长尾怪问题挤掉。
- **多租户会话上下文保护**：如果同一个 Redis 实例既缓存临时问答（带 TTL），又存用户的关键会话元数据，使用 `volatile-lru` 可以避免临时缓存把关键会话元数据踢丢。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. `volatile-lru` 和 `allkeys-lru` 最核心的区别是什么？
2. 为什么说半夜跑一次全量冷数据扫描时，LFU 比 LRU 更能保护热点缓存？
3. 如果 Redis 内存满了且策略是 `noeviction`，此时还能执行 `GET` 和 `DEL` 命令吗？

**自检参考要点**：1）`volatile-lru` 只在设置了过期时间的 key 中淘汰，`allkeys-lru` 在所有 key 中淘汰；2）LRU 只看“最近一次访问”，冷数据被扫一次就变成“最新”从而挤走热点；LFU 看“访问频率”，冷数据只访问一次依然会被优先淘汰；3）可以，`noeviction` 只拦截申请更多内存的写命令，不影响读和删除。
