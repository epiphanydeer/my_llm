# Redis 过期策略

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：Redis 给数据设了“保质期（TTL）”后，并不会傻傻地为每条数据雇一个倒计时闹钟到点就删（太费 CPU），而是采用 **“惰性删除 + 定期抽查删除”** 的组合拳，在省 CPU 和省内存之间找最佳平衡。

**生活大白话例子**：把 Redis 想象成一家生意火爆的生鲜超市，货架上的牛奶都贴了保质期（TTL）：

- **定时删除（不采用）**：如果给每一盒牛奶都配一个专职服务员盯着表，到期那一毫秒立刻扔掉，超市里 100 万盒牛奶就要雇 100 万个服务员，店老板直接破产（CPU 跑死）。
- **惰性删除（顾客拿的时候再看）**：平时店员不管它过期没过期；等有顾客伸手来拿这盒牛奶时，收银员顺手看一眼生产日期——过期了就当场扔进垃圾桶并告诉顾客“没货了”。
- **定期删除（店员每隔 10 分钟抽查几个货架）**：万一有些过期牛奶一直没人来买，老占着货架也不行。所以店员每隔一小段时间，随机抽查几排货架，把过期的顺手清理掉，抽查时间一到就停手去忙收银（绝不耽误接待顾客）。

## 2. 🧠 底层机制与核心对比

### 过期策略核心机制（大白话拆解）

- **过期字典（Expiry Dict）**：Redis 内部专门用一张字典记录“哪些 key 设了过期时间、具体什么时候过期”。只有设了 TTL 的 key 才会进这张表。
- **惰性删除（Lazy Expiration）**：**用的时候才查**。客户端每次读写某个 key 时，Redis 先查一下它过期没有；过期了就立刻删掉并返回空，没过期才正常返回。对 CPU 极友好，但“没人再访问的过期 key”会一直赖在内存里。
- **定期删除（Active Expiration）**：**后台抽样清理**。Redis 每秒会定时跑若干次（默认 10 次），每次从过期字典里**随机抽样**一批 key 检查，删掉其中过期的；如果过期比例高就再抽一轮，但有严格的时间上限（时间片限制），绝不长时间卡住主线程。
- **防踩坑小细节**：普通的 `SET key value` 覆盖写一个已有 TTL 的 key 时，**会把原来的过期时间清零变成永久有效**！如果想保留原 TTL，需要加上 `KEEPTTL` 选项。

### 三种过期清理思路对比表

| **策略名称** | **大白话做法** | **优点** | **缺点** | **Redis 是否采用** |
| --- | --- | --- | --- | --- |
| 定时删除 | 每个 key 配一个闹钟，到点立刻删 | 内存释放最及时，绝不浪费 | CPU 调度开销爆炸，高并发直接卡死 | **否** |
| **惰性删除** | **有人访问它时，顺便看一眼过期了就删** | **零额外 CPU 扫描开销** | **无人问津的过期 key 会长期占内存** | **是（主策略之一）** |
| **定期删除** | **后台每隔一小会儿随机抽查一批删掉** | **兜底回收冷门过期 key，限制时长不卡主线程** | **无法保证到期那一秒立刻物理删除** | **是（主策略之一）** |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问“Redis 的过期策略是什么”，注意**千万别和“内存淘汰策略”搞混**！按以下三步回答最清晰：

1. **直接给结论**：Redis 采用的是 **“惰性删除 + 定期删除”** 的组合策略，本质是在 **CPU 开销** 和 **内存占用** 之间做权衡。
2. **分别解释两者怎么配合**：
    - **惰性删除**是访问时触发检查，省 CPU 但清理不掉“再也没人访问的 key”；
    - **定期删除**是后台周期性带时间片限制地随机抽样删除，弥补惰性删除的内存泄漏风险，又不会因为全量扫描阻塞主线程。
3. **主动区分“过期策略”与“淘汰策略”**：点明过期策略针对的是“到期的 key”，而淘汰策略（如 LRU/LFU）针对的是“内存达到 `maxmemory` 上限”，如果还有大量漏网的过期 key 没被及时删掉，最后也会由内存淘汰策略兜底清理。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：为什么有时候 key 明明已经过期了，监控上看 Redis 内存却没有立刻降下来？**
    - **参考答法**：有两个原因：第一，Redis 的过期清理是**惰性 + 定期抽样**，TTL 到点那一刻并不保证立刻物理删除，可能要等下次被访问或被后台抽中才删；第二，即使 Redis 删了 key，底层的内存分配器（如 jemalloc）也可能会先留着这块空闲内存方便自己下次复用，不会立刻归还给操作系统。
- **追问 2：主从架构下，如果从节点上的 key 过期了，从节点会自己主动删掉吗？**
    - **参考答法**：不会由从节点自己做主删除，**过期删除以主节点为准**！当主节点因为惰性或定期删除清理掉一个过期 key 后，会向从节点同步一条 `DEL` 命令，从节点跟着删，这样才能保证主从数据一致（不过从节点在读数据时，如果发现 key 已过期会过滤掉不返回给客户端，避免读到脏数据）。
- **追问 3：过期策略和缓存淘汰策略到底有什么区别？**
    - **参考答法**：触发条件和对象完全不同。**过期策略**是时间驱动，只针对设置了 TTL 的 key，看“是不是到保质期了”；**淘汰策略**是空间驱动，只有内存触及 `maxmemory` 上限时才触发，按 LRU/LFU 等规则决定把谁踢出内存（哪怕它还没过期）。

## 5. 🤖 和大模型/AI 开发有什么关系

- **Agent 短期会话记忆的自动遗忘**：AI 客服或对话助手的上下文缓存通常只保留 30 分钟或 2 小时（设置 TTL）。借助 Redis 的过期策略，你完全不用自己写定时任务去扫表删过期对话，Redis 会在极低开销下自动清理冷掉的会话。
- **动态限流与验证码防重放**：用户登录验证码、API 防重放 `nonce` 令牌、大模型流式任务的临时状态都可以设几十秒的 TTL，既保证了安全性又防止内存被一次性历史数据撑爆。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. 为什么 Redis 不采用“给每个 key 设一个精准定时器，到点就删”的方案？
2. 如果只用惰性删除、不用定期删除，时间久了会发生什么问题？
3. 用 `SET key value` 重新覆盖一个原本还有 60 秒过期的 key 时，原来的过期时间还在吗？

**自检参考要点**：1）大量 key 同时维护定时器会消耗极高的 CPU 和调度资源，拖垮单线程主链路；2）过期后再也没人访问的 key 会变成“僵尸数据”，永远占着内存不释放；3）不在了，普通 `SET` 会清除原有 TTL 变成永久 key，除非显式带上 `KEEPTTL` 参数。
