# Redis 主从同步

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：为了防止单台 Redis 挂掉导致服务瘫痪，也为了让多台机器分担读压力，Redis 支持“一主多从”架构——新来的从节点通过**全量同步（打包发一张完整快照）**追平历史数据，之后日常就靠**增量同步（只补发最新的修改命令）**保持一致。

**生活大白话例子**：把主节点（Master）想象成总店老板，从节点（Replica/Slave）想象成新开张的分店店长：

- **全量同步（新店开业，一次性搬全套账本）**：新分店刚连上总店，啥也没有，只好跟总店说“老板，我是新人（`PSYNC ? -1`），给我发全套！”总店老板立刻拍一张当前完整库存快照（`BGSAVE` 生成 RDB）发过去；在打包和发送照片的这几分钟里，总店还在继续做生意，老板就把这几分钟的新账先记在一张临时纸条（复制缓冲区）上，等分店把快照加载完，再把纸条上的新账补发过去。
- **增量同步（半路断网重连，只补漏掉的那几页）**：分店断网了 2 分钟后重连，跟总店报上自己的暗号和最后记到的页码（`replid + offset`）。总店翻一下自己的近期流水备忘录（复制积压缓冲区 `repl_backlog_buffer`），发现“哎，你只漏了最近 50 笔，备忘录里都还留着呢”，于是直接把这 50 笔补发过去，不用重新搬整套账本！

## 2. 🧠 底层机制与核心对比

### 主从同步的核心步骤与状态（大白话拆解）

- **第一步：建立连接与握手**：从节点连上主节点 -> 发 `PING` 试探通不通 -> 发 `REPLCONF` 报端口和能力 -> 发 `PSYNC <replid> <offset>` 请求同步（首次连发 `PSYNC ? -1`）。
- **第二步：全量同步（首次复制或增量追不上时）**：主节点后台 `BGSAVE` 生成 RDB 发给从节点 -> 从节点清空旧数据并加载 RDB -> 主节点把生成和发送 RDB 期间积压的新写命令（存在复制缓冲区）补发给从节点。
- **第三步：命令传播（日常稳态）**：首次追平后，主节点每执行一条写命令，就异步发给从节点跟着执行；从节点定期回复 `ACK` 汇报自己当前的同步进度 `offset`。
- **第四步：断线重连时的增量同步**：靠三大核心状态配合——`master_replid`（主节点的复制身份 ID）、`offset`（主从双方各自记的复制进度偏移量）、`repl_backlog_buffer`（主节点内存里固定大小的环形备忘录）。只要从节点报上来的 `replid` 对得上，且 `offset` 之后的数据还在环形备忘录里没被新数据覆盖，就只补发增量！否则只能重新全量同步。

### 全量同步 vs 增量同步对比表

| **同步方式** | **触发时机（大白话）** | **传输内容** | **性能与网络开销** |
| --- | --- | --- | --- |
| **全量同步** | 第一次连接、`replid` 变了、或断线太久导致 `offset` 已被覆盖 | **整份 RDB 快照 + 期间积压的增量写命令** | **极高**（主节点需 `fork` 进程、占磁盘和网络带宽） |
| **增量同步** | 短暂断线重连，且缺失的数据还在 `repl_backlog_buffer` 里 | **仅缺失的那一小段增量写命令** | **极低**（精准补漏，秒级追平） |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问“Redis 主从同步是怎么实现的”，关键是要把 `PSYNC` **协议下的全量与增量流程**、以及**三个核心状态字段**讲清楚：

1. **先说明作用**：主从同步实现了**读写分离**（主写从读分摊流量），也是**哨兵（Sentinel）和集群（Cluster）高可用**的底层基石。
2. **完整走一遍连接与全量流程**：从节点发送 `PSYNC ? -1` -> 主节点 `BGSAVE` 生成 RDB 并发送 -> 期间新增写命令存入复制缓冲区 -> 从节点清空旧库加载 RDB -> 主节点补发缓冲区增量命令 -> 进入日常异步**命令传播**。
3. **重点讲透增量同步（断线重连）**：依靠 `replid`**（复制 ID）**、`offset`**（偏移量）** 和主节点的 `repl_backlog_buffer`**（环形复制积压缓冲区）**。只要断线后偏移量还在缓冲区范围内，就走增量补发，避免昂贵的全量复制。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：**`PSYNC` **和早期老版本的** `SYNC` **命令有什么本质区别？**
    - **参考答法**：老版本的 `SYNC` 非常笨，只要主从之间哪怕断线 1 秒钟，重连后也只能傻傻地重新走一遍全量 RDB 同步，极其耗费 CPU 和带宽；而 `PSYNC` 引入了 `replid + offset` 和 `repl_backlog_buffer`，支持**部分重同步（增量同步）**，短暂网络抖动后只需补发漏掉的那几条命令就行。
- **追问 2：为什么生产环境要特别注意调整** `repl_backlog_buffer` **的大小？**
    - **参考答法**：因为 `repl_backlog_buffer` 是一个固定大小的环形缓冲区，写满了就会覆盖最早的记录。如果它设得太小（比如默认 1MB），在写入高峰期只要网络抖动断线几秒钟，漏掉的命令就会被新命令覆盖掉，导致从节点重连时无法增量同步，被迫触发极其危险的**全量同步**（可能引发主节点 `fork` 阻塞和网卡打满）。通常建议按“平均每秒写入字节数 × 允许断线重连时间 × 2”来设置足够大的值。
- **追问 3：主从复制能保证“强一致性”吗？如果刚写完主节点立刻去读从节点，会怎样？**
    - **参考答法**：不能！Redis 的主从复制默认是**异步**的（属于最终一致性）。主节点执行完写命令就立刻给客户端返回成功了，随后才把命令异步发给从节点。如果在复制延迟的那几毫秒去读从节点，就可能读到旧数据（甚至根本读不到刚写进去的 key）。所以对强一致要求极高的读操作，必须直接读主节点。

## 5. 🤖 和大模型/AI 开发有什么关系

- **高并发 AI 知识库与特征缓存的读写分离**：当线上有几万个并发用户通过 RAG 检索系统读取热门文档缓存或用户画像时，单台 Redis 的网卡和单线程 CPU 很容易打满。通过**一主多从架构**，后台数据管线只写主节点，线上海量推理/检索请求分散到多个只读从节点，轻松实现读吞吐量的水平扩展。
- **理解 AI 服务“刚写入会话却读不到”的偶发 Bug**：如果你在多模态/Agent 系统里开启了 Redis 读写分离，刚把用户的上传文件状态写入主库，下一毫秒前端轮询路由到了从库，就可能因为主从异步复制延迟而报“文件不存在”。遇到这种状态强依赖的场景，应当强制路由到主节点读取。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. 在全量同步期间，主节点忙着生成和发送 RDB 快照，此时客户端还能往主节点写新数据吗？这些新数据怎么同步给从节点？
2. 决定断线重连后能不能走“增量同步”的三个关键要素是什么？
3. 为什么说 Redis 主从同步是“最终一致性”而不是“强一致性”？

**自检参考要点**：1）可以正常写；主节点会把这期间的新写命令先存进复制缓冲区，等从节点加载完 RDB 后再补发过去；2）`master_replid`（复制 ID 匹配）、`offset`（偏移量）以及未超出主节点 `repl_backlog_buffer`（环形积压缓冲区）的保留范围；3）因为主节点写入成功后不等从节点确认就返回了，命令是异步传播给从节点的，存在短暂延迟。
