# Redis 常见的数据结构

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：Redis 就像一个放在内存里的“百宝箱”，它不像普通数据库那样只能傻傻存表格，而是准备了 5 种最顺手的收纳盒（外加几种特种盒），让你按业务形状直接存取，快到飞起。

**生活大白话例子**：把 Redis 想象成家里玄关的智能收纳墙：

- **String（便利贴）**：一张纸条写一个值，比如“今天阅读量：1024”、或者门锁临时密码。
- **Hash（个人档案袋）**：一个袋子里按小格子分门别类放“姓名、年龄、城市”，只改“年龄”时不用把整个袋子撕了重写。
- **List（排队取餐号/双向传送带）**：左边塞进去、右边吐出来，天然适合做消息排队或“最新 10 条动态”。
- **Set（不重样的抽奖箱）**：扔进去两个一样的球会自动只留一个，还能瞬间算出“你和朋友共同关注了谁（交集）”。
- **ZSet（带分数的荣誉榜）**：每个名字都挂着一个分数，放进去自动按高分排好队，一眼就能拉出前十名（Top 10）。

## 2. 🧠 底层机制与核心对比

### 五大核心结构 + 扩展特种结构（大白话拆解）

- **String（字符串）**：最基础的键值对，最大存 512MB，底层用 **SDS（简单动态字符串）** 而不是 C 语言原生字符串（自带长度记录、防止溢出）。常用于缓存单值/JSON、点赞计数器、简单分布式锁。
- **Hash（哈希表）**：`field -> value` 结构，适合存对象属性。数据少时用紧凑结构省内存，数据多时转成哈希表保证速度；最大好处是**支持局部字段单独读写**。
- **List（列表）**：有序、可重复的双端队列，底层是 **quicklist**（把多个紧凑数组串成链表，兼顾省内存和双端插入速度）。常用于简单消息队列、最新评论时间线。
- **Set（集合）**：无序、**绝对不重复**，支持交集、并集、差集运算（底层用整数集合或哈希表）。常用于去重、抽奖名单、共同好友。
- **ZSet（有序集合）**：不重复且每个元素带一个 `score`（分数），自动按分数排序。底层同时用了**跳表（按分数范围排和查）+ 哈希表（按成员秒查分数）**。常用于排行榜、延迟任务队列。
- **Stream（消息流）**：专为消息队列设计的加强版结构，支持消息持久化、消费位点和消费者组，解决普通 `List` 弹完就丢、难确认的痛点。
- **三大特种结构**：**Bitmap**（按位记 0/1，适合亿级用户每日签到）、**HyperLogLog**（用极小内存估算海量去重 UV，允许微弱误差）、**Geospatial**（基于 ZSet 算“附近的人/门店”距离）。

### Redis 数据结构选型对比表

| **数据结构** | **大白话定位** | **底层核心实现** | **典型业务场景** |
| --- | --- | --- | --- |
| `String` | 万能便利贴 / 计数器 | SDS（简单动态字符串） | Token 缓存、文章阅读数、简单分布式锁 |
| `Hash` | 分格子的对象档案袋 | 紧凑列表 / 哈希表 | 用户信息、商品详情、购物车 |
| `List` | 双向传送带 | `quicklist`（压缩链表） | 最新动态列表、简单异步任务队列 |
| `Set` | 自动去重的抽奖箱 | 整数集合 / 哈希表 | 标签去重、共同好友（交集）、黑白名单 |
| `ZSet` | 自动排名的分数榜 | **跳表 + 哈希表** | 游戏积分榜、热搜榜、按时间戳的延迟队列 |
| `Stream` | 带回执的工业级快递流 | Radix Tree + listpack | 订单流水、需要 ACK 和消费组的可靠消息队列 |
| `Bitmap / HLL / Geo` | 特种工具箱 | 位图 / 概率计数 / ZSet | 签到打卡 / 千万级 UV 统计 / 附近门店 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问“Redis 常见数据结构”，不要只干背 5 个名字，按**“5 大基础 + 4 大扩展 + 底层设计亮点”**来答最有技术深度：

1. **先报 5 大核心结构及场景**：`String`（单值/计数）、`Hash`（存对象改局部字段）、`List`（双端队列/时间线）、`Set`（去重/交并差集）、`ZSet`（排行榜/延迟队列）。
2. **再补 4 个进阶结构**：`Stream`（完整消息流与消费组）、`Bitmap`（位图签到）、`HyperLogLog`（省内存 UV 统计）、`Geospatial`（地理位置）。
3. **顺手甩出两个底层亮点**：`String` 底层用 SDS 而不是 C 字符串；`ZSet` 底层用“哈希表 + 跳表”双剑合璧，既能 O(1) 查成员分数，又能高效按分数做范围排序。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：Redis 是用 C 语言写的，为什么不直接用 C 原生字符串，非要自己造一个 SDS？**
    - **参考答法**：三个原因：第一，C 字符串求长度要从头数到 `\0`（O(N)），而 SDS 直接把长度记在头部，**O(1) 就能拿到长度**；第二，C 字符串遇到 `\0` 就截断，存不了图片等二进制数据，SDS **二进制安全**；第三，SDS 自带空间预分配机制，频繁拼接修改时能避免缓冲区溢出、减少内存重新分配次数。
- **追问 2：**`ZSet` **为什么既要用哈希表，又要用跳表？只用一个不行吗？**
    - **参考答法**：各管一摊，缺一不可。只用跳表的话，想查某个指定用户现在的分数得从头找，不够快；只用哈希表的话，数据是无序的，没法拉出“第 1 名到第 10 名”。两者结合后，**哈希表负责 O(1) 定位成员分数，跳表负责按分数有序排序和范围查询**，查得快也排得快。
- **追问 3：**`List` **和** `Stream` **都能做消息队列，实际项目怎么选？**
    - **参考答法**：如果只是简单轻量级异步解耦、丢一两条也能接受，用 `List` 就够了；如果要求消息不能丢、需要多个消费者分摊（消费者组）、消费失败要能重试和 ACK 确认，就必须选 `Stream`（或者直接上 Kafka/RabbitMQ）。

## 5. 🤖 和大模型/AI 开发有什么关系

- **AI 对话上下文（短期记忆）存储**：多轮对话机器人每次都要快速拉取最近 10 轮历史消息，用 Redis `List` 或 `String`（存 JSON）按 `session_id` 缓存，毫秒级拼接好喂给大模型，比每次回查 MySQL 快一个数量级。
- **大模型限流与 Token 计数**：给免费用户做“每分钟最多问 20 次”或“每日 Token 消耗上限”，直接用 Redis `String`（`INCR` + 过期时间）或 `ZSet`（滑动时间窗口，用时间戳当 score）实现，既精准又抗得住高并发。
- **Redis Stack 作为轻量向量库**：现代 Redis 早已支持向量相似度检索（HNSW/Flat），在中小规模 RAG 应用里可以直接用同一套 Redis 既做业务缓存又做向量召回。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. 想存一个用户对象（包含姓名、头像、积分），而且经常只单独修改“积分”，用 `String` 存 JSON 好还是用 `Hash` 好？为什么？
2. `ZSet` 底层为什么要同时维护“哈希表”和“跳表”两套结构？
3. 如果想统计“全站每天有多少个不重复的访客（UV）”，要求内存越省越好、允许 1% 以内误差，该选哪种数据结构？

**自检参考要点**：1）用 `Hash` 更好，因为可以只更新 `score` 这一个字段，不用把整个 JSON 序列化再覆盖写一遍；2）哈希表用来按成员名 O(1) 查分值，跳表用来按分值排序和范围查找（如 TopN）；3）`HyperLogLog`。
