# 说一说事务隔离级别

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：事务隔离级别就是数据库在“多人同时改账会不会乱（数据准确性）”和“大家要不要排队干等（并发性能）”之间定下的四档安全等级——从几乎不管（读未提交）到彻底排队（串行化），MySQL 默认选的是兼顾性能与安全的第三档**可重复读（Repeatable Read）**。

**生活大白话例子**：把数据库想象成一间多人同时查账、改账的财务室，如果隔离没做好，会出现三种经典“灵异现象”：

- **脏读**：会计 A 把账本上的余额临时改成了 1000 但**还没盖章提交**，会计 B 凑过来一看就按 1000 报了税；结果一分钟后会计 A 发现算错了把刚才的修改涂掉撤回了——会计 B 读到了根本不存在的“脏”数据！
- **不可重复读**：会计 B 下午 2:00 看张三余额是 500；2:01 会计 A 修改并**正式提交**把张三余额改成了 800；2:02 会计 B 还没走出门，再看一眼张三余额变成了 800——同一趟活里两次看**同一行**结果不一样。
- **幻读**：会计 B 下午 2:00 统计“余额大于 500 的人一共有 3 个”；2:01 会计 A **新开户并提交**了一个余额 1000 的王五；2:02 会计 B 再按同样条件一数，凭空变成了 4 个人，像出现幻觉一样！

## 2. 🧠 底层机制与核心对比

### 四大隔离级别（大白话拆解）

- **读未提交（Read Uncommitted）**：门槛最低，别人**还没提交的草稿**你都能直接看到。性能最高，但脏读、不可重复读、幻读全都会发生，生产基本不用。
- **读已提交（Read Committed，简称 RC）**：只能看到别人**已经正式提交**的数据，彻底消灭了“脏读”。但同一事务里两次查同一行，仍可能因为中间别人提交了修改而变样（存在不可重复读和幻读）。
- **可重复读（Repeatable Read，简称 RR，MySQL 默认）**：事务一开始就拍好快照（通过 **MVCC**），全程无论别人怎么改并提交，你每次看同一行结果都一模一样，解决了不可重复读；而且 MySQL InnoDB 还通过 **Next-Key Lock（行锁 + 间隙锁）** 堵住了范围插入，在绝大多数场景下也避免了幻读。
- **串行化（Serializable）**：安全级别最高，直接对读写都加锁，大家排成一列纵队一个接一个执行。三大问题全无，但并发性能暴跌，极少在普通业务中使用。

### 四大隔离级别与并发问题对比表

| **隔离级别** | **大白话规则** | **脏读** | **不可重复读** | **幻读** | **并发性能与常用度** |
| --- | --- | --- | --- | --- | --- |
| 读未提交（RU） | 别人没保存的草稿都能看 | 会发生 | 会发生 | 会发生 | 性能最高，但数据太乱，几乎不用 |
| 读已提交（RC） | 只看别人已提交的结果 | **不会** | 会发生 | 会发生 | 较高（Oracle/PG 默认，部分互联网公司也会用） |
| **可重复读（RR）** | **进门拍快照，全程看同一份** | **不会** | **不会** | **InnoDB 基本避免** | **高且稳（MySQL 默认隔离级别）** |
| 串行化（Serializable） | 所有事务排队，一次只进一个 | **不会** | **不会** | **不会** | 极低（全加锁排队，极少用） |

## 3. 🗣️ 面试官视角：怎么串成体系回答

被问到“说一说事务隔离级别”，最佳回答结构是**“先讲三大并发问题 -> 再列四档隔离级别 -> 最后点出 MySQL 的默认选择与底层实现”**：

1. **先定义三个并发问题**：一句话区分**脏读**（读到未提交数据）、**不可重复读**（同事务内两次读同一行值变了，侧重修改/删除）、**幻读**（同事务内两次按条件查，行数变了，侧重范围新增）。
2. **由低到高列出四个隔离级别**：RU（全防不住）、RC（防脏读）、RR（MySQL 默认，防脏读和不可重复读，InnoDB 下还能很大程度防幻读）、Serializable（全防住但性能最差）。
3. **落到 MySQL 实现原理**：点明 InnoDB 在 RC 和 RR 下靠 **MVCC**（Read View 生成时机不同）实现快照读隔离，在 RR 下靠 **Next-Key Lock** 防止当前读的幻读。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：“不可重复读”和“幻读”听起来很像，到底怎么区分？**
    - **参考答法**：核心区别在于**数据是“同一行被改了”还是“凭空多出/少了整行”**。不可重复读针对的是**同一条记录的内容**被其他事务修改或删除后提交，导致前后两次读的值不一致（重点靠 MVCC 锁住旧版本解决）；幻读针对的是**同一个范围查询条件**，因为其他事务在范围里**新插入**了记录并提交，导致两次查出来的**总行数**不一样（重点靠间隙锁/临键锁拦住新插入解决）。
- **追问 2：为什么很多大厂（如阿里部分业务）会特意把 MySQL 默认的 RR 改成 RC？**
    - **参考答法**：主要有两个工程原因：第一，RC 模式下没有间隙锁（Gap Lock），大大减少了死锁和锁等待的概率，高并发写入吞吐量更好；第二，在早期的 Binlog Statement 格式下 RR 才刚需，现在主流都用 Row 格式 Binlog，改用 RC 完全没问题且并发更高。
- **追问 3：MySQL 默认的 RR 级别，是 100% 彻底杜绝幻读了吗？**
    - **参考答法**：不是 100% 绝对。如果在同一个事务里，先执行普通 `SELECT`（快照读），中间别人插了一条数据并提交，接着你自己在当前事务里执行了一句 `UPDATE`（当前读，会把新插入那行的 `DB_TRX_ID` 改成你自己的事务 ID），最后你再普通 `SELECT`，就会把那条本来不属于你的“新行”读出来——这就是经典的“混用快照读与当前读”引发的幻读特例。

## 5. 🤖 和大模型/AI 开发有什么关系

- **RAG 知识库增量同步与隔离级别选择**：当后台定时任务正在往数据库批量更新一批企业文档（事务未提交）时，线上用户正在通过 AI 问答接口检索文档。如果数据库设成“读未提交”，用户就会搜到更新到一半的残缺片段喂给大模型产生幻觉；用默认的 **RR 或 RC** 就能保证线上检索永远只看到完整已提交的知识版本。
- **多轮 Agent 状态机的一致性**：当多个异步回调（Webhook）同时更新同一个 Agent 会话状态时，理解隔离级别能帮你决定什么时候该用普通快照读、什么时候该用加锁读（`FOR UPDATE`），避免状态机跳变错乱。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. 读已提交（RC）解决了哪个问题，又遗留了哪两个问题？
2. 同样是结果变了，“不可重复读”和“幻读”在发生原因上有什么本质区别？
3. MySQL 默认的可重复读（RR）分别靠哪两个机制来解决“不可重复读”和“幻读”？

**自检参考要点**：1）RC 解决了**脏读**，但依然存在**不可重复读**和**幻读**；2）不可重复读是**同一行数据被修改**导致内容变了，幻读是**范围内被新插入了行**导致记录数变了；3）靠 **MVCC（复用事务开始时的 Read View）** 解决不可重复读，靠 **Next-Key Lock（行锁+间隙锁）** 在当前读时防止幻读。
