# 什么是数据库中的锁，有哪些类型？

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：数据库的锁就是“防撞门栓”，用来防止多个人同时修改同一份数据时把账改乱；按锁住的范围大小，从小到大分为**行级锁（只锁一行）**、**表级锁（锁整张表）和全局锁（锁整个库）**。

**生活大白话例子**：把数据库想象成一栋办公楼（整个实例），里面有很多会议室（表），每个会议室里有很多座位（行）：

- **全局锁**：整栋大楼拉闸只允许参观拍照、不准任何人搬东西（全库只读），专门用来做**全库备份**。
- **表级锁**：把整间会议室大门锁死，哪怕你只想改第 3 个座位上的名牌，别人也别想进这间屋子坐其他座位（并发度低，但管门成本小）。
- **行级锁**：会议室大门敞开，大家各坐各的，谁要改 5 号座位的资料，就只把 5 号座位锁起来（并发度极高，大家互不耽误，InnoDB 默认就用它）。

## 2. 🧠 底层机制与核心对比

### 按粒度拆解三类锁（大白话解释）

#### 一、全局锁（锁整栋楼）

- **全局锁（FTWRL）**：让整个数据库进入只读状态，拦住所有增删改和表结构修改，确保全库逻辑备份时前后数据像同一秒拍出来的快照（现在 InnoDB 备份通常用事务快照替代，避免长时间全库只读）。

#### 二、表级锁（锁整间屋）

- **表锁**：最原始的整表锁定（MyISAM 默认用它），开销小但并发极差，一人写全表堵死。
- **元数据锁（MDL）**：自动加在表结构上的保护锁，防止“有人正在查表数据时，另一个人突然把列删了或改名了”（保证读写数据 DML 与改表结构 DDL 不打架）。
- **意向锁（IS / IX）**：InnoDB 自动加的“门口挂牌”。事务想锁某一行之前，先在表门口挂个牌子说“里面有人锁了行”，这样别人想锁整张表时看一眼门口牌子就知道行不行，不用逐行检查。
- **AUTO-INC 锁（自增锁）**：专管自增主键（如 `id=1,2,3...`）的并发分配，保证多人同时插数据时自增号不撞车。

#### 三、行级锁（锁单个座位，InnoDB 核心）

- **记录锁（Record Lock）**：精准锁住索引里的某**一条**记录本身（写操作加排他锁，特定加锁读加共享锁）。
- **间隙锁（Gap Lock）**：不锁记录本身，专门锁住**两条记录之间的空隙**，防止别人往空隙里硬塞新数据（可重复读级别下用来防“幻读”）。
- **临键锁（Next-Key Lock）**：InnoDB 默认的行锁形态 = **记录锁 + 间隙锁**，既锁住当前这条记录，又锁住它前面的空隙（左开右闭区间）。
- **插入意向锁（Insert Intention Lock）**：一种特殊的间隙锁，表示“我打算往这个空隙里插一条新记录”。只要两个事务插的位置不冲突，彼此不会互相阻塞。

### 数据库锁类型全景对比表

| **锁粒度** | **具体锁名称** | **大白话作用** | **加锁方式** | **对并发的影响** |
| --- | --- | --- | --- | --- |
| 全局级 | 全局锁 | 全库只读，专供全库逻辑备份 | 手动命令 `FLUSH TABLES WITH READ LOCK` | 极高（全库无法写入） |
| 表级 | 表锁 | 锁整张表，MyISAM 默认方式 | 手动 `LOCK TABLES` 或引擎自动 | 高（阻塞整张表的并发读写） |
| 表级 | 元数据锁（MDL） | 防止查数据时有人同时改表结构 | 访问表时自动加锁 | 正常不阻塞，但长事务会堵住改表操作 |
| 表级 | 意向锁（IS / IX） | 表门口的“内有行锁”提示牌 | InnoDB 自动加 | 极低（意向锁之间兼容，只协调表锁） |
| 表级 | AUTO-INC 锁 | 保证并发插入时自增 ID 不重复 | 插入自增列时自动加 | 较低（插入完或分配完即释放） |
| 行级 | 记录锁（Record Lock） | 只锁住某一条索引记录 | InnoDB 基于索引自动加 | 低（只影响同一行） |
| 行级 | 间隙锁（Gap Lock） | 锁住记录之间的空隙，防别人新插数据 | RR 隔离级别下自动加 | 中（会锁住一段范围空隙） |
| 行级 | 临键锁（Next-Key Lock） | 记录锁 + 间隙锁，InnoDB 默认行锁 | RR 隔离级别下范围/非唯一查询自动加 | 中（兼顾防幻读与行互斥） |

## 3. 🗣️ 面试官视角：怎么串成体系回答

被问到“数据库有哪些锁”，切忌只说“行锁表锁”或“悲观锁乐观锁”就结束，建议按**“粒度从大到小（全局 -> 表级 -> 行级）”**清晰展开：

1. **全局锁**：用于全库只读备份（FTWRL），但现在 InnoDB 更常用一致性事务快照。
2. **表级锁**：包含显式表锁、保护表结构的 **MDL 元数据锁**、协调表锁与行锁的**意向锁**、以及管自增 ID 的 **AUTO-INC 锁**。
3. **行级锁（InnoDB 重点）**：分为**记录锁**（锁单条索引）、**间隙锁**（锁空隙防幻读）、**临键锁**（默认形态，记录+间隙）、以及**插入意向锁**。最后顺带提一句：InnoDB 行锁是**加在索引上的**，没走索引可能会退化成锁全表！

## 4. ❓ 高频面试追问与参考答法

- **追问 1：InnoDB 的行级锁到底锁的是“数据行”还是“索引”？如果查询没用到索引会怎样？**
    - **参考答法**：InnoDB 的行级锁是**基于索引实现**的，它锁的是索引记录。如果一条 `UPDATE` 或 `SELECT ... FOR UPDATE` 的 `WHERE` 条件没有命中索引，InnoDB 会沿着隐藏的聚簇索引做全表扫描，把扫描到的每一条记录（甚至间隙）都加上锁，结果等价于**“锁表”**，并发性能会瞬间雪崩！
- **追问 2：间隙锁主要解决什么问题？在什么隔离级别下才会出现？**
    - **参考答法**：间隙锁主要解决**幻读**问题（同一个事务里两次按范围查询，第二次突然多出别人新插入的行）。它通过锁住索引记录之间的空隙，阻止其他事务在范围里插入新记录。间隙锁只在 **可重复读（REPEATABLE READ）** 隔离级别下生效；在读已提交（RC）下默认是关闭的。
- **追问 3：表级锁里的“意向锁”看起来有点多余，它到底有啥用？**
    - **参考答法**：它是为了**快速检查兼容性**。试想如果表里有 1000 万行，现在有个事务想给整张表加表级写锁，难道要逐行去查这 1000 万行里有没有行锁吗？有了意向锁之后，任何事务加行锁前都会先在表上挂个意向锁；想加表锁的人只需看一眼表上有没有意向锁，O(1) 时间就能判断能不能加锁，省去了全表扫描检查的巨大开销。

## 5. 🤖 和大模型/AI 开发有什么关系

- **AI 计费与 Token 额度扣减的并发安全**：当用户同时开了多个对话标签页并发向大模型发请求时，后台需要实时扣减用户的剩余 Token 额度或余额。如果在 MySQL 里更新账户余额，必须依靠 InnoDB 的**行级排他锁**（如 `UPDATE accounts SET balance = balance - 100 WHERE user_id = 1 AND balance >= 100;`），确保高并发下只锁住当前这一个用户的行，既不会像表锁那样卡死全站用户，也不会扣成负数。
- **Agent 并发更新同一份工作流状态**：多 Agent 协同系统中，多个子 Agent 同时往数据库写入任务进度或抢占待处理任务时，理解行锁与索引的关系能帮你避免“因为没建索引导致整张任务表被锁死”的线上故障。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. 为什么在生产环境里，对一张大表做“加字段”等改表结构操作（DDL）时，如果正好有个慢查询没结束，整个表后续的所有读写都会被卡住？这涉及哪种锁？
2. 记录锁、间隙锁、临键锁（Next-Key Lock）三者是什么关系？
3. 为什么说“InnoDB 的 `UPDATE` 语句如果忘了走索引，并发就会退化成表锁一样慢”？

**自检参考要点**：1）涉及**元数据锁（MDL）**，慢查询拿着 MDL 读锁不放，DDL 申请 MDL 写锁被阻塞，而后续所有新请求又会被堵在 DDL 的写锁后面；2）临键锁 = 记录锁 + 间隙锁，既锁当前记录又锁前面的空隙；3）因为 InnoDB 行锁加在索引上，不走索引就只能扫描聚簇索引并给所有记录加锁，等同锁整张表。
