# 基本 SQL 语句

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：SQL 就是你和数据库仓库管理员沟通的“标准化普通话”，用来告诉它你要“找什么数据、怎么统计、改哪一行、或者怎么防止多个人同时改乱账”。

**生活大白话例子**：把数据库想象成一家超大超市的 Excel 账本系统（每张表就是一个 Excel Sheet，比如 `users` 顾客表、`orders` 订单表）。你不能直接冲进库房翻箱倒柜，只能通过 SQL 这张“标准提货单”发指令：想找人就填 `SELECT`（查），想把顾客表和订单表拼在一起看谁买了啥就填 `JOIN`（连表），想算今天一共卖了多少钱就填 `SUM` + `GROUP BY`（聚合分组），想改库存或加新会员就填 `INSERT / UPDATE / DELETE`（增删改）。

## 2. 🧠 底层机制与核心对比

### 核心子概念（大白话拆解）

- **数据查询（SELECT）**：就像在 Excel 里做“筛选、排序、去重、翻页”，只把你关心的列和行挑出来。
    - 极简示例：`SELECT name, age FROM users WHERE age > 25 ORDER BY age DESC LIMIT 10;`（挑出 25 岁以上用户，按年龄倒序拿前 10 条）
- **多表连接（JOIN 与子查询）**：当“用户信息”和“订单金额”分别记在两张表里时，用共同的编号（如 `user_id`）把两张表对齐拼起来。
    - 极简示例：`SELECT u.name, o.amount FROM users u LEFT JOIN orders o ON u.id = o.user_id;`（以左边的用户表为准，把每个人的订单金额拼过来，没下单的也保留名字）
- **聚合与分组（GROUP BY & HAVING）**：先按某个标签把数据“分堆”（比如按城市分堆），再对每一堆分别算数（计数、求和、平均），`HAVING` 则是算完之后再筛掉不达标的堆。
    - 极简示例：`SELECT city, COUNT(*) FROM users GROUP BY city HAVING COUNT(*) > 10;`（统计每个城市有多少用户，只留下超过 10 人的城市）
- **增删改（INSERT / UPDATE / DELETE）**：往账本里记新账、改旧账、撕掉错账。改和删一定要带 `WHERE` 条件，否则容易把整张表全改了。
    - 极简示例：`UPDATE users SET age = 28 WHERE id = 1;`
- **索引与执行计划（EXPLAIN）**：给账本加“目录”，并用 `EXPLAIN` 提前看数据库打算怎么查（是翻目录还是傻傻一页页全表翻）。
    - 极简示例：`EXPLAIN SELECT * FROM users WHERE age > 30;`
- **事务与锁（Transaction & Lock）**：给一连串操作套上“保险箱”，要么全成功要么全撤回；锁则决定修改数据时别人能不能同时插队改同一行。

### 核心类别对比表

| **语句类别** | **核心关键字** | **大白话作用** | **常见踩坑点** |
| --- | --- | --- | --- |
| 基础查询 | `SELECT / WHERE / ORDER BY / LIMIT` | 挑列、筛选、排序、分页 | 翻页太深时 `OFFSET` 会很慢，可用 `WHERE id > ? LIMIT 10` 优化 |
| 多表连接 | JOIN / LEFT JOIN / 子查询 | 把拆开放的几张表按关联键拼起来 | `INNER JOIN` 只留两边都有的，`LEFT JOIN` 会保留左边没匹配上的行 |
| 聚合分组 | `COUNT / SUM / GROUP BY / HAVING` | 先分堆再统计，再筛统计结果 | `WHERE` 在分组前过滤单行，`HAVING` 在分组后过滤统计值 |
| 数据写入 | `INSERT / UPDATE / DELETE` | 新增、修改、删除记录 | `UPDATE/DELETE` 漏写 `WHERE` 会酿成全表事故 |
| 性能排查 | `EXPLAIN / SHOW INDEX` | 看清查询有没有走目录（索引） | 不要盲目在生产大表直接加索引，先用 `EXPLAIN` 验证 |
| 事务控制 | `BEGIN / COMMIT / ROLLBACK / FOR UPDATE` | 打包执行或加锁防并发改乱 | `FOR UPDATE` 是悲观锁占位，用完必须及时提交释放 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官考基本 SQL，通常不是让你背语法，而是看你能不能把**“写得对”和“跑得快、改不乱”**串成一条线：

1. **先按职责分类**：把 SQL 拆成**查（SELECT/JOIN/GROUP BY）、改（INSERT/UPDATE/DELETE）、调优（EXPLAIN/索引）、并发安全（事务/锁）**四大块，说明白日常业务里 80% 都是围绕“精准筛选 + 合理连表 + 安全修改”展开。
2. **再点出高频业务题套路**：比如“查每个用户最后一笔订单”用 `GROUP BY + MAX` 或子查询连表，“查重复数据”用 `GROUP BY ... HAVING COUNT(*) > 1`，“深分页优化”用游标条件 `id > ?` 替代大 `OFFSET`。
3. **最后落到工程意识**：写查询时避免 `SELECT *` 和对条件列套函数（比如用范围查询代替 `DATE(register_time) = '2024-01-01'`），改数据必须带 `WHERE` 且核心资金/库存操作要包在事务里。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：**`WHERE` **和** `HAVING` **都能做过滤，到底有什么区别？**
    - **参考答法**：执行时机不同。`WHERE` 是在**分组之前**对每一行原始数据做筛选，不能直接用 `COUNT`、`SUM` 这类聚合函数；`HAVING` 是在 `GROUP BY` **分组并算完统计值之后**，对每一组的结果做二次过滤。
- **追问 2：**`LEFT JOIN` **和** `INNER JOIN` **选哪个？关联不上会怎样？**
    - **参考答法**：`INNER JOIN` 只保留两张表都能对上号的数据；`LEFT JOIN` 会把左表所有行都保留下来，右表对不上的字段填 `NULL`。比如“查所有用户及其订单（没下过单的用户也要显示）”，就必须用 `LEFT JOIN`。
- **追问 3：为什么面试总说深度分页** `LIMIT 10 OFFSET 100000` **很慢，怎么改？**
    - **参考答法**：因为 `OFFSET 100000` 会让数据库先数出前 100010 条再扔掉前 10 万条，白干大量活。工程上常改成“书签翻页”（延迟关联或游标分页），比如记住上一页最后一条的 `id`，下一页直接查 WHERE id > 上一页最大id LIMIT 10，直接从目录定位跳过前 10 万行。

## 5. 🤖 和大模型/AI 开发有什么关系

- **Text-to-SQL（自然语言转 SQL）**：在企业级 BI 助手或数据分析 Agent 中，大模型的核心任务就是把老板的一句“帮我查上个月华东区复购率最高的 5 个客户”，精准翻译成带 `JOIN`、`GROUP BY`、`ORDER BY` 和 `LIMIT` 的 SQL。你对 `HAVING`、`LEFT JOIN` 和防全表扫描的边界越清楚，越能写出高质量的 Few-shot 提示词（Prompt）和 SQL 校验护栏（Guardrail），防止 Agent 生成拖垮数据库的慢查询。
- **RAG 与结构化记忆检索**：AI 应用不仅靠向量库做语义检索，用户画像、权限控制、对话历史元数据、Agent 工具调用日志往往都存在关系型数据库里，靠基础 SQL 做精确过滤（`WHERE user_id = ? AND status = 'active'`）再喂给大模型。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. 如果你要统计“每个城市订单总额超过 1 万元的 VIP 城市”，应该用 `WHERE` 还是 `HAVING` 来判断“超过 1 万”？为什么？
2. 为什么大表翻到第 1000 页时，`LIMIT 10 OFFSET 10000` 会变慢？换成 `WHERE id > 10000 LIMIT 10` 为什么就快了？
3. 在给大模型写 Text-to-SQL 的系统提示词时，你会加上哪两条“保命规则”来防止它写出危险或极慢的 SQL？

**自检参考要点**：1）用 `HAVING`，因为“订单总额”是按城市 `GROUP BY` 分组求 `SUM` 后才算出来的；2）`OFFSET` 需要把前面 1 万条全扫描并丢弃，而 `id > 10000` 能直接利用主键目录跳过前面数据；3）例如：禁止生成不带 `WHERE` 的 `UPDATE/DELETE`、禁止无限制的 `SELECT *`（必须带 `LIMIT`）、尽量用范围条件替代对日期列套函数。
