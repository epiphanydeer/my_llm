# 索引失效的场景有哪些

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：索引失效就是你明明花了钱印了“书本目录”，但因为你提问题的方式太刁钻（比如只记得书名最后一个字、或者让数据库先做算术再找），数据库只好把目录扔一边，老老实实从第一页翻到最后一页（全表扫描）。

**生活大白话例子**：想象你手里有一本按“姓氏拼音”排好序的电话簿（索引）：

- **以通配符开头查（LIKE '%明'）**：你只知道对方名字最后一个字叫“明”，不知道姓什么，按姓氏排的电话簿完全帮不上忙，只能一页页从头翻。
- **对索引列套函数或算术（**`age + 1 = 30`**）**：目录上记的是每个人的原年龄，你非要按“明年几岁”去翻目录，目录对不上号，只能全表重算。
- **违背最左前缀（联合索引 (省, 市, 区) 只查 市）**：电话簿先按省排、再按市排，你不说哪个省直接找“朝阳区”，各个省都有朝阳区，还是得全本翻。

## 2. 🧠 底层机制与核心对比

### 索引失效的四大根源（大白话拆解）

#### 一、查询条件“折腾”了索引列（最常见 5 种）

1. **在索引列上用函数或数学计算**：索引存的是原始值，一旦对列做运算（如 `DATE_FORMAT(create_time, ...) = '2023-10-26'` 或 `price * 0.8 < 100`），B+ 树无法直接匹配。
    - 极简改法：把计算移到等号右边，例如 `price < 100 / 0.8`。
2. **以** `%` **或** `_` **开头的模糊匹配**：索引按从左到右的字符顺序排列，`'zhang%'` 能用上索引，但 `'%zhang%'` 找不到起点，直接失效。
3. **使用不等于（**`!=` **或** `<>`**）**：排除某个值往往意味着要保留绝大多数行，优化器算成本后常直接全表扫描。
4. **用** `OR` **连接不同的索引列**：如 `WHERE name = 'A' OR category = 'B'`（两列各自独立建了索引），优化器很难同时走两棵树，往往退化成全表扫（`OR` 连**同一列**通常能走索引）。
5. **隐式类型转换**：比如 `phone` 字段是字符串（`VARCHAR`），SQL 里却传了个数字 `WHERE phone = 13800138000`，MySQL 会在底层偷偷把整列字符串转成数字再比对，相当于给索引列套了个转换函数！

#### 二、违背联合索引的“最左前缀原则”

- 建了联合索引 `(a, b, c)`，必须从最左边的 `a` 开始连续匹配。只查 `WHERE b = 2` 或 `WHERE c = 3` 会直接失效；查 `WHERE a = 1 AND c = 3` 时，只有 `a` 能用上索引，`c` 用不上。

#### 三、优化器主动“嫌弃”索引

- 查询返回的结果集比例太大（比如超过 20%~30%）、索引列区分度太低、或者表的统计信息过期算错了成本，优化器会主动选择全表扫描。

#### 四、索引本身异常

- 索引损坏或未生效（极少见，可通过重建或检查表状态解决）。

### 常见索引失效写法 vs 正确改写对比表

| **踩坑类型** | **容易失效的 SQL 写法** | **大白话原因** | **推荐改写思路** |
| --- | --- | --- | --- |
| 索引列套函数 | `WHERE DATE(create_time) = '2024-01-01'` | 目录记的是原时间戳，不是转换后的日期 | 改成范围查：`create_time >= '2024-01-01 00:00:00' AND create_time < '2024-01-02 00:00:00'` |
| 索引列做计算 | `WHERE price * 0.8 < 100` | 目录按原价排，不按打折价排 | 把计算挪到右边：`WHERE price < 125` |
| 左模糊匹配 | `WHERE name LIKE '%zhang'` | 只知结尾不知开头，目录定位不到起点 | 尽量改右模糊 `'zhang%'`，或上全文索引 / ES |
| 隐式类型转换 | `WHERE phone = 13800138000`（列为字符串） | 数据库被迫把每行字符串转数字，等同套函数 | 严格对齐类型，加上单引号 `'13800138000'` |
| 违背最左前缀 | 联合索引 `(a,b,c)` 查 `WHERE b = 2` | 跳过了最左边的 `a`，后面列整体无序 | 查询带最左列 `a`，或调整联合索引列顺序 |
| `OR` 连不同列 | `WHERE a = 1 OR b = 2` | 两个独立目录难同时合并扫描 | 改写成 `UNION ALL` 或建立合适覆盖索引 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问“索引失效的场景有哪些”，最怕你零散背出一堆点。建议按**“SQL 写法问题 -> 联合索引规则 -> 优化器成本选择”**三层结构作答，既全面又有条理：

1. **SQL 条件写法破坏了索引有序性（5 大高频坑）**：对索引列用函数或算术运算、隐式类型转换、`LIKE '%...'` 左模糊匹配、`!=`/`<>` 不等于、用 `OR` 连接不同索引列。
2. **联合索引没遵守最左前缀原则**：跳过了最左列，或者中间列断档（以及范围查询列之后的列无法继续利用索引排序/等值）。
3. **优化器基于成本主动放弃索引**：比如查出的数据占比过高、索引列区分度太低、或者表统计信息不准。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：线上怎么快速判断一条 SQL 到底有没有走索引、是不是失效了？**
    - **参考答法**：用 `EXPLAIN` 命令看执行计划。重点盯三个字段：`type`（如果是 `ALL` 说明全表扫描，索引失效了；理想是 `ref`、`range` 或 `const`）、`key`（实际用到的索引名，为 `NULL` 就是没用上）、`rows`（预估扫描行数，越大越危险）。
- **追问 2：业务上确实需要 LIKE '%关键词%' 这种前后都模糊的搜索，怎么优化？**
    - **参考答法**：普通 B+ 树确实搞不定左模糊。如果数据量中等且只是搜文本，可以尝试 MySQL 的**全文索引（Full-Text）**；如果是高并发、海量文本搜索（比如商品搜索、日志检索），工业界标准做法是把搜索流量切到 **Elasticsearch** 这类专业搜索引擎（基于倒排索引）。如果是短字段且结果集全在索引里，也可以利用“覆盖索引扫描”勉强减少回表，但本质还是扫索引树。
- **追问 3：除了避免索引失效，平时还有哪些顺手就能做的 SQL 优化？**
    - **参考答法**：只查需要的列（少用 `SELECT *`，争取触发覆盖索引免回表）、用 `LIMIT` 控制返回行数、用游标条件替代大 `OFFSET` 深分页、小表驱动大表做 `JOIN`。

## 5. 🤖 和大模型/AI 开发有什么关系

- **Text-to-SQL 的头号质量杀手**：大模型在生成 SQL 时，非常容易写出 `WHERE YEAR(order_date) = 2025`（对时间列套函数）或者给字符串手机号忘了加引号（触发隐式类型转换），导致原本秒级的数据库直接被拖成全表扫描。在 AI 应用的 SQL 校验层里，加入针对“索引列套函数”和“隐式类型转换”的 AST 静态检查或改写规则，是保障生产库安全的关键一环。
- **AI 知识库精准关键词召回**：很多团队用 MySQL LIKE '%术语%' 给 RAG 做关键词兜底检索，数据一上十万条就卡死——理解了左模糊会让 B+ 树失效，你就会果断改用 MySQL 全文索引或专门的 BM25 倒排检索引擎。

## 6. 📝 节末费曼自检

尝试不看笔记，用大白话回答下面 3 个问题：

1. 为什么 `WHERE phone = 13800138000`（`phone` 是字符串类型）会让索引失效，而加上引号 `'13800138000'` 就好了？
2. 联合索引 `(a, b, c)`，执行 `WHERE a = 1 AND c = 3` 时，哪些列用上了索引，哪一列没用上？
3. 为什么 LIKE '张%' 能走索引，而 LIKE '%张' 却不行？

**自检参考要点**：1）字符串和数字比较时，MySQL 会把字符串列隐式转成数字，相当于对索引列套了函数；2）`a` 用上了索引，`c` 没用上（因为跳过了中间的 `b`）；3）B+ 树按字符从左到右排序，知道前缀 '张' 就能定位区间起点，不知道前缀就无法定位起点。
