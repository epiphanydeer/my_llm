# 什么时候不需要创建索引？

## 1. 🎯 一句话听懂 + 生活大白话例子

**一句话听懂**：索引就像给书印目录——既占纸张（磁盘空间），每次往书里插一页新内容还得把所有目录全改一遍（拖慢写入速度）；如果这本小册子总共才 10 页，或者某列几乎人人长得一样，印目录纯属赔本买卖。

**生活大白话例子**：

- **数据量极小的表**：一本只有 15 页的说明书，你从第 1 页翻到第 15 页只要 2 秒钟；非要印个目录，先翻目录再翻正文，反而更慢。
- **区分度极低的列**：如果一个 1000 人的班级名单里，“国籍”那一列 999 个都是“中国”，你按国籍建目录根本筛不掉几个人，还不如直接扫一遍名单。
- **疯狂写入的表**：一个每秒记几千条流水账的收银台小票本，每次记一笔账都要顺手把 5 本目录全部擦掉重写，收银员直接忙崩溃。

## 2. 🧠 底层机制与核心对比

### 六大不适合建索引的场景（大白话拆解）

- **数据量很小的表**：总共就几十、几百行，全表顺序扫描一两页就读完了，建索引还要先读索引树再回表，纯属画蛇添足。
- **写入极其频繁的表**：每次 `INSERT / UPDATE / DELETE` 改数据时，数据库都要同步调整对应的 B+ 树（甚至引发节点分裂/合并），索引越多，写入越慢。
- **区分度（选择性）很低的列**：比如性别（男/女）、开关状态（0/1），重复率极高，一个值对应全表一半数据，用索引还不如直接全表扫。
- **几乎不被拿来查的列**：很少出现在 `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY` 里的列，建了索引也是“吃灰”，白占空间和写入成本。
- **查询会返回大部分数据的场景**：哪怕表很大，如果一次查询要拿走 20%~30% 以上的数据，优化器算一笔账发现“跳着回表太费磁盘”，会直接弃用索引改走顺序全表扫。
- **查询条件本身用不上索引的列**：如果业务 SQL 总是对这列套函数（如 `LEFT(name, 1)`）或用前模糊（`LIKE '%abc'`），索引建了也触发不了。

### 建索引收益 vs 代价对比表

| **场景类型** | **建议策略** | **大白话原因** | **底层代价** |
| --- | --- | --- | --- |
| 几十到几百行的小表 | **不建** | 书太薄，直接翻完比查目录还快 | 额外 I/O（先查目录再回表） |
| 写多读少（如日志流水表） | **少建或不建** | 每次记账都得改目录，写速度暴跌 | 频繁维护 B+ 树结构与节点分裂 |
| 区分度极低的列（性别/布尔） | **不建** | 筛不掉多少人，目录形同虚设 | 优化器大概率直接放弃该索引 |
| 冷门不常查的列 | **不建** | 从来不翻的目录，印了白占书架 | 浪费磁盘空间和内存缓存（Buffer Pool） |
| 一次返回 >20%~30% 的查询 | **无需强求** | 要搬走半个仓库，按目录一箱箱拿不如直接推车全搬 | 随机回表 I/O 开销高于顺序扫描 |

## 3. 🗣️ 面试官视角：怎么串成体系回答

面试官问“什么时候不需要创建索引”，考察的是你有没有**“索引是一把双刃剑（用空间和写性能换读性能）”**的权衡思维：

1. **先亮出核心权衡原则**：索引不是免费的，它占用磁盘/内存空间，且会降低 `INSERT/UPDATE/DELETE` 的写入性能。
2. **分三个维度列举不建的场景**：
    - **表特征**：数据量极小的表、写多读少（频繁更新）的表。
    - **列特征**：区分度极低的列（如性别）、极少用于查询条件的列。
    - **查询特征**：每次返回大量行（比例过高）导致优化器弃用的场景，以及业务写法注定导致索引失效的列。
3. **补充落地做法**：实际项目里如果遇到既要频繁写又要查的表，会控制单表索引总数（一般建议不超过 5 个），或采用读写分离、历史数据归档。

## 4. ❓ 高频面试追问与参考答法

- **追问 1：你说“区分度低的列”不适合建索引，具体怎么量化判断一个列的区分度高不高？**
    - **参考答法**：可以看这列的**基数（Cardinality）**，最简单的方法是用 SQL 算一下唯一值占比：SELECT COUNT(DISTINCT 列名) / COUNT(*) FROM 表名;。比值越接近 1，说明区分度越高（比如手机号）；如果比值很低（例如低于 10% 甚至只有几个固定枚举值），通常说明区分度太低，单独建索引价值不大。
- **追问 2：如果一个表既要高频写入，又要高频查询，怎么权衡？**
    - **参考答法**：核心是**控制索引数量 + 架构分流**。只保留最核心查询路径上的 1~2 个联合索引，砍掉冗余单列索引；如果业务允许，把重度查询分流到只读从库或引入 Redis 缓存热点数据，让主库专心抗写入。最终一切以压测和监控数据为准。
- **追问 3：建了多余的索引，除了占硬盘，还会影响查询时的内存吗？**
    - **参考答法**：会的。InnoDB 会把热点索引页缓存在内存的 **Buffer Pool** 里。无用的索引不仅会在写入时被一起修改，还可能挤占宝贵的内存空间，或者让优化器在选执行计划时多走弯路。

## 5. 🤖 和大模型/AI 开发有什么关系

- **向量库与知识库写入吞吐优化**：在给 RAG 系统做全量知识库初始化（比如一次性导入 100 万份企业文档切片）时，原理和数据库一模一样——如果边插数据边实时更新 HNSW 向量索引和 B+ 树索引，写入速度会慢到怀疑人生。工程上的标准做法是**先关掉或延后建索引，等批量数据灌完后再统一建索引**。
- **Agent 对话日志表设计**：AI 产品的原始对话流水表属于典型的“高频写入、极少按内容全文筛选”的表，只需保留主键和 `(user_id, created_at)` 索引，切忌把 `prompt` 或 `response` 这种大文本字段随便建普通索引。

2. 哪怕某列有索引，为什么当一条 SQL 要查出全表 40% 的数据时，MySQL 还是会选择全表扫描？
