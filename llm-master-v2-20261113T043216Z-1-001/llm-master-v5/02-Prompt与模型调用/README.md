## 本章总结：项目设计与评测系统

先用一张图讲清请求、状态和失败出口，再用相同输入说明如何对照、如何评分、何时可以上线。下列案例可用作白板练习。

### 案例 1 · 结构化工单提取 API

**面试官可能问**　模型返回合法 JSON，却给不存在的设备开工单。怎么设计接口和验收？

```text
请求与身份 → 结构化生成 → JSON 与 Schema 校验 → 业务校验 → 审批或返回草稿
```

**系统设计**　Schema 检查输出形态。确定性业务层查询设备、归属和允许的动作，并在真正写入前校验。可纠正错误带字段路径回传，修复次数受截止时间约束。无法解析外部字段时返回可操作错误。

**评测系统**　同时准备文本输入与有意构造的合法错误样本，覆盖缺字段、错误设备、跨租户设备、互斥字段和长输出截断。对照只用 Schema 与加入业务校验的版本，比较合法率、正确写入率、误放行、纠错收益与 P95。

**常见追问与排障**　如果加两轮自修复后合法率涨了，查最终草稿的业务正确率是否真的变好，同时量化成功率、平均尝试次数和端到端耗时。

**现场参考回答**

> 我会在接口图上明确生成、校验和写入的边界，把“格式合法但业务错误”列为发布前的必测用例。

### 案例 2 · 流式查询先出字，断线后还能继续

**面试官可能问**　设备查询助手边输出边查工具，客户端断线后怎么恢复，怎样测试？

```text
带请求 ID 的会话 → 模型事件流 → 工具分发与配对 → 完成校验 → 状态查询或重连
```

**系统设计**　服务端区分部分输出、模型完成和工具终态。每轮保留完整的调用与结果，工具结果按原 ID 配对。重连优先查询既有请求状态，按事件游标补发可回放输出。明确标注无法恢复时的状态，副作用交给幂等执行层。

**评测系统**　用可重复的事件序列注入断线、429、SSE 缺最后一帧、两个工具一成功一失败和重复投递。基线是普通串行调用，候选是流式与可恢复版。核对成功状态、配对完整性、重复副作用、TTFT和端到端尾延迟。

**常见追问与排障**　首字变快但用户看到半截结果，分别用 TTFT 和完整成功率衡量。取一条断线 trace，查上次已确认的事件与后端终态。

**现场参考回答**

> 我把输出进度和业务完成当作两个状态来管理，再用断线和重放证明展示、账单与工具结果能对上。
