### 4.14 生产防线一：双模式防死循环熔断器 【🔥 必会】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：在 Step 4 里我们用 seen_calls 做过简单的单次完全去重，但在真实长链路排障中，死循环往往更狡猾：有时候模型确实需要间隔重试一次；有时候它不会连续调同一个工具，而是在两个工具之间来回横跳（A -> B -> A -> B）——比如先查 db-01 没问题，再去查 db-02 看不懂，又回头查 db-01，再查 db-02……简单去重很容易误杀或漏判！而且如果模型某次把参数字典写成 {"a": 1, "b": 2} 下次写成 {"b": 2, "a": 1}，普通字符串对比直接失效！

本节解法：引入 DualModeLoopBreaker（双模式防死循环熔断器）：① 用 json.dumps(..., sort_keys=True) 生成键序无关的规范化参数哈希指纹；② 同时检测 连续重复模式（A-A-A） 与 乒乓震荡模式（A-B-A-B），一旦命中立刻物理熔断并强制模型汇总退出或转人工。

大白话例子：就像客服接电话遇到鬼打墙：一种是用户连着问 3 遍一模一样的话（A-A-A）；另一种是用户先问售后、售后让他找技术、技术又让他找售后，来回踢皮球 2 个来回（A-B-A-B）。系统监测到这两种模式，立刻亮红灯切断自动循环，直接转接值班主管！

#### 2. 🧠 核心原理与五维拆解

| 维度 | 核心内容（闭卷背诵标准） |
| --- | --- |
| ① 输入什么 | 每次工具调用的 tool_name: str 与参数字典 args: Dict[str, Any]。 |
| ② 做什么 | 计算 sort_keys=True 的 SHA-256 短指纹并追加到 _history；滑动检查尾部 consecutive_limit 个指纹是否全等（A-A-A），以及尾部 oscillation_cycles * 2 个指纹是否呈周期 2 交替（A-B-A-B）。 |
| ③ 输出什么 | `{"tripped": bool, "mode": "CONSECUTIVE_REPEAT" |
| ④ 关键参数 | consecutive_limit（通常 3 次）、oscillation_cycles（通常 2 个周期，即长度 4 窗口 A-B-A-B）。 |
| ⑤ 工程 Trade-off | 规范化哈希 + 双模式滑窗能 100% 拦截隐蔽死循环，几乎零计算开销；唯一需要注意对“合法轮询类工具”（如 wait_job_status）应支持配置白名单豁免或放宽阈值。 |

知识扩展（面试加分盲区）：

为什么不用 str(args) 直接做指纹？：Python 字典在动态构造时键插入顺序可能不同（{"a": 1, "b": 2} vs {"b": 2, "a": 1}），str(args) 会产出两个完全不同的字符串导致漏判；必须用 json.dumps(..., sort_keys=True) 做规范化序列化（Canonicalization）。

熔断触发后怎么办？（优雅降级 Graceful Degradation）：千万不要直接给用户抛一个冷冰冰的 500 LoopDetectedError！正确做法是：向模型注入一条系统级强制指令（或剥夺其 tools 参数再调最后一次 LLM）——“已检测到重复探索且无新进展，禁止再调用任何工具，请基于目前已有观测结果向用户说明当前已查明的事实与卡点，并给出人工排查建议”。

#### 3. 💻 渐进式代码实操（Step 14：DualModeLoopBreaker 双模式熔断器）

演进说明：把 Step 4 简陋的 seen_calls 升级为支持规范化参数哈希、A-A-A 连续熔断与 A-B-A-B 乒乓震荡熔断的工业级组件。

```python
"""Step 14: Dual-Mode Loop Breaker (双模式防死循环熔断器).

解决生产 Agent 最隐蔽的两类死循环：
1. 连续重复模式 (A-A-A)：连续 N 次调用完全相同的工具与规范化参数。
2. 乒乓震荡模式 (A-B-A-B)：在两个等价调用之间来回横跳（例如反复查 A 再查 B 再查 A 再查 B）。
采用规范化 JSON 序列化 (sort_keys=True) 生成指纹，避免键序不同导致漏判。
"""

from __future__ import annotations

import hashlib
import json
from dataclasses import dataclass, field
from typing import Any, Dict, List


# [必记设计决策-规范化指纹] 必须用 json.dumps(..., sort_keys=True) 生成参数键序无关指纹，防 {"a":1,"b":2} 与 {"b":2,"a":1} 漏判
def canonical_signature(tool_name: str, args: Dict[str, Any]) -> str:
    """生成参数键序无关的规范化调用指纹."""
    payload = json.dumps({"tool": tool_name, "args": args}, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()[:16]


@dataclass
class DualModeLoopBreaker:
    """支持 A-A-A 连续熔断与 A-B-A-B 震荡熔断."""

    consecutive_limit: int = 3
    oscillation_cycles: int = 2
    _history: List[str] = field(default_factory=list)

    def record_and_check(self, tool_name: str, args: Dict[str, Any]) -> Dict[str, Any]:
        """记录本次调用指纹，若触发熔断则返回中断原因."""
        sig = canonical_signature(tool_name, args)
        self._history.append(sig)

        # 1. 检测 A-A-A 连续重复
        # [必背手撕-AAA连续熔断] 检查尾部 N 次调用指纹集合长度是否为 1，拦截连续无效重试
        if len(self._history) >= self.consecutive_limit:
            tail = self._history[-self.consecutive_limit :]
            if len(set(tail)) == 1:
                return {
                    "tripped": True,
                    "mode": "CONSECUTIVE_REPEAT",
                    "hint": f"工具 {tool_name} 已连续 {self.consecutive_limit} 次使用完全相同参数调用，触发熔断。",
                }

        # 2. 检测 A-B-A-B 乒乓震荡
        window_len = self.oscillation_cycles * 2
        # [必背手撕-ABAB乒乓熔断] 检查尾部 2*cycles 窗口是否呈现 a!=b 且奇偶位交替震荡，防止两工具间来回横跳
        if len(self._history) >= window_len:
            w = self._history[-window_len:]
            a, b = w[0], w[1]
            if a != b and all(w[i] == (a if i % 2 == 0 else b) for i in range(window_len)):
                return {
                    "tripped": True,
                    "mode": "PING_PONG_OSCILLATION",
                    "hint": "检测到 A-B-A-B 往返震荡调用，禁止继续重试，请汇总已有信息或转交人工。",
                }

        # [无需死背-脚手架] 统一返回字典结构可按业务自定义，重点记住需附带纠偏 hint
        return {"tripped": False, "mode": None, "hint": None}


if __name__ == "__main__":
    b1 = DualModeLoopBreaker(consecutive_limit=3)
    assert not b1.record_and_check("query_ticket", {"a": 1, "b": 2})["tripped"]
    assert not b1.record_and_check("query_ticket", {"b": 2, "a": 1})["tripped"]
    res1 = b1.record_and_check("query_ticket", {"a": 1, "b": 2})
    assert res1["tripped"] and res1["mode"] == "CONSECUTIVE_REPEAT"

    b2 = DualModeLoopBreaker(consecutive_limit=3, oscillation_cycles=2)
    assert not b2.record_and_check("check_node", {"node": "db-01"})["tripped"]
    assert not b2.record_and_check("check_node", {"node": "db-02"})["tripped"]
    assert not b2.record_and_check("check_node", {"node": "db-01"})["tripped"]
    res2 = b2.record_and_check("check_node", {"node": "db-02"})
    assert res2["tripped"] and res2["mode"] == "PING_PONG_OSCILLATION"
    print("Step 14 self-test passed!")
```

### 🧠 代码区记忆清单：背什么 vs 不背什么

🔒 不可替代的系统设计决策（必须记住，面试直接讲思路）：

键序无关签名：大模型两次生成同一参数时 JSON 键顺序可能不同，必须 sort_keys=True 后再做哈希，否则去重会漏判。

双模式熔断缺一不可：仅判“连续相同（A-A-A）”防不住“查 A -> 查 B -> 查 A -> 查 B”的乒乓震荡（A-B-A-B），两者必须同时检测。

✍️ 面试手撕/默写范围：

canonical_signature（sort_keys=True + 哈希）以及 CONSECUTIVE_REPEAT 和 PING_PONG_OSCILLATION 两个窗口判定条件。

🗑️ 无需死背的脚手架代码：

hashlib.sha256(...).hexdigest()[:16] 截断长度与 @dataclass 样板。

#### 4. 🗣️ 面试官视角：这段代码怎么讲

先声明不变量：只要连续 consecutive_limit 次完全同参调用，或出现 A-B-A-B 交替震荡，熔断器必定在 O(1) 时间内返回 tripped=True，且参数字典键序不影响指纹判定。

讲清关键行：canonical_signature 用 sort_keys=True 保证参数等价性；a != b and all(w[i] == (a if i % 2 == 0 else b) ...) 精确捕捉周期为 2 的往返横跳。

主动点出工程细节：如果业务中存在“翻页查询”或“异步任务状态轮询”，要么把 page/cursor 纳入参数指纹（翻页自然不会触发），要么对轮询工具单独配退避间隔和豁免标记。

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：Agent 在两个服务节点之间反复切换查询直到 max_steps=15 才退出，白白浪费 12 步钱

现象：日志显示 check_node(db-01) -> check_node(db-02) -> check_node(db-01) -> ...。

定位方法：原有去重只检查“是否连续两次相同”（prev == curr），完全漏掉了 A-B-A-B 震荡。

修复方案：上线 DualModeLoopBreaker，第 4 步即触发 PING_PONG_OSCILLATION 熔断并强制汇总退出。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：为什么不能只靠 max_steps 防死循环？

参考答法：max_steps 通常设得比较宽（比如 1015 步）以容纳复杂多步任务；如果第 2 步就已经陷入 A-B-A-B 死循环，等到第 15 步才截断意味着前 13 步全在空转烧钱、拉高延迟。DualModeLoopBreaker 能在第 34 步就提前止损（Early Stopping）。

Q2：在 A-B-A-B 检测中，为什么要加 a != b 这个判断条件？

参考答法：因为如果 a == b，那其实就是 A-A-A-A 连续重复模式，应该归类为 CONSECUTIVE_REPEAT 而不是 PING_PONG_OSCILLATION，保持故障归因语义清晰。
