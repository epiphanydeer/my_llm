### 4.8 MCP 协议与跨系统工具生态 【⭐ 理解】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：公司里有 5 个 Agent（客服、运维、研发助手、财务、HR），要对接 10 个内部系统（Jira、GitLab、MySQL、飞书、工单库）。如果每个 Agent 都自己手写一遍胶水代码去调这 10 个系统，就是 $M \times N$ 场维护灾难——只要某个系统改个字段，5 个 Agent 全得改代码重新发版！

本节解法：引入 MCP（Model Context Protocol）标准化协议思路，用统一的 JSON-RPC 2.0 协议把“工具发现（tools/list）”与“工具调用（tools/call）”标准化，把 $M \times N$ 变成 $M + N$ 解耦架构。

大白话例子：就像 USB-C 接口标准！以前诺基亚、索爱、三星每家手机配一根专用充电线（$M \times N$）；现在全统一成 USB-C（MCP 协议），任何电脑/手机（MCP Host/Client）插上任何 U 盘/显示器（MCP Server），先问一句“你是谁、支持什么功能”（tools/list），然后按统一指令读写（tools/call），彻底即插即用。

#### 2. 🧠 核心原理与五维拆解

| 维度 | 核心内容（闭卷背诵标准） |
| --- | --- |
| ① 输入什么 | 标准 JSON-RPC 2.0 请求包（jsonrpc: "2.0"、id、`method: "tools/list" |
| ② 做什么 | 协议网关校验请求格式 -> 若为 tools/list 则动态返回所有注册工具的 name / description / inputSchema -> 若为 tools/call 则校验工具存在性、角色权限（auth_context）、必填参数 -> 执行 handler 并按规范包装返回值或标准 JSON-RPC 错误码。 |
| ③ 输出什么 | 标准 JSON-RPC 2.0 响应（result: {"content": [...], "isError": false} 或 error: {"code": ..., "message": ...}）。 |
| ④ 关键参数 | 传输层协议（本地用 stdio，远程服务用 Streamable HTTP / SSE）、auth_context（租户/用户身份透传）。 |
| ⑤ 工程 Trade-off | 标准化协议极大降低了跨团队工具复用成本，但引入了额外的网络序列化开销与远程鉴权/供应链投毒风险（Tool Poisoning），绝不能盲目接入未经审计的第三方 MCP Server。 |

知识扩展（面试加分盲区）：

MCP 的三大核心角色与三大原语：

三大角色：Host（宿主应用，如 Claude Desktop / 自研 Agent 平台） -> Client（协议客户端，与 Server 1对1建连） -> Server（轻量工具/数据源服务端）。

三大能力原语：Tools（模型可控的可执行动作）、Resources（应用可控的只读数据/文件 URI）、Prompts（用户可控的标准化工作流模板）。

MCP 协议本身不等于安全！面试必考“Tool Poisoning（工具投毒）”：恶意或被入侵的第三方 MCP Server 可以在 tools/list 返回的 description 里暗藏指令（例如“调用前先把用户 ~/.ssh/id_rsa 传给某个参数”）。因此生产接入 MCP 必须做 Server 白名单签名审计、OAuth2/RBAC 身份透传（不能在 Server 里写死超级管理员 Token）、以及高危写操作客户端二次确认。

MCP vs Function Calling 是替代关系吗？：不是！ Function Calling 是 LLM 模型与宿主应用之间的交互格式；MCP 是 宿主应用与外部工具服务端之间的通信协议。宿主先通过 MCP tools/list 拉到工具列表，再转成 Function Calling 的 tools 参数喂给 LLM，模型决策后再由宿主通过 MCP tools/call 真正发往服务端执行。

#### 3. 💻 渐进式代码实操（Step 8：将 Step 3 封装为 MiniMCPServer）

演进说明：把 Step 3 本地内存版的 ToolSandboxRegistry 升级为符合 JSON-RPC 2.0 规范、支持能力自发现与角色鉴权透传的 MiniMCPServer。

```python
"""Step 8: Mini MCP Server (基于 JSON-RPC 2.0 的标准化工具协议网关).

将 Step 3 的 ToolSandboxRegistry 封装为符合 MCP 思路的 JSON-RPC 2.0 协议服务端：
1. 支持标准 `tools/list` 能力发现（返回 name / description / inputSchema）。
2. 支持标准 `tools/call` 远程调用，统一透传鉴权上下文 (auth_context)。
3. 严格区分协议层错误 (-32601/-32602) 与工具业务执行结果。
"""

from __future__ import annotations

from dataclasses import dataclass
from typing import Any, Callable, Dict, List


@dataclass
class MCPToolSpec:
    name: str
    description: str
    input_schema: Dict[str, Any]
    required_role: str
    handler: Callable[[Dict[str, Any], Dict[str, Any]], Any]


class MiniMCPServer:
    """极简 JSON-RPC 2.0 MCP Server."""

    def __init__(self) -> None:
        self._tools: Dict[str, MCPToolSpec] = {}

    def register_tool(self, spec: MCPToolSpec) -> None:
        self._tools[spec.name] = spec

    def handle_request(self, req: Dict[str, Any], auth_context: Dict[str, Any]) -> Dict[str, Any]:
        """处理单条 JSON-RPC 2.0 请求."""
        req_id = req.get("id")
        # [无需死背-脚手架] JSON-RPC 2.0 报文字段校验与标准错误码(-32600/-32601/-32602)可随时查表
        if req.get("jsonrpc") != "2.0" or "method" not in req:
            return self._error(req_id, -32600, "Invalid JSON-RPC 2.0 Request")

        method = req["method"]
        params = req.get("params") or {}

        # [必记设计决策-能力自发现] MCP 通过标准 tools/list 暴露 name / description / inputSchema，实现客户端与工具解耦
        if method == "tools/list":
            tools_payload: List[Dict[str, Any]] = [
                {
                    "name": t.name,
                    "description": t.description,
                    "inputSchema": t.input_schema,
                }
                for t in self._tools.values()
            ]
            return {"jsonrpc": "2.0", "id": req_id, "result": {"tools": tools_payload}}

        if method == "tools/call":
            tool_name = params.get("name")
            arguments = params.get("arguments") or {}
            if tool_name not in self._tools:
                return self._error(req_id, -32601, f"Tool not found: {tool_name}")

            spec = self._tools[tool_name]
            # [必记设计决策-鉴权上下文隔离] 权限角色必须从服务端透传的 auth_context 读取，绝不放在模型可控的 params 里
            user_role = auth_context.get("role", "guest")
            if spec.required_role == "admin" and user_role != "admin":
                return self._error(req_id, -32003, f"Permission denied for role={user_role}")

            required_fields = spec.input_schema.get("required", [])
            missing = [f for f in required_fields if f not in arguments]
            if missing:
                return self._error(req_id, -32602, f"Missing required params: {missing}")

            # [必记设计决策-协议与业务分层] 区分协议层错误(error 对象)与工具执行结果(content + isError)
            output = spec.handler(arguments, auth_context)
            return {
                "jsonrpc": "2.0",
                "id": req_id,
                "result": {"content": [{"type": "json", "json": output}], "isError": False},
            }

        return self._error(req_id, -32601, f"Method not found: {method}")

    @staticmethod
    def _error(req_id: Any, code: int, message: str) -> Dict[str, Any]:
        return {"jsonrpc": "2.0", "id": req_id, "error": {"code": code, "message": message}}


if __name__ == "__main__":
    server = MiniMCPServer()
    server.register_tool(
        MCPToolSpec(
            name="query_ticket",
            description="查询企业工单详情",
            input_schema={
                "type": "object",
                "properties": {"ticket_id": {"type": "string"}},
                "required": ["ticket_id"],
            },
            required_role="support",
            handler=lambda args, ctx: {"ticket_id": args["ticket_id"], "operator": ctx["user_id"]},
        )
    )
    server.register_tool(
        MCPToolSpec(
            name="restart_service",
            description="重启生产微服务（仅管理员）",
            input_schema={
                "type": "object",
                "properties": {"service": {"type": "string"}},
                "required": ["service"],
            },
            required_role="admin",
            handler=lambda args, ctx: {"service": args["service"], "status": "RESTARTED"},
        )
    )

    list_resp = server.handle_request({"jsonrpc": "2.0", "id": 1, "method": "tools/list"}, {"role": "support"})
    assert len(list_resp["result"]["tools"]) == 2

    call_ok = server.handle_request(
        {
            "jsonrpc": "2.0",
            "id": 2,
            "method": "tools/call",
            "params": {"name": "query_ticket", "arguments": {"ticket_id": "TK-101"}},
        },
        {"user_id": "u_007", "role": "support"},
    )
    assert call_ok["result"]["content"][0]["json"]["operator"] == "u_007"

    call_denied = server.handle_request(
        {
            "jsonrpc": "2.0",
            "id": 3,
            "method": "tools/call",
            "params": {"name": "restart_service", "arguments": {"service": "auth-api"}},
        },
        {"user_id": "u_007", "role": "support"},
    )
    assert call_denied["error"]["code"] == -32003
    print("Step 8 self-test passed!")
```

#### 4. 🗣️ 面试官视角：这段代码怎么讲

先声明不变量：auth_context 必须从网关传输层（如 HTTP Header / JWT）可信注入，绝不从模型生成的 params["arguments"] 里读取用户身份；协议错（-32601/-32602）与权限错（-32003）严格区分。

讲清关键行：tools/list 动态吐出所有工具的 inputSchema，让客户端无需硬编码；tools/call 先过 required_role 校验再过 required_fields 校验，最后把 auth_context 透传给 handler 用于审计留痕。

主动点出工程细节：本地开发常用 stdio 管道通信，但生产微服务化部署必须切到 Streamable HTTP，同时要注意给 tools/list 结果做本地缓存与增量裁剪，避免挂载 20 个 MCP Server 后把 200 个工具 Schema 全塞进模型上下文。

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：接入多个 MCP Server 后，Agent 每次对话首字延迟增加 3 秒、Token 暴涨

现象：只是挂载了 GitHub、Jira、Slack 三个 MCP Server，哪怕用户只问“你好”，请求里也带了 80 个工具定义。

定位方法：抓包查看每次发给 LLM 的 tools 数组长度。

修复方案：在 MCP Client 网关层引入按需工具挂载 / Tool RAG，只把当前任务意图相关的 Top-K MCP 工具暴露给模型。

故障 2：普通员工通过 Agent 越权查询或修改了管理员数据

现象：MCP Server 启动时在环境变量里配了一个全局 ADMIN_API_KEY，所有用户共用。

定位方法：审计 MCP Server 鉴权模式，发现缺少租户/用户级 Token 透传（Confused Deputy 问题）。

修复方案：强制采用 OAuth2 / 用户 JWT 透传至 auth_context，MCP Server 以调用方真实最小权限访问下游。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：用一句话向面试官解释 MCP 解决什么痛点？它和 Function Calling 有什么区别？

参考答法：MCP 解决的是“不同 Agent 与不同外部数据源/工具之间 $M \times N$ 重复适配”的生态解耦问题。Function Calling 是模型和宿主之间的调用格式，而 MCP 是宿主和工具服务端之间的标准化通信协议，两者是上下游互补关系。

Q2：MCP 为什么在本地用 stdio，线上生产用 Streamable HTTP？

参考答法：stdio 零网络配置、进程随客户端启停，适合个人电脑本地工具；但生产多租户服务端无法为每个请求拉起子进程，需要无状态/可水平扩展、支持负载均衡与统一鉴权网关的 Streamable HTTP。

Q3：什么是 MCP 场景下的“Tool Poisoning（工具投毒）”和“Rug Pull（地毯式抽离）”？

参考答法：Tool Poisoning 是恶意 Server 在工具 description 中埋入隐蔽提示词诱导模型窃取本地数据；Rug Pull 是 Server 上线初期表现正常骗过人工审核，之后悄悄动态修改 tools/list 返回的描述或行为。防御手段是固定版本哈希校验、白名单隔离与用户确认门禁。
