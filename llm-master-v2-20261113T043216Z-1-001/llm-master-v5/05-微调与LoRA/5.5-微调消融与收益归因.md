### 5.5 微调消融与收益归因 【🔥 必会】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：花了一周清洗数据、租卡训完 LoRA，面试官问：“你怎么证明这 10% 的提升是微调带来的，而不是写好一点的 Prompt 就能免费拿到？微调有没有把原本会做的通用题训傻？”

本节解法：建立 LoRAAblationTracker（微调消融追踪器）：把 Prompt / Few-shot 基线和 SFT-LoRA 放在同一套无泄漏金标集上逐样本成对对比，量化 fixed（Prompt 搞不定、LoRA 修好了）、regressed（LoRA 训退化了）与净收益 net_gain。

大白话例子：买了一台 5000 块的净水器（微调），必须拿“烧开的自来水（Prompt 基线）”和“净水器出来的水（LoRA）”做盲测对比——如果烧开水本来就能解决 80% 问题，净水器只多解决了 1% 还引入了新异味（退化），那这钱就花冤枉了！

#### 2. 🧠 核心原理与五维拆解

| 维度 | 核心内容（闭卷背诵标准） |
| --- | --- |
| ① 输入什么 | 金标答案 gold、Prompt 基线预测 prompt_preds、LoRA 预测 lora_preds。 |
| ② 做什么 | 计算各自准确率 -> 逐样本统计 fixed (p != g and l == g) 与 regressed (p == g and l != g) -> 判定 worth_deploying。 |
| ③ 输出什么 | 消融对比报告（prompt_acc、lora_acc、fixed、regressed、net_gain、worth_deploying）。 |
| ④ 关键参数 | net_gain = fixed - regressed（净修复数）、通用能力回归集（防灾难性遗忘）。 |
| ⑤ 工程 Trade-off | 严谨的三组消融（Zero-shot / Few-shot / LoRA）能帮你拦截“无效微调”，避免维护一套多余的 GPU 微调模型链路。 |

#### 3. 💻 渐进式代码实操（Step 5：LoRAAblationTracker 消融追踪）

演进说明：在 Step 4 训出 Checkpoint 后，用成对消融代码严格验收微调净收益。

```python
"""5.5 Step 5: 微调消融与收益归因追踪器 (Zero-shot vs Few-shot vs LoRA)."""

from __future__ import annotations

from typing import Dict, List


def compare_sft_ablation(
    gold: List[str],
    prompt_preds: List[str],
    lora_preds: List[str],
) -> Dict[str, object]:
    if not gold or not (len(gold) == len(prompt_preds) == len(lora_preds)):  # [无需死背-脚手架]
        raise ValueError("三组序列长度必须一致且非空")

    fixed = sum(1 for g, p, l in zip(gold, prompt_preds, lora_preds) if p != g and l == g)  # [必背手撕-成对消融Fixed错改对计数]
    regressed = sum(1 for g, p, l in zip(gold, prompt_preds, lora_preds) if p == g and l != g)  # [必背手撕-成对消融Regressed对改错计数]
    prompt_acc = sum(1 for g, p in zip(gold, prompt_preds) if p == g) / len(gold)
    lora_acc = sum(1 for g, l in zip(gold, lora_preds) if l == g) / len(gold)
    return {
        "prompt_acc": round(prompt_acc, 4),
        "lora_acc": round(lora_acc, 4),
        "fixed": fixed,
        "regressed": regressed,
        "net_gain": fixed - regressed,
        "worth_deploying": lora_acc > prompt_acc and (fixed - regressed) > 0,  # [必记设计决策-净收益为正且胜过Prompt基线才准上线]
    }


if __name__ == "__main__":  # [无需死背-脚手架]
    res = compare_sft_ablation(
        gold=["A", "B", "C", "D"],
        prompt_preds=["A", "X", "X", "D"],
        lora_preds=["A", "B", "C", "Y"],
    )
    assert res["fixed"] == 2 and res["regressed"] == 1 and res["worth_deploying"] is True
    print(f"Ch5 Step 5 self-test passed! res={res}")

```

### 🧠 代码区记忆清单：背什么 vs 不背什么

- **🔒 不可替代的系统设计决策**：微调上线评审不能只看总准确率微涨，必须满足 `lora_acc > prompt_acc` 且净收益 `fixed - regressed > 0`，防止“修了 2 个新 case 却弄坏 3 个老 case”。
- **✍️ 面试手撕/默写范围**：手写逐样本成对消融统计逻辑——`Fixed`（基线错、微调对）与 `Regressed`（基线对、微调错）的条件计数。
- **🗑️ 无需死背的脚手架代码**：序列长度一致性的 `ValueError` 防御校验、`round(..., 4)` 格式化与 `__main__` 单元测试。

#### 4. 🗣️ 面试官视角：这段代码怎么讲

先声明不变量：三组序列长度与样本顺序必须严格对齐；上线前提是 net_gain > 0 且不以牺牲核心通用能力为代价。

讲清关键行：把 fixed 与 regressed 独立统计，能立刻看清 LoRA 到底是在“修补 Prompt 短板”还是在“拆东墙补西墙”。

主动点出工程细节：除了业务集，微调上线前必须加跑一份 50~100 条通用能力回归集（General Capability Check），防止垂直 LoRA 把基础指令遵循或安全拒答能力训退化（俗称 Alignment Tax）。

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：LoRA 在垂类榜单涨了 8%，但用户用它做日常总结或格式转换时变傻了

现象：出现灾难性遗忘（Catastrophic Forgetting）。

定位方法：训练集 100% 是单一垂类窄格式样本，完全没混入通用指令数据。

修复方案：在 SFT 训集中按 10%~20% 比例混入通用指令回放数据（Replay / General Mix），或者降低 rank 与训练 Epoch。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：微调时怎么防止模型发生灾难性遗忘？

参考答法：① 首选 LoRA 冻结主干而不全参修改；② 控制学习率和 Epoch（通常 1~3 Epoch）；③ 在垂类训练集中混入 10%~20% 通用高质量指令数据做正则化回放；④ 上线前跑通用回归集验收。
