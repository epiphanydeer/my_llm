### 5.1 RAG 与 SFT / RLHF / DPO 选型决策 【🔥 必会】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：很多团队一遇到“大模型不懂公司内部业务”，第一反应就是“找几千条文档微调一个模型（SFT）”，结果训完发现新政策一改模型全过时，而且照样编造数字；反过来，也有人遇到“模型老是不按指定 JSON 格式吐结果”，却死磕 RAG 知识库！

本节解法：构建 RAG vs SFT vs DPO 选型路由器：① 动态事实、高频更新知识与强溯源需求走 RAG；② 固定输出格式、特定领域推理习惯与话术风格走 SFT (LoRA)；③ 人类偏好对齐（语气、安全性、拒答边界）在 SFT 后叠加 DPO。

大白话例子：就像开卷考试与闭卷习惯的区别：RAG 相当于给学生配一本随时更新的《最新法规手册》（查新知识、防瞎编、能指明出自第几页）；SFT 相当于考前刷题训练答题格式和行业术语（改习惯、定格式）；DPO 相当于告诉学生“哪种回答语气老板更喜欢、哪种违规问题必须直接拒绝”（对齐偏好）！

#### 2. 🧠 核心原理与五维拆解

| 维度 | 核心内容（闭卷背诵标准） |
| --- | --- |
| ① 输入什么 | 业务需求画像 RequirementProfile（知识是否周级更新、是否需精确溯源、是否需固定格式/风格、是否有偏好对比对、标注样本量）。 |
| ② 做什么 | 优先拦截动态知识与溯源需求路由至 RAG；若需同时固化格式且样本充足则推荐 RAG + SFT_LORA 组合；静态格式/逻辑定制走 SFT_LORA；有成对偏好数据走 SFT_THEN_DPO。 |
| ③ 输出什么 | 确定性选型路由及理由说明。 |
| ④ 关键参数 | 知识更新周期、样本量门槛（SFT 至少数百条高质量样本，DPO 需先有 SFT 基座）、幻觉容忍度。 |
| ⑤ 工程 Trade-off | 微调（SFT）是把模式“烤进权重”，推理零额外检索延迟但更新成本高且无法天然溯源；RAG 灵活可溯源但增加检索耗时与上下文长度。 |

知识扩展（面试加分盲区）：

为什么一般不建议用 SFT 给大模型“灌输新事实知识”？：全参或 LoRA 微调不仅成本高、周期长，还极易诱发灾难性遗忘（Catastrophic Forgetting），且模型依然可能在问到冷门细节时产生无法溯源的幻觉。新事实优先放进 RAG，微调只用来学“怎么用这些知识”。

RLHF (PPO) vs DPO 的核心区别：传统 RLHF 需要同时维护 Actor、Critic、Reference、Reward 四个模型，显存爆炸且训练极不稳定；DPO（Direct Preference Optimization） 通过数学重参数化直接把奖励函数隐式消掉，只需 Policy + Frozen Reference 两个模型，用类似分类的二元交叉熵损失直接优化偏好对 (chosen, rejected)，工程落地性价比极高。

#### 3. 💻 渐进式代码实操（Step 1：RAG 与 SFT/DPO 选型路由器）

演进说明：本章起点，将选型决策树代码化，杜绝“为了微调而微调”。

```python
"""5.1 Step 1: RAG 与 SFT/DPO 选型决策路由器."""

from __future__ import annotations

from dataclasses import dataclass
from typing import Dict


@dataclass(frozen=True)
class RequirementProfile:  # 五维选型约束建模
    knowledge_changes_weekly: bool
    requires_exact_citation: bool
    needs_strict_format_or_style: bool
    has_preference_pairs: bool
    labeled_samples: int


def route_rag_vs_sft(req: RequirementProfile) -> Dict[str, str]:
    """根据业务约束输出确定性的技术选型建议."""
    if req.labeled_samples < 0:  # 脚手架
        raise ValueError("labeled_samples 不能为负数")

    if req.knowledge_changes_weekly or req.requires_exact_citation:  # 动态知识与强溯源优先走RAG
        if req.needs_strict_format_or_style and req.labeled_samples >= 500:
            return {"route": "RAG + SFT_LORA", "reason": "动态知识靠 RAG 检索，固定格式与话术靠 LoRA 固化"}
        return {"route": "RAG_ONLY", "reason": "知识高频变化且需溯源，微调不仅贵且无法实时更新"}

    if req.has_preference_pairs and req.labeled_samples >= 300:  # 有偏好对先SFT再DPO对齐边界
        return {"route": "SFT_THEN_DPO", "reason": "先 SFT 学会基本能力，再用 DPO 对齐偏好与拒答边界"}

    if req.needs_strict_format_or_style and req.labeled_samples >= 200:  # 静态格式风格固化走LoRA
        return {"route": "SFT_LORA", "reason": "静态规则/格式/语气定制，LoRA 性价比最高"}

    return {"route": "PROMPT_ENGINEERING", "reason": "样本不足或需求简单，先用 Prompt + Few-shot 跑通基线"}  # 低成本基线兜底原则


if __name__ == "__main__":  # 脚手架
    assert route_rag_vs_sft(RequirementProfile(True, True, False, False, 1000))["route"] == "RAG_ONLY"
    assert route_rag_vs_sft(RequirementProfile(False, False, True, False, 800))["route"] == "SFT_LORA"
    assert route_rag_vs_sft(RequirementProfile(False, False, True, True, 500))["route"] == "SFT_THEN_DPO"
    print("Ch5 Step 1 self-test passed!")

```

### 示例说明与练习范围

- **本例的设计选择**：动态高频变化知识与强溯源需求必须优先走 RAG；已有偏好对时采用 `SFT -> DPO` 两段式对齐；样本不足时先用 Prompt + Few-shot 跑通基线，杜绝“为了微调而微调”。
- **代码练习｜能讲清设计**。会讲选型树，训练算法与路由类不背。
- **示例辅助代码**：`RequirementProfile` 数据类定义、负数参数防御校验与 `__main__` 断言测试。

#### 4. 🗣️ 面试官视角：这段代码怎么讲

先声明不变量：高频变化知识与强溯源需求永远优先路由到 RAG，绝不盲目微调；在样本量不足时优先用 Prompt 跑通基线。

讲清关键行：第 23~26 行体现了最经典的**RAG + SFT_LORA 黄金组合**——RAG 管动态事实，LoRA 管稳定格式与领域推理范式。

主动点出工程细节：做 DPO 前通常必须先做一轮 SFT（SFT_THEN_DPO），让模型先进入目标分布区域，直接对未微调基座跑 DPO 往往很难收敛。

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：微调完模型后，公司刚改了新制度，模型却依然回答去年的老条款

现象：把动态业务制度硬训进了 LoRA 权重。

定位方法：需求选型错误，混淆了“知识存储”与“能力适配”。

修复方案：剥离知识条款进 RAG 向量库，只保留推理与输出格式微调。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：面试官问：什么时候用 Prompt、什么时候用 RAG、什么时候用 SFT/LoRA、什么时候用 DPO？

参考答法：先用 Prompt/Few-shot 跑通基线；缺实时/私域/需溯源知识上 RAG；RAG 检索对了但模型输出格式总出错、领域术语不懂或需把复杂指令内化省 Prompt Token 时上 SFT(LoRA)；SFT 之后如果还要精细调节“更喜欢哪种语气/更安全的拒答边界”，再上 DPO。

Q2：DPO 相比传统 PPO (RLHF) 省了什么？有什么局限？

参考答法：省掉了单独训 Reward Model 和在线采样 PPO 的复杂四模型架构，显存减半且稳定；局限是 DPO 依赖离线静态偏好对，如果策略分布偏移太大，有时还是需要在线迭代采样（Iterative DPO / GRPO）。

## 面试重点｜设计、调参与排障

**面试官可能问**

系统答错旧规程、输出不稳定，你先改 Prompt、做 RAG，还是微调？

**参考回答（现场口述）**

先拆成两个问题。旧规程是知识版本问题，我优先修检索与有效期。输出稳定性先用 schema 和 Prompt 做约束，反复出现且有训练数据后再试 SFT。用同一题集分别评事实正确、格式成功率和成本。

**系统设计怎么选**

频繁更新、需要引用的知识用检索与版本治理。固定格式先用 Schema 和 Prompt；有足够标注且表现仍差再评估 SFT。DPO 用偏好对优化相对参考策略，适合有偏好数据的场景。

**参数或条件改变会怎样**

分别比较证据正确率、格式通过、质量和成本。不要用训练轮数掩盖旧索引或错误业务规则。

**系统出错怎么查、怎么验证**

先用正确证据和明确模板做上限测试，再定位能力缺口。报告哪条证据支持选 SFT，什么条件下回退。
