# 1.6 Token 用量：上下文、工具与缓存口径【🔥 必会】

## 1. 🎯 本节目标与大白话例子

本节目标：看懂 API 返回的 usage 账单，搞清楚 System Prompt、Tools Schema、多轮历史、Prompt Cache 命中是如何计入 Token 的。

大白话例子：每次调模型就像把一叠不断变厚的文件夹递给柜员看：文件夹最前面是公司章程（System）和工具说明书（Tools Schema），后面是历史聊天记录和最新问题。如果前面章程和说明书一字未改，柜员就可以直接调取刚才的记忆（Prompt Cache），不用从头重读。

## 2. 🧠 核心原理与五维拆解

输入 Token（Prompt Tokens）全口径：System + Tools Schema + Few-shot + 历史消息 + 当前 User 输入。注意：Tool Schema 定义本身也要算进每轮的输入 Token！

输出 Token（Completion Tokens）：包含可见回复、工具调用 JSON（tool_calls）以及推理模型隐藏的思维链（reasoning_tokens）。

Prompt Cache（前缀缓存）：当连续请求拥有完全一致的前缀（如固定 System + Tools Schema + 长背景资料，且超过最小缓存阈值如 1024 Tokens），引擎会复用 KV Cache，返回 cached_tokens 享受大幅降价与 TTFT 加速。

## 3. 💻 渐进式代码实操（ch1_code/step_06_token_usage_ledger.py）

```python
"""1.6 Token 用量：上下文、工具与缓存口径统计器"""
from dataclasses import dataclass
from typing import Dict


@dataclass
class TurnUsage:  # 脚手架。用量台账字段定义
    system_tokens: int
    tools_schema_tokens: int
    history_tokens: int
    user_tokens: int
    cached_tokens: int
    completion_tokens: int

    @property
    def prompt_tokens(self) -> int:
        return self.system_tokens + self.tools_schema_tokens + self.history_tokens + self.user_tokens  # Prompt全量口径。含系统提示、工具Schema、历史与本轮输入

    @property
    def uncached_input_tokens(self) -> int:
        return max(0, self.prompt_tokens - self.cached_tokens)  # 未命中缓存输入计算。总输入减去缓存命中并用0兜底

    @property
    def total_tokens(self) -> int:
        return self.prompt_tokens + self.completion_tokens

    def summary(self) -> Dict[str, float]:
        hit_rate = self.cached_tokens / self.prompt_tokens if self.prompt_tokens else 0.0  # 缓存命中率。注意分母为0时的安全保护
        return {
            "prompt_tokens": self.prompt_tokens,
            "cached_tokens": self.cached_tokens,
            "uncached_input_tokens": self.uncached_input_tokens,
            "completion_tokens": self.completion_tokens,
            "total_tokens": self.total_tokens,
            "cache_hit_rate": round(hit_rate, 4),
        }


if __name__ == "__main__":  # 脚手架。第2轮对话账单模拟
    turn2 = TurnUsage(
        system_tokens=600,
        tools_schema_tokens=900,
        history_tokens=1200,
        user_tokens=100,
        cached_tokens=1500,  # System + Tools Schema 命中前缀缓存
        completion_tokens=320,
    )
    stats = turn2.summary()
    assert stats["prompt_tokens"] == 2800 and stats["uncached_input_tokens"] == 1300
    assert stats["total_tokens"] == 3120
    print("[1.6 PASS]", stats)
```

## 4. 🗣️ 面试官视角：这段代码怎么讲

在多轮 Agent 系统里，很多同学只算用户发的那句话，结果上线发现 Token 暴涨 10 倍——因为每轮都要重复携带上千 Token 的 Tools Schema 和历史轮次。我的统计器会显式拆出 cached_tokens 与 uncached_input_tokens，并监控 cache_hit_rate。

## 5. 🔧 生产排障指南

坑 1：在 System Prompt 开头放动态时间戳 当前时间: 17:14:12 → 解法：前缀只要变了 1 个字符，整段 Prompt Cache 就会全部失效！动态变量必须放到消息末尾或 User 消息里。

坑 2：忽略推理模型的 reasoning_tokens 计费 → 解法：像 o1/R1 这类模型，虽然前端可能折叠思考过程，但后台按全部输出 Token 计费，需设好 max_completion_tokens。

## 6. ❓ 高频面试追问与参考答法

Q1：如何最大化提高生产环境的 Prompt Cache 命中率？ 答：1）保持 System Prompt、Tools Schema 和静态知识库前缀严格稳定；2）动态内容（时间戳、用户状态、当前 query）全部后置；3）对同一长文档的多轮提问尽量路由到同一推理节点（Prefix-Aware Routing）。

Q2：Tool Calling 场景下，工具返回的结果算输入还是输出 Token？ 答：模型决定调用工具生成的 tool_calls 参数算输出 Token；本地执行完工具后，把 role: tool 的结果拼接回上下文发给模型做下一轮推理时，这部分内容算输入 Token。

## 面试重点｜设计、调参与排障

**面试官可能问**

用户只问了一句话，实际输入为何几千 token？

**参考回答（现场口述）**

账单里的输入还包括系统提示、工具 schema、历史消息、检索结果和视觉序列。先用真实请求用量核实，再拆来源，检查是否重复拼了历史或上下文。保留当前任务相关证据和工具配对，用输入预算与质量对照选择裁剪方案。

**系统设计怎么选**

实际请求可能带系统指令、历史、工具 Schema、检索片段和图片。按真实请求拆出各部分。

**参数或条件改变会怎样**

压历史和候选能节省预算，但要测丢证据的比例。支持前缀缓存时，把稳定内容放到可复用的前缀。

**系统出错怎么查、怎么验证**

用脱敏 trace 比较模板、检索数量、重试次数和缓存用量。计费用提供方 usage，估算用于预警。
