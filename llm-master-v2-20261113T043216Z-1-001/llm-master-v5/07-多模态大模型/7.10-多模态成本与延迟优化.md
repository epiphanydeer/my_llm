### 7.10 多模态落地：Token 成本治理与分级级联优化 【🔥 必会】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：Demo 里传一张图几分钱，一上线账单和延迟一起爆炸！很多同学第一反应是“把 JPEG 压缩成更小的 KB 数”——结果账单纹丝不动！因为视觉模型按像素宽高与 Patch 切块数算 Token，不按文件 KB 大小算；更要命的是，一次用户请求背后可能召回 8 页 PDF + 裁剪复核 + 失败重试，成本被悄悄放大了十几倍！

本节解法：① 理解视觉 Token 计费与链路放大公式；② 落地降本三板斧（按任务选清晰度、先检索后看图、QualityCascadeRouter 分级级联：低清/OCR 初筛 + 低置信度升级高清复核）；③ 用每个成功任务的真实总成本算账，而非只看单次调用便宜了多少。

大白话例子：就像机场安检和海关：所有行李先过一遍便宜飞快的 X 光机初筛（低清/OCR），90% 一眼看清没问题的直接放行；只有 10% 阴影可疑的箱子才请资深安检员开箱放大精查（高分辨率裁剪/大模型）。既省掉了 80% 的精查人力，又没漏掉一件违禁品！

知识扩展（面试加分盲区）：

压缩图片文件 KB 大小 ≠ 减少视觉 Token：把 4000×3000 的 JPEG 从 5MB 压到 200KB，只要像素宽高还是 4000×3000，送进模型后切出来的 Patch 数可能一模一样！真正降视觉 Token 靠的是缩小送入分辨率 / 切换 detail="low" 档位 / 裁剪掉无关背景区域。

多模态模型“开思考”的烧钱与空返回陷阱：实测 DeepSeek-V4-Flash-Vision-Exp 等带思考模式的视觉模型时，对于纯粹的 OCR 抄录或 SVG 矢量重绘，默认开启思考可能直接烧光 12000 个 reasoning Token 触发 finish_reason="length" 导致正文返回为空！工程上必须按任务类型动态开关 Thinking（明确提取任务关闭思考，复杂图表跨步推理才开启）。

#### 3. 💻 渐进式代码实操（Step 10：QualityCascadeRouter 分级级联降本）

演进说明：全章收官模块，结合 Step 6 置信度分流与 Step 9 消融算账，量化验证分级级联如何做到“准确率不掉且单成功任务成本降 60%+”。

```python
"""7.10 Step 10: 多模态成本治理与分级级联路由 (Quality Cascade + 成功任务真实成本).

核心工程策略：
1. 先用低成本链路 (Low-Res / OCR) 初筛，仅把低置信度疑难样本升级到高分辨率裁剪复核。
2. 算账不看单次调用便宜了多少，而是核算“每个成功任务的真实总成本”（含重试与升级开销）。
"""

from __future__ import annotations

from dataclasses import dataclass
from typing import Dict, List


@dataclass(frozen=True)
class CascadeSample:
    sample_id: str
    low_res_conf: float
    low_res_correct: bool
    high_res_correct: bool


def simulate_quality_cascade(
    samples: List[CascadeSample],
    conf_threshold: float = 0.75,
    low_cost_per_req: float = 0.002,
    high_cost_per_req: float = 0.015,
) -> Dict[str, float | int]:
    """对比全量高分辨率 vs 分级级联路由的准确率与单成功任务成本."""
    if not samples:
        raise ValueError("样本不能为空")
    if not 0.0 <= conf_threshold <= 1.0:
        raise ValueError("conf_threshold 必须在 [0, 1] 内")

    all_high_cost = len(samples) * high_cost_per_req  # [无需死背-脚手架]
    all_high_succ = sum(1 for s in samples if s.high_res_correct)

    cascade_cost = 0.0
    cascade_succ = 0
    escalated_count = 0

    for s in samples:
        cascade_cost += low_cost_per_req
        if s.low_res_conf >= conf_threshold:  # [必记设计决策-高置信度样本直接走低清链路省Token]
            if s.low_res_correct:
                cascade_succ += 1
        else:
            escalated_count += 1
            cascade_cost += high_cost_per_req  # [必记设计决策-低置信度样本升级高清复核并累加双倍账单]
            if s.high_res_correct:
                cascade_succ += 1

    cost_per_succ_all_high = all_high_cost / max(1, all_high_succ)
    cost_per_succ_cascade = cascade_cost / max(1, cascade_succ)  # [必背手撕-按单成功任务真实总成本核算ROI]

    return {
        "total_samples": len(samples),
        "escalated_count": escalated_count,
        "all_high_acc": round(all_high_succ / len(samples), 4),
        "cascade_acc": round(cascade_succ / len(samples), 4),
        "all_high_total_cost": round(all_high_cost, 4),
        "cascade_total_cost": round(cascade_cost, 4),
        "cost_per_success_saving_pct": round(
            (cost_per_succ_all_high - cost_per_succ_cascade) / cost_per_succ_all_high * 100, 2
        ),
    }


if __name__ == "__main__":  # [无需死背-脚手架]
    cases = [
        CascadeSample("1", 0.92, True, True),
        CascadeSample("2", 0.88, True, True),
        CascadeSample("3", 0.95, True, True),
        CascadeSample("4", 0.45, False, True),
    ]
    report = simulate_quality_cascade(cases, conf_threshold=0.75)
    assert report["escalated_count"] == 1
    assert report["cascade_acc"] == 1.0 and report["all_high_acc"] == 1.0
    assert report["cost_per_success_saving_pct"] > 50.0
    print(f"MM Step 10 self-test passed! report={report}")

```

### 🧠 代码区记忆清单：背什么 vs 不背什么

- **🔒 不可替代的系统设计决策**：采用“低分辨率初筛 + 低置信度升级高清复核”的分级级联路由；成本核算不能只看单次调用单价，必须核算“每个成功任务的真实总成本”（把失败与升级的双倍调用账单算进去）。
- **✍️ 面试手撕/默写范围**：手写级联路由累加逻辑（高置信度直出、低置信度累加 `high_cost_per_req`）与 `cost_per_success = total_cost / max(1, succ_count)`。
- **🗑️ 无需死背的脚手架代码**：`CascadeSample` 数据类、百分比节省率格式化与 `__main__` 测试样例。

#### 4. 🗣️ 面试官视角：这段代码怎么讲

先声明不变量：cost_per_succ 必须以“成功解决的任务数”为分母，绝不能用“总调用单价”欺骗自己——如果低清链路准确率太差导致大量升级或失败，实际单成功任务成本反而可能高于直接上高清。

讲清关键行：第 40~49 行先累加固定低清初筛费，仅对 low_res_conf < conf_threshold 的样本叠加高清复核费，真实模拟级联总账单。

主动点出工程细节：对于多轮 Agent 对话携带图片，历史轮次里的旧图片千万不要每轮都原图重复送，应该在首轮提取结构化证据后替换成文本引用（或低清缩略），否则多轮累积视觉 Token 会指数爆炸。

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：把图片 JPEG 质量压到 50% 后，文件体积降了 80%，但 API 视觉 Token 账单几乎没变

现象：图片变成 100KB，Token 还是 1000+。

定位方法：混淆了“磁盘字节压缩”与“像素宽高缩放”。

修复方案：改用 img.thumbnail((1024, 1024)) 实际缩小像素宽高，或传 detail="low" 档位，并裁掉无关空白边距。

故障 2：多模态 OCR 任务偶发返回空字符串，后台却显示消耗了上万个输出 Token

现象：finish_reason="length" 且正文为空。

定位方法：开启了推理模型的默认 Thinking 模式，内部思考耗尽了 max_tokens。

修复方案：明确字符提取/格式转换类任务关闭 Thinking，复杂推理任务才开启并留足输出预算。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：多模态上线后 Token 成本暴增，你的系统性降本三板斧是什么？

参考答法：① 按任务选分辨率（能用 detail="low" 或缩图解决的绝不默认最高清）；② 先文本检索后看原图（PDF 先靠 OCR/目录召回 Top-K 页，只把相关页送给 VLM）；③ 分级级联（Quality Cascade）（便宜链路初筛，仅低置信度疑难样本升级高清复核），并用“单成功任务总成本”验收。

Q2：离线把图片全转成文字描述（Caption）存库替代原图，可行吗？

参考答法：只适合用于粗粒度语义召回（比如“找室内会议照片”）；一旦涉及精确图表数值、小字号文字、空间左右关系，Caption 是有损压缩必然丢细节，最终回答仍必须回到原图或裁剪区核验。
