## 本章总结：项目设计与评测系统

先用一张图讲清请求、状态和失败出口，再用相同输入说明如何对照、如何评分、何时可以上线。下列案例可用作白板练习。

### 案例 1 · 给问答服务做容量规划

**面试官可能问**　一张卡能装下模型，为什么长请求一多就超时？如何确定上线并发？

```text
请求分类 → 入口限流与队列 → 连续批处理 → Prefill 与 Decode → 分级超时 → 指标回传
```

**系统设计**　容量先估权重、运行余量与 KV 用量，再按输入与预计输出长度管理活跃 token。交互短请求与长文任务按业务分级，批处理与 admission 一起调。PagedAttention 提高 KV 分配效率，仍受实际 token 和显存约束。

**评测系统**　用按时间到达的短、长、突发和混合流量压测。基线为默认批处理，候选改并发或活跃 token 预算，一次改一项。报 TTFT、TPOT、P95、超时/OOM 和达标请求数，超时留在统计中。

**常见追问与排障**　总吞吐上升而达标吞吐下降时，先看排队时间、活跃 token 和长 Prefill 对短请求的影响。按长度切片找到可持续负载点。

**现场参考回答**

> 我先用容量公式拿一个压测起点，再按真实流量找满足时延目标的并发上限。不同长度请求单独计，不用平均吞吐承诺 SLA。

### 案例 2 · INT4 能装下，服务就一定更快吗

**面试官可能问**　把模型量化后显存降了。怎么选量化和回滚路径，验收哪些数据？

```text
同一 checkpoint 的不同权重格式 → 独立推理部署 → 同流量回放 → 质量与性能对账 → 灰度
```

**系统设计**　固定硬件、输入、输出上限和服务配置比较支持的量化格式。小 batch 可能受访存影响，大 batch 更看实际内核和解量化成本。能省出的显存可给更大 KV 空间，容量与速度分开衡量。

**评测系统**　固定任务集、真实流量及重复请求，对照高精度和量化版。比较关键任务成功率、长输入与数字题退化、TTFT、TPOT、P95、峰值显存与每成功任务成本。关键质量门槛不达标就留在旧版。

**常见追问与排障**　若量化后更慢，用同输入、固定输出长度分测 Prefill 与 Decode，再核对内核和 batch；同时查是否开启了别的吞吐特性。

**现场参考回答**

> 我会先说明量化解决的是哪类瓶颈，再用质量、性能和容量三组数据证明值得切流。
