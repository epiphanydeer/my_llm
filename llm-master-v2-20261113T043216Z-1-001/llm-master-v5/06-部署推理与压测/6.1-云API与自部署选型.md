### 6.1 云 API 与自部署选型及显存 TCO 测算 【🔥 必会】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：老板问：“咱们这个 8B 模型是直接调阿里云/OpenAI API，还是自己买 A100 跑 vLLM？一张 80GB 显卡到底能同时扛几个 32K 长上下文的并发请求？”——如果不会算显存公式和月度 TCO（总拥有成本）盈亏平衡点，只能拍脑袋瞎报！

本节解法：掌握 “静态权重显存 + 动态 KV Cache 显存”精确测算公式，并建立云 API 按量计费与自建 GPU 固定月租的 TCO 盈亏平衡点计算器。

大白话例子：就像决定打车还是买车：一个月只跑 500 公里（低并发），打网约车（云 API）最划算，还不用操心保养；如果每天跑几百公里（高并发稳定流量），买辆车（自建 GPU 集群）分摊下来每公里才几毛钱；但买车前必须先量好车库有多大（80GB 显存先扣掉车身重量，剩下的空间才能装行李并发）！

#### 2. 🧠 核心原理与五维拆解

| 维度 | 核心内容（闭卷背诵标准） |
| --- | --- |
| ① 输入什么 | 参数量 params_billion、权重字节 weight_bytes、层数 L、KV 头数 H_kv、Head 维度 d、KV 字节 kv_bytes、序列长度 S、GPU 总显存。 |
| ② 做什么 | 算静态权重 params * weight_bytes -> 算单 Token KV 占用 2 * L * H_kv * d * kv_bytes -> 扣除权重与运行时预留（CUDA Graph/激活等）后除以单请求 KV 占用，得到理论最大并发数；并核算 TCO 盈亏平衡点。 |
| ③ 输出什么 | weight_gb、per_token_kib、per_req_kv_gb、max_concurrency 及 break_even_million_tokens_per_month。 |
| ④ 关键参数 | H_kv（GQA/MQA 相比传统 MHA 把 KV 头数砍掉 4~8 倍，是长上下文并发的关键）、kv_bytes（FP8 KV Cache 减半）。 |
| ⑤ 工程 Trade-off | 云 API 零运维弹性极强，但数据出域且高并发单价贵；自建 vLLM 数据绝对私有且高负载边际成本低，但需承担空闲期卡租浪费与运维 SLA 风险。 |

#### 3. 💻 渐进式代码实操（Step 1：显存容量与 TCO 盈亏平衡测算器）

演进说明：第六章起点，把容量规划与架构选型公式落地为可复现的 Python 测算工具。

```python
"""6.1 Step 1: 显存容量测算 (静态权重 + 动态 KV Cache) 与云 API vs 自部署 TCO 盈亏平衡点."""

from __future__ import annotations

from typing import Dict


def estimate_vram_and_concurrency(
    params_billion: float,
    weight_bytes: int,
    num_layers: int,
    num_kv_heads: int,
    head_dim: int,
    kv_bytes: int,
    seq_len: int,
    gpu_vram_gb: float,
    runtime_reserve_gb: float = 4.0,
) -> Dict[str, float | int]:
    """根据标准注意力 KV Cache 公式测算单卡显存分布与最大理论并发数."""
    if params_billion <= 0 or seq_len <= 0 or gpu_vram_gb <= runtime_reserve_gb:
        raise ValueError("模型参数量、序列长度与可用显存必须合法")

    weight_gb = (params_billion * 1e9 * weight_bytes) / (1024**3)  # [必背手撕-静态权重显存测算公式]
    per_token_bytes = 2 * num_layers * num_kv_heads * head_dim * kv_bytes  # [必背手撕-GQA/MQA单Token KV Cache字节公式]
    per_req_kv_gb = (per_token_bytes * seq_len) / (1024**3)  # [必背手撕-单并发长序列KV显存占用]

    free_for_kv_gb = gpu_vram_gb - weight_gb - runtime_reserve_gb  # [必记设计决策-扣除运行时预留显存防OOM]
    max_concurrency = max(0, int(free_for_kv_gb // per_req_kv_gb))  # [必记设计决策-KV空间决定理论并发上限]

    return {
        "weight_gb": round(weight_gb, 2),
        "per_token_kib": round(per_token_bytes / 1024, 2),
        "per_req_kv_gb": round(per_req_kv_gb, 2),
        "free_for_kv_gb": round(max(0.0, free_for_kv_gb), 2),
        "max_concurrency": max_concurrency,
    }


def tco_break_even(
    monthly_gpu_cost_usd: float,
    api_cost_per_1m_tokens_usd: float,
) -> Dict[str, float]:
    """计算自建 GPU 相比按量付费云 API 的月度 Token 盈亏平衡点 (单位: 百万 Token)."""
    if monthly_gpu_cost_usd <= 0 or api_cost_per_1m_tokens_usd <= 0:
        raise ValueError("成本参数必须为正数")
    break_even_m_tokens = monthly_gpu_cost_usd / api_cost_per_1m_tokens_usd  # [必背手撕-自建与云API月度盈亏平衡点]
    return {"break_even_million_tokens_per_month": round(break_even_m_tokens, 2)}


if __name__ == "__main__":  # [无需死背-脚手架]
    res = estimate_vram_and_concurrency(
        params_billion=8.0, weight_bytes=2, num_layers=32, num_kv_heads=8,
        head_dim=128, kv_bytes=2, seq_len=32768, gpu_vram_gb=80.0,
    )
    assert res["per_token_kib"] == 128.0 and res["per_req_kv_gb"] == 4.0 and res["max_concurrency"] >= 10
    print(f"Ch6 Step 1 self-test passed! res={res}")

```

### 🧠 代码区记忆清单：背什么 vs 不背什么

- **🔒 不可替代的系统设计决策**：单卡最大理论并发数由扣除静态权重与运行时预留显存后的“剩余 KV Cache 空间”决定，测算时必须预留 `runtime_reserve_gb` 防止激活值与碎片引发 OOM。
- **✍️ 面试手撕/默写范围**：必背显存与成本核心公式——静态权重 `params * bytes / 1024^3`、单 Token KV 字节数 `2 * L * n_kv_heads * head_dim * kv_bytes`、以及自建 vs 云 API 月度盈亏平衡点 `monthly_gpu_cost / api_cost_per_1m`。
- **🗑️ 无需死背的脚手架代码**：输入参数合法性检查、字典字段封装与 `__main__` 自检断言。

#### 4. 🗣️ 面试官视角：这段代码怎么讲

先声明不变量：总显存必须同时覆盖“静态权重 + 运行时激活/CUDA Graph 预留 + 并发 KV Cache”，绝不能只算权重能塞进卡里就以为能跑高并发。

讲清关键行：per_token_bytes = 2 * num_layers * num_kv_heads * head_dim * kv_bytes 中的 2 代表 K 和 V 两份张量，且用 num_kv_heads 体现 GQA 的显存红利。

主动点出工程细节：实际部署还要预留约 10% 的 gpu_memory_utilization（vLLM 默认 0.9）给临时通信缓冲和激活峰值，避免突发长 Prompt 直接 OOM。

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：模型权重只有 14GB，跑在 24GB 显卡上，并发一到 4 个长请求就 OOM 崩溃

现象：单条请求好好的，一压测就爆显存。

定位方法：未扣除静态权重（14GB）和运行时预留（~3GB）后，剩余 KV 池只有 7GB，撑不住 4 条长上下文 KV Cache。

修复方案：改用 GQA 模型、开启 INT4/FP8 量化压缩权重或 KV Cache、或限制 max_model_len 上限。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：背出单请求 KV Cache 显存计算公式，并现场口算 8B 模型（32 层，8 个 KV 头，d=128，BF16）32K 上下文占多少显存？

参考答法：公式为 $2 \times L \times H_{\text{kv}} \times d \times \text{bytes} \times S$。单 Token 为 $2 \times 32 \times 8 \times 128 \times 2 = 128\text{ KiB}$；32K Token 约占 $128\text{ KiB} \times 32768 = 4\text{ GiB}$。
