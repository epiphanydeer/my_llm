### 6.4 并发压测、TTFT / TPOT 与 P95 延迟统计 【🔥 必会】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：服务上线前压测，很多同学只汇报一个“平均响应时间 1.2 秒”或者把“排队 P95 + Prefill P95 + Decode P95”直接相加！结果上线后要么长尾用户卡死 8 秒，要么算出来的理论延迟虚高 40% 吓唬自己！

本节解法：构建 StreamingBenchmarkSuite（流式压测与 SLA 统计套件）：① 正交拆解 TTFT（首字时间） 与 TPOT（字间时间）；② 对端到端真实耗时序列求 P95/P99（绝不把各阶段 P95 简单相加）；③ 用 **SLO Goodput（达标有效吞吐）**验收服务。

大白话例子：就像餐厅出餐体验：TTFT 是“从点完菜到第一道凉菜上桌等多久”（决定了顾客会不会烦躁离开）；TPOT 是“后面每道菜上菜间隔快不快”（每秒吐几个字，只要快过人眼阅读速度 50ms/字 就很流畅）；而“排队最久的那桌”和“点菜最多吃得最久的那桌”往往不是同一桌，所以绝不能把两桌的最坏时间硬加在一起！

#### 2. 🧠 核心原理与五维拆解

| 维度 | 核心内容（闭卷背诵标准） |
| --- | --- |
| ① 输入什么 | 流式请求日志 StreamMetrics(req_id, queue_ms, prefill_ms, decode_token_ms) 及 SLO 门槛 ttft_slo_ms、tpot_slo_ms。 |
| ② 做什么 | 计算单请求 ttft_ms = queue + prefill + first_tok、tpot_ms = mean(decode_token_ms[1:])、e2e_ms -> 对全量请求的独立序列分别求 P95 -> 统计同时满足两个 SLO 的 goodput_rate。 |
| ③ 输出什么 | ttft_p95_ms、tpot_p95_ms、e2e_p95_ms、goodput_rate。 |
| ④ 关键参数 | ttft_slo_ms（实时交互常要求 $\le 500\text{ms}\sim 1000\text{ms}$）、tpot_slo_ms（常要求 $\le 50\text{ms}$，即 $\ge 20\text{ tokens/s}$）。 |
| ⑤ 工程 Trade-off | Continuous Batching 提升了吞吐但可能让长 Prompt 的 Prefill 插队卡住正在 Decode 的请求（引发 TPOT 尖峰）；**Chunked Prefill（分块预填充）**把长 Prefill 切块与 Decode 混批，以略微牺牲单请求 TTFT 换取全系统 TPOT 极度平稳！ |

知识扩展（面试加分盲区）：

为什么各阶段 P95 不能相加？（概率论极值独立性）：排队最长（队列满时进来）的请求，它的 Prompt 可能只有 10 个字；而 Prefill 最长（10 万字文档）的请求可能恰好在系统空闲时到达、零排队。把两个不相关的极端分位数相加会严重高估端到端 P95 达 30%~50%，必须先算每条请求的完整 e2e_ms，再对 e2e_ms 列表统一求 np.percentile(..., 95)！

什么是 Goodput（有效吞吐）？：只看 tokens/s 总吞吐很容易作弊（把并发开到 200，虽然总吞吐很高，但每个用户卡成 PPT，TTFT 全超时）。Goodput 只统计在规定 SLO 延迟门槛内达标完成的请求吞吐，才是业务真正认可的容量指标。

#### 3. 💻 渐进式代码实操（Step 4：StreamingBenchmarkSuite 流式压测统计）

演进说明：第六章收官模块，验证“各阶段 P95 不可相加”与 SLO Goodput 统计。

```python
"""6.4 Step 4: 流式并发压测与 TTFT / TPOT / P95 / Goodput 统计套件."""

from __future__ import annotations

from dataclasses import dataclass
from typing import Dict, List
import numpy as np


@dataclass(frozen=True)
class StreamMetrics:
    req_id: str
    queue_ms: float
    prefill_ms: float
    decode_token_ms: List[float]

    @property
    def ttft_ms(self) -> float:
        first_tok = self.decode_token_ms[0] if self.decode_token_ms else 0.0
        return self.queue_ms + self.prefill_ms + first_tok  # [必背手撕-TTFT包含排队+Prefill+首Token]

    @property
    def tpot_ms(self) -> float:
        if len(self.decode_token_ms) <= 1:
            return 0.0
        return sum(self.decode_token_ms[1:]) / (len(self.decode_token_ms) - 1)  # [必背手撕-TPOT仅统计首字之后的平均生成间隔]

    @property
    def e2e_ms(self) -> float:
        return self.queue_ms + self.prefill_ms + sum(self.decode_token_ms)


def evaluate_sla(
    logs: List[StreamMetrics],
    ttft_slo_ms: float = 500.0,
    tpot_slo_ms: float = 50.0,
) -> Dict[str, float | int]:
    if not logs:
        raise ValueError("压测记录不能为空")

    ttfts = [x.ttft_ms for x in logs]
    tpots = [x.tpot_ms for x in logs]
    e2es = [x.e2e_ms for x in logs]
    good_reqs = sum(1 for x in logs if x.ttft_ms <= ttft_slo_ms and x.tpot_ms <= tpot_slo_ms)  # [必记设计决策-Goodput需同时满足TTFT与TPOT双SLO]

    return {
        "total_reqs": len(logs),
        "ttft_p95_ms": round(float(np.percentile(ttfts, 95)), 2),  # [必记设计决策-各阶段P95不可直接相加须按请求级统计]
        "tpot_p95_ms": round(float(np.percentile(tpots, 95)), 2),
        "e2e_p95_ms": round(float(np.percentile(e2es, 95)), 2),
        "goodput_rate": round(good_reqs / len(logs), 4),
    }


if __name__ == "__main__":  # [无需死背-脚手架]
    reqs = [
        StreamMetrics("r1", queue_ms=400.0, prefill_ms=50.0, decode_token_ms=[20.0, 20.0]),
        StreamMetrics("r2", queue_ms=20.0, prefill_ms=300.0, decode_token_ms=[20.0, 40.0, 40.0, 40.0]),
        StreamMetrics("r3", queue_ms=30.0, prefill_ms=60.0, decode_token_ms=[20.0, 25.0, 25.0]),
    ]
    sla = evaluate_sla(reqs, ttft_slo_ms=500.0, tpot_slo_ms=50.0)
    assert sla["goodput_rate"] == 1.0
    print(f"Ch6 Step 4 self-test passed! sla={sla}")

```

#### 4. 🗣️ 面试官视角：这段代码怎么讲

先声明不变量：e2e_p95_ms 必须直接对每条请求的完整端到端耗时序列求分位数，严禁由各阶段 P95 相加；goodput_rate 必须同时卡住 TTFT 与 TPOT 双 SLO。

讲清关键行：decode_token_ms[0] 归入 ttft_ms，decode_token_ms[1:] 的均值才算 tpot_ms，精确贴合流式 SSE 首包与后续字间间隔定义。

主动点出工程细节：压测时一定要用真实分布（长短请求混跑 + Poisson 随机到达），千万不要用固定 100 Token 等长请求去测吞吐，否则测不出长上下文抢占和 Chunked Prefill 的真实效果。

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：流式输出平时很丝滑，但每隔几秒就突然卡顿 1 秒多（TPOT P99 飙升）

现象：正在看打字机输出，突然卡住不动一下，然后又恢复。

定位方法：后台突然进来一个 32K 长上下文请求的 Prefill，独占了 GPU 算力 1 秒，把同批正在 Decode 的请求全堵住了。

修复方案：在 vLLM 中开启 --enable-chunked-prefill，把长 Prefill 拆成 512~2048 Token 小块和 Decode 混批调度。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：为什么不能把 Queue P95 + Prefill P95 + Decode P95 相加当作端到端 P95？

参考答法：因为不同阶段的极值往往发生在不同的独立请求上，简单相加相当于假设“最倒霉的排队、最长的输入和最慢的生成同时砸在一个人头上”，会严重虚高；必须对每个请求的完整耗时求分位数。

Q2：Chunked Prefill（分块预填充）解决了什么问题？

参考答法：解决了“长请求 Prefill 阻塞同一批次其他请求 Decode，导致 TPOT/ITL 剧烈抖动卡顿”的头阻塞（Head-of-Line Blocking）问题。
