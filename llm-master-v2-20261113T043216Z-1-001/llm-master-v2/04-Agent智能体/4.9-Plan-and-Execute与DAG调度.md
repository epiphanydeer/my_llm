### 4.9 Plan-and-Execute 与 DAG 并行调度 【⭐ 理解】

#### 1. 🎯 本节目标与大白话例子

上一步痛点：ReAct（边想边做）在 3~4 步的小任务上很灵活，但如果遇到“同时拉取日志 + 拉取监控指标 + 查询变更记录，最后汇总定位根因”这类步骤较长、且前几步明明互不依赖的任务时，ReAct 会一步一步串行调 LLM，既慢又容易半路走丢。更糟的是，如果第 3 步网络闪断挂了，重跑一遍前两步还得再花钱！

本节解法：引入 Plan-and-Execute + DAGTaskScheduler（有向无环图调度器）：先用 Planner 生成带依赖关系的任务图，再用 Kahn 拓扑排序做环检测和并行波次分批（Wave Batching），并配合 Checkpoint 断点续跑。

大白话例子：就像装修房子（硬装调度）：水电改造、买瓷砖、订橱柜互不依赖，可以同一周并行开工（Wave 1）；刷墙漆必须等水电和瓷砖完工才能进场（Wave 2）；万一刷漆那天工人请假中断了，明天续工时直接从“刷漆”继续，绝不会把水电敲掉重装一遍！

#### 2. 🧠 核心原理与五维拆解

> 图片待恢复：Plan-and-Execute 与 ReAct 架构对比

| 维度 | 核心内容（闭卷背诵标准） |
| --- | --- |
| ① 输入什么 | 任务节点字典 nodes: Dict[str, TaskNode]（每个节点含 task_id、前置依赖 deps、执行动作 action）及已持久化状态 completed_outputs。 |
| ② 做什么 | ① 构建邻接表与入度表；② 用 Kahn 算法按层剥离入度为 0 的节点生成并行波次 waves，若 visited_count != len(nodes) 则直接报错存在环依赖；③ 按波次执行，遇到 completed_outputs 中已有的节点直接跳过。 |
| ③ 输出什么 | waves: List[List[str]] 并行调度计划与所有节点的最终执行结果 Dict[str, str]。 |
| ④ 关键参数 | deps（依赖边）、completed_outputs（Checkpoint 持久化字典）。 |
| ⑤ 工程 Trade-off | Plan-and-Execute 把“规划大模型”和“执行小模型/工具”解耦，能用并行波次大幅压低延迟并支持断点续跑；缺点是如果初始计划漏了一步或环境剧变，需要触发 Re-planning（重规划），否则会按错计划一路跑到黑。 |

知识扩展（面试加分盲区）：

Plan-and-Execute 为什么能省钱又提速？：大小模型路由（Planner-Executor Split）！只在最开始用一次高智商大模型（如 GPT-4o / Claude Sonnet）把大纲和 DAG 拆出来，后面波次里大量的子任务执行（如提取字段、总结单篇文档）全交给便宜飞快的轻量模型（如 GPT-4o-mini / Qwen-7B）甚至纯代码并发跑完，综合成本直降 60%+。

LLM Compiler（并行函数调用图）：学术与工业界常把“Prompt 生成带 $1, $2 变量引用的 DAG 计划 + 调度器一有入度为 0 就立刻并发发射”称为 LLM Compiler 范式，比纯串行 ReAct 端到端延迟快 2~3 倍。

#### 3. 💻 渐进式代码实操（Step 9：新增 DAGTaskScheduler 并行调度与断点续跑）

演进说明：在前面单步循环之外，引入面向复杂多步任务的确定性 DAG 编排器，实现环检测、波次并行分组与 Checkpoint 断点续跑。

```python
"""Step 9: DAG Task Scheduler (Plan-and-Execute 与拓扑并行调度 + 断点续跑).

实现基于 Kahn 算法的 DAG 任务调度器：
1. 环检测 (Cycle Detection)：存在循环依赖时拒绝执行并报错。
2. 并行分批 (Parallel Wave Batching)：入度为 0 的无依赖任务自动编入同一并行波次。
3. 断点续跑 (Checkpoint Resume)：支持持久化已完成节点状态，失败恢复时跳过已完成波次。
"""

from __future__ import annotations

from collections import deque
from dataclasses import dataclass, field
from typing import Callable, Dict, List, Set


@dataclass
class TaskNode:
    task_id: str
    deps: List[str]
    action: Callable[[Dict[str, str]], str]


@dataclass
class DAGTaskScheduler:
    """支持并行分批与断点续跑的 DAG 调度器."""

    nodes: Dict[str, TaskNode]
    completed_outputs: Dict[str, str] = field(default_factory=dict)

    def plan_waves(self) -> List[List[str]]:
        """使用 Kahn 算法生成并行执行波次，并检测循环依赖."""
        in_degree: Dict[str, int] = {tid: 0 for tid in self.nodes}
        children: Dict[str, List[str]] = {tid: [] for tid in self.nodes}

        for tid, node in self.nodes.items():
            for dep in node.deps:
                if dep not in self.nodes:
                    raise ValueError(f"任务 {tid} 依赖不存在的节点 {dep}")
                in_degree[tid] += 1
                children[dep].append(tid)

        queue: deque[str] = deque(sorted(tid for tid, deg in in_degree.items() if deg == 0))
        waves: List[List[str]] = []
        visited_count = 0

        while queue:
            current_wave = list(queue)
            queue.clear()
            waves.append(current_wave)
            next_ready: List[str] = []
            for tid in current_wave:
                visited_count += 1
                for child in children[tid]:
                    in_degree[child] -= 1
                    if in_degree[child] == 0:
                        next_ready.append(child)
            queue.extend(sorted(next_ready))

        if visited_count != len(self.nodes):
            raise ValueError("检测到 DAG 循环依赖 (Cycle Detected)，无法调度")
        return waves

    def run(self, fail_once_on: Set[str] | None = None) -> Dict[str, str]:
        """按波次执行 DAG，自动跳过 checkpoint 中已完成的节点."""
        waves = self.plan_waves()
        fail_once_on = fail_once_on or set()

        for wave in waves:
            for tid in wave:
                if tid in self.completed_outputs:
                    continue
                if tid in fail_once_on:
                    fail_once_on.remove(tid)
                    raise RuntimeError(f"节点 {tid} 模拟执行中断")
                dep_results = {d: self.completed_outputs[d] for d in self.nodes[tid].deps}
                self.completed_outputs[tid] = self.nodes[tid].action(dep_results)
        return dict(self.completed_outputs)


if __name__ == "__main__":
    exec_counts = {"fetch_logs": 0, "fetch_metrics": 0, "diagnose": 0}

    def make_action(name: str) -> Callable[[Dict[str, str]], str]:
        def _fn(deps: Dict[str, str]) -> str:
            exec_counts[name] += 1
            return f"{name}_ok(deps={list(deps.keys())})"
        return _fn

    scheduler = DAGTaskScheduler(
        nodes={
            "fetch_logs": TaskNode("fetch_logs", [], make_action("fetch_logs")),
            "fetch_metrics": TaskNode("fetch_metrics", [], make_action("fetch_metrics")),
            "diagnose": TaskNode("diagnose", ["fetch_logs", "fetch_metrics"], make_action("diagnose")),
        }
    )
    waves = scheduler.plan_waves()
    assert waves == [["fetch_logs", "fetch_metrics"], ["diagnose"]], f"并行波次错误: {waves}"

    fail_set = {"diagnose"}
    try:
        scheduler.run(fail_once_on=fail_set)
        assert False, "应当抛出中断异常"
    except RuntimeError:
        pass

    final_out = scheduler.run(fail_once_on=fail_set)
    assert "diagnose" in final_out
    assert exec_counts["fetch_logs"] == 1 and exec_counts["fetch_metrics"] == 1
    assert exec_counts["diagnose"] == 1

    cyclic = DAGTaskScheduler(
        nodes={
            "A": TaskNode("A", ["B"], lambda _: "A"),
            "B": TaskNode("B", ["A"], lambda _: "B"),
        }
    )
    try:
        cyclic.plan_waves()
        assert False, "环依赖必须报错"
    except ValueError as e:
        assert "Cycle" in str(e)
    print("Step 9 self-test passed!")
```

#### 5. 🔧 生产排障指南（实现 -> 排障）

故障 1：Planner 生成了循环依赖（如任务 A 依赖 B，B 又依赖 A），调度器直接卡死或无限递归

现象：任务长时间处于 PENDING 既不执行也不报错。

定位方法：检查 Planner 输出的 DAG 是否缺少静态拓扑校验。

修复方案：调度前强制执行 Kahn 算法环检测（visited_count != len(nodes)），发现环直接打回 Planner 重规划或报错。

故障 2：前面已经花 30 秒查完 5 个数据源，第 6 步汇总节点超时导致全盘重来

现象：用户点击“重试”后又等了 30 秒且重复扣了 5 次外部接口费用。

定位方法：任务状态仅保存在内存局部变量，进程异常后全量丢失。

修复方案：每完成一个节点就把输出持久化到 Redis / DB（completed_outputs），重跑时基于 task_run_id 加载 Checkpoint 跳过已完成节点。

#### 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

Q1：ReAct 和 Plan-and-Execute 各自适合什么场景？能不能结合？

参考答法：ReAct 适合步骤少（3~5 步）、每一步高度依赖上一步未知观测的强探索任务；Plan-and-Execute 适合步骤多、依赖结构清晰、可并行加速或需控制长链路成本的任务。工业界常把两者结合：宏观用 Plan-and-Execute 拆成 3 个阶段 DAG，每个子阶段内部用受限步数的 ReAct 节点去执行。

Q2：Plan-and-Execute 最大的缺点是什么？怎么弥补？

参考答法：最大缺点是“计划赶不上变化”——如果执行到第 2 步发现前提假设错了，死板按原计划走下去必然失败。弥补方案是引入 Re-planner（动态重规划器）：每完成一个波次或遇到关键异常时，快速评估剩余计划是否依然有效，必要时局部改写后续 DAG。
