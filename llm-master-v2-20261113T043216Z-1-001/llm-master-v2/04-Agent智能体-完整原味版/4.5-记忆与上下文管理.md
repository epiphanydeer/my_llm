# Agent的记忆：短期、长期、RAG到底什么关系？

<a href="https://programmercarl.com/other/project_kamaClaude.html">
  <img src="../../assets/images/kama-claude.jpg?v=20261005" style="width:100%;cursor:pointer;" alt="KamaClaude">
</a>

上一篇我们讲了 [Agent 为什么容易翻车](./agent_failure_modes.md)。

核心就一句话：**Agent 能自主行动，就必须有工程护栏。**

死循环、误调用、上下文污染、权限越界，本质上都和“状态管理”有关。

一个 Agent 如果不知道自己做过什么、当前做到哪一步、哪些信息是真的、哪些只是猜测，那它就很容易跑偏。

所以这一篇，我们继续往下讲：

**Agent 的记忆到底怎么设计。**

很多录友一听 Agent 记忆，第一反应是：

“是不是把所有聊天记录都存起来，下次再塞给模型？”

不是。

这理解太粗了。

如果你真这么做，系统很快就会遇到三个问题：

- 上下文塞不下
- 噪音越来越多
- 旧信息和新信息互相打架

所以先记住一句话：

**Agent 记忆不是把历史全塞进 Prompt，而是把有价值的信息用合适的方式保存、检索、更新和遗忘。**

这篇我们就把短期记忆、长期记忆、RAG、Session State 之间的关系讲清楚。

![Agent 记忆分层与上下文污染关系](https://file1.kamacoder.com/i/web/20260526175836_agent_memory_01_memory_layers_compressed.png?v=20261005)

## 一、先搞清楚：Agent 为什么需要记忆

普通问答系统，不一定需要复杂记忆。

用户问一句。

模型答一句。

结束。

但 Agent 不一样。

Agent 往往要做多步任务。

比如用户说：

“帮我分析这个项目的技术债，然后按优先级给修复建议。”

Agent 可能要：

1. 先看项目目录。
2. 再看核心模块。
3. 再找复杂函数。
4. 再看测试覆盖。
5. 再总结优先级。

这个过程中，它必须记住：

- 用户最初的目标是什么
- 已经看过哪些目录
- 哪些文件有问题
- 哪些证据支撑当前判断
- 哪些步骤失败了
- 哪些结论只是临时假设

如果没有记忆，Agent 就会边做边忘。

前面刚查到的证据，后面忘了。

前面已经失败的工具，后面继续调用。

用户强调过的要求，后面又忽略。

这就是很多 Agent 看起来“不稳定”的原因之一。

**它不是单纯不会推理，而是缺少可管理的任务记忆。**

## 二、Agent 记忆至少分四类

讲 Agent 记忆，不要上来就说向量数据库。

先按用途分清楚。

一个比较实用的划分是四类：

**短期记忆、Session State、长期记忆、外部知识库。**

它们解决的问题不一样。

### 1. 短期记忆：当前对话里刚发生了什么

短期记忆通常就是当前对话上下文。

比如最近几轮聊天、最近几次工具调用、最近拿到的结果。

它的特点是：

- 生命周期短
- 和当前任务强相关
- 通常放在上下文窗口里
- 容易被窗口长度限制

比如用户前面说：

“我的项目是 Java 后端，主要用 Spring Boot。”

后面又问：

“那我这个简历项目怎么写？”

模型需要记住前面这句话。

这就是短期记忆。

### 2. Session State：当前任务进行到哪一步

Session State 不是聊天记录。

它是结构化状态。

比如：

```json
{
  "goal": "分析仓库技术债",
  "completed_steps": ["读取目录结构", "定位核心模块"],
  "failed_steps": [
    {
      "step": "读取测试覆盖报告",
      "reason": "文件不存在"
    }
  ],
  "evidence": ["core/payment/PayService.java 方法过长"],
  "missing_info": ["缺少测试覆盖率数据"]
}
```

你看，它不是把聊天原文堆起来。

它是在记录任务状态。

这对 Agent 特别重要。

因为 Agent 做多步任务时，最怕“做到一半开始总结”。

Session State 可以提醒它：

你哪些步骤完成了。

哪些证据拿到了。

哪些信息还缺。

现在能不能交付。

### 3. 长期记忆：跨会话保留的稳定信息

长期记忆是跨会话存在的。

比如用户长期偏好：

- 用户主要写 Java
- 用户准备秋招
- 用户简历希望突出项目难点
- 用户不喜欢太书面腔

再比如某个业务 Agent 的长期状态：

- 某客户属于高优先级客户
- 某项目常用的排查入口
- 某团队的代码规范

长期记忆的特点是：

- 不一定每次都用
- 必须经过筛选再写入
- 需要更新和遗忘
- 不能把临时信息当成长期事实

长期记忆最怕什么？

**把所有聊天都存进去。**

这样最后不是记忆。

是垃圾堆。

### 4. 外部知识库：Agent 可以查的资料

外部知识库常常用 RAG 实现。

比如：

- 公司文档
- API 文档
- 产品手册
- 代码仓库
- 面试题库
- 运维手册

它不是“用户记忆”。

它是外部知识来源。

Agent 在需要时检索相关资料，再放进上下文。

所以 RAG 更像是：

**Agent 的外部资料库。**

而长期记忆更像是：

**Agent 对用户、任务、历史经验的持久记录。**

![Agent 短期记忆、Session State、长期记忆和外部知识库四类记忆对比](https://file1.kamacoder.com/i/web/20260526175837_agent_memory_02_four_types_compressed.png?v=20261005)

## 三、短期记忆不是越长越好

很多录友会觉得：

“上下文窗口越大，短期记忆越强。”

这话只对一半。

上下文窗口大，确实能放更多历史。

但放得多，不代表效果一定好。

因为上下文里有很多噪音：

- 用户的临时猜测
- 工具返回的无关日志
- 已经被证伪的方向
- 过期的中间结论
- 重复的对话内容

如果这些都堆进去，模型反而会被干扰。

上一篇我们讲过上下文污染。

短期记忆越长，越容易污染。

所以短期记忆要做两件事。

**第一，保留当前任务相关信息。**

比如目标、约束、最近工具结果、关键证据。

**第二，丢掉不再有用的信息。**

比如重复对话、无关日志、已经证伪的假设。

短期记忆不是聊天记录全文。

它应该更像一份“当前任务摘要”。

![短期记忆从长对话中过滤关键任务摘要的过程](https://file1.kamacoder.com/i/web/20260526175838_agent_memory_03_short_memory_filter_compressed.png?v=20261005)

举个例子。

用户让 Agent 排查接口变慢。

原始对话可能很长：

- 用户猜是数据库问题
- Agent 查了数据库
- 数据库没问题
- Agent 查了发布记录
- 发现 22:05 有发布
- Agent 查了日志
- 发现第三方回调超时

短期记忆里真正该保留的是：

“目标：定位接口变慢原因。数据库方向已排除。22:05 有发布。22:10 后第三方回调超时增加。下一步应确认发布是否引入回调重试逻辑。”

这比把全部聊天原文塞进去更有用。

## 四、Session State 比聊天记录更适合多步任务

Agent 做多步任务时，最重要的不是“记住说过什么”。

而是“记住任务进展”。

这就是 Session State 的价值。

比如一个故障排查 Agent，可以维护这样的状态：

```json
{
  "goal": "定位支付接口变慢原因",
  "current_hypothesis": "第三方支付回调超时可能导致接口变慢",
  "confirmed_facts": [
    "22:10 后 /api/pay P95 从 300ms 升到 3.8s",
    "22:05 发布了 payment-service v2.3.1"
  ],
  "rejected_hypotheses": [
    "数据库慢查询导致接口变慢"
  ],
  "next_actions": [
    "检查 v2.3.1 是否改动回调重试逻辑",
    "查询第三方支付回调错误码分布"
  ]
}
```

这比一段长聊天有用得多。

因为它把信息分成了：

- 目标
- 假设
- 事实
- 已排除方向
- 下一步动作

Agent 每一步都能对照它推进。

而不是靠模型自己在长上下文里找重点。

![Session State 记录目标、假设、事实和下一步动作](https://file1.kamacoder.com/i/web/20260526175840_agent_memory_04_session_state_compressed.png?v=20261005)

很多生产系统里的 Agent，其实都要做状态管理。

否则一旦任务超过三五步，就很容易跑散。

特别是这些场景：

- 故障排查
- 代码库分析
- 长文档总结
- 数据分析报告
- 多轮客服处理
- 面试辅导和简历修改

只靠 conversation buffer，不够。

要有结构化状态。

## 五、长期记忆不能直接写入，必须过筛

长期记忆听起来很诱人。

用户说过什么都记住。

下次再来就像老朋友一样。

但工程上最怕这件事：

**把临时信息写成长期事实。**

比如用户今天说：

“我最近在看 Go。”

这是不是长期记忆？

不一定。

可能只是今天临时问一下。

再比如用户说：

“我可能想投后端。”

这是不是长期记忆？

也不一定。

它是一个不稳定意向。

如果 Agent 直接记成“用户目标是后端开发”，后面就可能持续误导。

所以长期记忆写入前，必须过筛。

至少要问四个问题：

**第一，这个信息是否长期稳定？**

比如“用户主要使用 Java”比“用户今天问了 Go”更适合长期记忆。

**第二，这个信息以后是否有用？**

比如“用户喜欢口语化讲解”有用。

“用户今天晚上 9 点问了一个问题”通常没用。

**第三，这个信息是否被确认过？**

用户明确说“我主要投 Java 后端”，比模型猜“用户可能投 Java”可靠。

**第四，这个信息是否涉及隐私或敏感信息？**

敏感信息不能随便写。

需要权限、用途和删除机制。

![长期记忆写入前的稳定性、有用性、确认和合规筛选](https://file1.kamacoder.com/i/web/20260526175841_agent_memory_05_write_gate_compressed.png?v=20261005)

长期记忆要像数据库写入。

不是像聊天记录自动追加。

它应该有写入规则、更新规则、删除规则。

否则越用越乱。

## 六、长期记忆怎么检索：不是全量塞回上下文

长期记忆存起来以后，下一步是怎么用。

很多人又会犯一个错：

“既然有长期记忆，那每次都把用户全部记忆塞进 Prompt。”

不行。

这和把全部聊天记录塞进去是一个问题。

长期记忆也要按需检索。

比如用户问：

“帮我优化这个简历项目。”

这时有用的长期记忆可能是：

- 用户目标是 Java 后端
- 用户准备校招
- 用户希望项目描述更像面试表达
- 用户已有 Redis 项目经历

但下面这些就没必要：

- 用户上次问过 MCP
- 用户曾经问过 C++ 智能指针
- 用户喜欢某个模型产品

所以长期记忆使用流程应该是：

1. 根据当前任务生成检索意图。
2. 从长期记忆里找相关条目。
3. 过滤过期和低置信度记忆。
4. 只把关键记忆放进上下文。
5. 生成回答后，根据需要更新记忆。

![长期记忆按当前任务检索、过滤、使用和更新的流程](https://file1.kamacoder.com/i/web/20260526175843_agent_memory_06_memory_retrieval_compressed.png?v=20261005)

这和 RAG 很像。

但对象不一样。

长期记忆检索的是用户偏好、历史任务、稳定状态。

RAG 检索的是外部知识、文档、资料。

这就是它们的区别。

## 七、RAG 不是 Agent 的长期记忆

这点很重要。

很多人会把 RAG 和长期记忆混为一谈。

“我把历史聊天记录存到向量数据库里，再检索出来，这不就是长期记忆吗？”

不完全是。

向量数据库只是存储和检索方式。

不等于记忆设计。

如果你把所有聊天记录原文扔进向量库，后面检索出来一堆碎片。

那只是“历史记录检索”。

不一定是“长期记忆”。

长期记忆应该是经过提炼的信息。

比如原始对话是：

“我现在主要准备 Java 后端，项目是一个网盘系统，希望简历不要写得太像流水账。”

长期记忆应该写成：

```json
{
  "type": "user_profile",
  "content": "用户主要准备 Java 后端方向",
  "confidence": 0.95,
  "source": "用户明确表达",
  "updated_at": "2026-05-26"
}
```

而不是把整段聊天原文丢进去。

RAG 更适合做外部知识库：

- 公司文档
- 产品说明
- API 手册
- 代码仓库
- 运维手册
- 面试题库

长期记忆更适合记录：

- 用户偏好
- 用户目标
- 历史任务结论
- 已确认的项目背景
- Agent 自己需要跨会话保留的状态

![RAG 外部知识库和 Agent 长期记忆的边界区别](https://file1.kamacoder.com/i/web/20260526175844_agent_memory_07_rag_vs_memory_compressed.png?v=20261005)

所以面试时别说：

“我们用向量数据库实现长期记忆。”

这句话太浅。

你要补一句：

“向量数据库只是检索层。长期记忆还要设计写入规则、记忆类型、置信度、更新时间、冲突处理和删除机制。”

这才像工程回答。

## 八、记忆也要会忘

记忆不是越多越好。

Agent 也要会忘。

否则长期记忆会出现三个问题。

### 1. 过期

用户去年准备 Java 后端。

今年转向大模型应用。

如果 Agent 还一直按 Java 后端给建议，就错了。

### 2. 冲突

用户之前说想投算法。

后来明确说不投算法，转投应用开发。

旧记忆和新记忆冲突。

这时不能都塞给模型。

要更新或降权旧记忆。

### 3. 噪音

长期记忆里存了太多低价值信息。

检索时就容易召回一堆无关内容。

所以记忆系统要有“遗忘机制”。

至少包括：

- 过期时间
- 置信度
- 更新时间
- 冲突合并
- 用户删除
- 低价值记忆清理

![Agent 长期记忆过期、冲突和噪音的更新遗忘机制](https://file1.kamacoder.com/i/web/20260526175846_agent_memory_08_forgetting_update_compressed.png?v=20261005)

记忆不是仓库。

不是只进不出。

它更像一个持续维护的状态系统。

## 九、Agent 记忆怎么设计更稳

如果你真要在项目里设计 Agent 记忆，可以按这个框架来。

### 1. 先定义记忆类型

不要只有一个 `memory` 表。

至少区分：

- 用户偏好
- 用户目标
- 项目背景
- 任务状态
- 历史结论
- 外部知识引用

不同类型的记忆，写入规则不同。

用户偏好可以长期保存。

任务状态可能会话结束就清掉。

外部知识引用应该回到 RAG 文档里。

### 2. 再定义写入规则

什么信息可以写？

什么信息不能写？

什么信息需要用户确认？

什么信息只作为临时状态？

这一步很重要。

没有写入规则，长期记忆很快会变脏。

### 3. 检索时按任务筛选

不要全量塞。

根据当前任务选择相关记忆。

比如简历优化任务，就检索求职方向、项目背景、写作偏好。

故障排查任务，就检索服务背景、历史事故、常用排查入口。

### 4. 使用后更新记忆

用户目标变了，要更新。

旧结论被推翻，要降权。

低价值记忆长期不用，要清理。

用户要求删除，要删除。

这才是完整闭环。

![Agent 记忆系统从定义类型到写入、检索、使用和遗忘的闭环](https://file1.kamacoder.com/i/web/20260526175848_agent_memory_09_memory_lifecycle_compressed.png?v=20261005)

## 十、面试时怎么回答 Agent 记忆

Agent 记忆现在面试也越来越容易被问。

尤其是你简历里写了“长期记忆”“个性化 Agent”“上下文管理”，面试官一定会追。

**面试官问：Agent 的短期记忆和长期记忆有什么区别？**

可以这样答：

“短期记忆主要服务当前会话和当前任务，比如最近几轮对话、工具调用结果、当前任务摘要，通常受上下文窗口限制；长期记忆是跨会话保留的稳定信息，比如用户偏好、长期目标、项目背景和历史结论。长期记忆不能直接把所有聊天都存起来，需要经过筛选、结构化、更新和遗忘。”

**面试官问：Session State 和聊天记录有什么区别？**

可以这样答：

“聊天记录是原始对话，噪音比较多；Session State 是结构化任务状态，记录目标、已完成步骤、失败步骤、证据、假设和下一步动作。Agent 做多步任务时，Session State 比单纯 conversation buffer 更可靠，因为它能防止任务中断、重复调用和提前交付。”

**面试官问：RAG 和长期记忆是什么关系？**

可以这样答：

“RAG 通常用于检索外部知识，比如文档、代码、知识库；长期记忆用于保存用户偏好、历史任务和稳定状态。它们都可能用向量检索，但语义不一样。向量数据库只是存储和检索方式，不等于长期记忆本身。长期记忆还要设计写入规则、置信度、更新时间、冲突处理和删除机制。”

**面试官问：长期记忆怎么防止变脏？**

可以这样答：

“不能把所有对话自动写入长期记忆。写入前要判断信息是否稳定、是否有用、是否被用户确认、是否合规。记忆条目要有类型、来源、置信度、更新时间。新信息和旧信息冲突时，要更新或降权旧记忆，过期和低价值记忆要清理。”

### 1. 什么是“原子轮次（Atomic Turn）”、“水位线（Watermark）”与“KV Cache 前缀命中率”？
- **为什么不能按条删消息，必须按“原子轮次（Atomic Turn）”整组删**：
  - 在一轮工具调用里，`[用户提问 -> 模型申请调工具(含 tool_call_id) -> 工具返回结果(含 tool_call_id) -> 模型总结]` 这几条消息就像连体婴儿一样绑在一起，叫一个**原子轮次**。
  - 如果你的滑动窗口按单条消息裁剪，把“模型申请调工具”那条删了，却把“工具返回结果”留在列表开头，大模型接口看到一张没头没尾的回执单，会当场报 `400 Orphan Tool Message` 崩溃！所以裁剪时**要么整轮一起留，要么整轮一起删**！
- **为什么不能每轮都删一点，要用“高低水位线（High/Low Watermark）批量裁剪”**：
  - 现代大模型推理全靠 **Prefix KV Cache（前缀缓存）** 省钱提速——只要你发给模型的历史消息前缀跟上一轮一模一样，前面的几千个 Token 就不用重新算，成本打 1 折、首字延迟快 5 倍！
  - 如果你每聊一句就删掉最前面的一句话，会导致整个消息列表的“排头兵”每轮都在变，**KV Cache 命中率直接跌成 0%**！
  - 正确做法：像抽水马桶水箱一样，平时只往后追加消息（100% 命中前缀缓存）；只有当总 Token 涨到 **85% 高水位线** 时，才一次性批量清理最老的几轮，降到 **60% 低水位线**，这样接下来的十几轮又能连续享受 100% 缓存命中！

```python
# 【循序渐进手搓版 Level 5（在 Level 4 基础上新增“原子轮次打包 + 高低水位线批量裁剪”）】
from typing import Dict, List

def pack_into_atomic_turns(messages: List[Dict[str, str]]) -> List[List[Dict[str, str]]]:
    """把零散的消息列表按 `user` 起点打包成不可拆散的原子轮次（Atomic Turns）"""
    turns: List[List[Dict[str, str]]] = []
    current_turn: List[Dict[str, str]] = []
    for m in messages:
        if m["role"] == "system":
            continue
        if m["role"] == "user" and current_turn:
            turns.append(current_turn)
            current_turn = [m]
        else:
            current_turn.append(m)
    if current_turn:
        turns.append(current_turn)
    return turns

def trim_memory_with_watermark(
    system_msg: Dict[str, str],
    messages: List[Dict[str, str]],
    high_watermark_chars: int = 200,
    low_watermark_chars: int = 120,
) -> List[Dict[str, str]]:
    """Level 5 核心积木：永不误删 system 消息 + 永不拆碎 tool_call 配对 + 水位线批量驱逐"""
    turns = pack_into_atomic_turns(messages)
    total_chars = lambda ts: len(system_msg["content"]) + sum(len(m["content"]) for t in ts for m in t)

    # 未超最高水位线：原样保留，保护 KV Cache 前缀稳定
    if total_chars(turns) <= high_watermark_chars:
        return [system_msg] + [m for t in turns for m in t]

    # 超过最高水位线：从最老的完整轮次开始整轮弹出，直到降回低水位线（至少保留最新 1 轮）
    while len(turns) > 1 and total_chars(turns) > low_watermark_chars:
        turns.pop(0)

    return [system_msg] + [m for t in turns for m in t]

def self_test() -> None:
    sys_m = {"role": "system", "content": "你是南矿安监助手"}
    history = [
        {"role": "user", "content": "第一轮：查1号皮带机" + "A" * 60},
        {"role": "assistant", "content": "call_1: get_temp"},
        {"role": "tool", "content": "结果：55度" + "B" * 60},
        {"role": "user", "content": "第二轮：查2号皮带机"},
        {"role": "assistant", "content": "call_2: get_temp"},
        {"role": "tool", "content": "结果：60度"},
    ]
    trimmed = trim_memory_with_watermark(sys_m, history, high_watermark_chars=150, low_watermark_chars=100)
    # 验证第1轮被整轮原子删除，绝不会留下孤儿 tool 消息，且第2轮完整保留
    roles = [m["role"] for m in trimmed]
    assert roles == ["system", "user", "assistant", "tool"]
    assert "第二轮" in trimmed[1]["content"]
    print("✅ [手搓版 Level 5] 原子轮次打包与高低水位线记忆裁剪器自检通过！")

if __name__ == "__main__":
    self_test()
```

### 面试追问

- 【🔥 必会】外企高频设计题：“长多轮会话中上下文超出窗口上限，你们是怎么做记忆裁剪的？直接删旧消息有什么致命坑？”
一句话结论：严禁按单条消息直接切片，必须以“原子轮次（Turn）”为单位整块淘汰，防止悬空 Tool 调用打崩 API。
展开原理/取舍：在包含工具调用的 Agent 交互中，一条 user 提问后面通常紧跟着 1 条带有 tool_calls 的 assistant 消息以及若干条对应的 tool 结果消息，这三者在协议语义上构成了不可分割的“逻辑整体”。若机械地使用 messages[-k:] 截断，极易把前半部分的调用请求切掉而残留后半部分的结果，导致服务端直接判定协议违规报错 400；正确方案是抽象出 AtomicTurn 数据结构，裁剪时从最旧的完整轮次整块剔除。

- 【🔥 必会】短期记忆、长期记忆与 RAG 到底是什么关系？
一句话结论：短期记忆是在内存 Context 里即时可见的消息；长期记忆是跨会话落盘存储、通过类似 RAG 机制按需召回的外部资产。
展开原理/取舍：① 短期记忆：物理上就是当前请求塞给 Transformer 的那一串 Token，负责维持当前任务的多轮推理链，会话结束即释放；② 长期记忆：是持久化在数据库（如 DynamoDB / PG）中的用户习惯、历史事实或总结画像；当用户开启新会话时，系统利用 RAG 的 Embedding 相似度检索，从长期记忆中把相关的旧事实捞出来塞入短期上下文。底层检索技术同构，但数据治理与时效更新逻辑截然不同。

- 【⭐ 理解】【排障题】线上采用“旧会话自动总结摘要（Summarization Memory）”方案，运行一周后模型经常自相矛盾，为什么？
一句话结论：摘要模型在压缩时发生了事实漂移（Information Decay），多次“摘要的摘要”引发误差滚雪球。
展开原理/取舍：让 LLM 对历史进行摘要（如将 2000 字压缩为 200 字），模型不可避免地会根据概率先验丢失微小的前提条件（如时间、责任主体），甚至将否定句误概括为肯定句；当会话持续变长，系统拿着旧摘要做二次摘要，形成了“传话筒效应（Chinese Whispers）”，最终注入的背景完全失真。工程治理：关键事实字段（如订单号、金额、审批状态）严禁走自由文本摘要，必须走结构化键值（Structured Key-Value）状态抽取。

### 故障模式与排障

- 故障模式：模型在长会话中突然“忘记”了一开始声明的核心业务规则

- 定位：排查上下文管理器是否在滑窗计算时，把索引从 0 开始滑动，把位于 messages[0] 的 System Prompt 一并给滑动滑出去了。

- 修复：系统提示词置顶锁死（Pinning）：在做任何上下文预算扣减时，第一步先扣除 System Prompt 的消耗，滑窗算法仅作用于历史对话列表 messages[1:]，确保核心系统规则永远位于 Prompt 首位。

- 故障模式：工具结果过于冗长迅速挤爆上下文窗口

- 定位：某个查询 SQL 或网络请求返回了一个几万行的原始 JSON 报表，单次写入直接消耗 10k Token。

- 修复：工具出参前置投影（Projection & Truncation）：在工具内部只提取大模型当前任务关心的核心列与指标，过滤无关字段；单条 Tool 消息硬截断至 1500 字符以内。

### 工程 trick 与坑

- 单向只读记忆的隔离：多租户场景下，跨用户严禁共享长期记忆向量库；每一个记忆检索 Query 必须携带 user_id 与 org_id 强隔离过滤，防止小保密员意外唤醒公司高管的私人对话记忆。

- Token 预算预留缓冲区（Output Buffer Reserve）：在计算输入预算时，切记留出模型输出回答所需的空余配额（如 reserve_tokens = 1000）。如果输入占满了全部窗口，模型将直接报错无空间生成下一个 Token。

### 循序渐进 Toy Code：Level 5 — 工业级原子轮次滑动窗口记忆管理器

代码难度定位：Level 5（原子轮次与滑动窗口）。手写一个严格保证 System Prompt 置顶锁死、工具调用与结果原子绑定、基于字符/Token 预算倒序裁剪的内存记忆管理器。

```python
"""
4.5 Toy Code: Level 5 - 工业级原子轮次滑动窗口记忆管理器
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
from typing import Any, Optional


@dataclass(frozen=True)
class ToolCallRecord:
    """工具调用与结果的原子绑定对"""
    call_id: str
    tool_name: str
    arguments_json_str: str
    observation_result_str: str


@dataclass(frozen=True)
class AtomicDialogueTurn:
    """不可分割的原子会话轮次 (Turn)"""
    turn_id: int
    user_prompt: str
    tool_interactions: tuple[ToolCallRecord, ...] # 本轮发生的全部工具交互
    final_assistant_reply: str

    def to_standard_messages(self) -> list[dict[str, Any]]:
        """将轮次平铺解构为标准 OpenAI 格式消息列表"""
        msgs: list[dict[str, Any]] = [
            {"role": "user", "content": self.user_prompt}
        ]
        
        # 若存在工具调用，严格按时序组装 assistant tool_calls 与 tool 结果
        if self.tool_interactions:
            assistant_call_msg: dict[str, Any] = {
                "role": "assistant",
                "content": None,
                "tool_calls": [
                    {
                        "id": ti.call_id,
                        "type": "function",
                        "function": {"name": ti.tool_name, "arguments": ti.arguments_json_str}
                    }
                    for ti in self.tool_interactions
                ]
            }
            msgs.append(assistant_call_msg)
            
            # 追加一一对应的 tool 观察结果
            for ti in self.tool_interactions:
                msgs.append({
                    "role": "tool",
                    "tool_call_id": ti.call_id,
                    "content": ti.observation_result_str
                })

        # 最终回答
        if self.final_assistant_reply:
            msgs.append({"role": "assistant", "content": self.final_assistant_reply})
            
        return msgs

    def estimate_char_size(self) -> int:
        """估算本轮次的字符总开销"""
        total = len(self.user_prompt) + len(self.final_assistant_reply)
        for ti in self.tool_interactions:
            total += len(ti.call_id) + len(ti.tool_name) + len(ti.arguments_json_str) + len(ti.observation_result_str)
        return total


class AtomicContextMemoryManager:
    """原子轮次上下文滑窗管理器"""

    def __init__(self, system_prompt: str, max_allowed_chars: int = 1000):
        if not system_prompt.strip():
            raise ValueError("系统提示词不能为空")
        if max_allowed_chars <= len(system_prompt):
            raise ValueError("最大预算必须大于系统提示词本身的开销")
            
        self.system_prompt = system_prompt
        self.max_allowed_chars = max_allowed_chars
        self.turn_history: list[AtomicDialogueTurn] = []

    def add_turn(self, turn: AtomicDialogueTurn) -> None:
        """追加一个完整的已闭环轮次"""
        self.turn_history.append(turn)

    def compile_messages_for_llm(self) -> tuple[list[dict[str, Any]], int]:
        """
        编译供 LLM 消费的消息列表
        
        核心不变量保证：
        1. System Prompt 位于最首位且永久不会被裁掉
        2. 绝不发生单条消息撕裂，严格以整轮（AtomicTurn）为单位倒序保留
        3. 总字符开销严格不超过 max_allowed_chars
        """
        # 1. 优先预留系统提示词的刚性预算
        system_msg = {"role": "system", "content": self.system_prompt}
        remaining_budget = self.max_allowed_chars - len(self.system_prompt)

        retained_turns: list[AtomicDialogueTurn] = []

        # 2. 从最新的轮次开始倒序向前装入
        for turn in reversed(self.turn_history):
            turn_cost = turn.estimate_char_size()
            if turn_cost <= remaining_budget:
                retained_turns.append(turn)
                remaining_budget -= turn_cost
            else:
                # 预算耗尽，停止向前装入更旧的历史轮次
                break

        # 3. 恢复正序时序排列
        retained_turns.reverse()

        # 4. 展平成标准 API 消息序列
        final_messages: list[dict[str, Any]] = [system_msg]
        for t in retained_turns:
            final_messages.extend(t.to_standard_messages())

        # 后置协议校验：检查绝不存在孤儿 tool 消息
        active_call_ids: set[str] = set()
        for m in final_messages:
            if m.get("tool_calls"):
                for tc in m["tool_calls"]:
                    active_call_ids.add(tc["id"])
            elif m.get("role") == "tool":
                assert m.get("tool_call_id") in active_call_ids, "严重协议违规：检测到悬空孤儿 Tool 结果！"

        return final_messages, len(retained_turns)


def self_test():
    """测试原子轮次滑窗管理器的协议安全性与预算裁剪"""
    sys_prompt = "你是企业合规助手。"
    # 限制预算为 200 字符（强制触发滑窗）
    memory = AtomicContextMemoryManager(system_prompt=sys_prompt, max_allowed_chars=220)

    # 构造第 1 轮（较旧的对话，带工具调用）
    turn1 = AtomicDialogueTurn(
        turn_id=1,
        user_prompt="查询1号配电箱状态",
        tool_interactions=(
            ToolCallRecord("call_001", "query_db", '{"id": 1}', '{"status": "正常"}'),
        ),
        final_assistant_reply="1号配电箱运行状态正常。"
    )

    # 构造第 2 轮（较新的对话，普通文本问答）
    turn2 = AtomicDialogueTurn(
        turn_id=2,
        user_prompt="那2号呢？",
        tool_interactions=(),
        final_assistant_reply="2号配电箱今日未见异常报告。"
    )

    memory.add_turn(turn1)
    memory.add_turn(turn2)

    # 1. 正常编译检验：在 220 预算下，应该完整容纳系统提示与 2 轮对话
    msgs, retained_count = memory.compile_messages_for_llm()
    assert retained_count == 2
    assert msgs[0]["role"] == "system"
    # 验证工具调用配对完整存在
    assert any(m.get("tool_call_id") == "call_001" for m in msgs)

    # 2. 触发预算压缩测试：收紧预算为 70 字符，强制淘汰旧的 Turn 1
    tight_memory = AtomicContextMemoryManager(system_prompt=sys_prompt, max_allowed_chars=70)
    tight_memory.add_turn(turn1)
    tight_memory.add_turn(turn2)

    tight_msgs, tight_retained = tight_memory.compile_messages_for_llm()
    # 核心安全断言：Turn 1 被整块淘汰，仅保留 Turn 2；且绝不残留 call_001 的孤儿结果！
    assert tight_retained == 1
    assert not any(m.get("tool_call_id") == "call_001" for m in tight_msgs)
    assert tight_msgs[1]["content"] == "那2号呢？"
    assert tight_msgs[0]["role"] == "system"

    print("✅ 4.5 原子轮次滑动窗口记忆管理器自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个遵循原子完整性的上下文管理器 AtomicContextMemoryManager。核心不变量是：每一个逻辑轮次 AtomicDialogueTurn 内部的 user、assistant[tool_calls]、tool[id] 与 final_reply 属于强引用绑定；任何裁剪操作以整轮为最小淘汰粒度，后置断言保证上下文内绝不存在没有父调用的悬空 tool_call_id。

- 关键行解析：在第 24-57 行，我把单轮交互封装为自闭环状态，向标准消息反序列化时严格保持时序；在第 85-115 行，我实现了优先保障 System Prompt 的倒序滑窗算法，仅对历史轮次做淘汰，确保核心系统规则不随会话增长而丢失。

- 主动说边界与坑：这段代码演示的是滑动窗口算法。在需要长文本跨轮记忆（如 50 轮会话）的企业级项目中，必须主动向面试官展开：被淘汰出滑窗的旧轮次并不会被丢弃，而是异步送入一个轻量级后台任务，抽取为三元组键值（如 User.last_inquired_device = 1）存入长期记忆库，在后续轮次中通过类似于 RAG 的机制动态回填唤醒。

### 本节收尾：费曼自述与闪卡

费曼自述：
“跟模型聊天就像在小黑板上写字。黑板写满了要擦掉一些旧字，但你绝不能只擦掉一半：比如你问了一句话‘拿钥匙开门’，你不能把‘拿钥匙’擦了，却留着‘门开了’，这样后面的裁判一看就觉得你在变魔术（报错 400）。擦黑板必须一整件事（一整轮问答和工具交互）一起擦干净，而且黑板最顶上的班规（System Prompt）永远不准擦！”

- Q：为什么在包含 Tool Calling 的上下文中，不能用简单的列表切片（如 messages[-5:]）截断？
A：因为工具调用请求与工具执行结果属于时序成对关系；随机位置截断容易裁掉上游的 Assistant 调用而残留孤儿 Tool 消息，直接引发 API 协议报错 400。

- Q：什么是上下文工程中的“System Prompt 置顶锁死（Pinning）”？
A：在滑窗裁剪时，先将 System Prompt 的 Token 消耗作为硬性预留扣除，滑窗淘汰仅作用于中间的历史轮次，确保全局安全与格式约束永远生效。

- Q：为什么短期记忆摘要（Summarization）如果处理不当会导致模型越来越笨？
A：因为自由语言摘要存在信息衰减与二次抽象失真；必须将关键事实字段结构化存储，防止多次摘要形成的传话筒效应。
