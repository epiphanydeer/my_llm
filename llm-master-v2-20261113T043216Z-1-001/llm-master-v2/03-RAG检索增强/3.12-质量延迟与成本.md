## 1. 🎯 本节目标与大白话例子

本节目标：掌握大模型应用“质量 - 延迟 - 成本”不可能三角的工程权衡，拆解 TTFT（首字延迟） 与 TPOT（生成速度） 构成，用数学反例证明为何各阶段 P95 绝不能直接相加，并在 Step 11 基础上实现 analyze_perf_and_cost() 逐请求剖析器。

大白话例子： 评价 RAG 系统的 P95 延迟，就像给接力赛跑计时：第一棒负责检索，第二棒负责重排，第三棒负责大模型吐字。 你绝对不能把“第一棒史上最慢的成绩 + 第二棒史上最慢的成绩 + 第三棒史上最慢的成绩”加起来当成队伍的 P95 成绩——因为这三个人几乎不可能在同一场比赛里同时拉胯！正确做法是掐表记录每一场比赛整支队伍跑完的总时间，再从这堆总时间里挑出最慢的那 5%（P95）。

## 2. 🧠 核心原理与五维拆解

### 一、延迟拆解：TTFT vs TPOT（原文档脉络）

TTFT（Time To First Token，首字延迟）：用户按下回车到屏幕上蹦出第一个字的时间。 $$\text{TTFT} = T_{\text{网络}} + T_{\text{检索}} + T_{\text{重排}} + T_{\text{LLM Prefill}}$$ 配合流式输出（Streaming），只要 TTFT 控制在 500~800ms 内，用户就会觉得系统秒回。

TPOT（Time Per Output Token，单字生成耗时）：决定流式打字机的流畅度，受模型参数量、量化精度和 max_tokens 长度限制影响。

### 二、为什么各阶段的 P95 绝不能直接相加？

分位数（Quantile）不是线性算子： $$\text{P95}(A + B + C) \neq \text{P95}(A) + \text{P95}(B) + \text{P95}(C)$$ 必须逐请求先求端到端总耗时 $T_{\text{total}} = T_{\text{ret}} + T_{\text{rerank}} + T_{\text{prefill}} + T_{\text{decode}}$，再对总耗时分布整体求 Nearest-Rank 分位数。

### 四、知识点扩展：压测统计避坑与隐性基础设施成本

压测严禁剔除超时请求：如果 5% 的请求因超时（>10s）失败，剔除它们再算 P95 会得出虚假的低延迟。必须全样本统计，超时请求按阈值计入。

冷启动 Warmup 隔离：正式采集基准前先发 100~200 条预热请求把模型和 HNSW 索引加载进内存。

隐性基建成本：除了大模型 API Token 费，常驻重排 GPU 实例（T4/A10G）、向量库内存节点、文档 OCR 解析费用往往占总成本的 30%~50%。

## 3. 💻 渐进式代码实操（Step 12：端到端尾延迟与成本剖析器）

相比 Step 11 新增/修改了什么： 在评测与审计体系基础上，新增 RequestProfile 与 analyze_perf_and_cost() 性能成本分析器，用 Decimal 杜绝浮点账单误差，并用断言亲自演示“P95 相加得出 300ms vs 真实端到端 P95 为 130ms”的反证案例。

### 【从零手写核心链路】

```python
"""3.12 Step 12: 在 Step 11 基础上新增逐请求端到端尾延迟（P50/P95/P99）与 Token 成本分析器"""
from dataclasses import dataclass
from decimal import Decimal
import math
from statistics import mean


@dataclass(frozen=True)
class RequestProfile:
    req_id: str
    retrieval_ms: float
    rerank_ms: float
    prefill_ms: float
    decode_ms: float
    in_tokens: int
    out_tokens: int


def nearest_rank_quantile(values: list[float], p: float) -> float:
    if not values or not (0.0 < p <= 1.0):
        raise ValueError("参数非法")
    s = sorted(values)
    return float(s[math.ceil(p * len(s)) - 1])


def analyze_perf_and_cost(
    profiles: list[RequestProfile],
    in_price_per_m: Decimal = Decimal("2.0"),
    out_price_per_m: Decimal = Decimal("6.0"),
) -> dict[str, object]:
    """逐请求先求和再求 P95，数学反证为何不能把各阶段 P95 直接相加。"""
    totals = [p.retrieval_ms + p.rerank_ms + p.prefill_ms + p.decode_ms for p in profiles]
    ttfts = [p.retrieval_ms + p.rerank_ms + p.prefill_ms for p in profiles]
    total_cost = sum(
        (Decimal(p.in_tokens) * in_price_per_m + Decimal(p.out_tokens) * out_price_per_m) / Decimal("1000000")
        for p in profiles
    )
    p50, p95, p99 = (nearest_rank_quantile(totals, q) for q in (0.50, 0.95, 0.99))
    assert p50 <= p95 <= p99
    return {"p50_ms": p50, "p95_ms": p95, "p99_ms": p99, "avg_ttft_ms": mean(ttfts), "total_cost": total_cost}


if __name__ == "__main__":
    reqs = [
        RequestProfile("R1", 100.0, 10.0, 10.0, 10.0, 1000, 200),
        RequestProfile("R2", 10.0, 100.0, 10.0, 10.0, 1000, 200),
        RequestProfile("R3", 10.0, 10.0, 10.0, 100.0, 1000, 200),
    ]
    res = analyze_perf_and_cost(reqs)
    # 若把各阶段 P95 直接相加会得出 300ms，但真实端到端 P95 只有 130ms
    assert math.isclose(res["p95_ms"], 130.0)
    assert res["total_cost"] == Decimal("0.0096")
    print("Step 12 self-test passed!")
```

说明：生产中通常配合 Locust 压测脚本与 Prometheus histogram_quantile(0.95, ...) 监控总延迟直方图。

① 声明不变量：核心统计不变量是分位数单调性 p50 <= p95 <= p99 以及基于 Decimal 的财务级零误差账单核算。

② 关键行解析：第 31~38 行先按单请求累加出真实墙钟总耗时 totals，再求分位数；if __name__ == "__main__": 里的 3 条样本构造了一个绝妙的反证——三个请求分别在不同阶段慢 100ms，但每个总耗时都是 130ms，直接粉碎“阶段 P95 相加=300ms”的常见统计谬误。

③ 主动点出工程细节（加分项）：我会向面试官补充高并发下的排队延迟雪崩问题：平均延迟低但高并发 P99 飙升，往往是因为重排模型或 LLM 推理节点没开 Continuous Batching（如 vLLM）导致请求在 HTTP 队列里排队；必须在网关加反压限流。

## 6. ❓ 高频面试追问与参考答法 + 📝 节末费曼自检

### 高频面试追问

Q1：为什么不能把检索 P95、重排 P95 和大模型 P95 直接相加作为系统总 P95？

参考答法：因为分位数不具备线性可加性。同一个请求几乎不可能在每个串行阶段同时遇到全链路最差长尾。相加会严重高估真实延迟；必须逐请求记录端到端总耗时，再对总耗时列表统一求 P95。

Q2：用户抱怨 RAG 响应太慢，你如何拆解并优化端到端延迟？

参考答法：拆成 TTFT（首字延迟） 和 TPOT（生成速度） 治理。降 TTFT 靠：减小初筛候选数、Rerank 量化或加高置信旁路、裁剪 Prompt 冗余、开启 Prompt Cache；降 TPOT 靠：流式输出、限制 max_tokens 或换推理更快的轻量模型。

Q3：在算力预算有限的情况下，如何既保召回率又压低 RAG 运营成本？

参考答法：三板斧——① 向量库开 SQ8 标量量化，内存省 70% 几乎不掉召回；② 系统指令开 Prompt Cache，输入单价打折；③ 分级 Rerank，只有当 BM25 和向量两路分歧大时才触发重排。

Q4：压测 RAG 时有哪些容易踩的统计陷阱？

参考答法：最常见三个坑：一是只算成功请求，把超时报错的 5% 踢掉导致假低延迟；二是没做 Warmup 预热就把冷启动加载索引的时间算进去；三是把阶段 P95 机械相加。
