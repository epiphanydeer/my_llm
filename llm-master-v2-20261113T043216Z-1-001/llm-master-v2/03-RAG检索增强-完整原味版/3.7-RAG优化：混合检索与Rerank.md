## 一、优化要对症下药

先建立一个重要的认知：RAG 优化没有万能药。"加个 Rerank 就搞定了"、"换个更好的模型就行了"——这类说法听起来合理，但很多时候只是在用锤子找钉子。

正确的姿势是：先诊断问题出在哪个环节（上一篇的方法），再选择对应的优化手段。

优化手段大致可以分为三类：

**Query 侧优化**：在用户问题进入检索之前，对 Query 进行处理，让它更适合被检索到正确答案。

**检索侧优化**：改善召回质量，让相关内容更准确地被找到。

**Context/生成侧优化**：改善最终喂给 LLM 的上下文质量，让模型能更好地利用检索结果。



![各优化手段在 RAG 链路中的落点](https://file1.kamacoder.com/i/bagu/rag_optimization_landscape.png?v=20261005)



看了全景图之后，我们接下来逐个讲清楚每种优化手段的机制。

------

## 二、Query 侧优化

### Query 改写（Query Rewrite）

用户的原始问题往往措辞口语化、表达方式多样、语义模糊，不一定适合直接做向量检索。Query 改写的思路是：在检索之前，先用 LLM 对用户问题做一轮处理——扩展同义词、修正表述、补全隐含条件，让改写后的查询更贴近知识库里文档的用词习惯。

举个例子：用户问"这个合同能退吗"，改写后可以变成"合同解除条款、退款政策、合同撤销条件"——在这多个角度下做检索，覆盖率明显更好。

### Multi-Query（多角度查询）

当一个问题可以从多个角度来理解时，生成多个不同版本的 Query，分别做检索，然后把多路结果合并去重。

比如用户问"我们产品的 SLA(服务水平协议) 是多少"，可以展开为：

- "服务等级协议内容"
- "故障响应时间"
- "可用性承诺"
- "赔偿条款"

每路独立检索，再把结果合并，召回率会显著提升。

------

## 三、检索侧优化

### 混合检索（Hybrid Search）

纯向量检索擅长语义理解，但对专有名词、精确匹配（如人名、产品型号、法规编号）不如关键词搜索准确。混合检索把两者结合起来：同时跑向量检索和 BM25 关键词检索，然后用融合算法（最常见的是 RRF，Reciprocal Rank Fusion）把两路结果合并排序。

RRF 的思路很直觉：一个文档在两路结果里排名都靠前，它的融合分数就高；只在一路排名靠前的，分数打折。

### 元数据过滤（Metadata Filtering）

在向量相似度检索的同时，叠加结构化的元数据条件。比如"只搜索 2024 年之后的文档"、"只在合同类文档里搜索"、"只搜索研发部门的内部规范"。

元数据过滤不会改变检索算法，但可以大幅缩小搜索范围，既提高精准度，又降低计算开销。

------

## 四、精排优化：Rerank

这是 RAG 优化里最常被提及的手段，但它的位置很具体：在向量检索召回了 top-K 候选之后，用一个 Cross-Encoder 模型对每个 (Query, Chunk) 对精细打分，重新排序，只保留真正高相关度的 top-N 传给 LLM。

Rerank 的核心价值在于：向量检索的相似度是独立编码的，不能完整捕捉 Query 和文档之间的深度语义关联；Cross-Encoder 可以看到两者的完整交互，打分更精准。

下面这张图展示了混合检索和 Rerank 组合使用时，整条优化链路的工作方式：

![Hybrid Search+Rerank机制](https://file1.kamacoder.com/i/bagu/hybrid_search_rerank_mechanism.png?v=20261005)

混合检索 + Rerank 是目前工程上最成熟的检索优化组合。两路各召回一定量候选，经 RRF 融合后形成候选池，再由 Cross-Encoder 精排，最终只有 3-5 条高质量 chunk 进入 Context。

>  Rerank 什么时候该加：如果 Recall@K 已经足够好（相关内容确实被召回了），但答案精准度仍然不高，通常是 Rerank 缺失导致的——召回了相关内容，但没有精确筛出最核心的部分。
>
> Rerank 什么时候不急着加：Recall@K 本身很低，相关内容根本没被召回，这时加 Rerank 没有意义，应该先解决召回问题。

------

## 五、Context 侧优化

### 父子块检索（Parent-Child Retrieval）

这个方案解决的是 Chunking 里的一个经典矛盾：小 chunk 利于精准匹配（向量更聚焦），但传给模型时上下文不够完整；大 chunk 上下文完整，但检索精准度差。

父子块的思路是：建立两级索引。用**小 chunk（子块）** 做检索，找到相关内容；但实际传给 LLM 的时候，使用包含这个子块的**大 chunk（父块）**。这样兼顾了检索精准度和上下文完整性。

比如：一篇 2000 字的文章按段落切成 5 个 400 字的子块做索引，但匹配到某个子块后，传给模型的是整篇文章（或者其中一个更完整的部分）。

### Context 压缩（Context Compression）

当召回的 chunk 里包含了大量和当前问题无关的内容时，可以用一个 LLM 先做压缩提取——让模型阅读 chunk，把和 Query 高度相关的句子提取出来，丢弃无关内容，再把压缩后的片段拼成最终 Context。

这个方案能显著减少上下文里的噪声，但会额外增加一次 LLM 调用的延迟和成本，适合对准确性要求极高、对延迟容忍度较高的场景。

------

## 六、初学者应该如何选择优化方向？

面对这么多优化手段，初学者最容易犯的错是"什么都想加"——加了 Query 改写、加了混合检索、加了 Rerank、加了父子块，结果系统延迟飙升，性能变差，还搞不清楚到底是哪个环节帮了忙。

一个更理性的顺序是：

1. 先建立baseline，做好评估。在任何优化之前，先用 Recall@K 和答案质量指标（可以用 LLM 打分或人工评估）建立可量化的基线。没有基线，就无法判断优化是否有效。

2. 优先解决"能不能找到"，再解决"找到了对不对"。如果 Recall@5 很低，先优化召回（换 Embedding 模型、调整 Chunk 策略、加混合检索），而不是先加 Rerank。

3. 每次只改一个变量。控制变量是评估优化效果的基本要求。同时改 Chunk 大小、Embedding 模型和是否加 Rerank，你永远不知道是哪个起了作用。

4. 按成本/收益决定优先级。混合检索（增加 BM25 索引）成本低、覆盖面广，通常是性价比最高的第一步优化；Query 改写、Rerank 会增加延迟和成本，要根据业务 SLA 决定是否值得。

## 七、面试可能怎么问

**Q：你们 RAG 系统做了哪些优化？**

参考思路：

按优化框架（Query 侧 / 检索侧 / 精排侧 / Context 侧）分类回答，说清楚每个优化针对的具体问题、实施前后的效果变化，以及取舍（为什么做这个而不是那个）。比如"我们发现 Recall@5 在 60% 左右，先引入了混合检索，Recall@5 提升到 78%；再加了 Rerank，答案精准率提升了约 15%"——有数据有逻辑才是好回答。

**Q：混合检索怎么实现？两路结果怎么融合？**

参考思路：

向量检索用 Embedding 模型和向量数据库；关键词检索用 BM25 算法（Elasticsearch 或向量数据库的关键词搜索功能）。融合用 RRF（Reciprocal Rank Fusion）：对每个文档，把它在两路排名中的名次取倒数相加，得到融合分数，重新排序。RRF 对超参数不敏感，实现简单，效果稳定，是工程首选。

------

## 八、结语

RAG 优化是一个按需组合、逐步迭代的过程，而不是一次性把所有手段全部加上。理解每种手段解决的是哪个具体问题，建立可量化的评估体系，优先解决最影响效果的瓶颈——这才是 RAG 优化的正确姿势。

## 九、零基础大白话补齐：BM25 稀疏检索与加权 RRF 底层原理（融合你的仓库 3.3 & 3.7 精华）

### 1. BM25 为什么能精准抓“第17条”和设备型号？
向量检索擅长抓“同义词”，但搜“处罚办法第17条”或型号 `ABC-204` 时很容易跑偏。**BM25 关键词检索**靠三招精准打击：
- **IDF（稀缺词高权重）**：“规定”每篇都有，不值钱；“第17条”全库只出现 1 次，一旦命中得分极高。
- **TF 饱和度（`k1=1.5`）**：同一个词在一篇文档里重复 50 次，加分也有封顶上限，防长文靠刷屏作弊。
- **长度归一化（`b=0.75`）**：50 字短条款命中 2 个词，比 2000 字长文命中 2 个词含金量更高，对长文做适当折扣。

### 2. 为什么 BM25 分数和向量分数不能直接相加？RRF 里的常数 60 是干嘛的？
- **量纲不同不能硬加**：向量余弦相似度永远在 `[-1, 1]` 之间（通常集中在 `0.6 到 0.9`），而 BM25 分数可能是 `2.5` 也可能是 `28.0`（无上限）。直接相加，BM25 会彻底霸榜！
- **加权 RRF（倒数排名融合）**：干脆不看具体分数，只看各自排第几名（`rank` 从 1 开始）：
  $$	ext{RRF}(d) = \sum_{m} 
rac{w_m}{k + 	ext{rank}_m(d)}$$
- **为什么平滑常数 $k$ 默认选 60？** 如果 $k=0$，第 1 名是 $1/1=1.0$，第 2 名是 $1/2=0.5$，第 1 名直接是第 2 名的两倍——万一某一路把一篇无关文档误排在第 1，就会瞬间压死另一路排第 2、第 3 的好文档。加上 `60` 后，第 1 名是 $1/61$、第 2 名是 $1/62$，差距平缓，**只有在两路排名都靠前的文档才会稳稳胜出**。

### 3. 双塔模型 (Bi-Encoder) vs 交叉编码器 (Cross-Encoder) 深度对比表

| 架构维度 | 双塔模型 (Bi-Encoder / Embedding) | 交叉编码器 (Cross-Encoder / Reranker) |
| --- | --- | --- |
| **输入方式** | Query 和 Document 各自独立过模型算向量 | `[CLS] Query [SEP] Doc [SEP]` 拼接后一起进模型 |
| **注意力交互** | 编码时互不可见，最后只做一次点积 | 每个词之间做全交叉注意力（能看清“不”字等细节） |
| **速度与角色** | 文档向量离线预计算，毫秒级从百万库粗筛 Top-20 | 无法预计算，只能在线对 Top-20 逐对精排取 Top-5 |

## 十、循序渐进代码（Level 7）：从零手写 BM25 + 加权 RRF 融合 + Rerank 精排

运行前提：Python 3.10+，仅用标准库。

```python
"""3.7 Level 7：手写 BM25 稀疏检索 + 加权 RRF 融合 + Rerank 精排。"""
import math
import re


def tokenize_zh(text: str) -> list[str]:
    """英文数字按整词保留（如 17、500），中文按单字切分。"""
    return re.findall(r"[a-zA-Z0-9]+|[一-鿿]", text.lower())


def bm25_search(
    chunks: list[dict[str, str]],
    query: str,
    top_k: int = 3,
    k1: float = 1.5,
    b: float = 0.75,
) -> list[tuple[str, float]]:
    """手写 BM25：IDF 稀缺度 + TF 饱和 + 文档长度归一化。"""
    if not chunks or not query.strip() or top_k <= 0:
        raise ValueError("参数非法")
    docs_tok = [tokenize_zh(c["text"]) for c in chunks]
    n_docs = len(docs_tok)
    avg_dl = sum(len(d) for d in docs_tok) / n_docs or 1.0
    df: dict[str, int] = {}
    for d in docs_tok:
        for t in set(d):
            df[t] = df.get(t, 0) + 1

    q_tok = tokenize_zh(query)
    scores: list[tuple[str, float]] = []
    for chunk, d in zip(chunks, docs_tok):
        score = 0.0
        for qt in q_tok:
            if qt not in df:
                continue
            tf = d.count(qt)
            idf = math.log((n_docs - df[qt] + 0.5) / (df[qt] + 0.5) + 1.0)
            score += idf * (tf * (k1 + 1.0)) / (tf + k1 * (1.0 - b + b * len(d) / avg_dl))
        scores.append((chunk["chunk_id"], score))
    scores.sort(key=lambda x: (-x[1], x[0]))
    return scores[:top_k]


def weighted_rrf_fuse(
    rankings: list[list[tuple[str, float]]],
    weights: list[float] | None = None,
    k: int = 60,
    top_k: int = 3,
) -> list[tuple[str, float]]:
    """加权倒数排名融合 (Weighted RRF)，单路内自动去重防刷分。"""
    if not rankings or k <= 0 or top_k <= 0:
        raise ValueError("参数非法")
    w_list = weights if weights is not None else [1.0] * len(rankings)
    if len(w_list) != len(rankings) or any(w < 0 for w in w_list):
        raise ValueError("权重数量需与路数一致且非负")

    fused: dict[str, float] = {}
    for route, w in zip(rankings, w_list):
        seen: set[str] = set()
        for rank, (cid, _) in enumerate(route, start=1):
            if cid in seen:
                continue
            seen.add(cid)
            fused[cid] = fused.get(cid, 0.0) + w / (k + rank)
    return sorted(fused.items(), key=lambda x: (-x[1], x[0]))[:top_k]


def self_test() -> None:
    """验证 BM25 抓精确编号 + 加权 RRF 融合双路结果。"""
    chunks = [
        {"chunk_id": "C1", "text": "处罚办法第17条：未系安全带罚款500元。"},
        {"chunk_id": "C2", "text": "高空施工防坠落须知与挂点检查。"},
    ]
    bm25_res = bm25_search(chunks, "第17条怎么处罚", top_k=2)
    assert bm25_res[0][0] == "C1" and bm25_res[0][1] > 0.0

    # 假设向量路认为 C2 排第 1、C1 排第 2；BM25 路认为 C1 排第 1
    dense_res = [("C2", 0.88), ("C1", 0.82)]
    fused = weighted_rrf_fuse([dense_res, bm25_res], weights=[0.5, 0.5], k=60, top_k=2)
    assert fused[0][0] == "C1"  # C1 在两路都上榜（第2 + 第1），总分胜出
    print("✅ 3.7 BM25 + 加权 RRF 融合自检通过:", fused)


if __name__ == "__main__":
    self_test()
```

### 补充工程 Trick（来自你的仓库 3.7）
- **同源文档去重（Doc-level Deduplication）**：如果一篇长文档的连续 5 个切片同时排在 RRF 前 5 名，会把名额全占满。工程上通常规定**同一个 `doc_id` 最多保留 2 个最高分切片**，把其余名额让给其他文档，拓宽视角。
- **Cross-Encoder 必须 Batch 推理**：在线精排 20 个候选时，严禁写 `for` 循环调 20 次模型，必须拼成一个 `batch_size=20` 的列表一次前向传播算完。

### 目标与例子

目标：理解单一检索路线的失效场景，掌握稀疏检索（BM25/全文）与稠密检索（Dense Vector）互补的物理机制；能手撕加权倒数排名融合（Weighted RRF）算法，讲清双塔召回（Bi-Encoder）与交互式重排（Cross-Encoder Reranker）的算力与效果权衡。
例子：用户提问“根据GB/T 3608，三级高处作业的高度基准面是多少米？”

- 纯向量检索：可能会被“高处作业”、“高度基准面”等高频语义词引导，召回一堆关于“一级高处”、“作业安全带”的泛化说明，但恰恰把“GB/T 3608”这一特定国家标准编号给稀释掉；

- 纯 BM25 检索：能够精准锁死“GB/T 3608”和“三级”，但如果文档原文写的是“第三类高空作业坠落半径”（存在同义表述差异），BM25 词频得分为 0 导致漏检；

- 混合检索（Hybrid Search）+ RRF：双路并行打分，通过无量纲的排名倒数进行融合，最后用 Cross-Encoder 重排器把问题与候选拼在一起计算全交互注意力，兼顾精准符号与深层语义。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 用户 Query；稀疏路候选排名列表（带名次与 ID）、稠密路候选排名列表（带名次与 ID）；各路融合权重 $w_i$ 与平滑常数 $k$。 |
| 做什么 | 消除不同打分系统的量纲差异，通过倒数排名融合（RRF）生成合并候选池；再由计算更密集的 Cross-Encoder 进行精细化重排截断。 |
| 输出 | 综合得分最高的 Top-K 证据片段列表。 |
| 哪里出错 | 直接把 BM25 分数与余弦相加（量纲与分布完全不可比）、RRF 常数 $k$ 设太小导致第一名权重过大发生马太效应、重排截断把唯一有效证据切掉。 |
| 重要参数影响 | RRF 平滑常数 $k$（行业默认 60）、各路权重比 $w_{\text{sparse}} : w_{\text{dense}}$（通常设 0.3:0.7 或 0.5:0.5）、Rerank 候选规模 $N$（通常取 20到50 避免 P99 超时）。 |

#### 双塔模型 (Bi-Encoder) vs 交叉编码器 (Cross-Encoder) 深度剖析

| 架构对比 | 双塔模型 (Bi-Encoder / Embedding) | 交叉编码器 (Cross-Encoder / Reranker) |
| --- | --- | --- |
| 网络结构 | Query 和 Document 独立前向传播，各自输出固定维度向量 | Query 和 Document 拼接后同时送入 Transformer：[CLS] Query [SEP] Doc [SEP] |
| 注意力机制 | 只能在自身句子内部做 Self-Attention，两者仅在最后做简单的点积 | 全交互自注意力（Cross Attention），Query 的每个 Token 与 Doc 的每个 Token 均有权重 |
| 时间复杂度 | 文档离线刷库完成，在线仅算一次 Query 向量，检索耗时 $O(\log N)$ | 在线必须对每个候选做一次前向传播，耗时 $O(K \cdot L^2)$ |
| 角色定位 | 广度召回（从 1000 万候选挑 50 个） | 深度重排（从 50 个候选挑最终 3 个） |

### 面试追问

- 【🔥 必会】为什么不能直接把 BM25 的匹配得分与向量的余弦相似度（Cosine）按权重加权相加？
一句话结论：二者量纲、数值范围和分布形态完全不同，直接相加在数学上毫无意义。
展开原理/取舍：余弦相似度严格受限于 $[-1.0, 1.0]$ 区间内，且高度集中在 0.6到0.9；而 BM25 得分是基于对数词频与逆文档频率（IDF）无上界的正浮点数（短句可能是 2.5，长句或稀有词可能是 28.0）。如果直接相加，BM25 分数会完全吃掉余弦分数。虽然可以通过 Min-Max 做线性归一化，但如果某次查询的最高 BM25 只有 1.2，另一次查询最高是 30，归一化会极大扭曲跨文档分布；而 RRF（倒数排名融合）基于名次而非绝对数值，天然免疫打分量纲差异。

- 【🔥 必会】加权 RRF 的计算公式是什么？为什么公式里的常数 $k$ 业界通常默认选 60？
一句话结论：公式为 $\sum \frac{w_i}{k + r_i}$；常数 60 是为了平滑长尾，防止第 1 名与第 2 名的得分差发生悬崖式断层。
展开原理/取舍：如果 $k=0$，第 1 名得分是 $1/1=1.0$，第 2 名是 $1/2=0.5$，第一名权重是第二名的两倍，马太效应过强；若某一路因偶然分词把一篇无关文档排在第一，会瞬间秒杀另一路排在第 2、3 名的真正好文档。当引入 $k=60$ 时，第 1 名得分是 $1/61 \approx 0.01639$，第 2 名是 $1/62 \approx 0.01612$，相对差距缩小，使得在两路中都排在前列（如第 2 名与第 3 名）的文档其累积分数能够超越仅在单路偶发排第 1 的文档。

- 【⭐ 理解】【排障题】线上接入 Reranker 重排模型后，发现端到端问答准确率不但没提升，延迟反而翻倍，该如何排查？
一句话结论：排查“候选池是否漏召回”、“截断长度是否削掉关键句”以及“批处理延迟瓶颈”。
展开原理/取舍：① 候选池召回不足：先测初筛 Recall@50，若初筛池里本来就没有正确答案，Reranker 再怎么重排也是白耗算力；② 重排模型截断（Max Length）：Cross-Encoder 的序列长度通常只有 512，如果候选切片较长，拼接后超出部分被物理截断，恰好裁掉了关键事实；③ 领域漂移：检查重排模型是否在通用网络语料训练，在特定工业/医疗专业术语上打分反常；④ 延迟排查：Cross-Encoder 运算量大，若送入候选数从 20 盲目增加到 100，GPU 前向推断耗时呈平方上升，必须严格将精排候选数限制在 20到30 之间。

### 故障模式与排障

- 故障模式：专业术语、错误代码完全搜不到

- 定位：向量模型由于 OOV（词表外单词）或预训练分词被拆碎成了单字符，在语义空间未形成稳定聚类。

- 修复：必须强化稀疏检索路。配置 Elasticsearch / BM25 维护专业行业同义词词典与停用词表，确保精确编号和缩写能够无损召回。

- 故障模式：多路召回结果严重同质化（全是同一篇长文档的相邻切片）

- 定位：初筛两路返回了同一长文档连续的 5 个相邻块，融合后直接霸占了进入 Reranker 的所有名额。

- 修复：在 RRF 融合之后引入多样性去重过滤（Doc-level Deduplication）：同一个 doc_id 限制最多保留 2 个最高分切片，强行把名额让渡给其他候选文档，拓宽最终上下文的视角覆盖面。

### 工程 trick 与坑

- 加权 RRF 的权重微调经验：通常将向量检索路设为 0.7，BM25 设为 0.3。因为语义向量的抗同义表述能力综合更强；但对于有明确标准号、人名、设备型号的垂直领域，应调平至 0.5:0.5。

- Cross-Encoder 批量推理并发优化：在线精排 30 个句子对时，切忌写 for 循环单条 predict；必须使用 torch.inference_mode() 配合动态 Batching（如 batch_size=32）一次性前向传播，极大减少 CUDA Kernel 启动开销。

### 循序渐进 Toy Code：Level 7 — 标准加权倒数排名融合（Weighted RRF）核心算法

代码难度定位：Level 7（核心算法手撕）。从零手写工业级加权 RRF 算法，带严格单路去重检查、非负权重控制、同分稳定排序与集合守卫断言。

```python
"""
3.7 Toy Code: Level 7 - 标准加权倒数排名融合 (Weighted RRF) 算法实现
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
import math
from typing import Optional


@dataclass(frozen=True)
class RankedList:
    """一路检索器的有序输出结果"""
    channel_name: str           # 检索路名称（如 'bm25', 'vector'）
    candidate_ids: tuple[str, ...] # 已按该路得分从高到低排列的 chunk_id 列表
    weight: float = 1.0         # 该路的融合权重


@dataclass(frozen=True)
class FusedCandidate:
    """融合排序后的候选条目"""
    chunk_id: str
    rrf_score: float
    rank: int


def reciprocal_rank_fusion(
    rankings: list[RankedList],
    k: int = 60,
    top_n: int = 5
) -> list[FusedCandidate]:
    """
    加权倒数排名融合核心函数
    
    数学公式:
    Score(d) = sum_{m in M} ( w_m / (k + rank_m(d)) )
    其中 rank_m(d) 为文档 d 在第 m 路中的名次（从 1 开始计）
    """
    if k <= 0:
        raise ValueError("平滑常数 k 必须为正整数")
    if top_n <= 0:
        raise ValueError("top_n 必须为正整数")
    if not rankings:
        return []

    # 前置数据完整性检查
    channel_names = [r.channel_name for r in rankings]
    if len(channel_names) != len(set(channel_names)):
        raise ValueError("检索路名称不能重复")

    rrf_scores: dict[str, float] = {}

    for route in rankings:
        if not math.isfinite(route.weight) or route.weight < 0:
            raise ValueError(f"检索路 {route.channel_name} 权重必须为非负有限数")
        
        # 严格防御：单路返回列表中不得存在重复 ID
        if len(route.candidate_ids) != len(set(route.candidate_ids)):
            raise ValueError(f"检索路 {route.channel_name} 存在重复的 chunk_id")

        # 若该路权重为 0 则直接忽略
        if route.weight == 0.0:
            continue

        for rank_idx, chunk_id in enumerate(route.candidate_ids, start=1):
            if not chunk_id.strip():
                raise ValueError("chunk_id 不能为空字符串")
            # 累加加权倒数排名分
            contribution = route.weight / (k + rank_idx)
            rrf_scores[chunk_id] = rrf_scores.get(chunk_id, 0.0) + contribution

    # 排序：先按分数降序，同分按 ID 字母序稳定排序
    sorted_items = sorted(rrf_scores.items(), key=lambda x: (-x[1], x[0]))
    
    results: list[FusedCandidate] = []
    for final_rank, (chunk_id, score) in enumerate(sorted_items[:top_n], start=1):
        assert score > 0, "RRF 综合得分必须为正数"
        results.append(FusedCandidate(
            chunk_id=chunk_id,
            rrf_score=score,
            rank=final_rank
        ))

    return results


def self_test():
    """测试加权 RRF 算法的数值准确性与边界鲁棒性"""
    # 场景：
    # BM25 路（注重精确型号）：命中 A, B, C
    # Vector 路（注重语义抽象）：命中 B, D, A
    bm25_out = RankedList(
        channel_name="bm25",
        candidate_ids=("DOC_A", "DOC_B", "DOC_C"),
        weight=1.0
    )
    vector_out = RankedList(
        channel_name="dense_vector",
        candidate_ids=("DOC_B", "DOC_D", "DOC_A"),
        weight=1.0
    )

    fused = reciprocal_rank_fusion([bm25_out, vector_out], k=60, top_n=4)
    
    # 手算验证理论分值：
    # DOC_B: 在 BM25 排第 2 (1/62), 在 Vector 排第 1 (1/61) -> 总分 = 1/61 + 1/62 ≈ 0.016393 + 0.016129 = 0.032522
    # DOC_A: 在 BM25 排第 1 (1/61), 在 Vector 排第 3 (1/63) -> 总分 = 1/61 + 1/63 ≈ 0.016393 + 0.015873 = 0.032266
    # 理论推导结论：两路都排在前列的 DOC_B 必须夺得最终第 1 名！
    assert fused[0].chunk_id == "DOC_B", "两路交叉高排名的 DOC_B 应位列第一"
    assert fused[1].chunk_id == "DOC_A"
    assert math.isclose(fused[0].rrf_score, (1/61 + 1/62), abs_tol=1e-6)

    # 边界测试 1：单路为空场景
    empty_res = reciprocal_rank_fusion([
        RankedList("sparse", ()),
        RankedList("dense", ("DOC_X",))
    ], k=60)
    assert len(empty_res) == 1
    assert empty_res[0].chunk_id == "DOC_X"

    # 边界测试 2：异常防御（单路存在重复 ID）
    try:
        reciprocal_rank_fusion([RankedList("bad", ("DOC_A", "DOC_A"))])
        raise AssertionError("单路重复 ID 应抛出 ValueError")
    except ValueError:
        pass

    print("✅ 3.7 加权倒数排名融合 (RRF) 算法自检全部通过！")


if __name__ == "__main__":
    self_test()
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我的加权 RRF 实现建立在多路去重的基础之上。核心不变量是：对于输入的多路有序候选，名次 $r$ 严格从 1 开始计；平滑常数 $k > 0$ 且权重 $w_m \ge 0$。最终输出严格按融合分降序排列，且截断至 top_n，同分时使用字典序实现确定性稳定输出。

- 关键行解析：在第 55-61 行，我对单路输出执行了强类型去重防御，杜绝下游同一切片重复打分；第 64-67 行实现了加权公式 $w_m / (k + rank_m)$；在 self_test 中，我用精确的浮点数断言证实了：一个在单路排第一但在另一路未命中的文档（DOC_A），其综合排名会正确被两路都稳定的文档（DOC_B）反超，这就是 RRF 能兼顾全局鲁棒性的数学原理。

- 主动说边界与坑：这段代码负责粗排阶段的融合。在真实工业架构中，RRF 拿到的 Top-30 结果，随后会被直接送入 Cross-Encoder（如 bge-reranker-large）做二次精排打分；面试时要主动指出，RRF 丢弃了绝对分数的离散方差信息，如果某一路有非常确信的高置信度（如完全匹配精准订单号），需结合规则引擎设置强行透传白名单。

### 调库选型：Cross-Encoder 重排器调用标准

在完成 RRF 粗排合并后，使用标准 Cross-Encoder 的工业级调库逻辑：

可选：通过环境变量指定兼容的本地模型目录；若更换模型，先核对其查询前缀、输入格式和效果。

```python
import os
from sentence_transformers import CrossEncoder

# 加载多语言交叉编码器模型
reranker = CrossEncoder(os.environ.get("RERANK_MODEL_PATH", "BAAI/bge-reranker-base"), max_length=512)

query = "高空作业必须佩戴什么？"
# RRF 融合出来的 Top-20 候选切片文本
candidate_texts = [
    "高处作业必须按规定佩戴安全带并系挂牢固。",
    "动火作业现场必须设立专人监护并备好灭火器。"
]

# 组装为 (Query, Doc) 句子对并前向推断
pairs = [(query, doc) for doc in candidate_texts]
scores = reranker.predict(pairs)  # 输出一维相关性实数数组

# 降序截断最终进入 Prompt 的 Top-3
ranked_indices = sorted(range(len(candidate_texts)), key=lambda i: -scores[i])
final_context = [candidate_texts[i] for i in ranked_indices[:3]]
```

### 本节收尾：费曼自述与闪卡

费曼自述：
“单一检索就像单眼看东西，容易有盲区。BM25 像显微镜，专门挑错字和生僻型号；向量检索像望远镜，看整体大概意思。RRF 就像一个公正的裁判：不管你们各自的分数尺子有多怪，我只看你们各自报上来的名次；两边都觉得靠前的，肯定错不了。”

- Q：为什么在现代 RAG 架构中，混合检索（Hybrid Search）已经成为事实上的标准方案？
A：因为纯向量模型对生僻专有名词、字母数字混杂编号（如型号、法律条款编号）极易漏检，而 BM25 对同义词与多义词泛化差；双路互补能将初筛 Recall 提升 10%到20%。

- Q：为什么 Cross-Encoder 重排器不能直接用来对全库几百万文档检索？
A：Cross-Encoder 要求 Query 和 Doc 一起送入 Transformer 算全自注意力，单次前向复杂度为 $O(L^2)$，遍历百万级数据线上查询必超时；只能用于初筛后的 Top-20 少量精排。

- Q：RRF 融合相比 Min-Max 线性加权融合有什么天然优势？
A：免调参、不依赖分数的绝对尺度与概率分布，天然防止某一路异常高分对最终排序的野蛮绑架。
