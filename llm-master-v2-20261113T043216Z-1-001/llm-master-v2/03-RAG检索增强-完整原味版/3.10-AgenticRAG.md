# Agentic RAG：RAG为什么一步一步长出了Agent能力？

前面我们已经讲过[为什么大模型需要 RAG](../app/why_rag.md)，也拆过[传统 RAG 的完整链路](../app/chain_of_rag.md)：用户提问，系统检索文档，拼进上下文，再让模型生成答案。

这套流程处理“退款政策是什么”没什么问题。

但问题一复杂，比如：

> 对比新旧两版退款政策，找出华东区的例外条款，再说明这些变化会影响哪些历史订单。

一次检索就开始吃力了。

它要查多个问题、多个版本、多个数据源，还要判断证据够不够。第一次没找到，不能硬着头皮往下答，得换个问法继续找。

**传统 RAG 把检索写死在流程里，Agentic RAG 则把检索变成 Agent 可以按需使用、反复使用的工具。**

![RAG到Agentic RAG演进](https://file1.kamacoder.com/i/web/20260819110919.jpg?v=20261005)

先把定义说清楚：**Agentic RAG 不是某一个固定算法，也不是某个框架的专属功能，而是一类架构模式。**

在这类系统里，大模型不只负责最后写答案，还参与决定：要不要检索、问题怎么拆、查哪个数据源、检索结果是否可用、要不要换个 Query 再查，以及什么时候可以停止。

## 一、先别急着上 Agent，看看 RAG 是怎么走到这一步的

这段演进不是官方规定的版本号，而是一条很典型的工程演进逻辑。

每往前走一步，都是因为上一步解决不了新的问题。

### 第一阶段：传统 RAG，把外部知识拿给模型看

2020 年的 RAG 论文把模型参数里的“参数化知识”和外部索引里的“非参数化知识”结合起来。

到了工程里，大家通常把它实现成一条固定在线链路：

**Query → 检索 Top-K → 拼接 Context → LLM 生成。**

它解决了大模型不知道私有数据、知识更新慢、答案无法溯源的问题。

但这条链路有一个隐含假设：**用户的一句话已经足够适合检索，而且第一次返回的 Top-K 就包含答案。**

现实里，这个假设经常不成立。

### 第二阶段：Advanced RAG，把每一环做得更精细

于是系统开始增加 Query 改写、Multi-Query、混合检索、Rerank、父子块检索、Context 压缩。

这些方法在[RAG 优化文章](../app/rag_optimization.md)里已经详细讲过。它们非常有用：检索召回更高了，送给模型的上下文也更干净了。

但要看清它的边界：**流水线变强了，流水线本身仍然是固定的。**

开发者提前规定每个请求都改写三次、查两个索引、做一次 Rerank。即使一个简单问题根本不需要检索，它也照跑；即使复杂问题一次没查全，它通常也不会自己增加下一轮。

### 第三阶段：自适应与纠错，让系统开始“看结果再决定”

接下来出现了一批很关键的思路：

- Self-RAG：按需检索，并对检索内容和生成结果进行反思
- CRAG：先评估检索结果，结果不可靠时触发纠正动作
- Adaptive-RAG：根据问题复杂度，在不检索、单步检索和多步检索之间选择

它们的实现并不相同，也不能全部简单等同于 Agentic RAG。

但它们推动了同一个变化：**检索不再是必走一次的固定步骤，而是一个可以判断、评估和纠错的过程。**

### 第四阶段：Agentic RAG，把检索交给目标驱动的 Agent

有了 Function Calling、ReAct 和 Agent 运行时之后，检索可以被包装成工具。

Agent 接到的不再只是一个待搜索的 Query，而是一个需要完成的目标。它可以先规划，再调用向量库、关键词搜索、数据库、网页搜索等工具，根据中间结果继续调整。

这就是 RAG 从“固定流水线”走到“动态检索循环”的关键一步。

| 阶段 | 谁决定检索路径 | 检索次数 | 结果不好怎么办 |
|---|---|---:|---|
| 传统 RAG | 开发者写死 | 通常 1 次 | 带着错误结果继续生成 |
| Advanced RAG | 开发者写死更多优化 | 固定若干次 | 依赖预设的改写、重排策略 |
| 自适应/纠错 RAG | 分类器或模型参与判断 | 0 到多次 | 评估、改写或补充检索 |
| Agentic RAG | Agent 根据目标和状态决定 | 动态 | 换 Query、换工具、补证据或拒答 |

## 二、Agentic RAG 到底要解决什么问题？

很多人会说：“我已经加了混合检索和 Rerank，为什么还需要 Agentic RAG？”

因为它们解决的不是同一层问题。

混合检索和 Rerank 解决的是：**这一次怎么查得更准。**

Agentic RAG 解决的是：**这次该不该查、该查几次、查什么、结果不够时下一步怎么办。**

![传统RAG固定检索困境](https://file1.kamacoder.com/i/web/20260819110922.jpg?v=20261005)

### 1. 一个 Query 装不下复杂问题

“对比两个版本并找出地区例外”至少包含版本检索、差异比较和地区过滤三个子问题。

把整句话直接向量化，可能每个方向都沾一点，但哪个都查不准。Agent 可以先拆成子问题，分别找证据，再合并。

### 2. 第一次检索错了，固定流程不会自救

传统 RAG 一旦召回了不相关文档，后面的 Rerank、Prompt 和大模型都只能在错误候选集里挣扎。

Agentic RAG 会先评估证据。相关性低、来源冲突或关键字段缺失，就重写 Query、扩大范围、换数据源，或者明确告诉用户证据不足。

### 3. 不同问题需要不同数据源

政策解释适合查文档库，历史订单要查数据库，刚发生的变化可能要查网页或业务 API。

单一向量库不是企业全部知识。Agent 的价值之一，就是在多个受控工具之间做路由。

### 4. 不是所有问题都值得检索

用户说“把上一段改得更口语化”，根本不需要查知识库。

如果系统每次都跑 Query 改写、向量检索和 Rerank，只会增加延迟、Token 和费用。Agent 可以判断直接回答，或者走一条更轻的路径。

### 5. 多跳问题需要带着新线索继续查

第一轮找到“新政策从 7 月生效”，第二轮才知道应该查“7 月之后的订单”，第三轮再核对“华东区例外”。

后一次检索依赖前一次结果，这种多跳问题很难靠一条预先写死的 Query 完成。

## 三、Agentic RAG 的核心原理

它的底层并不神秘，就是把[Agent 的规划、工具、执行和反馈](../app/agent_intro.md)放进 RAG 在线链路。

一个实用的 Agentic RAG，通常有五个角色：

1. **规划与路由**：判断任务复杂度，决定直接回答、单次检索还是拆成多步。
2. **检索工具**：向量检索、BM25、数据库、网页搜索和业务 API，各自暴露清晰能力。
3. **状态记录**：保存子问题、已查来源、候选证据、冲突点、剩余预算。
4. **证据评估**：检查相关性、完整性、来源可靠性和相互一致性。
5. **停止与生成**：证据足够就组织带引用的回答；证据不足且预算耗尽就拒答或请用户补充信息。

![Agentic RAG检索验证](https://file1.kamacoder.com/i/web/20260819110924.jpg?v=20261005)

它的运行过程，可以压缩成这个循环：

```text
理解目标
  ↓
决定：直接回答，还是调用检索工具？
  ↓
拆分子问题 → 选择数据源 → 执行检索
  ↓
评估证据：相关吗？完整吗？互相冲突吗？
  ↓
不够：改写 Query / 换工具 / 继续检索
足够：整合证据 / 标注来源 / 生成答案
```

这就是 ReAct 在检索场景里的落地：模型基于当前状态决定行动，工具返回观察结果，模型再决定下一步。

注意，**“反思”不能只靠模型拍脑袋说证据够了。**

生产系统通常还要加确定性规则：至少需要几类证据、是否命中指定版本、引用能否回到原文、数值是否来自结构化数据、最大允许几轮、总耗时和费用上限是多少。

Agent 负责动态决策，规则负责兜底。两者缺一不可。

## 四、用一个例子走完完整过程

假设用户问：

> 对比 2025 和 2026 两版差旅报销政策，并说明上海分公司的特殊规定。

传统 RAG 往往把整句话检索一次，拿回几段最相似的内容就开始回答。如果召回的全是 2026 版，总结写得再流畅，也没有完成“对比”。

Agentic RAG 会这样处理：

1. 识别出三个证据槽位：2025 总部政策、2026 总部政策、上海分公司补充规定。
2. 为三个槽位分别生成 Query，可以并行检索，减少串行等待。
3. 检查版本号、生效日期、适用组织和来源权限，而不只看向量相似度。
4. 如果缺少 2025 版，就去历史归档库继续查；如果两个来源冲突，就优先核对正式发布记录。
5. 三类证据齐全后再做差异比较，并让每条结论带回原始来源。

你会发现，真正的变化不是“多查了几次”，而是**系统知道自己为什么查、还缺什么、什么时候算查完。**

## 五、Agentic RAG 不等于多 Agent

这是一个很容易被带偏的地方。

一个 Agent 配几个检索工具，加上明确的状态机和证据检查，已经是 Agentic RAG。

只有当任务确实存在稳定的职责边界，比如法规检索、财务数据查询和证据审计需要不同权限或不同模型时，才值得拆成多个 Agent。

否则，多 Agent 会带来更多通信、上下文复制、错误传播和调试成本。

**先把单 Agent 的检索循环跑稳，再考虑多 Agent。**

## 六、它比传统 RAG 强，但也更难上线

Agentic RAG 不是免费午餐。

| 维度 | 传统 RAG | Agentic RAG |
|---|---|---|
| 路径 | 固定，容易预测 | 动态，每次可能不同 |
| 延迟 | 低且稳定 | 多轮工具调用，波动更大 |
| 成本 | 容易估算 | 与规划轮数、检索次数相关 |
| 调试 | 看固定链路 | 要看完整决策轨迹和工具结果 |
| 权限 | 一个检索入口较简单 | 多数据源需要逐工具鉴权 |
| 上限 | 适合简单、单跳问答 | 适合复杂、多跳、多源任务 |

落地时至少要守住六条：

- **限制循环**：设置最大步骤、超时、Token 和工具调用预算，防止越查越远。
- **工具要窄**：每个工具用途清晰，参数 Schema 和返回值稳定，别做一个“万能搜索”。
- **权限前置**：检索必须继承用户权限，不能让 Agent 绕过原系统访问敏感数据。
- **证据可回放**：记录每次 Query、命中文档、评分、选择理由和最终引用。
- **失败能降级**：Agent 超时或判断不稳时，可以退回固定 RAG、澄清问题或拒答。
- **分层评估**：既评估检索是否找全，也评估答案是否忠于证据；还要统计平均步骤、P95 延迟和单次费用。

工具怎么设计，可以继续看[Agent 工具设计](../app/agent_tool_design.md)；指标怎么拆，可以参考[RAG 评估](../app/rag_evaluation.md)和[Agent 评估](../app/agent_evaluation.md)。

## 七、什么场景值得用 Agentic RAG？

适合它的场景通常有这些特征：

- 问题需要多跳推理，后一步依赖前一步找到的新线索
- 一个请求包含多个子问题，需要拆解后分别检索
- 知识分散在文档库、数据库、网页和业务 API 中
- 对证据完整性、来源引用和冲突处理要求高
- 用户问题模糊，需要先澄清意图或动态调整检索方向

下面这些场景，固定 RAG 往往更划算：

- FAQ、产品手册等简单单跳问答
- 数据源单一，Query 模式稳定，检索命中率已经很高
- 对首字延迟要求严格，无法承受多轮模型和工具调用
- 流程有明确规则，用 Workflow 就能可靠完成

合理的升级顺序应该是：**先把传统 RAG 的文档、切片、检索和评估做好，再增加路由与纠错，最后才开放更动态的 Agent 循环。**

如果基础召回都做不好，套一层 Agent 只会让系统用更贵、更慢的方式找不到答案。

## 八、面试里怎么解释 Agentic RAG？

面试官如果问“Agentic RAG 和传统 RAG 有什么区别”，可以这样回答：

> 传统 RAG 的检索路径通常由开发者预先写死，用户问题经过一次或固定次数检索后直接生成。Agentic RAG 把检索封装成 Agent 工具，由模型根据任务状态决定是否检索、如何拆分 Query、选择哪个数据源，并对中间证据做评估；证据不足时可以改写或继续检索，足够时才停止并生成带引用的答案。它更适合复杂、多跳和多数据源问题，但会增加延迟、成本、可观测性和权限治理难度。

这段回答里，定义、原理、场景和代价都有了，比只说“Agentic RAG 更智能”有用得多。

**Agentic RAG 真正增加的不是一层 Agent 外壳，而是检索过程中的决策权、反馈和停止条件。**

## 九、零基础大白话补齐：CRAG 与防死循环三道锁（融合你的仓库 3.10 精华）

### 1. 什么是 CRAG（Corrective RAG，纠错式 RAG）？
大白话就是**在检索完、送给大模型生成之前，先安排一个“质检员”给捞回来的资料打个分**：
- **判为 Correct（资料很准）**：直接送去生成答案；
- **判为 Incorrect（捞回来的全是垃圾）**：直接扔掉，改调外部网页搜索或老实拒答，绝不把垃圾喂给生成模型；
- **判为 Ambiguous（半对半错）**：把内部资料和补充搜索拼在一起再答。

### 2. 怎么防止 Agentic RAG 陷入死循环把公司账户刷爆？
必须同时上**三道保险锁**：
1. **最大步数硬上限（`max_steps = 3`）**：最多只准查 3 轮，到点强制交卷或转人工。
2. **改写历史去重（Cycle Detection）**：如果模型第 2 轮改写出来的搜索词跟第 1 轮一模一样（原地打转），立刻刹车退出。
3. **原始问题锚定（防上下文漂移 Context Drift）**：每次改写时必须把用户最开始的原始问题贴在 Prompt 里对照，防止查着查着跑题到十万八千里外。

## 十、循序渐进代码（Level 10）：带去重探测与步数硬熔断的 Agentic RAG 循环

运行前提：Python 3.10+，仅用标准库。

```python
"""3.10 Level 10：最小 Agentic RAG 自适应检索控制器（含重复改写探测与硬步数熔断）。"""
from typing import Callable


def run_agentic_rag(
    original_query: str,
    retrieve_fn: Callable[[str], list[str]],
    rewrite_fn: Callable[[str, str, list[str]], str],
    is_sufficient_fn: Callable[[str, list[str]], bool],
    max_steps: int = 3,
) -> dict[str, object]:
    """循环检索与证据评估；遇证据充足、重复改写或达到 max_steps 时安全终止。"""
    if not original_query.strip() or max_steps <= 0:
        raise ValueError("original_query 非空且 max_steps > 0")

    current_query = original_query.strip()
    seen_queries = {current_query.lower()}
    collected_evidence: list[str] = []

    for step in range(1, max_steps + 1):
        new_docs = retrieve_fn(current_query)
        for doc in new_docs:
            if doc not in collected_evidence:
                collected_evidence.append(doc)

        if is_sufficient_fn(original_query, collected_evidence):
            return {"status": "ok", "steps": step, "evidence": collected_evidence}

        if step == max_steps:
            return {"status": "max_steps_fused", "steps": step, "evidence": collected_evidence}

        # 改写时同时传入 original_query，防止多跳改写跑题（Context Drift）
        next_query = rewrite_fn(original_query, current_query, collected_evidence).strip()
        if not next_query or next_query.lower() in seen_queries:
            return {"status": "cycle_detected", "steps": step, "evidence": collected_evidence}

        seen_queries.add(next_query.lower())
        current_query = next_query

    return {"status": "insufficient", "steps": max_steps, "evidence": collected_evidence}


def self_test() -> None:
    """验证两跳补齐证据、重复改写拦截与最大步数熔断。"""
    ok = run_agentic_rag(
        "对比新旧安全带罚款",
        retrieve_fn=lambda q: ["2025版罚200"] if "2025" in q else ["2026版罚500"],
        rewrite_fn=lambda orig, curr, ev: "2025 安全带 罚款",
        is_sufficient_fn=lambda orig, ev: len(ev) >= 2,
        max_steps=3,
    )
    assert ok["status"] == "ok" and ok["steps"] == 2

    cycle = run_agentic_rag(
        "查无此题",
        retrieve_fn=lambda q: [],
        rewrite_fn=lambda orig, curr, ev: curr,  # 故意原地重复
        is_sufficient_fn=lambda orig, ev: False,
        max_steps=3,
    )
    assert cycle["status"] == "cycle_detected" and cycle["steps"] == 1
    print("✅ 3.10 Agentic RAG 状态机与熔断器自检通过")


if __name__ == "__main__":
```

### 目标与例子

目标：掌握从传统线性 RAG 向自适应智能体检索（Agentic RAG）演进的技术动力，理解路由分发（Routing）、自校正检索（Corrective RAG / CRAG）与多跳推理（Multi-hop Reasoning）的设计范式，能手写带硬熔断预算守卫的自适应动态检索控制器。
例子：用户提问“对比 2026 年新版规程中，登高作业与密闭空间作业在监护人资质上的核心差异。”

- 传统线性 RAG：一次性拿着这句话去向量库检索 Top-3，结果大概率只召回了关于“登高作业”的碎片，密闭空间的信息全被淹没，模型只能半蒙半猜；

- Agentic RAG 控制流：Agent 首先识别出这是一个复合比较型问题，自主将其拆解为两个子问题（Sub-queries）：①“2026登高作业监护人资质要求”；②“2026密闭空间作业监护人资质要求”；分别调用检索工具拿齐两份证据，评估发现证据充足后，再统一汇总生成对比表格；若某一路检索结果为空，则自主触发 Query 改写再次重试。

### 概念与五要素

| 核心要素 | 说明 |
| --- | --- |
| 输入 | 用户复杂 Query、可用异构数据源工具集（Tool Schemas）、全局 Token/步数硬预算。 |
| 做什么 | 将静态单向的 Retrieve -> Generate 改造为带条件跳转的状态机：评估证据充足度 → 动态改写/下钻 → 循环终止决策。 |
| 输出 | 多轮聚合事实证据与结构化答案，以及全生命周期执行轨迹（Action Trace）。 |
| 哪里出错 | 改写震荡引发死循环（Infinite Loop）、延迟和 Token 费用随重试次数呈几何级膨胀、多跳过程上下文漂移。 |
| 重要参数影响 | 最大迭代步数 max_steps（生产绝对硬顶，通常设为 2到3 次）、全局超时（Timeout）、查询历史去重缓存。 |

#### RAG 三代演进路线架构全景

```text
[初代 Naive RAG]
  用户问题 ───────► 向量初筛 ───────► 拼入 Prompt ───────► 模型回答 (单向无反馈)

[二代 Advanced RAG]
  用户问题 ─► Query改写 ─► 混合检索(BM25+向量) ─► RRF融合 ─► Cross-Encoder重排 ─► 生成

[三代 Agentic RAG] (状态感知与闭环自愈)
  ┌─────────────────────── 状态控制器 (State Machine) ◄─────────────────────┐
  │                                                                         │
  ▼                                                                         │
用户意图分析 ──► 动态数据源路由 ──► 工具检索 ──► 证据充分性反思 (Self-Reflection)
                                                        │
                      ┌─────────────────────────────────┴─────────────────┐
                      ▼ 充足                                              ▼ 缺失/矛盾
                  综合生成回答                                       改写 Query 并重新检索
                                                                    (受 Max Steps 熔断守卫)
```

### 面试追问

- 【🔥 必会】什么时候根本不需要 Agentic RAG？盲目上 Agent 会带来哪些工程灾难？
一句话结论：单文档、意图简单、固定问答库绝不上 Agent；否则会导致延迟失控、费用飙升与系统不可控。
展开原理/取舍：如果业务 90% 的问题都是“什么是安全带”、“请假流程怎么走”，二代 Advanced RAG（混合检索+重排）在 200ms 内就能交出极高质量答案；若盲目引入 Agent 动态决策：① 延迟暴增：每多一轮意图反思和 Query 改写，端到端延迟增加 1.5到3 秒；② 费用翻倍：多轮 ReAct 工具调用消耗数倍 Token；③ 确定性降低：Agent 存在自主偏航与重复调用的失控风险。

- 【🔥 必会】【排障题】生产环境的 Agentic RAG 出现了死循环调用（卡在一直检索但就是不生成），该如何做工程熔断？
一句话结论：必须建立“硬步数上限 + Query 历史哈希去重 + 降级兜底”三层熔断网。
展开原理/取舍：① 最大迭代步数（Max Steps Hard-limit）：循环计数器达到硬阈值（如 step >= 3）时，强制中断循环，严禁无休止反思；② 历史动作去重（Cycle Detection）：将每轮生成的改写 Query 计算哈希并存入集合，一旦模型生成了与历史完全相同或语义高度重叠的 Query，直接判定为震荡死循环并打断；③ 优雅降级：熔断触发后，将当前已累积的所有次优证据直接拼装为 Prompt，提示模型“证据可能不完整，请基于现有线索回答”，或直接安全拒答。

- 【⭐ 理解】什么是 Corrective RAG (CRAG) 的核心思想？
一句话结论：在检索之后引入轻量级评分器，判断证据是“Correct（正确）”、“Ambiguous（模糊）”还是“Incorrect（错误）”。
展开原理/取舍：若判定为 Correct，直接送入生成；若判定为 Incorrect，系统彻底丢弃该检索结果，转向通用网络搜索或触发回退拒答；若判定为 Ambiguous，则将内部知识切片与外部扩展搜索结合。CRAG 将“检索质量审计”前置于大模型最终生成之前，有效阻止了垃圾上下文对下游推理的污染。

### 故障模式与排障

- 故障模式：多跳检索中的“上下文漂移（Context Drift）”

- 定位：在第二跳改写查询时，模型受第一跳无关干扰信息的影响，生成了完全偏离用户原始意图的新 Query。

- 修复：在改写 Prompt 中强制绑定原始 Query（Pin User Intent），要求模型每一次改写都必须对照最初始的用户目标进行因果校验，防止“跑偏”。

- 故障模式：多工具调用时的权限越界（Tool Privilege Escalation）

- 定位：Agent 自主决定调用“企业内部员工薪资接口”来补充背景证据，绕过了用户的单点鉴权。

- 修复：用户安全上下文透传（Token Propagation）。Agent 调用的每一个外部 Tool，必须强制向下透传当前发起会话用户的真实 JWT/Token，由目标工具的数据源负责行级权限校验，严禁让 Agent 拥有超级管理员工具池。

### 工程 trick 与坑

- 单次改写数量控制：若需要生成并发子查询（Sub-queries），必须限制 max_sub_queries <= 3，防止模型一口气生成 10 个子问题造成后端向量库瞬时并发被打崩。

- 结构化输出约束：Agent 决策下一步动作时（ACTION: RETRIEVE | GENERATE | REFUSE），必须使用 JSON Schema 严格模式（Strict Mode），严禁让模型用自然语言自言自语后靠弱正则猜测意图。

### 循序渐进 Toy Code：Level 10 — 自适应动态检索状态机与防死循环熔断控制器

代码难度定位：Level 10（控制流闭环与状态机）。手写一个完整的自适应动态检索循环控制器，内置最大步数硬熔断、动作历史去重与证据充足度判定。

```python
"""
3.10 Toy Code: Level 10 - 自适应动态检索状态机与防死循环熔断控制器
依赖：Python 3.10+ 标准库
"""
from dataclasses import dataclass
from enum import Enum
import hashlib
from typing import Callable, Optional


class ControllerStatus(str, Enum):
    """状态机终止状态"""
    SUCCESS_EVIDENCE_READY = "SUCCESS_EVIDENCE_READY"       # 证据充足，成功退出
    BUDGET_EXHAUSTED = "BUDGET_EXHAUSTED"                   # 达到最大步数硬熔断
    CYCLE_DETECTED = "CYCLE_DETECTED"                       # 检测到重复 Query 震荡死循环
    TOOL_FAILED = "TOOL_FAILED"                             # 工具执行异常


@dataclass(frozen=True)
class RetrievedEvidence:
    """证据对象"""
    chunk_id: str
    content: str


@dataclass(frozen=True)
class ExecutionTrace:
    """全流程动作与状态轨迹"""
    status: ControllerStatus
    total_steps: int
    attempted_queries: tuple[str, ...]
    final_evidence: tuple[RetrievedEvidence, ...]
    decision_log: tuple[str, ...]


# 声明函数契约类型
RetrieverFunc = Callable[[str], list[RetrievedEvidence]]
EvaluatorFunc = Callable[[str, list[RetrievedEvidence]], bool]
RewriterFunc = Callable[[str, list[RetrievedEvidence]], str]


class AgenticRetrievalController:
    """自适应检索循环控制器"""

    def __init__(
        self,
        retriever: RetrieverFunc,
        evaluator: EvaluatorFunc,
        rewriter: RewriterFunc,
        max_steps: int = 3
    ):
        if max_steps <= 0:
            raise ValueError("max_steps 必须为正整数")
        self.retriever = retriever
        self.evaluator = evaluator
        self.rewriter = rewriter
        self.max_steps = max_steps

    def execute(self, initial_query: str) -> ExecutionTrace:
        """执行自适应检索动态循环"""
        if not initial_query.strip():
            raise ValueError("初始查询不能为空")

        current_query = initial_query.strip()
        query_history: list[str] = []
        query_hashes: set[str] = set()
        decision_logs: list[str] = []
        accumulated_evidence: dict[str, RetrievedEvidence] = {}

        for step in range(1, self.max_steps + 1):
            # 1. 死循环震荡检测（通过规范化哈希）
            normalized_q = " ".join(current_query.lower().split())
            q_hash = hashlib.md5(normalized_q.encode("utf-8")).hexdigest()
            
            if q_hash in query_hashes:
                decision_logs.append(f"第 {step} 步: 检测到重复查询 '{current_query}'，触发死循环熔断。")
                return ExecutionTrace(
                    status=ControllerStatus.CYCLE_DETECTED,
                    total_steps=step,
                    attempted_queries=tuple(query_history),
                    final_evidence=tuple(accumulated_evidence.values()),
                    decision_log=tuple(decision_logs)
                )

            query_hashes.add(q_hash)
            query_history.append(current_query)
            decision_logs.append(f"第 {step} 步: 正在执行检索，Query: '{current_query}'")

            # 2. 调用外部检索工具
            try:
                candidates = self.retriever(current_query)
            except Exception as e:
                decision_logs.append(f"第 {step} 步: 检索工具执行异常: {str(e)}")
                return ExecutionTrace(
                    status=ControllerStatus.TOOL_FAILED,
                    total_steps=step,
                    attempted_queries=tuple(query_history),
                    final_evidence=tuple(accumulated_evidence.values()),
                    decision_log=tuple(decision_logs)
                )

            # 汇总累加证据去重
            for item in candidates:
                accumulated_evidence[item.chunk_id] = item

            # 3. 证据充足度反思评估（Self-Reflection）
            evidence_list = list(accumulated_evidence.values())
            is_sufficient = self.evaluator(initial_query, evidence_list)
            
            if is_sufficient:
                decision_logs.append(f"第 {step} 步: 证据充足度评估通过，停止迭代。")
                return ExecutionTrace(
                    status=ControllerStatus.SUCCESS_EVIDENCE_READY,
                    total_steps=step,
                    attempted_queries=tuple(query_history),
                    final_evidence=tuple(evidence_list),
                    decision_log=tuple(decision_logs)
                )

            # 4. 证据不足，触发自适应改写（若已是最后一步则无需改写）
            decision_logs.append(f"第 {step} 步: 当前证据不足以回答问题。")
            if step < self.max_steps:
                current_query = self.rewriter(initial_query, evidence_list)
                decision_logs.append(f"第 {step} 步: 生成改写后的探索 Query: '{current_query}'")

        # 步数预算耗尽硬熔断
        decision_logs.append(f"已达到最大步数上限 ({self.max_steps})，触发硬熔断保护。")
        return ExecutionTrace(
            status=ControllerStatus.BUDGET_EXHAUSTED,
            total_steps=self.max_steps,
            attempted_queries=tuple(query_history),
            final_evidence=tuple(accumulated_evidence.values()),
            decision_log=tuple(decision_logs)
        )


def self_test():
    """测试自适应状态机在正常收敛、循环震荡与步数超限时的行为"""
    # 模拟知识库数据源
    kb = {
        "高空作业": [RetrievedEvidence("C1", "高处作业需持证上岗。")],
        "高处作业 安全防护 细则": [RetrievedEvidence("C2", "高处作业必须佩戴五点式安全带并双钩互锁。")]
    }

    # 1. 模拟检索工具
    def mock_retriever(q: str) -> list[RetrievedEvidence]:
        for k, v in kb.items():
            if k in q:
                return v
        return []

    # 2. 模拟充足性判断器：必须包含“五点式安全带”才算充足
    def mock_evaluator(q: str, evs: list[RetrievedEvidence]) -> bool:
        return any("五点式安全带" in e.content for e in evs)

    # 3. 模拟改写器
    def mock_rewriter(q: str, evs: list[RetrievedEvidence]) -> str:
        return "高处作业 安全防护 细则"

    controller = AgenticRetrievalController(
        retriever=mock_retriever,
        evaluator=mock_evaluator,
        rewriter=mock_rewriter,
        max_steps=3
    )

    # 测试场景 1：两步自适应收敛成功
    trace1 = controller.execute("高空作业")
    assert trace1.status == ControllerStatus.SUCCESS_EVIDENCE_READY
    assert trace1.total_steps == 2
    assert len(trace1.final_evidence) == 2
    assert "五点式安全带" in [e.content for e in trace1.final_evidence][1]

    # 测试场景 2：死循环震荡拦截（改写器反复输出相同 Query）
    def buggy_rewriter(q: str, evs: list[RetrievedEvidence]) -> str:
        return "高空作业" # 恶意返回历史相同 Query
        
    buggy_controller = AgenticRetrievalController(
        retriever=mock_retriever,
        evaluator=mock_evaluator,
        rewriter=buggy_rewriter,
        max_steps=3
    )
    trace2 = buggy_controller.execute("高空作业")
    assert trace2.status == ControllerStatus.CYCLE_DETECTED
    assert trace2.total_steps == 2 # 在第二步立即被哈希集合拦截

    # 测试场景 3：硬预算耗尽熔断
    def never_sufficient_evaluator(q: str, evs: list[RetrievedEvidence]) -> bool:
        return False
        
    exhaust_controller = AgenticRetrievalController(
        retriever=mock_retriever,
        evaluator=never_sufficient_evaluator,
        rewriter=lambda q, e: f"变体_{len(e)}",
        max_steps=2
    )
    trace3 = exhaust_controller.execute("未知查询")
    assert trace3.status == ControllerStatus.BUDGET_EXHAUSTED
    assert trace3.total_steps == 2

    print("✅ 3.10 自适应动态检索状态机自检全部通过！")
```

#### 这段代码怎么在面试里讲（三段式）

- 声明不变量：我设计了一个有限状态机 AgenticRetrievalController。核心不变量是：循环执行步数严格满足 1 <= total_steps <= max_steps；每轮尝试的 Query 具有强哈希唯一性，严禁出现 $Q_i = Q_j (i \neq j)$；状态机必然且仅能在预定义的 4 种强类型状态中退出。

- 关键行解析：在第 64-75 行，我实现了基于 MD5 规范化字符串的死循环探测（Cycle Detection），在下发检索之前就地阻断了模型震荡改写的行为；第 95-107 行实现了证据充足性反思（Self-Reflection），一旦当前累积证据满足判定，立即跳出循环，避免无效调用；第 118-124 行是保底硬熔断网，防止费用和延迟穿透。

- 主动说边界与坑：这段代码是动态控制原语。在生产复杂场景（如接入真实大模型做改写和反思）中，必须向面试官指出：改写和评估函数也应当采用低延迟小模型（如 Qwen2.5-3B 或 7B），严禁使用超大推理模型作为每一步的控制器，否则会带来严重的 TTFT 延迟雪崩；更多通用 Agent 工具链设计将在下一章（第 4 章）展开。

费曼自述：
“传统的 RAG 就像只能投一次篮的队员，投不进就认输；Agentic RAG 是能看清篮板球的队员：投偏了，自己看一眼‘没进’，赶紧抢下篮板球换个角度再投一次。但教练必须在场边盯紧秒表：哪怕你再想投，最多只准试两三次；如果一直在同一个地方转圈圈，裁判马上吹哨叫停！”

- Q：传统 RAG（静态流水线）与 Agentic RAG（动态流水线）的最根本分水岭是什么？
A：是否存在“运行时反思与自适应决策闭环”。传统 RAG 执行固定 DAG；Agentic RAG 能根据各阶段产生的证据质量动态决定重试、改写、补查还是终止。

- Q：防范 Agentic RAG 陷入死循环震荡的三个最重要工程手段是什么？
A：设置硬步数上限（Max Steps）、记录历史 Query 签名拦截重复改写、设定单次请求全局超时（Timeout）。

- Q：在实际生产中，如何平衡 Agentic RAG 的回答质量与端到端 P99 延迟？
A：限制最大重试深度为 2；改写与反思使用低延迟小模型（SLM）；仅对置信度极低的问题触发重试，高频明确问题直接走快速静态通路。
